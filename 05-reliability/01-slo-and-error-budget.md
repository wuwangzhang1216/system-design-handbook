# 01 · SLO 与错误预算

> SLO 不是"可靠性目标"，是**不可靠性配额**。写下 99.9%，你真正做的决定是：这个月我允许自己坏 43.2 分钟，并且我打算把这 43.2 分钟花掉。
> 一个从不用完错误预算的团队，不是可靠，是发布得太慢了。

---

## 1. SLI：唯一正确的形式是 `好事件 / 有效事件`

```
SLI = good events / valid events × 100%
```

这个比值形式不是风格问题，它强制你回答三个必答题：

1. **什么算一个"事件"？**（一次 HTTP 请求？一次页面加载？一个 Agent 会话？）
2. **什么算"好"？**（判定必须能在遥测里用一行表达式算出来）
3. **什么算"有效"？**（哪些事件根本不该进分母）

### 规则一：SLI 定义在用户旅程上，不定义在组件上

```
❌ 组件视角                          ✅ 旅程视角
┌──────────┐                    ┌─────────────────────────────────┐
│ DB 可用性 │ 99.95%             │ 旅程：登录 → 加载工作区 → 首屏渲染 │
├──────────┤                    │ good  = 端到端 < 2s 且 无错误    │
│ 缓存命中率│ 94%                │ valid = 已认证用户的真实首屏请求  │
├──────────┤                    │ 目标  = 99.9%                   │
│ MQ 堆积   │ < 1000             └─────────────────────────────────┘
└──────────┘
每个组件都"绿"，用户仍然打不开页面
```

**给每个微服务定 SLO 是 Mid 的做法。** 200 个服务 × 每个 4 个 SLO = 800 个 SLO，没有人看，也没有一个能回答"用户现在爽不爽"。正确做法是：**给 3–7 条关键用户旅程定 SLO**，内部服务不定独立 SLO，而是从旅程 SLO 里**分配依赖子预算**（见 §5）。

### 规则二：延迟 SLI 是"阈值达标率"，不是"分位数"

```
❌ SLO: p99 延迟 < 500ms
✅ SLI: (延迟 ≤ 500ms 且 状态码非 5xx 的请求数) / (有效请求数)
   SLO: ≥ 99.9%，滚动 28 天窗口
```

`p99 < 500ms` 有三个问题：
- **p99 不能跨维度聚合。** 10 个实例各自的 p99 取平均或取最大，都不是整体 p99（详见 [02-observability.md](02-observability.md) §2）。
- **p99 是统计量，不是事件流。** 你无法从它算出"这个月烧了多少错误预算"。
- **它对分母不敏感。** QPS 从 1 万掉到 10，p99 可能反而变好，但用户已经进不来了。

工程上直接落成两个 counter，**根本不需要直方图**：

```promql
# 好事件：直接在应用侧打一个满足 SLO 条件的计数器
sum(rate(http_requests_slo_good_total{journey="workspace_load"}[5m]))
/
sum(rate(http_requests_slo_valid_total{journey="workspace_load"}[5m]))
```

如果你非要从直方图里算，**SLO 阈值必须正好是一个 bucket 边界**（`le="0.5"`），否则 `histogram_quantile` 给你的是相邻 bucket 之间的线性插值——一个被你自己的 bucket 划分虚构出来的数字。

### 规则三："有效事件"的定义是政治问题，必须写下来

| 该不该进分母 | 判断 |
|---|---|
| 健康检查 / 探针 | **不进**。它们不是用户 |
| 爬虫 / 合成监控 | 分开定 SLI，不要混进用户 SLI |
| 400/401/403/404 | **默认不进 good，但要进 valid**——除非你能证明是客户端的错。把 4xx 一律排除是常见的粉饰手法 |
| 429（你限流了） | **算坏事件**。用户不关心你是主动拒绝还是崩了 |
| 客户端超时后取消的请求 | 进 valid，进坏事件。用户已经走了 |
| 计划内维护窗口 | 若用户可见，**照样扣预算**。否则你会用"维护窗口"洗掉所有故障 |

> **面试金句**
> "我不会说 SLO 是 99.9%，我会说：这条旅程每月允许 43 分钟的坏体验，其中我给数据库分了 10 分钟、给认证服务分了 5 分钟、给我自己的代码分了 20 分钟，剩 8 分钟是未分配缓冲。这样当认证服务上个月烧了 12 分钟时，我有一个具体的数字去跟他们的 TL 谈，而不是'感觉你们最近不太稳'。"

## 2. 可用性数字表（必背）

以 30 天月（43,200 分钟）/ 365 天年（525,600 分钟）计：

| 可用性 | 每周 | 每月 | 每年 | 现实中意味着什么 |
|---|---|---|---|---|
| 99% | 100.8 min | **7.2 h** | 3.65 天 | 内部工具 / 早期 MVP |
| 99.5% | 50.4 min | 3.6 h | 1.82 天 | |
| 99.9%（三个 9） | 10.1 min | **43.2 min** | 8.76 h | **绝大多数 B2B SaaS 的合理起点** |
| 99.95% | 5.0 min | 21.6 min | 4.38 h | 付费主链路 |
| 99.99%（四个 9） | 1.01 min | **4.32 min** | 52.6 min | 需要多可用区 + 自动故障转移 + 无人工介入的回滚 |
| 99.999%（五个 9） | 6.05 s | 25.9 s | 5.26 min | **人来不及反应**。必须全自动，且发布本身就是最大威胁 |

**四个 9 是自动化命题，不是"更努力"命题**：99.99% 意味着从故障发生到完全恢复的中位时间必须 < 4 分钟（假设一个月只坏一次）。人接到告警、打开电脑、看 dashboard 就超了。**五个 9** 更狠——一次发布的回滚窗口（金丝雀观察 + 回滚生效）通常就 > 26 秒，所以要么发布根本不影响这条路径，要么你在骗自己。

**每加一个 9 的成本大致是上一个的 3–10 倍**（冗余度、演练频率、值班规模、变更管控开销全部上台阶）。定 SLO 的正确方向因此是**从下往上找到刚好用户不投诉的那个点**，不是从上往下砍。

## 3. SLO 目标怎么定：从业务影响倒推

四步法，按顺序做，不要跳：

**① 先测，别猜。** 用过去 28–90 天真实数据算出当前 SLI。绝大多数团队会发现实际在 99.5% 徘徊，而 PPT 上写着 99.99%。

**② 找用户痛感阈值。** 从工单、NPS 掉点、留存曲线里找拐点。核心问题是"低于多长的中断用户根本没注意到"——通常是 30 秒–2 分钟量级，取决于客户端是否自动重试。

**③ 目标 = 略好于当前 + 略好于痛感阈值，取严者，且下季度真能达到。** 定 99.99% 而实际 99.5%，结果是错误预算永远为负、政策永远被豁免、SLO 变成装饰品。

**④ 算边际成本，让产品决定。** 99.9%→99.95% 要什么（多一个 AZ，$8k/月）？99.95%→99.99% 要什么（跨区双活 + 双倍容量，$120k/月 + 2 个 FTE）？把这两个数字摆到桌上，可靠性目标就不再是工程单方面的道德负担。

**反直觉但正确**：如果你的客户端（App / SDK / Agent）能自动重试且用户无感，那么**几秒钟的完全不可用应该定义成"零个坏事件"**。SLI 应该测量的是"用户旅程成功了吗"，不是"某次 HTTP 调用成功了吗"。这一条能让你的可用性数字合理地上升一个 9，而且是真实的。

## 4. 依赖链的可用性乘法

### 串联相乘

```
用户 ──▶ CDN ──▶ API GW ──▶ Auth ──▶ Profile ──▶ FeatureFlag ──▶ DB
       99.99%   99.95%    99.9%    99.9%      99.9%          99.95%

端到端 = 0.9999 × 0.9995 × 0.999 × 0.999 × 0.999 × 0.9995 = 99.58%
                                              = 每月 3.0 小时不可用
```

**每个团队都觉得自己 99.9% 很体面，用户拿到的是 99.58%。**

N 个 99.9% 的硬依赖串联：

| N | 端到端可用性 | 每月不可用 |
|---|---|---|
| 1 | 99.900% | 43.2 min |
| 3 | 99.700% | 2.16 h |
| 5 | 99.501% | 3.59 h |
| 10 | 99.004% | 7.17 h |
| 20 | 98.02% | 14.3 h |
| 50 | 95.12% | **35.1 h** |

这张表就是**"分布式单体"最致命的量化证据**：把一个单体拆成 50 个必须同步调用的服务，你在架构上给自己判了 95% 可用性。

### 打破乘法的三种手段

**a) 冗余（并联）—— 效果最好，上限最硬**

```
A_parallel = 1 - (1 - A)^n     （前提：故障独立）
2 × 99% → 99.99%    2 × 99.9% → 99.9999%
```

⚠ **"故障独立"几乎从不成立。** 共享失败域包括：同一份配置推送、同一个 DNS、同一次部署、同一张证书、同一个控制面、同一个 IAM。经验法则：**冗余最多买回 1–2 个 9**，之后收益被相关性吃光。判断方法：列出这两个副本共享的一切，那就是你的真实上限。

**b) 优雅降级 —— 把硬依赖变软依赖，性价比最高**

```
硬依赖：FeatureFlag 服务挂 → 页面 500
软依赖：FeatureFlag 服务挂 → 用本地缓存的上一次快照 → 页面正常

A_effective = 1 - (1 - A_dep) × (1 - A_fallback)
   A_dep=0.999，A_fallback=0.99（缓存里有值的概率）→ 0.99999
```

这是**唯一不需要加钱**的手段：把 FeatureFlag / 推荐 / 个性化 / 用量统计从关键路径上摘下来，给每个都想好"挂了返回什么"。做完之后依赖链常常从 12 个硬依赖缩到 3 个。

**c) 异步化**：写入走 Outbox / 消息队列，用户拿到 202，下游挂 30 分钟不影响旅程的成功判定。代价是最终一致性与补偿（见 [`02-architecture-patterns/02-event-driven-and-cqrs.md`](../02-architecture-patterns/02-event-driven-and-cqrs.md)）。

### 依赖预算分配（Staff 级手法）

把旅程的 43.2 min/月 预算显式切分：

| 归属 | 分配 | 上月实际 | 状态 |
|---|---|---|---|
| 自身代码与部署 | 20 min | 11 min | ✅ |
| 主数据库 | 10 min | 4 min | ✅ |
| 认证服务（内部依赖） | 5 min | **12 min** | ❌ 超支 240% |
| 第三方支付网关 | 5 min | 2 min | ✅ |
| 未分配缓冲 | 8 min | — | 已被认证服务吃掉 7 min |

这张表把"跨团队可靠性谈判"从形容词变成了数字。**它也是唯一能让上游团队认真对待你的东西。**

## 5. 错误预算与燃尽率

```
错误预算（事件数） = (1 - SLO) × 有效事件总数
错误预算（时间）   = (1 - SLO) × 窗口长度
燃尽率 burn rate  = 观测到的错误率 / (1 - SLO)
```

燃尽率 = 1 表示"刚好在月底用完预算"。燃尽率 = 14.4 表示"以这个速度，50 小时用完整月预算"。

| 燃尽率 | 对应错误率（SLO=99.9%） | 30 天预算耗尽时间 |
|---|---|---|
| 1× | 0.1% | 30 天 |
| 2× | 0.2% | 15 天 |
| 6× | 0.6% | 5 天 |
| **14.4×** | 1.44% | **50 小时** |
| 100× | 10% | 7.2 小时 |
| 1000× | 100%（完全宕机） | **43.2 分钟** |

**一致性自检**：1000× 燃尽（全挂）的耗尽时间 43.2 分钟，正好等于 §2 表里 99.9% 的月度停机额度——算不出这个说明公式错了。**算例**：900M 请求/月（≈347 rps），SLO 99.9% → 预算 900,000 个失败请求；一次 43 分钟完全宕机 = 43×60×347 ≈ 895,000 个失败请求，**一次故障吃掉整月预算**。这就是为什么"快速回滚"比"少出 bug"的 ROI 高一个量级。

## 6. 多窗口多燃尽率告警

### 为什么单窗口一定是错的

**单一短窗口**（"过去 5 分钟错误率 > 1%"）：噪音大（一个坏 pod、一次滚动重启、一个爬虫全都触发），且有**致命盲区**——持续 0.3% 的慢速泄漏（3× 燃尽）10 天耗光整月预算，**永远不触发**。

**单一长窗口**（"过去 3 天错误率 > 0.1%"）：慢，而且**重置时间是灾难**——故障修复后告警还会继续 fire 接近 3 天（坏数据要慢慢滚出窗口）。值班的人会直接静音它，然后忘记取消静音。

### Google SRE 的多窗口多燃尽率参数表

来自 [SRE Workbook, Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/)，针对 99.9% SLO / 30 天窗口：

| 严重度 | 长窗口 | 短窗口 | 燃尽率阈值 | 触发时已消耗预算 | 全挂时的检测时延 |
|---|---|---|---|---|---|
| **Page** | 1 h | 5 min | **14.4** | 2% | **≈ 52 秒** |
| **Page** | 6 h | 30 min | **6** | 5% | ≈ 2.2 分钟 |
| **Ticket** | 3 d | 6 h | **1** | 10% | ≈ 1.2 小时 |

三条规律，理解了就能自己推导任何 SLO 的参数：

1. **消耗预算 = 燃尽率 × 长窗口 / 总窗口**。`14.4 × 1h / 720h = 2%`；`6 × 6h / 720h = 5%`；`1 × 72h / 720h = 10%`。三档分别对应"烧掉 2% / 5% / 10% 预算就该有人管"。
2. **检测时延 = (1-SLO) × 燃尽率 × 长窗口 / 实际错误率**。全挂（错误率 100%）时：`0.001 × 14.4 × 60min / 1.0 = 0.86 min`。
3. **短窗口 = 长窗口 / 12，唯一作用是压缩重置时间**。它作为 `AND` 条件存在：只有当"长窗口超阈值"**且**"短窗口仍在超阈值"时才告警。故障一恢复，短窗口 5 分钟内就掉下去，告警自动消。**没有短窗口的多燃尽率告警，是残废的。**

### 可直接抄的 PromQL

```yaml
# ① 记录规则：把 SLI 预计算成 5m/30m/1h/6h/3d 五个窗口（不要在告警表达式里现算）
- record: journey:slo_error:ratio_rate5m
  expr: |
    1 - ( sum(rate(http_requests_slo_good_total{journey="workspace_load"}[5m]))
        / sum(rate(http_requests_slo_valid_total{journey="workspace_load"}[5m])) )

# ② 告警：长窗口 AND 短窗口，两者都超阈值才响
- alert: WorkspaceLoadBurnRateFast              # page，2% 预算
  expr: |
    journey:slo_error:ratio_rate1h > (14.4 * 0.001)
    and journey:slo_error:ratio_rate5m > (14.4 * 0.001)
  for: 2m
  labels: {severity: page, slo: workspace_load}
  annotations:
    summary: "错误预算燃尽 14.4×，约 50 小时耗尽整月预算"
    runbook: "https://runbooks/…/workspace-load"

- alert: WorkspaceLoadBurnRateSlow              # ticket，10% 预算
  expr: |
    journey:slo_error:ratio_rate3d > (1 * 0.001)
    and journey:slo_error:ratio_rate6h > (1 * 0.001)
  labels: {severity: ticket, slo: workspace_load}
```

⚠ **低流量服务的分母陷阱**：QPS = 0.5 的服务，5 分钟窗口只有 150 个请求，2 个失败就是 1.3% 错误率 → 直接触发 14.4× 页告警。对策：加最小事件数门槛（`and sum(rate(valid[1h])) > 1`），或对低流量服务只保留长窗口 + 工单级别。另外，3 天窗口的 `rate()` 在高基数下会拖垮 Prometheus——必须用 recording rule 预计算。

## 7. 错误预算政策：没有牙齿的 SLO 是装饰品

**政策必须在事故发生之前写好并被签字。** 事后再谈"要不要冻结发布"，永远谈不成。

| 剩余预算 | 状态 | 强制规则 |
|---|---|---|
| > 50% | 🟢 绿 | 正常发布；**主动做混沌演练**（预算多说明你测试得不够）；可加大金丝雀步长 |
| 25–50% | 🟡 黄 | 发布需 SLO owner 审批；禁止跳过金丝雀阶段；新功能一律 flag 默认关闭 |
| 0–25% | 🟠 橙 | **冻结所有非可靠性相关的发布**；下个 sprint ≥ 30% 容量投入 postmortem action item |
| < 0（超支） | 🔴 红 | 只允许 P0 修复与可靠性工作；例外需 VP 级书面豁免并公开记录；触发强制 postmortem review |

配套的四条细则（真正被忽略的地方）：

1. **用滚动 28/30 天窗口，不是日历月。** 日历月会诱导出"月末冻结、月初狂发"的畸形节奏。
2. **豁免必须留痕**（谁批的、为什么、何时撤销）。三个月后回顾豁免列表：如果全是同一个人同一个理由，说明 SLO 定错了。
3. **处置对象是"变更速率"，不是"某个人"。** 把 SLO 挂进个人绩效，结果一定是有人去改 SLI 的测量口径。依赖方超支子预算时，你有权把它降级为软依赖——这条要写进政策，否则跨团队谈判没有筹码。
4. **预算长期用不完 = SLO 定低了或发布太慢。** 连续两季度剩余 > 70%，应主动收紧 SLO 或加快发布。这是最反直觉、也最能体现 Staff 视角的一条。

## 8. SLO 与 SLA 的区别与关系

| | **SLO**（内部目标） | **SLA**（合同承诺） |
|---|---|---|
| 受众 | 工程团队 | 客户 / 法务 / 销售 |
| 违反后果 | 冻结发布、改优先级 | **退款 / 服务积分 / 客户流失** |
| 严格程度 | 严 | 松 |
| 测量口径 | 你自己定义的 SLI，粒度细 | 合同定义，通常是粗粒度的"月度不可用分钟数" |
| 谁能改 | 工程 + 产品，季度 review | 需要重新签合同 |

**核心关系：SLO 必须严于 SLA，且错误预算留 3–10 倍余量。**

```
SLA  99.9%  → 月度 43.2 min，违反要退 10% 月费
  ↓ 留 2× 余量
SLO  99.95% → 月度 21.6 min（内部目标）
  ↓ 燃尽 2% 就页告警
告警 触发点 = 消耗 0.43 min 时（≈26 秒）
```

典型 SLA 赔付阶梯（B2B SaaS，2026 年中的常见形态）：`< 99.9% 退 10% 月费 / < 99.0% 退 25% / < 95.0% 退 100%`。

**但 SLA 里最贵的从来不是赔款，是"连续 N 个月违反 → 客户可无责终止合同"那一条。** 设计 SLA 时第一个要算的数字就是这个 N，那才是你的真实红线。

## 9. AI 系统的 SLI：返回了 ≠ 有用

传统 SLI 假设"HTTP 200 + 延迟达标 = 用户满意"。LLM/Agent 系统里这个假设**完全不成立**：一个 200 响应可以是空的、被截断的、拒答的、幻觉的、或者格式不合法导致下游解析失败的。

### 分三层定义，从确定性到主观性

**第 1 层：确定性断言（免费、可在每条请求上算、是 SLI 的骨干）**

| 失效模式 | 判定表达式 |
|---|---|
| 空响应 | `len(output_text) == 0 and tool_calls == []` |
| 被截断 | `finish_reason == "length"` |
| 结构化输出 / 工具参数不合法 | JSON Schema 校验失败 |
| Agent 死循环 | 同一 `(tool_name, args_hash)` 在一个会话内重复 > 3 次 |
| 超出步数预算 | `steps > max_steps` 且未产出终答 |
| 流式中断 | 流开始了但从未收到终止事件（`finish_reason` / `[DONE]`） |

**这一层能覆盖 60–80% 的真实故障，且完全不需要 LLM judge。** 先做完这层再谈质量评估。

**第 2 层：延迟 SLI —— 必须至少两个指标，只写一个等于没写**

| 指标 | 定义 | 备注 |
|---|---|---|
| **TTFT**（time to first token） | 首 token 到达客户端的时间，含网络 + 排队 + prefill | 用户感知"卡不卡" |
| **TPOT / ITL**（time per output token） | 首 token 之后的平均产出间隔 | 用户感知"流得顺不顺" |
| **goodput** | **每秒完成且同时满足 TTFT 与 TPOT 阈值的请求数** | 唯一能用来做容量规划的指标 |

> ⚠ 关键反例：在同一个 chatbot 负载上，两个**同样满足 TTFT ≤ 1.5s** 的配置，P95 TPOT 一个约 50 ms、另一个约 494 ms——**差 10 倍**（2026-07 实测量级）。
> **只在 SLO 文档里写 "P95 TTFT < 2s" 而不写 TPOT，等于没有 SLO。**

另外：TTFT 与输入长度强相关（prefill 是 O(输入 token 数)），**TTFT 直方图必须按输入长度分桶**（<2K / 2–16K / 16–128K / >128K），否则一个长上下文请求就把整条曲线拉飞，而这个"劣化"其实符合物理规律。可抄的生产 SLA 量级：**mean TTFT ≤ 2.5 s、mean TPOT ≤ 20 ms**（744B MoE / 24×B300 / 16K–256K ctx，2026-07；条件不同不可移植）。

**第 3 层：质量 SLI —— 采样 + 校准过的判定**

在每条请求上跑 judge 的成本和延迟都不允许，做法是**分层采样**：

```
100% 请求  → 第 1 层确定性断言（实时，进 SLI）
 1–5% 请求 → LLM judge 打分（异步，进质量 SLI，按租户/场景分层抽样）
0.1% 请求 → 人工标注（周级，用来校准 judge）
```

judge 上线门槛：**与人工标注的 Cohen's kappa ≥ 0.6 可上线，≥ 0.8 算强**（人-人基线本身只有 0.5–0.8）。两条纪律：**换 judge 模型 = 换测量标准**，必须重跑校准并给 SLI 打版本号，否则你会看到 SLI 在零代码变更时跳变；judge 的系统性偏差**方向因模型而异**——风格偏差量级 0.10–0.76 远大于位置偏差（≤0.04），冗长偏差有的模型 +0.24~+0.44（偏好长答案）而 Claude 系为 −0.12（偏好简洁）。详见 [`04-ai-agent-systems/06-evaluation-and-observability.md`](../04-ai-agent-systems/06-evaluation-and-observability.md)。

### 非确定性下的可用性：用 `pass^k` 而不是 `pass@k`

同一个请求跑 8 次成功 4 次——这算 50% 可用还是 100% 可用？

- `pass@k`：k 次里**至少一次**成功的概率 = 能力上界。**用它汇报 Agent 可靠性是系统性高估。**
- `pass^k`：k 次**全部**成功的概率，随 k 单调下降。**这才是可靠性。** 衰减形状可参考 τ-bench retail 域：`pass^1 < 50%` 而 `pass^8 < 25%`（[arXiv:2406.12045](https://arxiv.org/abs/2406.12045)，2024-06，模型已换但形状成立）。

**工程推论**：对会重复提交同一任务的场景（重试、批处理、定时任务），SLO 必须定在 `pass^k` 上，k 取 4–8。一个 `pass^1 = 90%` 的 Agent，在用户连做 8 件事的会话里全对概率只有 43%。

### 一个 AI Agent 的完整 SLI 定义示例

场景：企业内的代码修改 Agent（接需求 → 改代码 → 跑测试 → 提 PR）。

```yaml
journey: agent.code_change
window: 28d                       # 滚动窗口，不用日历月
error_budget_policy: standard-v2  # 见 §7
slis:
  # ── L1 确定性断言：100% 请求上计算，SLI 的骨干 ──
  - name: request_availability
    good:  agent_requests_total{outcome!~"infra_error|provider_error|timeout"}
    valid: agent_requests_total{synthetic="false"}
    objective: 0.999              # = 43 min / 30d
  - name: stream_completion       # 流开始了但没收到 finish_reason = 坏事件
    good:  agent_streams_total{terminated="clean"}
    valid: agent_streams_total
    objective: 0.995
  - name: tool_call_validity
    good:  agent_tool_calls_total{schema_valid="true"}
    valid: agent_tool_calls_total
    objective: 0.99
  - name: no_runaway_loop
    good:  agent_sessions_total{repeated_calls_lt="4", steps_within_budget="true"}
    valid: agent_sessions_total
    objective: 0.995
  # ── L2 延迟与经济性：TTFT 必须按输入长度分桶，各桶各目标 ──
  - name: ttft
    good:  agent_ttft_seconds_bucket{le="2.5", isl_bucket="2k-16k"}
    valid: agent_requests_total{isl_bucket="2k-16k", streaming="true"}
    objective: 0.95
  - name: tpot                    # 只写 TTFT 不写 TPOT = 没有 SLO
    good:  agent_requests_total{p95_tpot_ms_le="50"}
    valid: agent_requests_total{streaming="true"}
    objective: 0.95
  - name: cost_per_session        # 尾部会话烧 20× 是真实故障，必须进预算
    good:  agent_sessions_total{cost_usd_le="2.00"}
    valid: agent_sessions_total
    objective: 0.95
  # ── L3 质量：5% 分层抽样 + 校准过的 judge，异步计算 ──
  - name: task_success
    good:  agent_sessions_scored_total{verdict="pass"}
    valid: agent_sessions_scored_total
    objective: 0.85               # 不是 99.9%，理由见下
    judge:
      model: <pinned-model-id>
      calibration_kappa: 0.72
      calibrated_at: 2026-07-14   # 过期 30 天该 SLI 标记为不可信
    note: "pass = 测试通过 且 diff 未触碰 allowlist 外的文件"
```

**三个必须解释的设计决定：**

1. **`task_success` 目标是 85% 而非 99.9%。** 质量 SLI 和可用性 SLI 是两个物种：前者衡量"产品行不行"，后者衡量"系统坏没坏"。混进一个 99.9% 里的结果是永远超支、政策永远被豁免。**质量 SLI 要有自己的目标和自己（更温和）的政策。**
2. **成本被定义成 SLI。** 一个陷入循环的会话可以烧掉正常会话的 20–50 倍 token，而它在传统 SLI 里表现为"成功"。把 `cost_per_session ≤ $X` 作为好事件，这类故障才会进入错误预算、进而进入告警。
3. **`judge` 带 `calibrated_at`。** SLI 的定义本身有保质期，这在传统系统里不存在。过期未校准的质量 SLI 应标记为"不可信"，而不是继续计入预算。

## 10. 什么时候不要这么做 / 反模式

| 反模式 | 为什么错 | 正确做法 |
|---|---|---|
| 给每个微服务定 SLO | 800 个 SLO 无人看，且与用户体验无关 | 3–7 条用户旅程 SLO + 依赖子预算分配 |
| SLO 写成 "p99 < 500ms" | 分位数不能跨维度聚合，也算不出错误预算 | 阈值达标率 `good/valid` |
| 目标定 99.99%，实际 99.5% | 预算永远负，政策永远豁免，SLO 变装饰 | 定下季度真能达到的目标，逐季收紧 |
| 用日历月做窗口 | 诱导月末冻结、月初狂发 | 滚动 28/30 天 |
| 单窗口告警 | 短窗口噪音大且对慢燃烧盲；长窗口重置时间灾难 | 多窗口多燃尽率（14.4/6/1） |
| 把 4xx 全部排除出 valid | 掩盖参数校验 bug、鉴权 bug、限流 | 按来源归因，429 一律算坏事件 |
| 请求数加权的全局 SLI | 一个爆量大客户能掩盖 1000 个小客户全挂 | 同时看 **per-tenant SLI**：达标租户数 / 总租户数 |
| SLO 进个人绩效 | 一定会有人去改 SLI 的口径 | SLO 约束的是**变更速率**，不是人 |
| 没有错误预算政策 | SLO 只是一个仪表盘数字 | 事前签字的分档政策 + 留痕的豁免流程 |
| 给 AI 质量 SLI 定 99.9% | 那是产品能力问题不是可靠性问题 | 质量 SLI 单独目标（80–90% 量级）+ 单独政策 |
| 用 `pass@k` 汇报 Agent 可靠性 | 系统性高估 | `pass^k`，k ≥ 4 |

**最后一条最重要的反模式：把 SLO 当成"永远不要出事"的承诺。**

> SLO 的全部意义在于**授权你把错误预算花掉**。一个季度结束时预算还剩 80%，说明你本可以多发 4 倍的版本、多做 3 次架构迁移、多跑 10 次混沌演练，但你没有。这不是可靠，这是保守——而保守的成本不出现在任何 dashboard 上。

## 面试官会追问

1. 你的 SLI 分子分母各是什么？4xx 和 429 怎么处理？为什么？
2. 为什么不能把 SLO 写成 "p99 延迟 < 500ms"？
3. 六个 99.9% 的服务串起来，用户拿到多少可用性？你怎么把它拉回 99.9%？
4. 单窗口告警有什么问题？多窗口告警里那个短窗口解决的是什么？
5. 14.4 这个燃尽率是怎么来的？换成 99.99% 的 SLO，参数还成立吗？
6. 错误预算这个月超支了，你具体会停掉什么？谁有权豁免？豁免怎么留痕？
7. SLA 承诺 99.9%，你的内部 SLO 定多少？为什么要留倍数余量？
8. 一个 Agent 陷入循环，跑了 400 步、烧了 $40，最后给出了正确答案。你的 SLI 判它成功还是失败？`pass@k` 和 `pass^k` 该用哪个？
