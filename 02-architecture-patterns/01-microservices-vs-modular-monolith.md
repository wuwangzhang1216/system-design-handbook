# 01 · 服务边界：微服务、模块化单体（modular monolith）与分布式单体（distributed monolith）

> 微服务的价值不是技术上的，是组织上的。如果你的团队不需要独立部署，你付的是纯成本。

---

## 1. 微服务真正解决的问题

| 声称的好处 | 真相 |
|---|---|
| "可以独立扩展" | 大部分服务的瓶颈是同一个数据库；单体也可以水平扩容（horizontal scaling） |
| "技术栈自由" | 通常变成"5 种语言、5 套工具链、没人能全栈调试" |
| "故障隔离（fault isolation）" | **只有在做了熔断（circuit breaker）/降级（graceful degradation）/隔板（bulkhead）之后才成立**，否则同步调用链让故障传播更快 |
| **"团队自治（team autonomy），独立部署（independent deployability）"** | ✅ **这是唯一真实且巨大的好处** |
| "代码更清晰" | 模块化单体也能做到，且不用付网络的代价 |

**核心判据**：
> 你的部署瓶颈是不是"要等其他团队"？如果是 → 微服务有价值。
> 如果只有一个团队 → 微服务的成本远大于收益。

### 微服务的真实成本清单

```
每个新服务的固定成本：
  □ CI/CD 流水线
  □ 部署配置与环境（dev/staging/prod）
  □ 监控 Dashboard + 告警规则 + SLO
  □ 服务发现注册
  □ 日志聚合配置
  □ 密钥管理
  □ 依赖升级与安全补丁
  □ 容量规划
  □ On-call 归属
  □ 文档与 runbook

每次跨服务调用的运行成本：
  □ 网络延迟 +0.5–2 ms
  □ 序列化/反序列化 CPU
  □ 需要处理：超时、重试、熔断、幂等
  □ 跨 AZ 流量费
  □ 调试要跨服务追踪
  □ 本地开发要跑起多少个服务？
```

**经验数字**：一个服务的年度"存在成本"（不含开发功能）大约是 **0.2–0.5 个工程师**。10 个服务 = 2–5 人只是在维持系统运转。

> **面试金句**：
> "微服务的收益是**离散**的（能不能独立部署，是或否），成本是**连续**的（每个服务每年 0.2–0.5 人，每跳调用 +0.5–2 ms 且要新写超时/重试/熔断/幂等（idempotency）四件套）。所以判据只有一条：**你的部署是不是在等别的团队**。是 → 收益一次性兑现；否 → 你只是在按服务数量线性缴税。"

## 2. 分布式单体：最糟糕的结果

**症状清单**（中三条以上就是了）：

| 症状 | 说明 |
|---|---|
| ☠️ 多个服务共享同一个数据库/表 | 无法独立演进 schema，事实上是一个系统 |
| ☠️ 改一个功能要同时改 3 个服务并协调发布 | 边界切错了 |
| ☠️ 服务间同步调用链（synchronous call chain）超过 3 层 | 延迟叠加 + 故障传播（failure propagation） |
| ☠️ 必须按特定顺序部署 | 没有版本兼容性 |
| ☠️ 本地开发要启动 10 个服务 | 开发体验崩坏 |
| ☠️ 一个服务挂了全站不可用 | 没有降级 |
| ☠️ 有一个"公共库"（shared library）被所有服务依赖，改它要全量重新部署 | 共享代码变成了耦合 |

**这比单体差**：你付了微服务的所有成本，却没得到独立部署的好处。

**共享数据库为什么是死刑**：
```
Service A ─┐
Service B ─┼─→ 同一个 orders 表
Service C ─┘

- A 想加个列 → 要通知 B、C 确认不会破坏
- B 的慢查询 → 拖垮 A 和 C
- 谁负责这张表的数据完整性？没人
- 事实上你有一个单体，只是把它拆成了三个部署单元
```

## 3. 正确的边界划分方法

### 方法 1：按业务能力（business capability）/ 限界上下文（DDD）

**限界上下文（Bounded Context）**：同一个词在不同上下文里含义不同 —— 这就是边界。

```
"订单" 在不同上下文中：
  销售上下文：报价、折扣、客户意向
  履约上下文：拣货、包装、发货地址、承运商
  财务上下文：应收、税、发票、退款
  客服上下文：状态、退换货记录

→ 这不是一个"Order 服务"，而是三四个上下文各自有自己的订单视图
→ 它们通过事件同步，而不是共享一张 orders 表
```

**面试信号**：能识别出"同一个名词在不同上下文有不同模型"，是 DDD 理解到位的标志。

### 方法 2：按变化频率与变化原因

> 一起变的东西放一起，不一起变的分开。（高内聚 high cohesion = 单一变更原因 single reason to change）

如果"每次改 A 都要改 B"，那 A 和 B 应该在同一个服务里。

### 方法 3：按数据所有权（data ownership）

**每份数据必须有且只有一个服务是它的"真相源"（owner）。**
其他服务只能通过 API 或事件获取，不能直接读写。

如果两个服务都想"拥有"同一份数据 → 边界画错了。

### 方法 4：按团队（康威定律 Conway's Law 的正向应用）

> "系统的架构会趋同于组织的沟通结构。" —— Conway

**逆康威策略（Inverse Conway Maneuver）**：先设计你想要的架构，再据此组织团队。

**Team Topologies 的四种团队类型：**
| 类型 | 职责 |
|---|---|
| **流式对齐团队**（Stream-aligned） | 端到端负责一条价值流，是主体 |
| **平台团队（platform team）** | 提供内部产品（部署、可观测、数据），降低流式团队的认知负荷 |
| **赋能团队（enabling team）** | 帮助流式团队掌握新能力，临时性 |
| **复杂子系统团队（complicated-subsystem team）** | 需要专业知识的部分（推荐引擎、推理引擎） |

**认知负荷（cognitive load）是核心指标**：一个团队能装下的领域数量是有限的。如果一个团队维护 15 个服务，他们对每个服务的理解都是浅的。

## 4. 模块化单体：被低估的选项

```
monolith/
├── modules/
│   ├── billing/
│   │   ├── api/          ← 只有这里对外暴露（public）
│   │   ├── internal/     ← 其他模块禁止访问（编译期强制）
│   │   └── db/           ← 独立的 schema，不允许跨模块 JOIN
│   ├── orders/
│   └── identity/
└── main.go
```

**关键约束（必须由工具强制，不能靠自觉）：**
1. 模块只能通过公开接口互相调用（Java 的 module system、Go 的 internal 包、.NET 的 InternalsVisibleTo、ArchUnit 测试）
2. **每个模块有独立的数据库 schema，禁止跨 schema 的外键和 JOIN**
3. 模块间通信用进程内的事件总线（event bus，接口和真实消息队列一致）
4. 每个模块有自己的集成测试

**收益**：
- 保持了逻辑边界和团队自治
- **没有网络延迟、没有分布式事务（distributed transaction）、没有服务发现**
- 一个进程，一次部署，本地一键跑起
- **当某个模块真的需要独立扩展时，把它拆出去只需要把进程内事件总线换成 Kafka**

**这是 Shopify、GitHub、Stack Overflow 的实际架构**（都是巨型单体 + 严格模块化）。

**Senior 的默认建议**：
> "先做模块化单体，把边界画对。边界画对了，拆分随时可以做，成本是几周。边界画错了，无论单体还是微服务都是灾难，重画的成本是几个季度。**所以先在便宜的地方（单体内）试错边界。**"

## 5. 什么时候真的该拆

拆分的**触发条件**（不是"我觉得该拆了"，而是可观测的信号）：

| 信号 | 说明 |
|---|---|
| **部署冲突（deployment contention）** | 团队因为要等别人的代码合并而阻塞，每周多次 |
| **扩展特征差异巨大** | 某个功能需要 GPU / 需要 100× 的实例数 / 需要完全不同的存储 |
| **故障隔离刚需** | 某个功能不稳定但不能影响核心（如第三方集成、报表生成） |
| **合规隔离（compliance isolation）** | 某部分数据必须在特定区域或有特殊访问控制 |
| **技术栈刚需** | 某个功能必须用另一种语言（如 ML 推理用 Python，或需要 Rust 的性能） |
| **构建/测试时间** | 单体的 CI 超过 20 分钟，且无法通过增量构建解决 |

**最先该拆出去的三类：**
1. **异步/后台处理**（报表、批处理、通知）—— 天然解耦，风险最低
2. **资源特征特殊的**（GPU 推理、大内存的搜索索引）
3. **第三方集成层**（不稳定的外部依赖，隔离在防腐层里）

## 6. 拆分的执行：绞杀者模式（Strangler Fig）

```
阶段 0：单体处理全部流量
        Client → [Monolith]

阶段 1：加一个路由/门面层（此时行为完全不变）
        Client → [Facade] → [Monolith]

阶段 2：新服务上线，读流量影子对比（不影响用户）
        Client → [Facade] ─┬→ [Monolith] → 返回给用户
                           └→ [New Svc] → 只做对比，记录差异

阶段 3：小比例切流（1% → 10% → 50%），随时可回滚
        Client → [Facade] ─→ 1% [New Svc] / 99% [Monolith]

阶段 4：全量切换，旧代码保留但不再调用

阶段 5：删除旧代码 ← 这一步经常被跳过，导致永久的技术债
```

**数据迁移是最难的部分：**
```
1. 双写：新老库都写（新库失败不影响主流程，只告警）
2. 回填历史数据
3. 一致性校验（定期比对，量化差异率）
4. 读切换（先读新库，对比老库，不一致时用老库并告警）
5. 读完全切到新库
6. 停止双写
```
**每一步之间要有观察期（bake time，通常几天到几周），且每一步都可回滚（rollback）。**

⚠️ 双写（dual write）阶段的一致性问题：两个写不是原子的。用 CDC 或 Outbox（outbox pattern）做最终校验和修复，不要指望双写本身能保证一致。

## 7. 服务间通信的选择

```
                 需要立即知道结果吗？
                    /          \
                  是            否
                  /              \
          同步调用              异步事件
         (gRPC/HTTP)          (Kafka/队列)
              |                    |
        必须处理：            必须处理：
        - 超时                - 幂等
        - 重试(幂等)          - 乱序
        - 熔断                - 重复
        - 降级                - DLQ
        - deadline 传播        - 最终一致的用户体验
```

### 编排（Orchestration）vs 编舞（Choreography）

**编排**：一个协调者显式调用各个服务
```
        [Order Saga Orchestrator]
         │      │       │
         ▼      ▼       ▼
      支付    库存    物流
```
✅ 流程可见、易调试、易改、状态集中
❌ 协调者是耦合点和单点（single point of failure）

**编舞**：服务通过事件互相触发
```
Order创建 ──event──> 支付服务 ──event──> 库存服务 ──event──> 物流
```
✅ 完全解耦、易加新消费者
❌ **没有人知道完整流程是什么**、调试地狱、循环依赖（circular dependency）难发现

**Senior 的判断**：
> **有明确业务流程和补偿逻辑的用编排（Saga Orchestrator），纯通知性质的用编舞。**
> 编舞在超过 3 跳后就不可维护了 —— 没有任何一个地方能看到"下单之后到底发生了什么"。

## 8. 防腐层（Anti-Corruption Layer）

当你要集成一个你不控制的系统（遗留系统、第三方 API）：

```
[你的领域模型] ←→ [防腐层：翻译 + 适配] ←→ [外部系统的模型]
```

**价值**：
- 外部系统的怪异概念不会污染你的模型
- 外部 API 变更只影响一层
- 可以在防腐层加缓存、重试、熔断、限流（rate limiting）
- **可以 mock 掉做测试**

**AI 场景的应用**：LLM Provider 的 API 差异（OpenAI / Anthropic / Google 的消息格式、工具调用（tool calling）格式、流式格式都不同）→ **必须有一层统一抽象**，否则换模型要改遍全代码库。见 [`06-case-studies/02-llm-gateway.md`](../06-case-studies/02-llm-gateway.md)。

## 9. AI/Agent 系统的服务边界（service boundary）

现代 AI 应用的典型分层（这是一个新的、正在成型的标准架构）：

```
┌─────────────────────────────────────────────────────┐
│  产品层（Product）                                    │
│  会话管理、UI 状态、用户偏好、协作                      │
├─────────────────────────────────────────────────────┤
│  Agent 编排层（Orchestration）                        │
│  Agent 循环、规划、工具选择、子代理、状态机              │
├─────────────────────────────────────────────────────┤
│  上下文层（Context）                                  │
│  检索、重排、记忆、压缩、上下文组装                      │
├─────────────────────────────────────────────────────┤
│  工具层（Tools）                                      │
│  工具注册、参数校验、沙箱执行、MCP Server              │
├─────────────────────────────────────────────────────┤
│  模型网关（Model Gateway）                            │
│  路由、限流、缓存、重试、成本计量、审计、Provider 抽象   │
├─────────────────────────────────────────────────────┤
│  推理层（Inference）                                  │
│  自建 GPU 集群 / 第三方 API                           │
└─────────────────────────────────────────────────────┘
```

**为什么这样切：**

| 边界 | 理由 |
|---|---|
| **模型网关必须独立** | 变化频率极高（新模型每几周一个）；需要集中的成本控制和审计；是安全边界（trust boundary） |
| **工具层必须独立** | 需要不同的安全隔离（沙箱）；扩展特征不同（工具可能很重） |
| **上下文层可以独立** | 需要向量库（vector store）等专门存储；可被多个 Agent 复用 |
| **编排层贴近产品** | 变化最快，与业务逻辑耦合，通常不该过早抽象成通用平台 |

**反模式（anti-pattern）**：过早地把"Agent 平台"做成通用框架。在你有 3 个以上真实用例之前，通用抽象一定是错的。

## 10. 什么时候不要这么做（反模式清单）

| 反模式 | 为什么错 / 正确做法 |
|---|---|
| **团队 < 10 人就上微服务** | 一个服务年成本 0.2–0.5 人。5 个人拆 8 个服务 = 2–4 人在维持运转，等于团队产能砍半。**先模块化单体** |
| **按技术分层拆服务**（API 层 / 业务层 / DAO 层各一个服务） | 每次业务变更都要改 3 个服务、协调 3 次发布。这是分布式单体的最快路径。按业务能力拆 |
| **"先拆了再说，边界以后再调"** | 进程内改边界是几天，跨服务改边界是几个季度（要迁数据、要兼容期、要双写）。**边界试错必须在单体内做** |
| **同步调用链超过 3 层** | 可用性是乘法：4 个 99.9% 串联 = 99.6%，一年多 3.5 小时不可用；延迟也是加法（4 跳 ≈ +2–8 ms 且尾延迟 tail latency 叠加）。超过 3 层就改异步 |
| **多个服务共享一张表** | 见 §2。你付了微服务的成本却得到单体的耦合 |
| **用"公共库"消除重复** | 一个被 20 个服务依赖的 common 库，改一行要协调 20 次发布 —— 共享代码是最隐蔽的同步耦合（synchronous coupling）。**宁可复制，也不要为了 DRY 造跨服务依赖** |
| **绞杀者迁移不删旧代码**（停在阶段 4） | 两套逻辑长期并存，新 bug 要修两遍，且没人敢删。**把"删除旧路径"写成有 owner 和截止日的行动项** |
| **编舞超过 3 跳** | 没有任何一处能回答"下单之后到底发生了什么"。有补偿逻辑的流程一律用 Saga 编排器 |
| **每个服务一个数据库品种** | "多语言持久化"（polyglot persistence）的实际代价是 N 套备份/恢复/升级/监控/on-call 知识。**存储品种数应该 ≤ 2，除非有硬需求** |

**最后一条，也是最容易被忽略的**：

> 拆分不是一次架构决策，是一次**组织决策**。如果拆完之后没有人的 on-call 归属、绩效目标、发布节奏（release cadence）跟着变，那么半年后这些服务会重新长成一个必须协调发布的整体 —— 只是这次带着网络延迟。**能独立部署的前提是有人独立负责。**
