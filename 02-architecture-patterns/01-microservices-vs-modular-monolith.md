# 01 · 服务边界：微服务、模块化单体（modular monolith）与分布式单体（distributed monolith）

> 微服务的价值不是技术上的，是组织上的。如果你的团队不需要独立部署，你付的是纯成本。

---

## 读这一章之前

**你在工作中遇到过这个**

三年前团队把单体拆成了 8 个服务。这周你要在结算页加一个"优惠券可用余额"字段 —— 改动落在 promo、pricing、order 三个仓库，三个 PR，而且必须按 promo → pricing → order 的顺序发布，因为中间那一跳的接口不向后兼容。
排期那天 pricing 的发布窗口被另一个团队的 hotfix 占掉，你的功能整整晚了一周。
你们付了微服务的全部成本（8 条流水线、8 套告警、8 个 on-call 轮值），却仍然要开会协调发布 —— 这一章讲的就是这件事为什么会发生，以及它是边界问题还是组织问题。

**需要先懂的概念**

| 概念 | 一句话 | 详见 |
|---|---|---|
| 水平扩展 | 加更多台一样的机器，而不是把一台换得更强 | [00-concepts §4](../00-foundations/00-concepts.md#4-什么是扩展垂直-vs-水平) |
| 可用性相乘 | 串在一条链上的依赖，可用性是乘法：0.999³ = 99.7% | [00-concepts §10](../00-foundations/00-concepts.md#10-可用性几个-9-是什么意思) |
| 有状态 vs 无状态 | 替换任意实例时，正确处理请求是否依赖该实例独有的先前上下文；持久状态与可恢复会话应外置 | [00-concepts §9](../00-foundations/00-concepts.md#9-有状态-vs-无状态) |
| 同步 / 异步 | 调用方是不是原地等结果 | [00-concepts §8](../00-foundations/00-concepts.md#8-同步--异步--阻塞--非阻塞) |
| 网络延迟量级 | 同 AZ 一次往返 0.2–0.5 ms，跨 AZ 0.5–2 ms | [01-fundamentals §2](../00-foundations/01-fundamentals.md#2-只背三个数量级其余用作估算查表2026-校准版) |
| 幂等 | 同一操作执行多次，效果和执行一次相同 | [01-fundamentals §5](../00-foundations/01-fundamentals.md#5-幂等idempotency分布式系统的第一公民) |

**这一章要回答的问题**

1. 微服务真正买到的是什么？哪些"好处"其实模块化单体也能给，而且不用付网络的钱？
2. 边界画对了没有 —— 有没有不靠感觉、可观测的判断信号？
3. 我已经在单体上了，第一个该拆出去的是什么？数据怎么迁才能每一步都可回滚？
4. 拆完之后服务之间怎么通信？什么时候该同步调用，什么时候该发事件？

**本章新引入的术语**

| 术语 | English | 一句话定义 |
|---|---|---|
| 模块化单体 | modular monolith | 一个进程、一次部署，但内部按业务划成模块，模块之间只能走公开接口，由编译器或架构测试强制 |
| 分布式单体 | distributed monolith | 已经拆成多个可独立部署的服务，但改一个功能仍要同时改多个服务、并按固定顺序发布 |
| 限界上下文 | bounded context | 一个模型定义有效的范围；同一个业务名词（如"订单"）在两个上下文里指的是两组不同的字段和规则 |
| 数据所有权 | data ownership | 每份数据只有一个服务能直接读写它的存储，别的服务只能通过接口或事件拿到 |
| 康威定律 | Conway's Law | 系统最终会长成组织沟通结构的样子；反过来先定架构、再据此组织团队，叫逆康威策略 |
| 认知负荷 | cognitive load | 一个团队需要同时装在脑子里的系统与领域的数量；超过上限后，对每一个的理解都会变浅 |
| 熔断器 | circuit breaker | 下游失败率超过阈值后，调用方在一段时间内直接快速失败、不再发真实请求，冷却后再试探性放行 |
| 隔板 | bulkhead | 给每个下游或每类流量分配独立的线程／连接配额，让一个下游卡死时不会吃光全部资源 |
| 绞杀者模式 | Strangler Fig | 在旧系统前加一层路由，把功能一块块搬到新实现并逐步切流，旧系统被逐渐"绞死"而不是一次性替换 |
| 编排 / 编舞 | orchestration / choreography | 一个协调者按顺序显式调用各个服务 / 各服务只订阅事件、各自触发下一步，没有中心 |
| 防腐层 | anti-corruption layer | 夹在你的模型和外部系统之间的一层翻译代码，让外部的概念和格式不进入你的领域模型 |

## 1. 微服务真正解决的问题

| 声称的好处 | 真相 |
|---|---|
| "可以独立扩展" | 大部分服务的瓶颈是同一个数据库；单体也可以水平扩容（horizontal scaling） |
| "技术栈自由" | 通常变成"5 种语言、5 套工具链、没人能全栈调试" |
| "故障隔离（fault isolation）" | **只有在做了熔断（circuit breaker）/降级（graceful degradation）/隔板（bulkhead）之后才成立**，否则同步调用链让故障传播更快 |
| **"团队自治（team autonomy），独立部署（independent deployability）"** | 通常是最重要的收益；前提是边界、ownership 与发布流程真的独立 |
| "代码更清晰" | 模块化单体也能做到，且不用付网络的代价 |

**核心判据**：
> 你的部署瓶颈是不是"要等其他团队"？如果是 → 微服务有价值。
> 如果只有一个团队且没有独立扩展、故障/安全隔离或技术运行时等硬约束 → 模块化单体通常应先被认真比较。

### 微服务的真实成本清单

```
每个新服务的固定成本：
  □ CI/CD 流水线
  □ 部署配置与环境（dev/staging/prod）
  □ 监控 Dashboard + 告警规则 + SLO
  □ 服务发现注册
  □ 日志聚合配置
  □ 密钥管理
  □ 依赖升级与安全补丁
  □ 容量规划
  □ On-call 归属
  □ 文档与 runbook

每次跨服务调用的运行成本：
  □ 网络、排队与序列化延迟（在目标部署上测量）
  □ 序列化/反序列化 CPU
  □ 需要处理：超时、重试、熔断、幂等
  □ 跨 AZ 流量费
  □ 调试要跨服务追踪
  □ 本地开发要跑起多少个服务？
```

服务有持续的存在成本，但不存在通用的“每服务多少工程师”。用本组织的部署、升级、告警、事故、依赖维护和认知负荷数据估算，并明确 owner 与替补。

> **面试金句**：
> "微服务的独立部署收益只有在 ownership 与兼容性真的独立时才兑现；每条边界却持续增加网络、发布、可观测与故障处理成本。我会先说明要解决的是组织等待、独立扩展、故障/安全隔离还是运行时差异，再用数据证明收益超过边界税。"

## 2. 分布式单体：最糟糕的结果

**症状清单**（命中越多，分布式单体风险越高；不是按固定条数判定）：

| 症状 | 说明 |
|---|---|
| ☠️ 多个服务不受约束地直接读写同一批表 | ownership 不清、schema 与事务耦合，无法独立演进；共享物理数据库但独立 schema/权限/owner 不一定有问题 |
| ☠️ 改一个功能要同时改 3 个服务并协调发布 | 边界切错了 |
| ☠️ 同步调用链的深度和扇出使延迟/可用性预算无法满足 | 延迟叠加 + 故障传播（failure propagation）；阈值应由 SLO 与实测决定 |
| ☠️ 必须按特定顺序部署 | 没有版本兼容性 |
| ☠️ 本地开发要启动 10 个服务 | 开发体验崩坏 |
| ☠️ 一个服务挂了全站不可用 | 没有降级 |
| ☠️ 有一个"公共库"（shared library）被所有服务依赖，改它要全量重新部署 | 共享代码变成了耦合 |

**这比单体差**：你付了微服务的所有成本，却没得到独立部署的好处。

**共享表为什么容易成为强耦合**：
```
Service A ─┐
Service B ─┼─→ 同一个 orders 表
Service C ─┘

- A 想加个列 → 要通知 B、C 确认不会破坏
- B 的慢查询 → 拖垮 A 和 C
- 谁负责这张表的数据完整性？没人
- 事实上你有一个单体，只是把它拆成了三个部署单元
```

## 3. 正确的边界划分方法

### 方法 1：按业务能力（business capability）/ 限界上下文（DDD）

> DDD = Domain-Driven Design，领域驱动设计：先把业务里的概念、名词和它们的边界理清楚，再让代码结构照着这个划分长，而不是反过来先建表再想业务。

**限界上下文（Bounded Context）**：同一个词在不同上下文里含义不同 —— 这就是边界。

```
"订单" 在不同上下文中：
  销售上下文：报价、折扣、客户意向
  履约上下文：拣货、包装、发货地址、承运商
  财务上下文：应收、税、发票、退款
  客服上下文：状态、退换货记录

→ 这不是一个"Order 服务"，而是三四个上下文各自有自己的订单视图
→ 它们通过事件同步，而不是共享一张 orders 表
```

**面试信号**：能识别出"同一个名词在不同上下文有不同模型"，是 DDD 理解到位的标志。

### 方法 2：按变化频率与变化原因

> 一起变的东西放一起，不一起变的分开。（高内聚 high cohesion = 单一变更原因 single reason to change）

如果"每次改 A 都要改 B"，那 A 和 B 应该在同一个服务里。

### 方法 3：按数据所有权（data ownership）

**每份数据必须有且只有一个服务是它的"真相源"（owner）。**
其他服务只能通过 API 或事件获取，不能直接读写。

如果两个服务都想"拥有"同一份数据 → 边界画错了。

### 方法 4：按团队（康威定律 Conway's Law 的正向应用）

> "系统的架构会趋同于组织的沟通结构。" —— Conway

**逆康威策略（Inverse Conway Maneuver）**：先设计你想要的架构，再据此组织团队。

**Team Topologies 的四种团队类型：**
| 类型 | 职责 |
|---|---|
| **流式对齐团队**（Stream-aligned） | 端到端负责一条价值流，是主体 |
| **平台团队（platform team）** | 提供内部产品（部署、可观测、数据），降低流式团队的认知负荷 |
| **赋能团队（enabling team）** | 帮助流式团队掌握新能力，临时性 |
| **复杂子系统团队（complicated-subsystem team）** | 需要专业知识的部分（推荐引擎、推理引擎） |

**认知负荷（cognitive load）是核心指标**：一个团队能装下的领域数量是有限的。如果一个团队维护 15 个服务，他们对每个服务的理解都是浅的。

## 4. 模块化单体：被低估的选项

```
monolith/
├── modules/
│   ├── billing/
│   │   ├── api/          ← 只有这里对外暴露（public）
│   │   ├── internal/     ← 其他模块禁止访问（编译期强制）
│   │   └── db/           ← 明确 owner；跨模块访问受约束
│   ├── orders/
│   └── identity/
└── main.go
```

**关键约束（尽量由工具和测试强制，不能只靠自觉）：**
1. 模块只能通过公开接口互相调用（Java 的 module system、Go 的 internal 包、.NET 的 InternalsVisibleTo、ArchUnit 测试）
2. 每份数据有明确 owner。独立 schema/权限是强边界选项；如果保留跨模块外键或 JOIN，要让 owner 管理契约并记录它会增加未来拆分成本，而不是一律禁止
3. 模块间通过公开调用或进程内事件通信。进程内事件可模拟接口形状，但它与真实消息队列的提交、重复、乱序、失败和可见性语义并不相同
4. 每个模块有自己的集成测试

**收益**：
- 保持了逻辑边界和团队自治
- **没有网络延迟、没有分布式事务（distributed transaction）、没有服务发现**
- 一个进程，一次部署，本地一键跑起
- 清晰边界能降低未来拆分成本；真正拆出时仍要设计网络契约、数据迁移、独立部署、超时、幂等、可观测和故障语义，绝不是只替换事件总线

许多大型产品长期保留重要单体或模块化单体，同时也可能配套多个服务；引用公司案例只能说明这种形态可扩展，不能把外部公司当前内部架构当作你的选型证明。

**Senior 的默认建议**：
> "没有独立部署等硬约束时，我先做模块化单体，在进程内低成本验证边界。边界稳定后，仍会为数据迁移、网络故障与运维能力单独估算拆分，而不会承诺固定几周；如果边界错误，无论部署形态都会付出重构成本。"

## 5. 什么时候真的该拆

拆分的**触发条件**（不是"我觉得该拆了"，而是可观测的信号）：

| 信号 | 说明 |
|---|---|
| **部署冲突（deployment contention）** | 团队因为要等别人的代码合并而阻塞，每周多次 |
| **扩展特征差异巨大** | 某个功能需要 GPU / 需要 100× 的实例数 / 需要完全不同的存储 |
| **故障隔离刚需** | 某个功能不稳定但不能影响核心（如第三方集成、报表生成） |
| **合规隔离（compliance isolation）** | 某部分数据必须在特定区域或有特殊访问控制 |
| **技术栈刚需** | 某个功能必须用另一种语言（如 ML 推理用 Python，或需要 Rust 的性能） |
| **构建/测试时间** | 单体的 CI 超过 20 分钟，且无法通过增量构建解决 |

**最先该拆出去的三类：**
1. **异步/后台处理**（报表、批处理、通知）—— 天然解耦，风险最低
2. **资源特征特殊的**（GPU 推理、大内存的搜索索引）
3. **第三方集成层**（不稳定的外部依赖，隔离在防腐层里 —— 下面 §8 会展开防腐层）

## 6. 拆分的执行：绞杀者模式（Strangler Fig）

```
阶段 0：单体处理全部流量
        Client → [Monolith]

阶段 1：加一个路由/门面层（此时行为完全不变）
        Client → [Facade] → [Monolith]

阶段 2：新服务上线，读流量影子对比（不影响用户）
        Client → [Facade] ─┬→ [Monolith] → 返回给用户
                           └→ [New Svc] → 只做对比，记录差异

阶段 3：小比例切流（1% → 10% → 50%），随时可回滚
        Client → [Facade] ─→ 1% [New Svc] / 99% [Monolith]

阶段 4：全量切换，旧代码保留但不再调用

阶段 5：删除旧代码 ← 这一步经常被跳过，导致永久的技术债
```

**数据迁移是最难的部分：**
```
1. 选定旧库为迁移期权威来源；在同一事务写业务变更与 outbox，或用 CDC 把已提交变化投递到新库
2. 回填历史数据
3. 一致性校验（定期比对，量化差异率）
4. 读切换（先读新库，对比老库，不一致时用老库并告警）
5. 读完全切到新库
6. 停止复制/双写并清理旧路径
```
**每一步之间要有覆盖完整业务周期和故障场景的观察期，并写明回滚条件。** 时长由流量、结算周期和风险决定。

⚠️ 应用直接双写新老库无法原子提交，失败会留下分叉。迁移期优先保留一个权威写源，用 CDC 或 transactional outbox 复制已提交变化；投递仍可能重复/乱序，所以新库按稳定事件 ID 与版本幂等应用，并持续校验和对账。两者详见 [`01-building-blocks/03`](../01-building-blocks/03-messaging-and-streams.md)。

## 7. 服务间通信的选择

```
                 需要立即知道结果吗？
                    /          \
                  是            否
                  /              \
          同步调用              异步事件
         (gRPC/HTTP)          (Kafka/队列)
              |                    |
        必须处理：            必须处理：
        - 超时                - 幂等
        - 重试(幂等)          - 乱序
        - 熔断                - 重复
        - 降级                - DLQ
        - deadline 传播        - 最终一致的用户体验
```

（图里两个还没解释的词：**DLQ** = dead letter queue，死信队列 —— 反复消费失败的消息被移出主队列、单独存起来等人处理，见 [`01-building-blocks/03`](../01-building-blocks/03-messaging-and-streams.md)；**deadline 传播** = 把"这次调用还剩多少毫秒"随请求一层层传下去，每层只减不加，见 [`00-foundations/01 §9`](../00-foundations/01-fundamentals.md#9-幂等--重试--超时三件套必须一起设计)。）

### 编排（Orchestration）vs 编舞（Choreography）

**编排**：一个协调者显式调用各个服务（这个协调者常被叫作 **Saga 编排器** —— Saga 指"把一个跨服务的长流程拆成 N 个各自提交的本地事务，每步配一个反向操作，中途失败就逆序执行这些反向操作"，完整展开在[下一篇 §2](02-event-driven-and-cqrs.md#2-saga跨服务事务的现实解法)）
```
        [Order Saga Orchestrator]
         │      │       │
         ▼      ▼       ▼
      支付    库存    物流
```
✅ 流程可见、易调试、易改、状态集中
❌ 协调者是耦合点；若状态只在单实例内才是单点。生产实现应让 worker 可替换、状态持久化，并用可靠 claim/lease/fencing 让多实例安全接管

**编舞**：服务通过事件互相触发
```
Order创建 ──event──> 支付服务 ──event──> 库存服务 ──event──> 物流
```
✅ 发布者与新增消费者在部署上更松耦合
❌ **没有人知道完整流程是什么**、调试地狱、循环依赖（circular dependency）难发现

**Senior 的判断**：
> 有明确生命周期、超时与补偿责任的流程通常更适合可观察的编排；纯通知、消费者互不影响时编舞更自然。不要用固定“3 跳”判定：看能否画出 owner、状态机、失败/重放路径并在一次 trace 中解释全流程。

## 8. 防腐层（Anti-Corruption Layer）

当你要集成一个你不控制的系统（遗留系统、第三方 API）：

```
[你的领域模型] ←→ [防腐层：翻译 + 适配] ←→ [外部系统的模型]
```

**价值**：
- 外部系统的怪异概念不会污染你的模型
- 外部 API 变更只影响一层
- 可以在防腐层加缓存、重试、熔断、限流（rate limiting）
- **可以 mock 掉做测试**

**专项提示（AI）**：若产品确实要支持多个 LLM Provider，可用防腐层统一本产品需要的能力，同时保留供应商特有能力的显式逃生口；只有一个提供商或能力差异很大时，过早追求“完全统一”也会制造错误抽象。见 [`06-case-studies/02-llm-gateway.md`](../06-case-studies/02-llm-gateway.md)。

## 9. 专项选读：AI/Agent 系统的服务边界

通用 Full Stack 路径可以先跳到 [§10](#10-什么时候不要这么做反模式清单)。下面是可选逻辑分层，不代表每一层都要独立部署。

现代 AI 应用的典型分层（这是一个新的、正在成型的标准架构）：

```
┌─────────────────────────────────────────────────────┐
│  产品层（Product）                                    │
│  会话管理、UI 状态、用户偏好、协作                      │
├─────────────────────────────────────────────────────┤
│  Agent 编排层（Orchestration）                        │
│  Agent 循环、规划、工具选择、子代理、状态机              │
├─────────────────────────────────────────────────────┤
│  上下文层（Context）                                  │
│  检索、重排、记忆、压缩、上下文组装                      │
├─────────────────────────────────────────────────────┤
│  工具层（Tools）                                      │
│  工具注册、参数校验、沙箱执行、MCP Server              │
├─────────────────────────────────────────────────────┤
│  模型网关（Model Gateway）                            │
│  路由、限流、缓存、重试、成本计量、审计、Provider 抽象   │
├─────────────────────────────────────────────────────┤
│  推理层（Inference）                                  │
│  自建 GPU 集群 / 第三方 API                           │
└─────────────────────────────────────────────────────┘
```

**为什么这样切：**

| 边界 | 理由 |
|---|---|
| **模型网关可独立** | 多产品共享、需要集中的成本控制/审计或独立扩缩容时收益明显；小系统可先做进程内模块 |
| **工具执行可独立隔离** | 不可信代码、不同权限或重型工具需要沙箱/独立故障域；简单只读工具不必因此拆服务 |
| **上下文层可以独立** | 需要向量库（vector store）等专门存储；可被多个 Agent 复用 |
| **编排层贴近产品** | 变化最快，与业务逻辑耦合，通常不该过早抽象成通用平台 |

**反模式（anti-pattern）**：在真实用例尚未揭示共同点时就把“Agent 平台”抽象成通用框架。判断依据是稳定、重复出现的能力与契约，不是固定用例数量。

## 10. 什么时候不要这么做（反模式清单）

| 反模式 | 为什么错 / 正确做法 |
|---|---|
| **没有明确边界收益就上微服务** | 先量化独立部署/扩展/隔离收益，并确认每个服务有 owner、自动化和可观测；团队人数本身不是充分判据 |
| **按技术分层拆服务**（API 层 / 业务层 / DAO 层各一个服务） | 每次业务变更都要改 3 个服务、协调 3 次发布。这是分布式单体的最快路径。按业务能力拆 |
| **"先拆了再说，边界以后再调"** | 跨服务改边界还要迁数据、兼容契约和双轨运行，通常比进程内重构贵。没有硬约束时先在模块内验证边界 |
| **同步调用链越过端到端预算** | 逐跳延迟、可用性与重试会组合，扇出还放大尾延迟（见 [`00-concepts §3`](../00-foundations/00-concepts.md#3-为什么平均值是骗人的p50--p90--p99)）。按 SLO 预算决定缩短、并行、降级或异步，不按固定层数 |
| **多个服务共享一张表** | 见 §2。你付了微服务的成本却得到单体的耦合 |
| **用"公共库"消除重复** | 一个被 20 个服务依赖的 common 库，改一行要协调 20 次发布 —— 共享代码是最隐蔽的同步耦合（synchronous coupling）。**宁可复制，也不要为了 DRY 造跨服务依赖** |
| **绞杀者迁移不删旧代码**（停在阶段 4） | 两套逻辑长期并存，新 bug 要修两遍，且没人敢删。**把"删除旧路径"写成有 owner 和截止日的行动项** |
| **无 owner、状态机与全链路观测的长编舞** | 无法回答流程进行到哪、谁补偿。明确业务流程通常用持久化编排；简单通知仍可编舞 |
| **无硬需求的多语言持久化** | 每种存储都增加备份、恢复、升级、监控和 on-call 知识；按已证明的查询/容量需求引入，不设通用“最多两种” |

**最后一条，也是最容易被忽略的**：

> 拆分不是一次架构决策，是一次**组织决策**。如果拆完之后没有人的 on-call 归属、绩效目标、发布节奏（release cadence）跟着变，那么半年后这些服务会重新长成一个必须协调发布的整体 —— 只是这次带着网络延迟。**能独立部署的前提是有人独立负责。**

---

## 这一章的三句话

1. **微服务最常见的核心收益是独立 ownership 与部署，也可能服务于独立扩展、故障/安全隔离和运行时差异。** 每条边界都增加持续成本，必须指出它在解决哪个已存在的约束。
2. **边界画错后，微服务还要额外承担网络契约和数据迁移。** 没有硬约束时，先用模块化单体低成本验证边界；拆分时间必须按真实数据与依赖估算。
3. **能独立部署的前提是有人独立负责。** 如果 on-call 归属、绩效目标、发布节奏没跟着一起拆，半年后这些服务会重新长成一个必须协调发布的整体，只是这次带着网络延迟。
