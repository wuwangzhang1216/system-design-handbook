## 1. 一个请求到底经历了什么

**这一节是全书的骨架**，后面所有架构图都是下面这张图的变体。
你在手机上刷到一条帖子点了个赞，心变红了，用时约 0.1 秒。这 0.1 秒里，你的点击穿过了至少六种完全不同的软件。

```
[你的手机]
   │ ① 点击瞬间客户端先把心变红（乐观更新 optimistic update）—— 你感到的"快"有一半是装出来的
   ▼
[② DNS]         把 api.example.com 翻译成一个 IP 地址        0 ms（本机缓存）～ 50 ms（递归查上去）
   ▼
[③ CDN / 边缘]  离你最近的一批机器：静态资源直接返回，       你 → 边缘 10–30 ms
   │             API 请求在这里做 TLS 握手后**回源**（下表 ③ 解释这个词）
   ▼
[④ 负载均衡器]  从 40 台一模一样的机器里挑一台还活着的        < 1 ms
   ▼
[⑤ API 服务]    验 token、查权限、判断这次点赞合不合法        1–10 ms（自身 CPU）
   │
   ├──▶ [⑥ 缓存 Redis]    "这帖子现在多少赞？"有就不打扰 DB    0.2–1 ms（同机房）
   ├──▶ [⑦ 数据库]        写下 user_42 赞了 post_99，断电不丢  5–20 ms（刷盘 + 等副本，
   │                      副本 = 同一份数据在另一台机器上的拷贝，§5 讲）
   └──▶ [⑧ 消息队列]      "通知作者 / 更新热榜 / 写数仓"       1–5 ms（只等"我收下了"）
              │
              └──▶ [⑨ 后台消费者]  几十毫秒～几秒后慢慢做完，此时用户早就看到成功了
   ▼
⑩ 200 OK 一路原路返回手机 —— 端到端 p50 ≈ 80–150 ms（你感觉"瞬间"的那 0.1 秒）
```

> 上面出现了 **p50**，下面 §2 还会出现 **p99** —— 这是本章唯一两处"先用后讲"的词，因为不给个数字这张图就没法读。
> 现在只需要知道：**p50 = 把所有请求按耗时排序后正中间那个（一半的请求比它快）；p99 = 排在 99% 位置那个（只有最慢的 1% 比它还慢）。**
> 完整解释和它们为什么比平均值重要，在 [§3](#3-为什么平均值是骗人的p50--p90--p99)。

### 每一跳的三件事

| # | 组件 | 它在干什么（一句话） | 典型耗时 | 它挂了会怎样 |
|---|---|---|---|---|
| ② | **DNS** | 把域名翻译成 IP 地址 | 0–50 ms | 全站打不开。但客户端有缓存 TTL（**TTL = time to live，一份缓存的存活时长，到点自动作废**），影响会**延迟几分钟才爆发，也延迟几分钟才恢复** |
| ③ | **CDN / 边缘节点** | 把静态内容放到离用户近的地方，并就近接入；边缘手上没有的内容就**回源**（origin fetch：到后面那个权威来源真正取一次，见 [`01/02`](../01-building-blocks/02-caching.md)） | 10–30 ms | 图片 / JS 挂掉；API 可能仍能直连源站，但延迟涨到跨洲级别 |
| ④ | **负载均衡器 (load balancer)** | 把请求分给一堆功能相同的机器，跳过挂掉的 | < 1 ms | **入口全断**。所以 LB 自己必须有冗余 |
| ⑤ | **API 服务** | 执行业务逻辑：鉴权、校验、编排下面几步 | 1–10 ms | 挂一台没事，LB 摘掉它 —— **前提是它无状态，见 §9** |
| ⑥ | **缓存 (cache)** | 把查过 / 算过的结果暂存在快的地方 | 0.2–1 ms | 危险。命中率 90% 的缓存挂掉 = 数据库瞬间承受 **10 倍**流量 |
| ⑦ | **数据库 (database)** | 权威地、持久地存下这条数据 | 5–20 ms（写） | 写全失败；读**可能**还能从只读副本走（见 §5） |
| ⑧ | **消息队列 (message queue)** | 收下"待办事项"，让下游按自己的节奏做 | 1–5 ms | 看你怎么写的：要么主流程被拖住，要么这些后续动作**静默丢失** |
| ⑨ | **后台消费者 (consumer)** | 真正干那些不用让用户等的活 | 秒级 | 用户看不出来，但通知不发、热榜不更新 —— **最难发现的那类故障** |

### 从这张图能读出三件事

**第一，"快"是分层做出来的。** Web API 的 100 ms 里网络和等待经常占大头，真正的计算可能只有几毫秒 ——
所以先用**链路追踪（tracing：记录一次请求在每一跳分别花了多久）**把时间拆开；如果大头在网络，就减少跳数和往返；
如果大头在计算、锁或排队，就优化对应部分。
**先测量，再优化。**

**第二，同步路径和异步路径是两条命。** ⑤⑥⑦ 在**关键路径（critical path）**上，它们慢用户就慢、它们挂请求就失败；
⑧⑨ 被移出了关键路径，它们慢用户不知道、它们挂用户也不知道（这既是优点也是隐患）。
**"哪些事必须在用户等待期间完成"是系统设计里最高频的一个判断。**

**第三，这张骨架能套到任何题上。** 设计短链、朋友圈、打车，高层图都是这条链的变体：
换掉 ⑦ 的存储选型、在 ⑥ 加一层、把 ⑧ 变成主角，仅此而已。

> 💡 **面试里为什么考它**：45 分钟的题，前 10 分钟你要画出高层架构。画不出这条链的人会一上来纠结
> "用 MySQL 还是 Mongo"，顺序做反了；能画出的人先立框架再逐个深挖 —— 这是节奏分。

## 2. 延迟、吞吐、并发 —— 三个最常被混淆的词

你的服务变慢了。你加了一倍机器，QPS 上去了，但**用户感受到的慢一点没变**。老板问你为什么，你要能在 30 秒内说清。

```
  ┌───────────────────── 100 公里 ─────────────────────┐
  入口 ═══════════════════════════════════════════ 出口
        🚗   🚗   🚗   🚗   🚗   🚗   🚗   🚗
        └───────── 此刻还在路上的 8 辆车 ─────────┘
  延迟 (latency)     = 一辆车从入口开到出口花了多久       → 单个用户的体验
  吞吐 (throughput)  = 每小时有多少辆车通过出口           → 系统的产能
  并发 (concurrency) = 此刻已进未出的车有几辆             → 系统里的在途量
```

| 词 | English | 定义 | 单位 |
|---|---|---|---|
| **延迟** | latency | 单个请求从发出到收到结果经过的时间 | ms |
| **吞吐** | throughput | 单位时间内系统完成的请求数 | QPS / rps / TPS |
| **并发** | concurrency | 某一时刻已经开始但还没结束的请求数（也叫**在途请求 in-flight requests**） | 个 |

⚠️ **延迟不是 delay**。delay 指"本该早点发生却被推迟了"，latency 指"这件事本身就需要这么久"。
英文面试说 "the delay is 100ms" 会让对方以为你在讲某个异常。

### Little's Law —— 三者的关系

全书唯一一条你必须记住的公式，而且它非常简单：**`并发 L = 吞吐 λ × 延迟 W`**。
严格地说，Little's Law 用的是**稳定系统在一段足够长时间里的平均值**：进入速率长期等于完成速率，系统里的请求不会无限堆积。
容量估算里常用“峰值 QPS × 峰值时段的平均延迟”做近似，但不要把某一秒的瞬时峰值和另一个时段的延迟随意相乘。

**直觉版**：一小时通过 6000 辆车、每辆在路上开 30 分钟，那么路上任意时刻约有 `6000 × 0.5 = 3000` 辆车 ——
因为每辆车"占用路面"半小时，而车是持续进来的。

```
算一遍：你的服务峰值 2000 QPS，平均延迟 50 ms
  → 并发 = 2000 × 0.05 = 100 个请求同时在处理
  → 每请求占一个线程 = 需要 ≥ 100 个线程；每请求占 2 MB = 需要 200 MB 常驻

某天下游变慢，延迟 50 ms → 500 ms，流量没变：
  → 并发 = 2000 × 0.5 = 1000 个 → 线程池只有 200 个（按上面算出的 100 个留了 2 倍余量配的）
                                → 1000 − 200 = 800 个请求在门外排队
  → 排队让延迟继续涨 → 并发继续涨 → 雪崩
```

**这条链要能脱口而出**：下游变慢 → 并发上升 → 资源耗尽 → 自己也挂。
很多"莫名其妙的连锁故障"就是这四步。

### 那个反直觉的结论

**加宽车道能让每小时通过更多车，但不会让任何一辆车开得更快。**
翻译成工程语言：**加机器提高吞吐，但不降低单个请求的延迟。** 一个查询本身要跑 200 ms，加 100 台机器它还是 200 ms。

**唯一的例外**（也很重要）：如果当前延迟里**有一大部分是排队等出来的**，加机器减少排队，延迟会降。
但它降的是"排队时间"，不是"干活时间"。干活时间只能靠改算法、加索引、加缓存、减少往返来降。

区分这两者是 senior 和 mid 的一条分界线：
> "现在 p99 是 400 ms，其中服务时间只有 30 ms，剩下 370 ms 全在队列里等 —— 这个加机器有用。反过来就一点用都没有。"

> 💡 **面试里为什么考它**：几乎每道题的容量估算都要用 Little's Law 反推连接数、线程数、内存。
> 而"加机器降不降延迟"是最经典的送命题。完整的排队论在 [`00/02 §3`](02-capacity-estimation.md)。

## 3. 为什么平均值是骗人的：p50 / p90 / p99

监控面板显示"平均响应时间 74 ms"，看起来很健康。但客服每天收到十几条"卡死了"的投诉，你查日志查不出问题。
面板没骗你，它只是**回答了一个没人关心的问题**。

**手算一遍：**

```
某分钟内你的接口收到 100 个请求：
  50 个：20 ms（缓存命中）  40 个：40 ms（查了一次库）
   9 个：200 ms（赶上 GC）   1 个：3000 ms（连接池满，排了 3 秒队）

第一步：排序 —— 分位数的定义就建立在排序上
  位置:  1 ──────────── 50 ─────── 90 ───── 99  100
  值:   [20 20 … 20 20][40 … 40][200 … 200][3000]
         └── 50 个 ──┘└─ 40 个 ┘└─ 9 个 ─┘└1 个┘
```

| 指标 | 怎么算 | 结果 | 含义 |
|---|---|---|---|
| **平均值** | (50×20 + 40×40 + 9×200 + 1×3000) ÷ 100 | **74 ms** | 没有任何一个真实请求耗时 74 ms |
| **p50**（中位数） | 排序后第 50 个 | **20 ms** | 一半请求比它快 |
| **p90** | 排序后第 90 个 | **40 ms** | 90% 的请求比它快 |
| **p99** | 排序后第 99 个 | **200 ms** | 99% 的请求比它快 |
| **max** | 最后一个 | **3000 ms** | 最惨的那个用户 |

**看清楚这里发生了什么：平均值 74 ms 比 p90（40 ms）还大。** "平均"这个数字比 **90% 的真实请求都慢** ——
它既不代表典型用户，也不代表倒霉用户，谁都不代表。一个 3 秒的请求就把它拉走了 30 ms（3000 ms ÷ 100 个请求 = 它一个人给平均值贡献了 30 ms），
而这正是长尾分布（long-tail distribution）的常态。

> **p99 = 把所有请求按耗时排序后，排在第 99% 位置的那个值。** 读作 "P ninety-nine"，正式场合说 "the ninety-ninth percentile"。

**为什么 senior 更关心分位数**：① 平均值很容易被异常值拉动，而系统的问题常藏在长尾里；
② p99 给出了最慢 1% 与其余请求的边界，能直接描述“绝大多数用户至少有多快”；
③ 延迟 SLO 常写成“99% 的请求在 200 ms 内返回”，比平均值更贴近用户体验。
SLO 不只这一种写法：成功率、错误率、可用性也都可以成为 SLO；平均延迟同样可测量，只是通常不适合作为用户体验承诺。

### p99 比它的名字听起来重要得多

```
一个页面加载要发 20 个 API 请求（很常见）。先假设每个请求变慢的概率独立，且各有 1% 概率落进最慢的 1%：
  完全不撞上 p99 = 0.99²⁰ = 81.8%  →  至少撞上一个 = 18.2%
  即每 5 次页面加载，就有 1 次的整体耗时被那个"1% 的慢请求"决定
换成 p90 更吓人：
  至少撞上一个 p90 = 1 − 0.9²⁰ = 88%  →  几乎每次加载都会遇到一个"最慢 10%"的请求
而用户一天加载几十次页面。对他来说，"偶尔卡一下"不是偶尔，是天天。
```

这就是**尾延迟（tail latency）**为什么值得单独有个名字。在同样的独立性假设下，扇出（fan-out）到 100 个后端并等全部返回时，
63% 的请求会撞上至少一个慢后端。现实中的慢请求可能共享机房、依赖或 GC，彼此相关，因此这个算式是估算，不是保证 ——
完整推导在 [`00/01 §7 尾延迟放大`](01-fundamentals.md)。

### 一个几乎所有人都犯过的错误：分位数不能取平均，也不能相加

```
两台机器，你想知道整体 p99：
  机器 A：990 个请求全部 10 ms → p99(A) = 10 ms
  机器 B： 10 个请求全部 1000 ms → p99(B) = 1000 ms

  错误做法：(10 + 1000) / 2 = 505 ms
  正确做法：1000 个请求合起来排序 → 位置 1–990 是 10 ms，991–1000 是 1000 ms
            p99 = 第 990 个 = 10 ms
  真实答案 10 ms，平均法给 505 ms —— 差 50 倍。反方向的严重低估也会发生，所以完全不可用。
```

**正确做法**：监控系统存的不是"p99 这个数"，而是**直方图的桶（histogram buckets）**
——"0–10 ms 有多少个、10–50 ms 有多少个……"。桶可以相加，加完再算分位数。
（Prometheus 的 `histogram_quantile`、OTel 的 explicit bucket histogram 就是干这个的。）
英文面试可以直接用这句：*"Percentiles don't aggregate — you have to sum the buckets first."*

> 💡 **面试里为什么考它**：面试官问"你的 p99 是多少"，你答一个平均值，这一轮基本废了。
> 而"三个服务的 p99 加起来是不是链路的 p99"是高频陷阱题（答案：不是，而且通常更糟）。

## 4. 什么是"扩展"：垂直 vs 水平

你的服务撑不住了。摆在面前两条路：把这台 4 核 16 G 换成 32 核 128 G；或者再买 7 台一样的。
**这两条路会把你带进完全不同的两本书。**

| | English | 做法 | 上限 |
|---|---|---|---|
| **垂直扩展** | scale up / vertical scaling | 把**同一台**机器换得更强 | 硬。单机核数、内存、带宽都有物理天花板 |
| **水平扩展** | scale out / horizontal scaling | **加更多台**机器分担工作 | 理论上没有，实践中被"协调成本"卡住 |

⚠️ 中文两件事都叫"扩容"，英文必须分清。面试里 "scale out" 和 "scale up" 是两个完全不同的方案。

```
垂直扩展                        水平扩展
   ┌────┐                       ┌──┐┌──┐┌──┐┌──┐
   │ 32 │  ← 换成一台更大的      └──┘└──┘└──┘└──┘
   │ 核 │                       ┌──┐┌──┐┌──┐┌──┐
   └────┘                       └──┘└──┘└──┘└──┘   8 台一样的小机器

简单：代码一行不改               复杂：本书剩下的全部内容
上限：撞到最大机型就没了          上限：撞到协调成本
风险：它挂了你就全挂了            风险：它们中总有一台是挂的
```

**垂直扩展被低估了。** 现在一台机器可以有 192 核、2 TB 内存、几百万 IOPS（IOPS = 每秒能完成多少次磁盘读写操作），这个规格下多数创业公司的全部热数据都能塞进单机内存。
"先垂直扩展，把水平扩展推迟两年"在很多场合是**正确且省钱**的答案 —— 面试里敢这么说并给出触发条件
（"等热数据装不下 / 等写入超过 X"），是加分的。

**但它有一个躲不掉的问题：一台机器永远是单点。** 就算性能够，它也会重启、坏盘、被断电。
所以真实系统即使不需要水平扩展的**性能**，也需要水平扩展的**冗余**。

### 这一节是全书所有麻烦的源头

一旦从"一台"走到"多台"，下面这条因果链就被触发了。**本书剩下的 40 篇，基本就是在处理这条链上的每个节点：**

```
                              机器不止一台
                                    │
    ┌───────────────┬───────────────┴────────┬──────────────────┐
    ▼               ▼                        ▼                  ▼
①请求会落到任意    ②数据一台放不下         ③任何一台都会挂     ④它们之间要通信，
  一台 —— 你上一      / 一台写不动                                而网络会断、会慢
  秒的会话在别台      │                       │                  │
    │                ▼                       ▼                  ▼
    ▼             把数据切开 → 分片 shard  每份存多份 → 副本    ⑤断的时候，两边
 §9 有状态        · 跨机查询/事务怎么办    · 写哪一份？谁权威？    都以为自己是对的
    vs 无状态     · 分片键选错 = 热点      · 读到旧的怎么办？      → CAP 定理
                    （§5）                   （§5）→ §6 一致性    → 共识 (01/05)
```

把这张图记住。**你在后面每一篇里遇到的复杂度，都能在这张图上找到它的出生地。**
分片键、复制延迟、脑裂、共识、分布式事务 —— 单机上根本不存在，全都是"多台机器"这一个决定的利息。

图里有两个后面会反复出现的词，先各给一句，免得你带着它们往下读：
**热点（hot key）**= 绝大部分负载压在极少数的键上 —— 分片键选得不好时，一个分片被打爆而其余分片闲着，
"均匀打散"对它无效，必须给它单独一条路径（[`00/03 §4`](03-tradeoff-framework.md)）；
**脑裂（split-brain）**= 网络断开后两边都以为自己是权威、各自接受写入 —— 下一节 §5 会画出它长什么样。

> 💡 **面试里为什么考它**：问"数据量涨 100 倍怎么办"，差的回答直接跳到"分库分表"；
> 好的回答先说清**为什么必须水平扩展**（装不下？写不动？还是要跨 AZ 冗余？
> **AZ = availability zone 可用区：云厂商同一地区里彼此独立供电、独立网络的一组机房，跨 AZ 部署 = 一个机房整个断电你也不全挂**）——这三个原因对应三种不同的切法。

## 5. 副本、分片、分区 —— 三个被混用的词

同事说"我们把这张表做了分区"。你要在 3 秒内判断：他是把数据**复制**了几份，还是把数据**切开**放到不同机器上？
这两件事解决的问题完全相反。

| 词 | English | 是什么 | 为了解决什么 |
|---|---|---|---|
| **副本** | replica / replication | 同一份数据的多个**完整拷贝**，放在不同机器上 | ① 一台挂了还有别的（可用性）② 读请求分给多台（读扩展） |
| **分片** | shard / sharding | 把数据**切成互不重叠的块**，每块放不同机器 | ① 一台装不下（容量）② 一台写不动（写扩展） |
| **分区** | partition | **三个常见层面的意思，见下** | —— |

```
副本 —— 每台都有全部数据                  分片 —— 每台只有一部分数据
 ┌───────────┐┌───────────┐┌───────────┐  ┌───────────┐┌───────────┐┌────────────┐
 │用户 1–1000万││用户 1–1000万││用户 1–1000万│  │用户 1–333万││用户334–666万││用户667–1000万│
 └───────────┘└───────────┘└───────────┘  └───────────┘└───────────┘└────────────┘
 容量：没变（仍要一台装得下）              容量：×3   写：×3
 读：×3   写：没变（甚至更差，要同步 3 份） 挂一台：那 1/3 用户全不可用，数据可能永久丢失
 挂一台：数据不丢，服务不断                新麻烦：跨分片的查询和事务变得极难

真实系统 —— 两个一起用（3 分片 × 3 副本 = 9 台）
  分片 0 [主][副][副]    分片 1 [主][副][副]    分片 2 [主][副][副]
          └ 同一份数据的 3 个拷贝 ┘
```

> **副本解决"某台会挂"和"读太多"；分片解决"数据太大"和"写太多"。它们互相独立，真实系统两个都要。**

### 必须点明的歧义：partition 有三个常见意思

英文里 `partition` 至少用在三个不同层面，中文经常都译成“分区”。**读 CAP 时分不清它们，你会彻底困惑。**

| 用法 | 中文 | 含义 | 出现在 |
|---|---|---|---|
| **partition ①** | 逻辑分区 | 数据在一个系统内部的逻辑切块；不保证每块在不同机器上 | PostgreSQL 表分区、Kafka partition |
| **partition ②** | 分片 | 数据按路由规则分到不同节点；是水平扩展的部署单位 | database shard、shard key |
| **partition ③** | 网络分区 | 网络故障，机器之间**断了联系**（机器本身还活着） | CAP 里的 P、network partition、split-brain |

逻辑分区和分片经常重合，但**不等价**：一张 PostgreSQL 表可以在同一台数据库里分成 12 个月份分区，这没有水平扩展；
Kafka 的 partition 也可能因为副本和 leader 调度而分布在不同 broker 上。只有当切块同时成为跨节点的路由、容量或负载单位时，本书才叫它 **shard**。

```
partition ③（网络分区）长这样：
   ┌────────────────┐                     ┌────────────────┐
   │ 节点 A  节点 B │ ╳╳╳ 网络断了 ╳╳╳ │     节点 C     │
   └────────────────┘   ──── ✕ ────       └────────────────┘
     ↑ 还活着、还在收请求，以为 C 挂了       ↑ 也还活着、也在收请求，以为 A、B 挂了

   危险在于：两边都继续接受写入 → 出现两个"权威" → 脑裂（split-brain）
   同一个账户可能在左边被扣 100，在右边也被扣 100。
```

**消歧惯例**（本书用法）：说表或日志内部切块用 **逻辑分区 / partition**；说跨节点的数据切分用 **分片 / shard / sharding**；
说网络故障**永远说全 "network partition"**，不要简称。
⚠️ 英文里网络分区**不叫** "network split" —— 这是中文母语者的高频错译。

> 💡 **面试里为什么考它**：问"数据量大怎么办"你答"加副本"，就暴露了没分清这两件事（副本对容量毫无帮助）；
> 反过来问"怎么保证高可用"答"分片"是同样的错。这是最容易被一眼看穿的基础漏洞。

## 6. 什么是"一致性" —— 一个词，两种完全不同的意思

**这是本章最重要的一节。** 读慢一点。

你和朋友坐在一起，两人都在手机上看**同一个**银行账户，余额都是 1000 元。
你转入 100 元，你的屏幕立刻显示 1100。你对朋友说："刷新一下。"他会看到多少？
**答案取决于系统给你的是哪种一致性。**

**为什么会看到不一样**：因为 §5 说过，这份数据存了**多个副本**。你的写只落到其中一份（主副本），复制到别的副本需要时间。

```
时间轴 →    0 ms          5 ms          50 ms          200 ms
  你     ──[写入 +100]─────────────────────────────────────▶
  主副本 ────────────[余额 = 1100]────────────────────────▶
  从副本 ──────────────────[还是 1000]──────[余额 = 1100]─▶
  朋友的请求正好落到           ↑ 他此时刷新      ↑ 他此时刷新
  从副本上                     读到 1000         读到 1100
       ← 在最终一致系统里，读到 1000 是合法的、不算 bug 的、监控也不报警的
```

复制要多久？同机房 0.5 ms，跨机房 2–5 ms，跨大洲 **60–150 ms**（光速下限，见 `00/01 §1`）。
所以跨洲部署的系统里，"不一致窗口"是**肉眼可见**的。

| | English | 定义 | 朋友看到什么 | 代价 |
|---|---|---|---|---|
| **强一致（本书约定）** | strong consistency | 写入成功后，**之后才开始**的读不会返回这次写之前的旧值 | 一定是 1100 或更晚的新值 | 通常要读权威副本，或由复制 / 共识协议协调 → 增加网络往返或降低故障时的可用性 |
| **最终一致** | eventual consistency | 停止写入后，**最终**所有副本收敛到同一值；中间不同人可能读到不同值，**没有承诺多久** | 可能 1000，可能 1100 | 便宜、快、网络分区时还能用。代价是要处理"用户看到旧数据" |

⚠️ 注意定义里那句：**"没有时间上界"**。实践中通常几十毫秒到几秒，但**理论上的承诺就是没承诺**，所以不能靠它保证正确性。

`strong consistency` 在工程讨论里是一个容易含糊的口语总称，不同产品可能拿它指不同保证。为避免后文摇摆，**本书未特别说明时，
“强一致”专指下面的 linearizability（线性一致）**。另外，“写要等多数副本”只是常见实现思路，不是定义本身；
多数副本必须配合正确的复制或共识协议，不能仅凭“写了两台”就自动得到线性一致。

**最终一致不是"有 bug"**，它是被明确选择的取舍：点赞数慢半秒没人在乎，账户余额慢半秒会出事。
**同一个系统里不同的数据可以选不同的一致性** —— 这句话是 senior 级别的标志。

### 现在讲最大的坑：ACID 的 C 和 CAP 的 C 是两个东西

两个都写作 **Consistency**，中文都译成"一致性"。**它们之间没有任何关系，只是撞名。**

| | ACID 里的 C | CAP 里的 C |
|---|---|---|
| **在讲什么** | 一个事务执行完，数据必须**仍然满足你定义的所有业务规则** | 对外表现得像一份最新数据，已完成操作的顺序不违背真实时间（linearizability） |
| **具体例子** | 余额不能为负；借方合计 = 贷方合计；外键指向的行必须存在 | 你写完后，朋友从另一台机器读，读到的是新值 |
| **谁保证的** | 应用和数据库共同保证：你定义正确的状态转换，数据库执行约束、隔离与回滚 | 复制协议 / 共识算法 |
| **适用范围** | 一次事务前后的业务正确性 | 分布式副本对外暴露的操作历史 |
| **不满足会怎样** | 数据脏了，业务算错账 | 用户读到旧数据 |

> **ACID 的 C 问“事务有没有把有效状态变成另一个有效状态”；CAP 的 C 问“整个系统对外是否像一份最新副本”。**
> CAP 并不要求每台机器内部在同一纳秒保存完全相同的字节；落后的副本只要不对外返回旧值，仍可能满足 C。

还有第三个撞名的：**缓存一致性（cache coherence）**—— 缓存里的值和数据库里的不同步，也常被简称"一致性问题"。
所以有人说"我们这里有一致性问题"，先问一句：**是哪一种？**

### linearizable（线性一致）是什么

这个词从下一篇开始反复出现，先给一句话：

> **线性一致 = 系统表现得就像只有一份数据、所有操作排成一条线依次发生，**
> **而且这条线不和真实时间矛盾 —— 你写完之后才开始的任何读，一定读到这次写（或更新的值）。**

它就是本书把“强一致”具体化后的精确定义。回到刚才的场景：只要你的"转入 100"返回成功了，
**在那之后**你朋友的任何一次读，都不可能读到 1000，哪怕他在另一个大洲。

**它不是什么：**
- **linearizable ≠ serializable（可串行化）**。serializable 管**多个事务之间**不互相干扰（§7）；
  linearizable 管共享对象上的操作次序是否尊重真实时间。两者正交 —— 一个系统可以可串行化但不线性一致（读到一个陈旧但自洽的快照）。
- **linearizable ≠ 快**。恰恰相反，它通常意味着每次操作都要跨机器达成一致：同机房多 1–2 ms，跨洲多 100 ms 以上。

此外还有顺序一致、因果一致、读己之写等不同保证；它们并不全都能简单排在同一把“强弱尺子”上。
完整谱系和每档成本在 [`00/01 §4`](01-fundamentals.md)。**这一章只要求你分清 linearizable 和 eventual，并记住前者是那句“像只有一份数据”。**

> 💡 **面试里为什么考它**：一致性是系统设计面试区分度最高的维度。Mid 答"用事务"；
> senior 答"这条链路可以最终一致因为 X，那条必须线性一致因为 Y，代价是多一个 RTT"
> （**RTT = round-trip time，一次网络往返：消息发过去 + 回应传回来的总时间**，就是上表里那个"至少多一个网络往返"）。
> 而把 ACID 的 C 和 CAP 的 C 混着说，面试官会立刻降档。

## 7. 事务与隔离级别

从你的账户转 100 元给朋友。这需要两步：你 −100，他 +100。
**如果服务器在两步中间断电了会怎样？** 100 元凭空消失。事务（transaction）就是为了让这不可能发生。

| 字母 | English | 中文 | 在这次转账里意味着 | 不满足会怎样 |
|---|---|---|---|---|
| **A** | Atomicity | 原子性 | 两条 UPDATE **要么都生效，要么都不生效** | 断电时钱凭空消失或凭空出现 |
| **C** | Consistency | 业务约束（**注意 §6 的撞名**） | 转账前后**总额不变**，余额不能为负 | 账对不上；余额 −50 |
| **I** | Isolation | 隔离性 | 别人不会看到"你扣了但他还没加"的中间状态 | 别人算总额时算出少了 100 |
| **D** | Durability | 持久性 | 一旦返回成功，立刻断电也不丢 | 用户看到成功，重启后钱回来了 |

**A 和 D 通常靠日志等机制实现**（先把恢复所需的信息持久化，再改数据；崩溃后照日志重放或回滚）；
**C 由应用和数据库共同保证**：业务规则由你定义，数据库用 `CHECK`、`UNIQUE`、外键、隔离和回滚等机制帮你守住；
**I 是本节剩下的全部内容** —— 因为它不是开关，而是**一个可以调的旋钮**。

### 隔离级别 = "允许被干扰到什么程度"

如果全世界的事务排队一个一个跑就不会有干扰 —— 但那样一台机器一秒只能跑几十个事务。
所以数据库让事务并发跑，再给你一个旋钮：**你愿意容忍多少干扰，换多少性能。**
三种"干扰"各配一条两事务时间轴，**看懂这三张图这一节就过了**：

```
① 脏读 dirty read —— 读到了别人还没提交的数据
   事务 A:  BEGIN ──[余额 1000 → 900]───────────────── ROLLBACK ✗ 它反悔了
   事务 B:                └──[读到 900]──[基于 900 做判断]──✗ 这个 900 从没真实存在过

② 不可重复读 non-repeatable read —— 同一行，读两次值不一样
   事务 A:  BEGIN ─[读余额 = 1000]────────────────[再读余额 = 900]── ?
   事务 B:                   [余额 −100]─COMMIT    同一事务、同一行、两个值
   后果：A 的前后逻辑基于两个不同的事实 —— "先检查余额够，再扣款"中间被人插了一脚

③ 幻读 phantom read —— 同一个范围查询，两次行数不一样
   事务 A:  BEGIN ─[COUNT(*) WHERE 部门=销售 → 5 人]────[再查 → 6 人]─ ?
   事务 B:                  [INSERT 一个新销售]─COMMIT   多出来一行"幻影"
   和 ② 的区别：② 是"已有的行值变了"，③ 是"凭空多出/少了行"——
   所以行锁挡不住它，得锁范围
```

| 隔离级别 | English | 脏读 | 不可重复读 | 幻读 | 谁在用 |
|---|---|---|---|---|---|
| 读未提交 | Read Uncommitted | ✗ 可能 | ✗ 可能 | ✗ 可能 | 最快，基本没人用 |
| **读已提交** | **Read Committed** | ✓ 不会 | ✗ 可能 | ✗ 可能 | PostgreSQL / Oracle / SQL Server **默认** |
| **可重复读** | **Repeatable Read** | ✓ 不会 | ✓ 不会 | ✗ 标准允许\* | MySQL InnoDB **默认** |
| 可串行化 | Serializable | ✓ 不会 | ✓ 不会 | ✓ 不会 | 最慢，有冲突时事务会被中止重试 |

\* 这张表列的是 SQL 标准允许的现象，具体实现可能更强：PostgreSQL 的 Repeatable Read 基于快照隔离，不会出现普通幻读；
MySQL InnoDB 的 RR 用 **MVCC** + **next-key lock**，也挡住了大部分幻读场景。看名字还不够，最终要查你所用数据库的文档。
（一手来源：[PostgreSQL Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html)、
[MySQL InnoDB Transaction Isolation Levels](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)。）
（**MVCC = multi-version concurrency control，多版本并发控制**：更新时不覆盖旧值，而是另存一个新版本，
每个事务按自己开始的时刻去挑该看哪个版本，所以读不用等写、写不用等读；完整讲法见 [`01/01`](../01-building-blocks/01-storage-engines.md)。
**next-key lock**：不只锁住命中的那几行，连它们之间的"空隙"一起锁住，别人就插不进新行 —— 这正是行锁挡不住幻读、而它能挡住的原因。）

**Serializable 的定义**：多个事务并发执行的结果，必须**等价于它们按某个顺序一个一个跑**的结果。
（回到 §6：这就是它和 linearizable 的区别 —— 它不要求那个顺序和真实时间一致。）

### 这一节唯一必须记住的事

> **你的数据库默认隔离级别几乎肯定不是 Serializable。** 这是大量线上 bug 的出生地：

```sql
BEGIN;                                              -- 你以为放进事务就安全了
SELECT balance FROM accounts WHERE id = 1;          -- 两个请求都读到 100
-- 应用层判断：100 >= 80，两个请求都认为够扣
UPDATE accounts SET balance = 20 WHERE id = 1;      -- 都把自己算出的绝对值写回
COMMIT;
```

在 Read Committed 下，两个并发请求可能同时通过检查。像上面这样写绝对值，两个请求都写成 20，用户花了 160 却只扣 80，
这是**丢失更新（lost update）**；如果检查后改用两次相对扣减 `balance = balance - 80`，最终会得到 −60，
这是**检查与更新之间的竞态导致超扣**。两种 bug 的根因相同：事务保证每次提交完整，却不自动把“读取 → 判断 → 写入”变成不可分割的一步。

| 正确写法 | 怎么做 | 适用 |
|---|---|---|
| **加锁读** | `SELECT ... FOR UPDATE`，读的时候就锁住这行 | 最直观，但锁持有时间长 |
| **原子更新** | `UPDATE ... SET balance = balance - 100 WHERE id = 1 AND balance >= 100`，再检查**影响行数是不是 1** | 最好，一条语句里完成判断和修改 |
| **版本号 / CAS** | `UPDATE ... WHERE id = 1 AND version = 7`，失败则重读重试 | 乐观并发（optimistic concurrency），冲突少时最快 |

还有一种更隐蔽、连 Snapshot Isolation 都挡不住的异常叫**写偏斜（write skew）**
（**Snapshot Isolation 快照隔离**：事务开始那一刻给整个库拍张"快照"，此后这个事务读到的全是快照里的样子，别人后来的提交它一概看不见 ——
上表的"可重复读"档在 PostgreSQL / MySQL 里就是靠它实现的，所以它比 Read Committed 强、但仍不是 Serializable），
在 [`00/01 §4`](01-fundamentals.md) —— 那里有一个医生排班的经典例子。

> 💡 **面试里为什么考它**：库存、余额、座位、优惠券 —— 一半的案例题都是并发扣减。
> 面试官会直接问"两个人同时下单怎么保证不超卖"。答"用事务"不及格；
> 答"默认隔离级别挡不住这个，我用 `UPDATE ... WHERE stock > 0` 并检查影响行数"才是及格线。

## 8. 同步 / 异步 / 阻塞 / 非阻塞

你的接口调了一个第三方服务，对方要 2 秒才返回。你的服务器有 200 个线程，流量 200 QPS ——
用 §2 算一下：`200 × 2 = 400` 个并发 > 200 个线程，线程全占满，新请求排队。
有人说"改成异步就好了"。你要知道这句话对在哪、错在哪。

**关键：这四个词不是四选一，是两个维度的组合。**

| 维度 | 问的是 | 两端 |
|---|---|---|
| **同步 / 异步** | **结果什么时候给你？** 这次调用直接返回，还是稍后另行通知 | sync / async |
| **阻塞 / 非阻塞** | **等的时候，那个线程能不能去干别的？** | blocking / non-blocking |

```
打电话（同步 + 阻塞）      拨号 → 等对方接 → 说完 → 挂断，你才能干别的；整个人被占住
发微信（异步）             发出去 → 立刻去干别的 → 他回了手机弹一下你再看；你没被占住
发完盯着屏幕等回复         ← 接口异步了，用法还是等。这就是很多人"改成异步"后没变快的原因
```

| 组合 | 代码长什么样 | 那 2 秒里线程在干嘛 |
|---|---|---|
| **同步阻塞** | `result = http.get(url)` | **睡着**，什么也不干；线程仍占调度和栈空间（Linux 常默认预留约 8 MB 虚拟地址空间，但不是立刻占满等量物理内存） |
| **异步非阻塞** | `result = await async_http.get(url)` / callback / epoll | 被**还给线程池或事件循环**，去处理另外几十个请求 |
| **消息队列式异步** | `queue.send(task)`，结果稍后靠回调 / 轮询 / WebSocket 拿 | 调用方**根本不等结果**，请求当场返回 |

回到开头：改成 `await` 之后，那 400 个在途请求不再需要 400 个线程，它们只是 400 个很小的状态对象，
几个线程轮流推进就行。**这就是异步真正解决的问题：让"并发数"和"线程数"解耦。**
但 `await` 只是语法，不是魔法：只有底层调用本身提供真正的异步 I/O，等待期间线程才会被释放；
对一个阻塞 API 外面套 `async` / `await`，它仍然可能占住线程。

### 三个必须澄清的点

**① 异步 ≠ 并行（parallel）。**
并行是**多个 CPU 核真的在同时执行**代码；异步是**一个任务在等 I/O 时，这条执行线索去推进别的任务**。
Node.js 的一个事件循环线程同一时刻只执行一个 JS 回调，所以业务 JS 默认不并行；但操作系统 I/O、libuv worker pool、
子进程和 Worker Threads 都可能在并行工作，不能把“事件循环单线程”说成“整个运行时完全不并行”。
（一手来源：[Node.js Event Loop and Worker Pool](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop)、
[Node.js Worker Threads](https://nodejs.org/api/worker_threads.html)。）
它快不是因为"同时做很多事"，而是"等网络的那 99% 时间没浪费"。
推论：**异步救不了 CPU 密集型任务** —— 瓶颈是计算而不是等待时，改 async 一点用没有，你需要多核 / 更好的算法。

**② 非阻塞 ≠ 更快。**
单个请求的延迟**不会**因为改成异步而变短。第三方还是要 2 秒，一秒少不了（异步甚至因调度开销略慢）。
变的是**同样的机器能同时扛住多少请求**。用 §2 的话说：**异步提高的是吞吐上限和并发容量，不是延迟。**

**③ 异步不是免费的。** 四样东西会变难：**错误处理**（跨 callback、future、队列或进程边界后，异常未必还能沿原调用链传播）、
**超时**（每个异步操作都要自带 deadline，忘一个就永远挂着）、
**调试**（一个请求的日志散落在多个线程和进程，必须靠 trace id 串）、
**背压**（同步模型线程用完就自动挡住了；异步模型可以无限接收，直到 OOM）。

最后一条特别重要：**带有限线程数和有限等待队列的同步阻塞模型，有个“意外的优点” —— 它天然形成并发上限**
（限流 rate limiting：给单位时间内能放进来的请求数设上限，超出的直接拒绝或挡在门外 —— 200 个线程意味着最多约 200 个正在占线程执行；
若等待队列无界，它仍然可能把内存耗尽）。
换成异步后这个保护消失了，你必须自己加**并发限制**。背压（backpressure）的完整内容在 [`00/01 §6`](01-fundamentals.md)。

> 💡 **面试里为什么考它**：问"这个下游要 2 秒，你怎么设计"，你要能分清两种答案：
> 改成异步 I/O（省线程，用户还是等 2 秒）和改成消息队列（用户不等了，但结果要另想办法送达）。
> 把这两个都叫"异步"而说不清区别，是最常见的表述失分。

## 9. 有状态 vs 无状态

凌晨 3 点你要给 20 台服务器发新版本，能不能一台一台重启、每台停 30 秒？
**这个问题的答案完全取决于这个服务是不是无状态的。**

> **无状态服务（stateless service）= 处理任意一个请求所需的业务状态，要么在请求里，要么在共享的外部存储里；
> 换一台同版本的机器，不依赖上一台机器独有的历史上下文，也能正确处理。**

注意定义里没说"没有变量"。关键是**跨请求的、且只存在于这一台机器上的数据**。

**判断方法（唯一需要记住的）：把请求随机换到另一台机器，它能否在不读取原机器内存或磁盘的情况下继续正确处理？
不能 → 有状态；能 → 无状态。** “杀掉会不会永久丢数据”只能判断持久状态，判断不了 WebSocket 连接、租约、进行中的工作流等临时但重要的状态。

```
✓ 无状态：校验 JWT 的 API 服务 —— 密钥在配置里，用户信息在数据库里，请求自带 token
          杀掉它 → 下一个请求换台机器，结果完全一样

⚠ 看起来无状态，其实有状态（最容易踩的一类）
    · session 存在本机内存 → 杀掉 = 那批用户被踢下线
    · 上传文件先落本地磁盘再处理 → 杀掉 = 文件没了
    · 进程内的定时任务 / 去重集合 / 计数器 → 杀掉 = 状态丢失
    · 进程内缓存本身没问题（丢了能重建），但"只有这台机器算过的结果"就有问题

✗ 天然有状态（这本来就是它们的工作）：数据库、Redis、Kafka broker；
    维持 WebSocket 长连接的推送服务 —— 连接本身就是状态：这个用户的连接就在这台机器上
```

| 你想做的事 | 无状态服务 | 有状态服务 |
|---|---|---|
| 加一台机器 | 启动就能接流量 | 先决定"它负责哪部分数据"，还要把数据搬过去 |
| 滚动重启 | 随便重启，LB 摘掉再放回 | 先把状态迁走或等它自己转移，否则丢数据 / 断连接 |
| 自动扩缩容 | 按 CPU 拉起来就行 | 缩容要先排空（drain），扩容要重新分配 |
| 请求路由 | 随便发给任何一台 | 必须发给**特定的那一台**（有状态路由 stateful routing） |
| 一台挂了 | 别的机器能直接接新请求；已有连接仍可能需要重连 | 要选新负责人、恢复或重建状态，这段时间那部分能力可能不可用 |

> **这一节最重要的一句话："无状态"不是没有状态，是把状态推给了别人。**

你的 API 服务之所以能随便重启，是因为 session 进了 Redis、文件进了对象存储、数据进了数据库。
**整个系统的状态总量一点没变**，只是从"散落在 40 台无差别机器上"变成了"集中在少数几个专门管状态的组件里"。
而那几个组件怎么复制、怎么分片、怎么在挂掉时选出新的负责人 —— **就是这本书剩下的全部内容。**

> 💡 **面试里为什么考它**：面试官画完架构图后常问"这个服务能水平扩展吗"，真正在问的是"它有状态吗"。
> 而聊天、协作编辑、打车这类题（[`06/11`](../06-case-studies/11-chat-messaging.md)、
> [`06/05`](../06-case-studies/05-realtime-collaboration.md)、[`06/13`](../06-case-studies/13-ride-hailing.md)）整题的难点就是**必须有状态**时怎么办。

## 10. 可用性：几个 9 是什么意思

销售签合同时承诺了"99.99% 可用性"。你需要知道：这句话给你留了**每年 52 分钟**的停机预算，
而一次不太顺利的数据库主从切换就能用掉其中一半。

> **可用性（availability）= 在一段时间里，系统能够正确服务请求的时间比例。**

更贴近用户的算法是按请求算：**成功请求数 ÷ 总请求数**（时间口径会掩盖"只有 5% 用户挂了但挂了一整天"）。
口径选择见 [`05/01`](../05-reliability/01-slo-and-error-budget.md)。

| 可用性 | 俗称 | 每月允许停机 | 每年允许停机 | 这个档位意味着 |
|---|---|---|---|---|
| **99%** | 两个 9 | 7 小时 12 分 | 3.65 天 | 内部工具、批处理 |
| **99.9%** | 三个 9 | 43 分 12 秒 | 8 小时 46 分 | 大多数 SaaS 的默认承诺 |
| **99.95%** | | 21 分 36 秒 | 4 小时 23 分 | 付费版常见档位 |
| **99.99%** | 四个 9 | 4 分 19 秒 | 52 分 36 秒 | **必须自动故障转移** —— 人工介入来不及 |
| **99.999%** | 五个 9 | 25.9 秒 | 5 分 15 秒 | 极少有系统真做到；通常是营销话术 |

（月按 30 天算。）**读表的正确方式**：别把"每年 52 分钟"想成"一年可以坏一次坏 52 分钟"，要想成"从故障发生到自动恢复的
全过程，一年总共只有 52 分钟预算，还要分给若干次故障"。所以 99.99% 不是"更努力"能达到的，它要求**架构上根本不依赖人的反应速度**。

### 依赖的可用性会相乘（最常被忽略的一条）

下面的乘法成立有两个前提：**每个依赖都是请求成功的必要条件，而且它们的故障近似独立**。它适合做第一版预算，
不是线上真实可用性的证明；如果几个服务共享同一 AZ、网络或发布系统，必须用实际故障重叠数据评估。

```
用户 ──▶ [ 网关 99.9% ] ──▶ [ 订单服务 99.9% ] ──▶ [ 数据库 99.9% ] ──▶ 成功
         任何一环挂掉用户就看到失败，所以：
         0.999 × 0.999 × 0.999 = 0.997003 ≈ 99.7%
         每年停机 = 8760 小时 × (1 − 0.997) ≈ 26.3 小时      （8760 = 365 天 × 24 小时）
              ↑ 三个"三个 9"串起来，只剩不到"两个半 9"
```

在这些假设下，**每加一个必要的串行依赖，整体可用性只会更低。** 一条链上挂 10 个彼此独立的 99.9% 依赖：
`0.999¹⁰ ≈ 99.0%`，一年停机约 **87 小时**。

两个用法：① **减少关键路径上的依赖数量** —— 这是提升可用性最便宜的手段，比给每个依赖加冗余便宜得多；
② **把非关键依赖移出关键路径** —— 推荐服务挂了就不显示推荐，而不是整页 500。这叫**优雅降级（graceful degradation）**，
它必须被**具体定义**（"关掉推荐模块，只返回时间线"），不能是"尽力而为"。

### 冗余会往另一个方向相乘

两个各 99% 的实例互为备份，在切换机制本身可靠且故障独立的理想条件下，两个都挂的概率 = `0.01 × 0.01 = 0.0001`
→ 可用性 **99.99%**。
**但这个计算有一个极强的前提：两次失败必须互相独立。**
现实里它们几乎从不独立 —— 同机架断电、同 AZ 光纤被挖断、一次错误的配置推送同时打死两台、
两台依赖同一个数据库或同一张证书、同样的代码遇到同样的输入同样地崩溃。
这类**相关失败（correlated failure）**让乘法失效，
所以"我加了台备机，可用性从 99% 变 99.99%"通常**不成立**。面试里更好的表述：
> "理论上是 99.99%，但两台在同一个 AZ、用同一份配置，相关失败会吃掉大部分收益。
> 要真拿到那个数，得跨 AZ 部署 + 配置分批推送。"

> 💡 **面试里为什么考它**：这是 [START-HERE 自测第 11 题](../START-HERE.md)。它是少数几个能**当场用算术验证**的知识点，
> 所以面试官很爱问 —— 答不出 `0.999³ = 99.7%` 会被判定为"没有量化习惯"。

## 11. 三个最常见的优化手段各在优化什么

**缓存、队列、索引。** 这三个词会出现在你的每一次系统设计里，它们优化的是三件完全不同的事。

### ① 缓存（cache）—— 省掉重复的劳动

**原理**：把查过一次或算过一次的结果，放在**更快或更近**的地方，下次直接拿。
```
优化前：商品详情页每次请求查 3 次数据库 → 3 × 6 ms = 18 ms，数据库承受 3000 QPS
优化后：结果缓存 60 秒，命中率 95%
        命中（95%）0.5 ms / 未命中（5%）18 ms → 平均 1.4 ms      ← 快 13 倍
        数据库只承受 3000 × 5% = 150 QPS                          ← 降到 1/20
```

| 代价 | 说明 |
|---|---|
| **数据会旧** | 60 秒内价格改了，用户看到的还是老价。接不接受是业务决定 |
| **多了一个会挂的组件** | 而且后果是**非线性的**：95% 命中的缓存挂掉 = 数据库瞬间承受 20 倍流量 |
| **失效逻辑是新的 bug 源** | 删除缓存、更新缓存、TTL、版本号等都有适用场景；没有脱离业务的一种“唯一正确答案”，但写错可能留下长期脏值（[`01/02`](../01-building-blocks/02-caching.md)） |
| **内存要钱** | 而且要一直花，不管有没有人访问 |

### ② 队列（message queue）—— 把同步变异步、把尖峰削平

**原理**：把"不必在用户等待期间完成"的工作移出关键路径，并让下游按**自己的速度**消费。
```
优化前：写订单 50 ms → 发确认邮件 300 ms → 更新推荐 200 ms → 写数仓 100 ms
        用户等 650 ms；而且邮件服务挂了，下单就失败
优化后：写订单 50 ms → 投递事件 3 ms → 用户等 53 ms              ← 快 12 倍
        邮件服务挂了：订单照样成功，事件堆在队列里，等它恢复再消费
削峰：   一秒内突发 10000 条 —— 没队列下游被打死；
        有队列则先收下这 10000 条，下游按 500 rps 稳定消费，约 20 秒消化完
        若上游持续 10000 rps、下游持续只有 500 rps，队列只会越积越多，不能凭空创造产能
```

| 代价 | 说明 |
|---|---|
| **用户看到"成功"时事情还没做完** | 业务状态会暂时不完整，最终才收敛；这与 §6 的副本最终一致有关但不是同一个问题。要想清楚：中间失败了谁来告诉用户？ |
| **消息可能重复或丢失** | at-most-once 可能丢；可靠消息常选 at-least-once，因此消费端必须幂等。端到端 exactly-once 通常很难，或只在有限边界内成立（[`00/01 §5`](01-fundamentals.md)） |
| **顺序通常不保证** | 某些系统能保证同一 partition / message group 内的顺序，但仍要满足特定生产、消费配置。“先删后建”变成“先建后删”是真实事故 |
| **多了一个要运维的系统** | 还要监控积压（lag）—— 队列里堆了 100 万条而无人告警是常见事故 |
| **调试变难** | 一次业务从"一个栈"变成"跨三个系统"，必须靠链路追踪串起来 |

### ③ 索引（index）—— 把"全部翻一遍"变成"直接定位"

**原理**：额外维护一个**按查询键组织好的**结构（有序树或哈希），把"扫全表逐行比对"变成"几次定位"。
```
优化前：1000 万行的 users 表，WHERE email = 'a@b.com'
        数据库真的要读 1000 万行逐行比对 → 数百 MB I/O，1–3 秒
优化后：在 email 上建 B-Tree 索引
        树高 3–4 层 → 几次页面查找 → 定位到那一行 → 热缓存时可能 < 1 ms
```

这些数字只用于建立量级直觉；缓存命中、存储介质、行宽、回表和并发负载都会改变真实结果，最终以 `EXPLAIN (ANALYZE)` 和监控为准。

| 代价 | 说明 |
|---|---|
| **写变慢** | 每次 INSERT / UPDATE / DELETE 都要维护**每一个**索引 —— 这就是**写放大（write amplification）** |
| **占空间** | 几个索引加起来经常超过表本身 |
| **选择性差时经常没用** | “性别”这类低基数列通常筛不掉多少行，优化器可能选择全表扫描；但数据高度倾斜、覆盖索引或位图索引等场景仍可能受益 |
| **多了会选错** | 索引一多，查询优化器有时选错那一个，某个查询突然慢 100 倍 |

三者做的是同一件事：**缓存**拿内存成本 + 数据新鲜度换读延迟，**队列**拿结果的即时性 + 复杂度换关键路径延迟，
**索引**拿写入速度 + 磁盘空间换读延迟。**系统设计里没有"优化"，只有"把成本挪到你更能承受的地方"。**

> 💡 **面试里为什么考它**：问"这里怎么优化"，Mid 答"加缓存"；senior 答"加缓存，命中率我估 90%，但这意味着缓存挂掉时
> 数据库要承受 10 倍流量，所以回源路径上要加并发上限"。**能说出代价的那半句话，才是分数。**

## 12. 本章术语速查

| 中文 | English | 一句话定义 | 常见混淆 |
|---|---|---|---|
| 延迟 | latency | 单个请求从发出到收到结果的时间 | ⚠ 不是 delay |
| 吞吐 | throughput | 单位时间完成的请求数 | 加机器提高的是它，不是延迟 |
| 并发 / 在途请求 | concurrency / in-flight requests | 此刻已开始未结束的请求数 | ⚠ 不等于并行 parallelism；⚠ 不说 on-the-way |
| Little's Law | Little's Law | 稳定系统里，平均并发 = 平均吞吐 × 平均延迟 | 单位要一致；瞬时峰值不能随意混算 |
| 分位数 | percentile | 排序后处在某个百分比位置的值 | ⚠ **不能取平均、不能相加**，要合并直方图桶 |
| p50 / p99 | p50 / p99 | 一半 / 99% 的请求比它快 | p50 是中位数，不是平均值 |
| 尾延迟 | tail latency | p95/p99 那一段的统称 | ⚠ 不是 tail delay |
| 关键路径 | critical path | 用户必须等它完成的那条链 | 移出关键路径 = 变成异步 |
| 垂直 / 水平扩展 | scale up / scale out | 换更强的单机 / 加更多台机器 | ⚠ 中文都叫"扩容"，英文必须分；水平扩展是本书全部复杂度的源头 |
| 副本 | replica / replication | 同一份数据的多个完整拷贝 | 解决可用性和读扩展，**不解决容量** |
| 分片 / 分片键 | shard / sharding / shard key | 把数据切成互不重叠的块分放；分片键决定一行落到哪块 | 解决容量和写扩展，**不提高可用性**；分片键选错 = 热点，改起来极贵 |
| 逻辑分区 / 分片 | partition / shard | 系统内部的逻辑切块 / 跨节点的数据与路由单位 | 两者经常重合但不等价；同机分区没有水平扩展 |
| 网络分区 / 脑裂 | network partition / split-brain | 机器都活着但互相通信不了；两边都以为自己是权威 | ⚠ 与数据 partition 不是一件事；⚠ 不叫 network split |
| 强一致 | strong consistency | 口语总称；本书未说明时专指 linearizability | 写成功后，后来开始的读不能返回更旧的值 |
| 最终一致 | eventual consistency | 停止写入后最终收敛，中间可能读到旧值，**无时间上界** | ⚠ 形容词说 eventually consistent；不是 bug，是取舍 |
| 线性一致 / 可串行化 | linearizability / serializability | 表现得像只有一份数据且尊重真实时间 / 并发事务的结果等价于某个串行顺序 | ⚠ **两者不等价**：前者管操作历史，后者管事务隔离 |
| ACID 的 C | Consistency（业务约束） | 事务结束后数据仍满足你定义的业务规则 | ⚠ **和 CAP 的 C 毫无关系** |
| CAP 的 C | Consistency（线性一致） | 系统对外像一份最新副本，已完成操作的顺序不违背真实时间 | ⚠ **和 ACID 的 C 毫无关系** |
| 事务 / 原子性 / 持久性 | transaction / atomicity / durability | 一组要么全做要么全不做的操作；返回成功后满足承诺的故障模型下不丢 | 用了事务 ≠ 并发安全；数据库通常靠日志等机制实现 |
| 隔离级别 | isolation level | 允许并发事务互相干扰到什么程度 | ⚠ **默认几乎肯定不是 Serializable** |
| 脏读 | dirty read | 读到别人未提交、之后可能回滚的数据 | 那个值可能从未真实存在过 |
| 不可重复读 / 幻读 | non-repeatable read / phantom read | 同一事务内同一行值变了 / 同一范围查询行数变了 | 前者是"值变了"，后者是"行凭空出现"，行锁挡不住后者 |
| 乐观并发 | optimistic concurrency | 不加锁，提交时用版本号检查有没有被人改过 | 冲突多时反而更慢 |
| 同步 / 异步 · 阻塞 / 非阻塞 | sync / async · blocking / non-blocking | 结果是直接给还是稍后另行通知 · 等待期间线程能不能干别的 | ⚠ **异步 ≠ 并行**；⚠ **非阻塞 ≠ 单个请求更快** |
| 无状态 / 有状态 | stateless / stateful | 换一台机器能否不依赖原机器上下文继续正确处理 | "无状态"不是没有状态，是**把状态推给了别人** |
| 可用性 | availability | 能正确服务请求的时间（或请求）比例 | 必要且故障独立的串行依赖可近似相乘 |
| 优雅降级 / 相关失败 | graceful degradation / correlated failure | 部分依赖挂掉时明确定义地少做一些事 / 多个副本因同一原因一起挂 | 降级必须写清降到什么；相关失败让"冗余提高可用性"的乘法失效 |
| 缓存命中率 | cache hit rate | 请求中直接从缓存拿到结果的比例 | 90% 命中 = 它挂掉时数据库承受 10 倍 |
| 幂等 | idempotency | 同一操作执行多次，效果和执行一次相同 | at-least-once 可能重复，所以消费端必须幂等 |
| 写放大 | write amplification | 一次逻辑写入引发多次实际写入 | 索引越多写放大越大 |

<details>
<summary><strong>参考答案（答完再展开；重点是判断自己的模型，不是逐字背）</strong></summary>

1. **请求链路**：客户端先更新界面，经 DNS 找到入口，再经过 CDN / 边缘和负载均衡进入 API；API 可能访问缓存、数据库和消息队列，
   后台消费者完成非关键工作。DNS / LB 故障会影响入口，API 单实例故障可由 LB 摘除，缓存故障可能把流量放大到数据库，数据库故障影响权威读写，
   队列或消费者故障会造成投递失败或积压。准确答案取决于具体系统，不要求每条链都有所有组件。

2. **三者关系**：延迟是一个请求花多久，吞吐是单位时间完成多少，并发是当前有多少请求在途。稳定系统长期平均满足
   `并发 = 吞吐 × 延迟`。加机器主要提高总产能；若原请求没有排队，它本身的计算和网络路径没有缩短，因此延迟不会自动下降。

3. **600 个**：`3000 requests/s × 0.2 s = 600 requests`。这是峰值时段近似成立、系统没有无限积压时的容量估算。

4. **平均值被少量慢请求拉高**，所以它比 p90 还大。三台机器的 p99 都是 100 ms，**无法推出整体 p99**：还需要各机器请求量和完整分布，
   正确做法是合并原始样本或直方图桶后重算，不能平均三个 p99。

5. **垂直扩展**是换更强的单机，简单但有硬上限和单点风险；**水平扩展**是增加机器。多机后请求路由、数据分片、副本、网络故障和协调问题
   都出现了，因此带出后续的大部分分布式系统内容。

6. **副本**保存同一份数据的多个拷贝，主要解决故障和读扩展；**分片**把不同数据放到不同节点，主要解决容量和写扩展。
   加副本不会让单台机器需要保存的数据变少，所以不能解决“单机装不下”。

7. `partition` 常指三件事：数据库表或日志的**逻辑分区**、跨节点部署和路由的**数据分片**、CAP 语境中节点之间失联的
   **网络分区**。逻辑分区不一定是分片；网络分区与前两者完全不同。

8. 本书把**强一致**具体约定为 linearizability：写成功后，后来开始的读不能返回写之前的旧值；**最终一致**允许暂时读旧值，
   只承诺停止写入后最终收敛。eventual consistency 本身**不承诺一个有限的收敛时间上界**。

9. **ACID C** 是事务前后数据仍满足业务不变量；**CAP C** 是分布式系统对外提供线性一致的操作历史。
   它们同名但不是同一个性质，可以分别满足或不满足。

10. **Linearizable**：系统对外像只有一份数据，所有操作可排成不违背真实时间的顺序。
    **Serializable**：并发事务的结果等价于某个串行顺序，但那个顺序不一定符合真实时间；前者约束操作历史，后者约束事务隔离。

11. **脏读**：B 读到 A 尚未提交、后来回滚的值；**不可重复读**：A 在同一事务两次读同一行，中间 B 提交更新，结果不同；
    **幻读**：A 两次执行同一范围查询，中间 B 插入或删除匹配行，结果集合改变。

12. 默认隔离级别可能允许两个事务同时读取并通过检查，事务边界不会自动让“读 → 判断 → 写”不可分割。
    可用 `SELECT ... FOR UPDATE`、带条件的原子 `UPDATE` 并检查影响行数，或版本号 / CAS 失败重试。

13. **异步**让任务在等待 I/O 时释放执行资源，**并行**让多个 CPU 核同一时刻执行工作。真正的异步 I/O 通常提高并发容量和吞吐上限，
    但下游仍需 2 秒时，单个请求通常仍要约 2 秒；CPU 密集任务要靠并行或减少计算。

14. **无状态判据**：换一台同版本机器，能否不依赖原机器独有的历史上下文继续正确处理。若三个服务都是必要串行依赖且故障近似独立，
    `0.999³ = 0.997003 ≈ 99.7%`；不满足独立性时不能只靠这个乘法。

15. **缓存**用内存和新鲜度换读延迟与数据库负载；**队列**用结果即时性和额外复杂度换短关键路径与削峰；
    **索引**用写放大和空间换查询速度。三者都在搬移成本，不是免费加速。

</details>
