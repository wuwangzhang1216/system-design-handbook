# 03 · 取舍框架：如何做可辩护的架构决策

> 架构不是"选最好的"，是"在这组约束下，选一个能活到下一次重写的"。

---

## 1. 需求澄清（requirements clarification）清单（面试前 5 分钟必问）

面试里最大的失分点不是设计错，是**开始得太早**。下面这张表，挑 6–8 个最相关的问下去。

### 功能边界
- 核心用例是哪 3 个？哪些明确**不做**（out of scope）？
- 谁是用户：终端消费者 / 企业员工 / 开发者 / 另一个服务？
- 读写比例（read/write ratio）？（10:1 和 1:10 是完全不同的两个系统）

### 规模
- 现在多少用户/QPS/数据量？**目标是多久后到多少**？
- 增长曲线：线性还是病毒式（viral growth）？
- 峰谷比（peak-to-average ratio）？有没有可预测的尖峰（traffic spike：黑五、开学、财报日）？

### 质量属性（quality attributes，挑最关键的 2–3 个）
| 属性 | 要问的具体问题 |
|---|---|
| 延迟 | p50/p99 目标？用户是否感知？超时后行为？ |
| 可用性 | 99.9%（月停 43min）还是 99.99%（4.3min）？停机的业务代价？ |
| 一致性 | 哪条链路不能有陈旧读（stale read）？哪条可以？ |
| 持久性（durability） | 丢一条数据的代价？RPO/RTO？ |
| 成本 | 有预算上限吗？$/请求的目标？ |
| 安全合规 | PII？数据驻留（data residency）？SOC2/HIPAA/GDPR？ |

### 约束
- 团队规模与技能（3 人团队不要上 Kubernetes + Service Mesh + 微服务）
- 现有技术栈与遗留系统
- 上线时间压力
- 自建 vs 采购（build vs buy）的政策

**面试话术模板**：
> "在开始画之前我想确认几件事：这个系统的核心是读多写少的检索场景，还是写密集的流水场景？我们的可用性目标是 3 个 9 还是 4 个 9 —— 这会决定我要不要做跨 region。数据里有没有 PII，需不需要考虑数据驻留？"

## 2. 决策的四象限法

对每个关键决策，填这张表：

```
┌─────────────────────────────┬─────────────────────────────┐
│  选项 A                      │  选项 B                      │
├─────────────────────────────┼─────────────────────────────┤
│  ✅ 优势（可量化）            │  ✅ 优势                      │
│  ❌ 代价（可量化）            │  ❌ 代价                      │
│  💣 什么时候会撞墙            │  💣 什么时候会撞墙            │
│  🔄 换出去的成本              │  🔄 换出去的成本              │
└─────────────────────────────┴─────────────────────────────┘
```

**第四行「换出去的成本」是 Senior 特有的思考。** 决策的可逆性（reversibility）比决策的正确性更重要。

### 可逆性分级（Bezos 的双向门 two-way door / 单向门 one-way door）

| 级别 | 例子 | 决策方式 |
|---|---|---|
| **双向门**（易改） | 用哪个日志库、CI 配置、缓存 TTL | 快速决定，别开会 |
| **半可逆** | 数据库选型（有数据了但可迁移）、内部 API 形状 | 讨论，写 ADR，留迁移路径（migration path） |
| **单向门**（极难改） | 数据模型、分片键（shard key）、对外 API 契约（API contract）、编程语言、多租户隔离级别（tenant isolation） | 慎重，做原型验证，考虑最坏情况 |

**面试金句**：
> "分片键是这里唯一的单向门决策 —— 一旦上线并且有 TB 级数据，改分片键就是一次跨季度的迁移项目。所以我愿意在这一点上多花时间，其余的我先选简单方案，跑出来再说。"

## 3. 常见取舍的量化表

### 一致性 vs 延迟
| 方案 | p99 延迟增量 | 一致性 |
|---|---|---|
| 本地读（只读主库缓存） | +0 | 可能陈旧 |
| 读从库 | +0 | 复制延迟（replication lag）内陈旧（毫秒~秒） |
| 读从库 + 会话粘性（session stickiness） | +0 | Read-your-writes |
| 读主库 | +1 RTT | 强 |
| Quorum 读（跨 AZ） | +2–5 ms | 线性一致（配 quorum 写） |
| 跨 region 共识 | +60–150 ms | 线性一致 |

### 规范化 vs 反规范化（normalization vs denormalization）
| | 规范化 | 反规范化 |
|---|---|---|
| 写 | 1 次 | N 次（扇出） |
| 读 | JOIN，多次 IO | 1 次 |
| 一致性 | 天然 | 需要维护，可能不一致 |
| 存储 | 小 | 大（冗余） |
| 改 schema | 一处 | 所有副本 |
| **适用** | 写多、关系复杂、报表 | 读多、固定查询模式、feed |

**判据**：读写比 > 10:1 且查询模式稳定 → 反规范化。否则先规范化，用缓存解决读。

### 推 vs 拉（Push vs Pull）
以 Feed 系统为例：

| | 写扩散（Push / fan-out on write） | 读扩散（Pull / fan-out on read） |
|---|---|---|
| 发帖 | 写 N 个收件箱（N=粉丝数） | 写 1 次 |
| 读 Feed | 读 1 次 | 读 M 次（M=关注数）+ 归并 |
| 大 V（celebrity user）发帖 | 灾难（1 亿粉丝 = 1 亿次写） | 无影响 |
| 延迟 | 读快 | 读慢 |
| **实践** | **混合（hybrid）**：普通用户 push，大 V pull，读时归并（merge on read） | |

这个"混合方案"是 Twitter/微博的真实做法，也是面试里的标准满分答案。

### 同步 vs 异步
```
同步：  客户端 → 服务 → 依赖 → 返回
        ✅ 简单、错误立即可见、易调试
        ❌ 延迟叠加、故障传播、耦合可用性

异步：  客户端 → 服务 → 队列 → 返回 ACK
                        └→ Worker 处理
        ✅ 削峰、解耦、可重试
        ❌ 最终一致、状态查询复杂、调试难、需要幂等和死信队列
```

**判据**：用户是否需要立即知道结果？
- 需要 → 同步（或"同步返回 job_id + 轮询/推送"）
- 不需要 → 异步

**反模式（anti-pattern）**：把异步做成"同步 + 轮询（polling）"，客户端每 100ms 轮询一次状态。这既有异步的复杂度，又有同步的延迟，还多了轮询压力。改用 SSE / WebSocket / webhook。

## 4. ADR：架构决策记录（Architecture Decision Record）

每个单向门决策都应该有一份 ADR。模板：

```markdown
# ADR-014: 用户数据以 tenant_id 作为分片键

- 状态：已接受
- 日期：2026-03-12
- 决策者：平台组

## 背景
预计 18 个月内到 5 万租户、最大租户 200 万用户。单库在 ~8 TB 时
会遇到备份窗口超过 6 小时的问题（已实测）。

## 决策
以 tenant_id 哈希分片，初始 64 个逻辑分片映射到 8 个物理库。

## 备选方案
1. user_id 分片 —— 否决：跨租户查询无法路由，且租户级操作
   （导出、删除、迁移）要扫全部分片。
2. 不分片，垂直扩容 —— 否决：最大实例 ~64 vCPU，按增长 14 个月见顶。
3. 单租户单库 —— 否决：5 万个数据库的运维和连接开销不可接受。

## 后果
✅ 租户级操作在单分片内完成；噪音邻居可通过迁移分片解决。
❌ 跨租户分析查询必须走数据仓库（接受，已有 CDC 到 Lakehouse）。
❌ 超大租户（>单分片容量）需要单独的"专属分片"逃生舱 —— 见 ADR-021。
⚠️ 逻辑分片数 64 是上限假设：若超过 64 个物理库，需要重新哈希。
   缓解：逻辑分片可以 1:N 映射到物理库，先做逻辑分片再做物理拆分。

## 复审触发条件
- 单个租户数据量超过 500 GB
- 物理库数量达到 32（一半容量）
```

**ADR 的价值不在于记录选了什么，在于记录 (a) 否决了什么和为什么，(b) 什么条件下要重新考虑。**

## 5. 演进式架构（evolutionary architecture）：为变化设计

### 不要一次设计到终局（big design up front）

```
❌ 错误：DAU 1000 的产品，一上来就设计成千万级架构
   结果：复杂度拖垮团队速度，产品死于迭代太慢，架构从未被用到

✅ 正确：设计一个能活到 10× 的架构，并明确标出 10× 时会在哪里撞墙
```

**面试话术**：
> "v0 我用单体 + Postgres + Redis，能撑到 5000 QPS。撞墙信号是主库写入 IOPS 超过 60% 或复制延迟持续 > 1s。到那时我做两件事：读写分离（read/write splitting）+ 把最重的写路径（事件流水）拆到独立的时序存储（time-series store）。真正需要分片是在 5 万 QPS，那大概是第 3 年的事，届时分片键我已经在 schema 里预留了。"

这一段包含了 Senior 的三个信号：**分阶段、有触发条件、为未来预留但不提前实现**。

### 演进的四个杠杆（lever，按顺序用）

1. **加缓存**（最便宜，1 天）
2. **读写分离 / 加只读副本**（1 周）
3. **拆分热点路径（hot path）到独立服务/存储**（1 个月）
4. **分片 / 分库分表（sharding）**（1 个季度，且是单向门）

**永远从上往下用。** 直接跳到 4 的团队通常是在用复杂度掩盖没做性能分析。

### 预留而不实现（Preparedness without Premature Work）

| 预留动作 | 成本 | 未来收益 |
|---|---|---|
| schema 里带 `tenant_id` 列 | 几乎为零 | 将来分片不用改数据模型 |
| 所有 ID 用全局唯一（globally unique，ULID/Snowflake）而非自增 | 几乎为零 | 合并/拆库不冲突 |
| 业务逻辑不直接写 SQL，走仓储层（repository layer） | 小 | 换存储时改一处 |
| 对外 API 从第一天就带版本 | 几乎为零 | 不用做痛苦的破坏性变更（breaking change） |
| 事件用 schema registry | 小 | 消费者可独立演进 |
| 从第一天打 trace | 小 | 出问题时能查 |

这些是"**便宜的可选项（cheap options）**"—— 现在花很少，未来省很多。Senior 的直觉就是识别这类东西。

## 6. 复杂度预算（complexity budget）

**核心思想**：团队的复杂度承载能力是有限的、可耗尽的资源。每引入一个组件，就消耗一部分。

粗略的经验值：

| 团队规模 | 可维护的服务数 | 可维护的数据存储种类 |
|---|---|---|
| 1–3 人 | 1（单体） | 1–2（PG + 对象存储） |
| 4–10 人 | 2–4 | 2–3（+Redis） |
| 10–30 人 | 5–15 | 3–5（+Kafka / 搜索） |
| 30+ 人 | 按团队边界切 | 各团队自主 |

**每个新组件的真实成本**（不只是"跑起来"）：
- 学习曲线
- 监控与告警
- 备份与恢复演练（restore drill）
- 版本升级
- 安全补丁
- 容量规划（capacity planning）
- **凌晨 3 点有人能修它吗？**

**面试金句**：
> "技术上 Kafka 更合适，但这个团队只有 6 个人且没人运维过 Kafka。我会先用托管的（managed）SQS/Pub-Sub，等消息量或语义需求（顺序、回放 replay）真的逼到了，再迁 Kafka —— 迁移成本我评估是 2 周，而现在提前上的成本是持续的运维税（operational tax）。"

## 7. "什么时候不要这么做" —— 反模式清单

| 流行做法 | 什么时候是错的 |
|---|---|
| 微服务（microservices） | 团队 < 20 人；领域边界（domain boundary）还没稳定；没有成熟的 CI/CD 和可观测性（observability） |
| 事件溯源（event sourcing） | 不需要审计/时间旅行（time travel）；团队不熟；查询模式复杂多变 |
| CQRS | 读写模型其实一样；一致性要求高；只是为了"看起来专业" |
| Kubernetes | 服务 < 5 个；没有专职平台人；托管 PaaS 够用 |
| 多云（multi-cloud） | 没有具体的合规/议价理由；会让你降级到所有云的最小公共子集（lowest common denominator） |
| GraphQL | 只有一个前端；查询模式固定；团队没准备好处理 N+1 和查询复杂度攻击（query complexity attack） |
| Service Mesh | 服务 < 20 个；没有多语言；不需要 mTLS 强制 |
| 自建向量数据库 | 数据 < 1000 万向量；Postgres + pgvector 或托管服务够用 |
| **多 Agent 系统** | 任务能被单 Agent 顺序完成；子任务间有强依赖；见 `04/05` |
| **微调模型（fine-tuning）** | 提示工程（prompt engineering）+ 检索还没做到位；数据 < 1000 条高质量样本 |

## 8. 把取舍讲清楚的四句话结构

面试中每做一个决策，用这个结构说：

```
1. 【选择】  "我选 X。"
2. 【理由】  "因为在这个场景下 [具体约束]，X 在 [具体维度] 上比 Y 好 [量化差距]。"
3. 【代价】  "代价是 [具体的坏处]，我接受它是因为 [业务上无所谓 / 有缓解手段]。"
4. 【边界】  "如果 [某个条件变化]，我会重新考虑，改用 Y。"
```

**示例：**
> 1. 我选用 Postgres 而不是 Cassandra 做主存储。
> 2. 因为我们的写入是 5k TPS 且需要事务性的多表更新，Postgres 一个实例就能扛，而 Cassandra 没有跨分区事务，我要在应用层自己做 Saga —— 那是几周的工作和长期的正确性风险。
> 3. 代价是单点写入上限大约 2 万 TPS，且垂直扩容有天花板。我接受，因为按目前增长这是 3 年后的问题。
> 4. 如果写入超过 1.5 万 TPS 或者单表超过 5 TB，我会先做按 tenant_id 的分片（schema 已预留），而不是换数据库。

## 面试官会追问

1. 如果预算砍一半，你会去掉什么？
2. 如果团队只有 3 个人，这个设计怎么改？
3. 这个设计里最可能出错的地方是哪？
4. 哪个决策是不可逆的（irreversible）？你怎么降低它的风险？
5. 一年后流量涨 10×，第一个撑不住的是什么？
6. 你说"用 X"，什么情况下 X 是错的选择？
