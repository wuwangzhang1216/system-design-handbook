# 03 · 取舍框架：如何做可辩护的架构决策

> 架构不是"选最好的"，是"在这组约束下，选一个能活到下一次重写的"。

---

## 读这一章之前

**你在工作中遇到过这个**

两年前你为了"以后好扩展"选了 `user_id` 做分片键，评审会上讨论了 5 分钟就过了。
今天最大的那个企业客户提了一个再普通不过的要求："把我们公司的数据整体导出，然后全部删掉" —— 这个操作要扫全部 64 个分片、跑 11 个小时，中途失败还不能续跑。
你算了一下改成 `tenant_id` 分片要多久：全量迁移，横跨两个季度。
当初那 5 分钟里没有人问出口的问题只有一句：**"如果这个选错了，改回来要多久？"**

**需要先懂的概念**

| 概念 | 一句话 | 详见 |
|---|---|---|
| 分片 / 分片键 | 把数据切成互不重叠的块分放，分片键决定一行落到哪一块 | [00-concepts §5](00-concepts.md) |
| 强一致 / 最终一致 | 写完之后别人立刻读到的一定是新值，还是可能是旧值 | [00-concepts §6](00-concepts.md) |
| 同步 / 异步 | 用户要不要原地等着结果 | [00-concepts §8](00-concepts.md) |
| 可用性的几个 9 | 99.9% = 每月停 43 分钟；99.99% = 4.3 分钟 | [00-concepts §10](00-concepts.md) |
| 一致性的价钱 | 每往强的方向爬一级，通常多付一个跨节点往返 | [01-fundamentals §4](01-fundamentals.md) |
| 容量与成本估算 | 撞墙点在哪、$/请求是多少 —— 取舍有数字才吵得清 | [02-capacity-estimation](02-capacity-estimation.md) |

**这一章要回答的问题**

1. 为什么"一上来就开始画图"是设计题里最大的失分点？开工之前到底该问哪几个问题？
2. 两个方案各有各的道理时，怎么把"我觉得"变成一张能被对方当场反驳的对照表？
3. 哪些决策错了随手能改，哪些错了要还一整个季度？怎么在动手**之前**就认出后者？
4. 一个 6 人的团队，凭什么理由拒绝"技术上更合适"的方案，而不显得是在偷懒？

**本章新引入的术语**

| 术语 | English | 一句话定义 |
|---|---|---|
| 可逆性 | reversibility | 一个决定后来发现错了，改回来要付多大代价 |
| 单向门 / 双向门 | one-way door / two-way door | 单向门是走过去就几乎回不来的决定；双向门是随时能推回去的决定 |
| ADR | architecture decision record | 一页纸的决策记录：当时的背景、选了什么、否决了什么、什么条件下要重新考虑 |
| 质量属性 | quality attributes | 系统"做得好不好"的那几个维度：延迟、可用性、一致性、持久性、成本、合规 |
| RPO / RTO | recovery point objective / recovery time objective | 故障后最多能接受丢掉多长时间的数据 / 最多能接受服务中断多久 |
| 读写比 | read/write ratio | 读请求数与写请求数之比；10:1 和 1:10 会导出两个完全不同的系统 |
| 规范化 / 反规范化 | normalization / denormalization | 同一份事实只存一处、读的时候再拼起来 / 提前把要一起读的数据冗余地存在一起 |
| 写扩散 / 读扩散 | fan-out on write / fan-out on read | 发布时就写进每个粉丝的收件箱 / 发布时只写一份，读的时候再去拉所有关注对象并归并 |
| 演进式架构 | evolutionary architecture | 只设计到当前规模的 10 倍，同时写明下一堵墙在哪、撞墙前会出现什么信号 |
| 复杂度预算 | complexity budget | 一个团队能同时养活的组件数量是有限的，每引入一个就花掉一部分 |
| 便宜的可选项 | cheap options | 现在几乎不花钱、却保住了未来某个选择权的做法（例如 schema 里先留一列 `tenant_id`） |
| 运维税 | operational tax | 一个组件上线之后要一直付的成本：监控、告警、升级、打补丁、恢复演练、半夜有人能修 |

## 1. 需求澄清（requirements clarification）清单（面试前 5 分钟必问）

面试里最大的失分点不是设计错，是**开始得太早**。下面这张表，挑 6–8 个最相关的问下去。

### 功能边界
- 核心用例是哪 3 个？哪些明确**不做**（out of scope）？
- 谁是用户：终端消费者 / 企业员工 / 开发者 / 另一个服务？
- 读写比例（read/write ratio）？（10:1 和 1:10 是完全不同的两个系统）

### 规模
- 现在多少用户/QPS/数据量？**目标是多久后到多少**？
- 增长曲线：线性还是病毒式（viral growth）？
- 峰谷比（peak-to-average ratio，见 [`02 §1`](02-capacity-estimation.md)）？有没有可预测的尖峰（traffic spike：黑五、开学、财报日）？

### 质量属性（quality attributes，挑最关键的 2–3 个）
| 属性 | 要问的具体问题 |
|---|---|
| 延迟 | p50/p99 目标？用户是否感知？超时后行为？ |
| 可用性 | 99.9%（月停 43min）还是 99.99%（4.3min）？停机的业务代价？ |
| 一致性 | 哪条链路不能有陈旧读（stale read：读到的是还没同步过来的旧值，见 [00-concepts §6](00-concepts.md)）？哪条可以？ |
| 持久性（durability） | 丢一条数据的代价？RPO/RTO？ |
| 成本 | 有预算上限吗？$/请求的目标？ |
| 安全合规 | PII？数据驻留（data residency）？SOC2/HIPAA/GDPR？ |

（**PII** = personally identifiable information，能定位到具体自然人的信息：姓名、手机号、身份证号、精确位置。**数据驻留**指某国/某区域用户的数据必须存放在该地境内，它直接决定你能不能做单一全球主库。**SOC2 / HIPAA / GDPR** 分别是通用安全审计标准、美国医疗数据法规、欧盟个人数据法规 —— 三者对架构的共同后果是：给数据的存放位置、保留期限和访问审计加上硬约束。详见 [`03-saas-platform/04`](../03-saas-platform/04-isolation-and-compliance.md)。）

### 约束
- 团队规模与技能（3 人团队不要上 Kubernetes + Service Mesh + 微服务）
- 现有技术栈与遗留系统
- 上线时间压力
- 自建 vs 采购（build vs buy）的政策

**面试话术模板**：
> "在开始画之前我想确认几件事：这个系统的核心是读多写少的检索场景，还是写密集的流水场景？我们的可用性目标是 3 个 9 还是 4 个 9 —— 这会决定我要不要做跨 region。数据里有没有 PII，需不需要考虑数据驻留？"

## 2. 决策的四象限法

对每个关键决策，填这张表：

```
┌─────────────────────────────┬─────────────────────────────┐
│  选项 A                      │  选项 B                      │
├─────────────────────────────┼─────────────────────────────┤
│  ✅ 优势（可量化）            │  ✅ 优势                      │
│  ❌ 代价（可量化）            │  ❌ 代价                      │
│  💣 什么时候会撞墙            │  💣 什么时候会撞墙            │
│  🔄 换出去的成本              │  🔄 换出去的成本              │
└─────────────────────────────┴─────────────────────────────┘
```

**第四行「换出去的成本」是 Senior 特有的思考。** 决策的可逆性（reversibility）比决策的正确性更重要。

### 可逆性分级（Bezos 的双向门 two-way door / 单向门 one-way door）

| 级别 | 例子 | 决策方式 |
|---|---|---|
| **双向门**（易改） | 用哪个日志库、CI 配置、缓存 TTL | 快速决定，别开会 |
| **半可逆** | 数据库选型（有数据了但可迁移）、内部 API 形状 | 讨论，写 ADR，留迁移路径（migration path） |
| **单向门**（极难改） | 数据模型、分片键（shard key）、对外 API 契约（API contract：你对外承诺的字段、语义和错误码 —— 一旦有你控制不了的调用方，就改不动了）、编程语言、多租户隔离级别（tenant isolation：不同客户的数据是共表、共库还是各自独立，见 [`02-architecture-patterns/03`](../02-architecture-patterns/03-multi-tenancy.md)） | 慎重，做原型验证，考虑最坏情况 |

**面试金句**：
> "分片键是这里唯一的单向门决策 —— 一旦上线并且有 TB 级数据，改分片键就是一次跨季度的迁移项目。所以我愿意在这一点上多花时间，其余的我先选简单方案，跑出来再说。"

## 3. 常见取舍的量化表

### 一致性 vs 延迟
| 方案 | p99 延迟增量 | 一致性 |
|---|---|---|
| 本地读（只读主库缓存） | +0 | 可能陈旧 |
| 读从库 | +0 | 复制延迟（replication lag）内陈旧（毫秒~秒） |
| 读从库 + 会话粘性（session stickiness） | +0 | Read-your-writes |
| 读主库 | +1 RTT | 强 |
| Quorum 读（跨 AZ） | +2–5 ms | 线性一致（配 quorum 写） |
| 跨 region 共识 | +60–150 ms | 线性一致 |

表里三个词的意思：**复制延迟（replication lag）**是主副本写完到从副本追上之间的那段时间差 —— 在这段时间里从库上读到的就是旧值。
**会话粘性（session stickiness）**是把同一个用户的请求固定发到同一台机器/同一个库，从而至少保证他读得到自己刚写的东西（read-your-writes）。
**Quorum**（多数派）是指 N 个副本里至少 N/2+1 个确认才算数：写多数派 + 读多数派，两个集合必然有交集，所以读一定能碰到最新的那份（见 [`01-building-blocks/05`](../01-building-blocks/05-consensus-and-coordination.md)）。

### 规范化 vs 反规范化（normalization vs denormalization）
| | 规范化 | 反规范化 |
|---|---|---|
| 写 | 1 次 | N 次（扇出） |
| 读 | JOIN，多次 IO | 1 次 |
| 一致性 | 天然 | 需要维护，可能不一致 |
| 存储 | 小 | 大（冗余） |
| 改 schema | 一处 | 所有副本 |
| **适用** | 写多、关系复杂、报表 | 读多、固定查询模式、feed |

**判据**：读写比 > 10:1 且查询模式稳定 → 反规范化。否则先规范化，用缓存解决读。

### 推 vs 拉（Push vs Pull）
以 Feed 系统为例：

| | 写扩散（Push / fan-out on write） | 读扩散（Pull / fan-out on read） |
|---|---|---|
| 发帖 | 写 N 个收件箱（N=粉丝数） | 写 1 次 |
| 读 Feed | 读 1 次 | 读 M 次（M=关注数）+ 归并 |
| 大 V（celebrity user）发帖 | 灾难（1 亿粉丝 = 1 亿次写） | 无影响 |
| 延迟 | 读快 | 读慢 |
| **实践** | **混合（hybrid）**：普通用户 push，大 V pull，读时归并（merge on read） | |

这个"混合方案"是 Twitter/微博的真实做法，也是面试里的标准满分答案。

大 V 是**热点（hot key）**最典型的形态 —— 绝大部分负载压在极少数的键上，所以任何"均匀打散"的策略对它都无效，必须给它单独一条路径。这个模式会在本书里反复出现（热门商品、热门文档、热门分区）。

### 同步 vs 异步
```
同步：  客户端 → 服务 → 依赖 → 返回
        ✅ 简单、错误立即可见、易调试
        ❌ 延迟叠加、故障传播、耦合可用性

异步：  客户端 → 服务 → 队列 → 返回 ACK
                        └→ Worker 处理
        ✅ 削峰、解耦、可重试
        ❌ 最终一致、状态查询复杂、调试难、需要幂等和死信队列
```

（**幂等**：同一个操作执行多次和执行一次效果相同，见 [`01 §5`](01-fundamentals.md)。**死信队列 dead letter queue**：反复消费失败的消息不再无限重试，而是被挪进一个单独的队列，等人工或补偿流程处理 —— 没有它，一条毒消息会把整个消费者卡死，见 [`01-building-blocks/03`](../01-building-blocks/03-messaging-and-streams.md)。）

**判据**：用户是否需要立即知道结果？
- 需要 → 同步（或"同步返回 job_id + 轮询/推送"）
- 不需要 → 异步

**反模式（anti-pattern）**：把异步做成"同步 + 轮询（polling）"，客户端每 100ms 轮询一次状态。这既有异步的复杂度，又有同步的延迟，还多了轮询压力。改用 SSE / WebSocket / webhook（**SSE** = server-sent events，服务端通过一条长连接单向持续推送；**webhook** 则是反过来，由服务端在事情做完时主动回调你留下的一个 URL，见 [`01-building-blocks/04`](../01-building-blocks/04-networking-and-edge.md)）。

## 4. ADR：架构决策记录（Architecture Decision Record）

每个单向门决策都应该有一份 ADR。模板：

```markdown
# ADR-014: 用户数据以 tenant_id 作为分片键

- 状态：已接受
- 日期：2026-03-12
- 决策者：平台组

## 背景
预计 18 个月内到 5 万租户、最大租户 200 万用户。单库在 ~8 TB 时
会遇到备份窗口超过 6 小时的问题（已实测）。

## 决策
以 tenant_id 哈希分片，初始 64 个逻辑分片映射到 8 个物理库。

## 备选方案
1. user_id 分片 —— 否决：跨租户查询无法路由，且租户级操作
   （导出、删除、迁移）要扫全部分片。
2. 不分片，垂直扩容 —— 否决：最大实例 ~64 vCPU，按增长 14 个月见顶。
3. 单租户单库 —— 否决：5 万个数据库的运维和连接开销不可接受。

## 后果
✅ 租户级操作在单分片内完成；噪音邻居可通过迁移分片解决。
❌ 跨租户分析查询必须走数据仓库（接受，已有 CDC 到 Lakehouse）。
❌ 超大租户（>单分片容量）需要单独的"专属分片"逃生舱 —— 见 ADR-021。
⚠️ 逻辑分片数 64 是上限假设：若超过 64 个物理库，需要重新哈希。
   缓解：逻辑分片可以 1:N 映射到物理库，先做逻辑分片再做物理拆分。

## 复审触发条件
- 单个租户数据量超过 500 GB
- 物理库数量达到 32（一半容量）
```

（例子里的 **CDC** = change data capture，变更数据捕获：订阅数据库自己的变更日志（WAL / binlog），把每一行的增删改实时变成一条事件流，
所以分析库能跟着 OLTP 库走而不用反复全量扫表 —— 完整讲法见 [`01-building-blocks/03 §4`](../01-building-blocks/03-messaging-and-streams.md)。）

**ADR 的价值不在于记录选了什么，在于记录 (a) 否决了什么和为什么，(b) 什么条件下要重新考虑。**

## 5. 演进式架构（evolutionary architecture）：为变化设计

### 不要一次设计到终局（big design up front）

```
❌ 错误：DAU 1000 的产品，一上来就设计成千万级架构
   结果：复杂度拖垮团队速度，产品死于迭代太慢，架构从未被用到

✅ 正确：设计一个能活到 10× 的架构，并明确标出 10× 时会在哪里撞墙
```

**面试话术**：
> "v0 我用单体 + Postgres + Redis，能撑到 5000 QPS。撞墙信号是主库写入 IOPS 超过 60% 或复制延迟持续 > 1s。到那时我做两件事：读写分离（read/write splitting：写只走主库，读分给只读副本）+ 把最重的写路径（事件流水）拆到独立的时序存储（time-series store：按时间顺序追加、按时间范围查询、老数据自动降采样或过期的那类存储）。真正需要分片是在 5 万 QPS，那大概是第 3 年的事，届时分片键我已经在 schema 里预留了。"

这一段包含了 Senior 的三个信号：**分阶段、有触发条件、为未来预留但不提前实现**。

### 演进的四个杠杆（lever，按顺序用）

1. **加缓存**（最便宜，1 天）
2. **读写分离 / 加只读副本**（1 周）
3. **拆分热点路径（hot path：占掉绝大部分流量或资源的那一小段链路 —— 注意它和上面的"热点 hot key"不是一回事，前者是一段代码路径，后者是一个数据键）到独立服务/存储**（1 个月）
4. **分片 / 分库分表（sharding）**（1 个季度，且是单向门）

**永远从上往下用。** 直接跳到 4 的团队通常是在用复杂度掩盖没做性能分析。

### 预留而不实现（Preparedness without Premature Work）

| 预留动作 | 成本 | 未来收益 |
|---|---|---|
| schema 里带 `tenant_id` 列 | 几乎为零 | 将来分片不用改数据模型 |
| 所有 ID 用全局唯一（globally unique，ULID/Snowflake）而非自增 | 几乎为零 | 合并/拆库不冲突 |
| 业务逻辑不直接写 SQL，走仓储层（repository layer） | 小 | 换存储时改一处 |
| 对外 API 从第一天就带版本 | 几乎为零 | 不用做痛苦的破坏性变更（breaking change） |
| 事件用 schema registry（把事件的字段定义集中登记，改字段时自动检查新旧是否兼容） | 小 | 消费者可独立演进 |
| 从第一天打 trace（一次请求穿过所有服务的完整记录，靠同一个 id 串起来） | 小 | 出问题时能查 |

这些是"**便宜的可选项（cheap options）**"—— 现在花很少，未来省很多。Senior 的直觉就是识别这类东西。

## 6. 复杂度预算（complexity budget）

**核心思想**：团队的复杂度承载能力是有限的、可耗尽的资源。每引入一个组件，就消耗一部分。

粗略的经验值：

| 团队规模 | 可维护的服务数 | 可维护的数据存储种类 |
|---|---|---|
| 1–3 人 | 1（单体） | 1–2（PG + 对象存储） |
| 4–10 人 | 2–4 | 2–3（+Redis） |
| 10–30 人 | 5–15 | 3–5（+Kafka / 搜索） |
| 30+ 人 | 按团队边界切 | 各团队自主 |

**每个新组件的真实成本**（不只是"跑起来"）：
- 学习曲线
- 监控与告警
- 备份与恢复演练（restore drill）
- 版本升级
- 安全补丁
- 容量规划（capacity planning）
- **凌晨 3 点有人能修它吗？**

**面试金句**：
> "技术上 Kafka 更合适，但这个团队只有 6 个人且没人运维过 Kafka。我会先用托管的（managed）SQS/Pub-Sub，等消息量或语义需求（顺序、回放 replay）真的逼到了，再迁 Kafka —— 迁移成本我评估是 2 周，而现在提前上的成本是持续的运维税（operational tax）。"

## 7. "什么时候不要这么做" —— 反模式清单

| 流行做法 | 什么时候是错的 |
|---|---|
| 微服务（microservices） | 团队 < 20 人；领域边界（domain boundary）还没稳定；没有成熟的 CI/CD 和可观测性（observability：能不能只靠系统吐出来的日志、指标、trace，回答一个你事先没预料到的问题） |
| 事件溯源（event sourcing） | 不需要审计/时间旅行（time travel）；团队不熟；查询模式复杂多变 |
| CQRS | 读写模型其实一样；一致性要求高；只是为了"看起来专业" |
| Kubernetes | 服务 < 5 个；没有专职平台人；托管 PaaS 够用 |
| 多云（multi-cloud） | 没有具体的合规/议价理由；会让你降级到所有云的最小公共子集（lowest common denominator） |
| GraphQL | 只有一个前端；查询模式固定；团队没准备好处理 N+1（查一个列表 1 次，再为列表里每一项各查一次，总共 N+1 次）和查询复杂度攻击（query complexity attack：构造一个嵌套极深的查询，让服务端自己把自己算死） |
| Service Mesh | 服务 < 20 个；没有多语言；不需要 mTLS（双向 TLS：不只客户端验服务端的证书，服务端也验客户端的）强制 |
| 自建向量数据库 | 数据 < 1000 万向量；Postgres + pgvector 或托管服务够用 |
| **多 Agent 系统** | 任务能被单 Agent 顺序完成；子任务间有强依赖；见 `04/05` |
| **微调模型（fine-tuning）** | 提示工程（prompt engineering）+ 检索还没做到位；数据 < 1000 条高质量样本 |

## 8. 把取舍讲清楚的四句话结构

面试中每做一个决策，用这个结构说：

```
1. 【选择】  "我选 X。"
2. 【理由】  "因为在这个场景下 [具体约束]，X 在 [具体维度] 上比 Y 好 [量化差距]。"
3. 【代价】  "代价是 [具体的坏处]，我接受它是因为 [业务上无所谓 / 有缓解手段]。"
4. 【边界】  "如果 [某个条件变化]，我会重新考虑，改用 Y。"
```

**示例：**
> 1. 我选用 Postgres 而不是 Cassandra 做主存储。
> 2. 因为我们的写入是 5k TPS 且需要事务性的多表更新，Postgres 一个实例就能扛，而 Cassandra 没有跨分区事务，我要在应用层自己做 Saga（把一个跨多个服务/分区的长流程拆成 N 个各自独立提交的本地事务，每步配一个"反向操作"，中途失败就按相反顺序把已做的撤销掉；它没有隔离性，中间状态对外可见 —— 见 [`02-architecture-patterns/02 §2`](../02-architecture-patterns/02-event-driven-and-cqrs.md)）—— 那是几周的工作和长期的正确性风险。
> 3. 代价是单点写入上限大约 2 万 TPS，且垂直扩容有天花板。我接受，因为按目前增长这是 3 年后的问题。
> 4. 如果写入超过 1.5 万 TPS 或者单表超过 5 TB，我会先做按 tenant_id 的分片（schema 已预留），而不是换数据库。

---

## 这一章的三句话

1. **决策的可逆性比决策的正确性更值得你花时间。** 双向门的事就该在 5 分钟内拍板，把省下来的全部争论押到那两三个单向门上（数据模型、分片键、对外 API 契约）—— 在双向门上开一小时会，是这个行业最常见的时间浪费。
2. **一个架构决策的质量，不看它选了什么，看它有没有写下"什么条件下我会改主意"。** 没有复审触发条件的决策，一年之后就变成了没人敢碰、也没人说得清为什么的历史遗留。
3. **"技术上更合适"不是理由，"这个团队凌晨 3 点修得了它"才是。** 复杂度是一笔有上限的预算，超支的部分不会消失，它会以事故、以离职、以"这块只有某某懂"的形式还回来。
