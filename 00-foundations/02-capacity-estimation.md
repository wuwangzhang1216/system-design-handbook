## 读这一章之前

**你在工作中遇到过这个**

你按 DAU 100 万、人均 10 次算出"平均 116 QPS"，申请了 4 台 16 核机器就上线了。晚上 8 点流量是全天均值的 4 倍，CPU 涨到 85% —— 还没满 —— 但 p99 从 80 ms 变成 1.6 秒，客服群炸了。
你加了 4 台机器压下去，第二天老板问"那到底该几台、一个月多少钱"，你答不上来。
或者另一种版本：你给新上的 AI 功能报的月成本是 2 万美金，第一个月账单来了 19 万 —— 差的那一项是 Agent 每一轮都把整段历史重新发一遍，而你是按"一次对话算一次调用"估的 token。

| 概念 | 一句话 | 详见 |

**这一章要回答的问题**

1. 给你一句"做个 500 万 MAU 的协作文档"，怎么在 3 分钟内算出要多少台机器、多少存储、一个月多少钱？
2. CPU 才 80%，为什么延迟已经是原来的 5 倍？目标利用率到底该定在哪个数？
3. 加机器为什么会让吞吐先升后降？这个拐点由什么决定？
4. AI 产品的成本结构和传统 SaaS 差在哪？为什么"先做出来、以后再优化成本"这条经验在这里是错的？

**本章新引入的术语**

| 术语 | English | 一句话定义 |
|---|---|---|
| 峰谷比 | peak-to-average ratio | 一天里请求最密集的那一分钟的速率，除以全天平均速率 |
| 利用率 | utilization | 一段时间里资源真正在干活的比例；CPU 利用率 70% = 100 秒里有 70 秒在执行指令 |
| 目标利用率 / 头部空间 | target utilization / headroom | 算机器数时故意按不满的利用率算（如 65%），剩下那段余量就是头部空间，用来吸收突发和慢请求 |
| 排队延迟 | queueing delay | 请求到达之后、真正开始被处理之前，在队列里干等的那段时间 |
| M/M/1 | M/M/1 | 最简单的排队模型：请求随机到达、只有一个处理者、每个的处理时间也随机；用它只凭利用率就能算出排队时间 |
| 通用可扩展性定律 | USL, Universal Scalability Law | 一条"吞吐随机器数怎么变"的公式，里面有两项惩罚：串行竞争 α，和机器之间互相协调的开销 β |
| 读放大 | read amplification | 一次逻辑上的读，底层实际读了好几次（多层文件、多个索引、多个副本） |
| 前缀缓存 | prefix caching | 大模型把多次请求开头完全相同的那一段的计算结果复用，这部分按低得多的价格计费 |
| 单位经济 | unit economics | 把成本和收入都摊到"一个用户"或"一次请求"上看，判断规模做大之后是赚还是亏 |
| 边际成本 | marginal cost | 多服务一个用户、多处理一次请求，额外增加的那一点成本 |
| 出网流量费 | egress cost | 云厂商对"数据离开它的网络"单独收的钱，按 GB 计价；数据进来通常免费 |
| Cell 架构 | cell-based architecture | 把系统切成若干套互相独立的完整单元，每个单元自带全套组件，故障和流量都不跨单元扩散 |

## 1. 估算的黄金流程

```
业务量  →  QPS  →  单请求资源  →  机器数  →  成本
   ↓         ↓          ↓            ↓         ↓
 DAU/MAU   峰谷比   CPU/内存/IO   利用率上限  $/月
```

**六步法：**

1. **写下已知量**（DAU、每人每天动作数、数据保留期）
2. **算平均 QPS**：`DAU × 人均次数 / 86400`
3. **算峰值 QPS**：平均 × 峰谷比（peak-to-average ratio；Web 通常 2–3×，秒杀 flash sale 10–100×）
4. **算单请求成本**（CPU ms / 内存 / IO 次数 / 网络字节）
5. **算机器数**：`峰值QPS × 单请求CPU毫秒 / (1000 × 核数 × 目标利用率)`，目标利用率（target utilization）取 **60–70%**（留头部空间 headroom 给尾延迟）
   > ⚠️ **那个 1000 不能省。** QPS 的单位是「每秒」，单请求 CPU 的单位是「毫秒」——不换算就会把答案放大 1000 倍。
   > 代入检验：2000 QPS、单请求 5 CPU ms、16 核、0.65 → `2000 × 5 / (1000 × 16 × 0.65)` = **0.96，即 1 台**，
   > 与 [§2 换算表](#2-常用换算表背下来)「16 核机器跑 5 ms 请求 ≈ 2000 QPS」对上。**算完永远回头对一次换算表**，量级错误都是这样抓出来的。
6. **加乘数**：副本数 × 冗余 × 环境数

⚠️ **第 3 步和第 5 步用峰值，但不是所有维度都用峰值。** 一条独立的规则，漏掉它是本篇最容易犯的错：

| 你在算什么 | 用哪个数 | 为什么 |
|---|---|---|
| **容量维度**：机器数、连接数、带宽、单机 QPS 上限 | **峰值** | 系统必须在最忙的那一秒还活着 |
| **按用量计费的累计量**：月存储增量、月出网 GB、S3 请求数、日志总量、token 数 | **均值** | 一个月里只有极少数秒处于峰值，用峰值算累计量会高估一个峰谷比倍数（这里 3×） |
| **按预置资源计费的月账单**：EC2 / RDS 台数 × 730 h、预留带宽、预置 IOPS | **峰值定规格 × 整月时长** | 机器是按峰值配的，但它整月都在计费 —— 这一格既不是纯峰值也不是纯均值，是两者的乘积 |

**一句话判据**：先问「这个数是**按用量出账**还是**按预置出账**」，再问「它衡量的是**最忙那一秒**还是**一整月加起来**」。

**永远说出你的假设（state your assumptions）**。面试官不在乎你算的是 87 台还是 100 台，在乎你有没有说"我假设峰谷比 3×"。

## 3. 排队论（queueing theory）：为什么 80% 利用率（utilization）是危险的

### Little's Law

```
L = λ × W
在系统中的请求数 = 到达率 × 平均停留时间
```

用法举例：
> 目标 p50 延迟 100 ms，峰值 5000 QPS
> → 并发在途请求数（in-flight requests）L = 5000 × 0.1 = **500**
> → 如果每个请求占一个线程，需要 500 个线程（→ 该用异步/协程了）
> → 如果每个请求占 2 MB 内存，需要 1 GB 常驻

### 排队论的响应时间公式：先分清 M/M/1 和 M/M/c

```
W  = S / (1 − ρ)          ← 响应时间（sojourn time）= 排队 + 被服务
Wq = ρS / (1 − ρ)         ← 只有排队那一段（queueing delay）
                            ρ = 利用率, S = 服务时间, W = Wq + S
```

⚠️ **这两个是不同的量，说错会被追问。** 面试里说"排队延迟"却写 `S/(1−ρ)`，等于把服务时间算进了排队。

**但更要紧的是第二件事：上面是 M/M/1 —— 一个队列、一个服务台。** 你的部署几乎肯定不是。
一台 16 核容器跑 16 个 worker 是 **M/M/c**（一个队列、c 个服务台），同样的 ρ 下均值放大小得多：

| 利用率 ρ | M/M/1（c=1） | M/M/c，c=4 | c=8 | **c=16** | c=32 |
|---|---|---|---|---|---|
| 50% | 2× | 1.09× | 1.01× | 1.00× | 1.00× |
| 70% | 3.3× | 1.36× | 1.11× | **1.03×** | 1.00× |
| 80% | 5× | 1.75× | 1.29× | **1.10×** | 1.03× |
| 90% | **10×** | 2.97× | 1.88× | **1.37×** | 1.14× |
| 95% | **20×** | 5.46× | 3.11× | **1.98×** | 1.43× |

（M/M/c 用 Erlang-C：`W/S = 1 + C(c,ρ) / (c(1−ρ))`。c=1 那一列就还原成 `1/(1−ρ)`。）

**所以"CPU 才 80% 为什么这么慢"的答案不是"因为 5×"** —— 在 16 核上按这个模型只有 1.10×。真正的原因通常是下面这些，它们才是你该查的：

| 真实原因 | 为什么模型看不见 |
|---|---|
| **服务时间不是指数分布** | 真实 Web 请求是重尾的（CV² > 1）。M/G/c 下等待时间大致按 `(1+CV²)/2` 放大，CV²=5 就是 3 倍于上表 |
| **c 个核不是 c 个独立服务台** | 共享内存带宽、锁竞争、STW GC、超线程共享执行单元 —— 有效并行度远小于核数，实际落在上表更靠左的列 |
| **80% 是平均值** | 它掩盖单核热点、单分片热点、单连接池耗尽。一个被打满的分片就是一个 ρ→1 的 M/M/1 |
| **瓶颈根本不是 CPU** | 连接池、下游依赖、磁盘 —— 那些地方各自有自己的 ρ，且往往真的是单服务台 |
| **p99 比均值差得多** | 上表全是**均值**。所有模型里尾部都比均值恶化得快，而你的 SLO 写在 p99 上 |

**工程结论**（结论不变，但理由要说对）：
- 稳态（steady state；指没有突发、到达速率和处理速率大致平衡的常态）目标利用率 **60–70%**。
  理由**不是**"80% 有 5× 放大"，而是：重尾服务时间 + 有效并行度低于核数 + 要给尾延迟和扩容时延留头部空间
- 超过 80% 必须自动扩容（autoscaling；按负载指标自动增减机器数），且扩容速度要快过流量增长
- 批处理（batch）系统可以跑到 90%+（不在乎延迟），在线服务（online serving）不行
- **单服务台的地方要单独找出来**：单主库、单分片、单连接、单线程的锁 —— 那些地方 M/M/1 的 5× 是真的

> 💡 **面试里怎么说**：「利用率到 80% 时延迟会非线性上升。单服务台按 `1/(1−ρ)` 是 5 倍；我这是 16 核，按 M/M/c 均值只有 1.1 倍，
> 但真实服务时间是重尾的、核之间还有锁和 GC 争用，所以我仍然按 60–70% 留余量。」
> —— 这个回答同时给出了模型、模型的适用边界、和不照搬模型的理由，比背一个 5× 强得多。

### 通用可扩展性定律（USL）—— 比 Amdahl 更实用

```
C(N) = N / (1 + α(N−1) + βN(N−1))
       α = 竞争（串行部分）， β = 一致性开销（跨节点协调）
```

关键洞察：**β > 0 时，吞吐（throughput）会先升后降**。加机器会让系统变慢。

典型症状：
- 分布式锁竞争（lock contention；多个节点抢同一把锁，抢不到的只能排队） → β 大
- 每个节点都要和其他所有节点同步（全网状 full mesh：N 个节点两两互连，共 N(N−1)/2 条连接） → β ∝ N²
- 数据库连接数随应用节点线性增长 → 打爆 DB

**面试可用**：
> "我不会无脑说'水平扩展（horizontal scaling）'。这个设计里，写路径要经过一个全局序号生成器，那就是 α 项；如果再加跨节点的两阶段提交（two-phase commit：先让所有参与者都回答'我准备好了'，再统一让它们提交，见 [`01-building-blocks/05`](../01-building-blocks/05-consensus-and-coordination.md)），β 项会让扩展在 20 节点左右见顶。所以我先把这两个去掉。"

## 4. 完整估算示例 A：一个协作文档 SaaS

**需求**：类 Notion 的产品，目标 500 万 MAU。

**Step 1 — 用户与活跃度**
```
MAU = 5M，DAU/MAU = 0.3  →  DAU = 1.5M
人均每天：打开 20 个文档，编辑 5 个文档，每个编辑产生 200 次按键
```

**Step 2 — QPS**
```
读：1.5M × 20 / 10⁵         = 300 QPS  平均
写（编辑操作）：
   1.5M × 5 × 200 / 10⁵     = 15,000 ops/s 平均  ← 注意！
峰值（3×）：读 900，写 45,000 ops/s
```
👉 **第一个洞察**：按键级别的写入量比"文档保存"高 3 个数量级（order of magnitude）。这直接否决了"每次编辑写一次 DB"的设计。

**Step 3 — 修正设计**
```
按键 → 客户端本地缓冲 200ms → 批量成一个 op batch
       → WebSocket 送到协作服务（内存中的文档 session）
       → 每 2s 或每 100 ops 落一次盘
落盘写入：45,000 / 100 = 450 TPS   ✅ 单个 Postgres 集群扛得住
```

**Step 4 — 连接数**（⚠️ 连接数是**容量**维度，必须用峰值）
```
日均同时在线：DAU × 在线时长占比 = 1.5M × (30min / 24h) ≈ 31,000 并发 WebSocket
峰值 3×                                            ≈ 94,000 并发
每连接内存 ~40 KB（含缓冲区） → 94,000 × 40 KB     ≈ 3.8 GB
单机 50k 连接是安全值 → 峰值需 2 台跑满；为 HA 跨 AZ 取 3 台
```
（**HA** = high availability，高可用，即"挂一台不影响对外服务"；**AZ** = availability zone，可用区，同一个 region 内部电力、制冷、网络互相独立的一组机房 —— 跨 AZ 部署是为了让一次机房级故障打不死整个服务。）

👉 **第二个洞察**：连接不是瓶颈，**文档会话的内存驻留**才是。热文档要有会话亲和性路由（session affinity routing：同一个文档的所有连接固定路由到同一台机器，因为那份会话就驻留在它的内存里）。这里的"热文档"就是**热点（hot key）**的一种形态 —— 绝大部分负载压在极少数的键上，均分策略对它无效。

**Step 5 — 存储**
```
文档数 = 5M 用户 × 50 文档 = 250M 文档
平均 20 KB       → 5 TB
操作日志（保留 30 天用于回溯）：
   ⚠️ 这里用均值 15,000，不是峰值 45,000 —— 见 §1 六步法的「峰值 / 均值」规则
   15,000 ops/s × 100 B × 2.6M s/月 = 3.9 TB/月
   保留 30 天 ⇒ 稳态占用也是约 3.9 TB，和 5 TB 的正文语料同量级
   → 值得做压缩 + 周期快照（只留快照之间的 op），能再降 3–5×；不必砍保留期
   → 但 op log 不进 3 副本热存储：单副本写本地盘 + 落 S3 归档
      （回溯是低频操作，用不着热副本）⇒ 约 $90/月 S3

文档主存储：5 TB × 3 副本 + 索引 ≈ 20 TB
```
> ⚠️ **别把 op log 和文档存储混在一个数里。** 它们的保留期、副本数、访问频率、单价全都不同 ——
> 20 TB 这个数只包含文档。如果你把 op log 也做 3 副本热存储，那是 3.9 × 3 = 11.7 TB，主存储要写成 ~32 TB，Step 6 的存储成本翻一倍。
> **估算里每出现一个"总共 X TB"，都要能说出它把什么算进去了、把什么排除了。**
> 💡 **这一步是本篇最容易错的一步。** 用峰值 45,000 会算出 11.7 TB/月，把一个"压一压就好"的问题误判成"必须砍掉 23 天回溯能力"的问题。
> **月度累计量永远用均值** —— 一个月里处于峰值的秒数只占很小一部分。反过来，Step 3 的落盘 TPS 和 Step 4 的连接数必须用峰值。

**Step 6 — 成本粗算**
```
计算：协作服务 6 × c6i.4xlarge   ≈ $3,500/月
      API 服务 20 × c6i.2xlarge  ≈ $6,000/月
存储：20 TB gp3                   ≈ $1,600/月
数据库：Aurora 3 实例 r6g.4xlarge ≈ $5,000/月
CDN + 出网流量                    ≈ $3,000/月
                                  ────────────
                                   ~$19,000/月
÷ 5M MAU = $0.0038/MAU/月
```
👉 **第三个洞察**：如果定价 $10/用户/月、付费转化（paid conversion）3%，收入 = 5M × 3% × $10 = $1.5M/月，基础设施占收入 1.3%，**健康**。

## 5. 完整估算示例 B：一个 AI Agent 平台（现代重点）

**需求**：给开发者提供云端编码 Agent，1 万个日活开发者。

**Step 1 — 会话与轮次**
```
DAU = 10,000
人均每天 8 个 Agent 会话，每会话平均 12 轮（含工具调用）
总轮次 = 10,000 × 8 × 12 = 960,000 轮/天  ≈ 11 轮/s 平均，33 轮/s 峰值
```

**Step 2 — Token 量（这才是钱）**
```
每轮：输入 ~25,000 token（含代码上下文、历史）
      输出 ~800 token
日输入 token = 960,000 × 25,000 = 2.4 × 10¹⁰ = 240 亿 token/天
日输出 token = 960,000 × 800    = 7.7 亿 token/天
```

**Step 3 — 缓存的决定性作用**
```
Agent 的多轮对话中，前缀高度重复（系统提示 + 工具定义 + 历史）
假设前缀缓存命中率 85%：
  未命中输入：240亿 × 0.15 = 36 亿
  命中输入：  240亿 × 0.85 = 204 亿（价格约为 1/10）

成本（按 $3/M 输入、$0.3/M 缓存读、$15/M 输出）：
  未命中：3,600 M × $3   /M = $10,800/天
  缓存读：20,400 M × $0.3/M = $6,120/天
  输出：  770 M × $15    /M = $11,550/天
                            ───────────
                             $28,470/天 ≈ $854k/月
```
👉 **第一个洞察**：**没有前缀缓存（prefix caching）的话，输入成本会是 $72,000/天**，即多花 $1.6M/月。前缀缓存不是优化，是生死线。

👉 **第二个洞察**：$854k/月 ÷ 10,000 DAU = **$85/开发者/月**。如果你卖 $20/月，你在烧钱。必须：
- 降低每轮上下文（更精准的检索 retrieval，而非把整个仓库塞进去）
- 用更小的模型做规划/分类，只在难任务上用大模型
- 限制轮次上限（turn limit）、加超时

**Step 4 — 沙箱容量**
```
并发会话数 = 11 轮/s × 平均会话时长 180s / 12 轮 ≈ 165 并发会话（Little's Law）
峰值 3× → ~500 并发沙箱
每沙箱 2 vCPU / 4 GB → 1000 vCPU / 2 TB 内存
按 60% 利用率 → 需要 ~1700 vCPU
   c6i.8xlarge = 32 vCPU / 64 GiB（2 GiB per vCPU，正好匹配沙箱的 2 vCPU / 4 GB）
   1700 / 32 = 53.1 → 54 台 × $1.36/h × 730 h ≈ $54,000/月（按需价 on-demand）
   ⇒ 1 年 Savings Plan 约 −40% → ~$32,000/月
```
> ⚠️ **实例规格必须查过再写。** 说"27 台"就意味着每台 64 vCPU（那是 c6i.**16**xlarge），
> 而 c6i.8xlarge 只有 32 vCPU。面试官只要知道这个数就能一秒抓到，然后会开始怀疑你前面所有数字。
> **报机型时把 vCPU 数一起说出来**（"54 台 c6i.8xlarge，每台 32 核"），既防错也显示你真算过。
> 这里用按需价，是为了和上面模型成本用的 list 价保持同一口径 —— **两边计价口径必须一致，否则占比是假的**。

👉 **第三个洞察**：沙箱计算成本($54k)只有模型成本($854k)的 **6%**。优化方向要放对地方 —— 别去抠容器启动时间，去抠 token。
（就算你把沙箱成本优化到 0，总账单也只降 6%；而把前缀缓存命中率从 85% 提到 95%，省下的比整个沙箱集群还多。）

**Step 5 — 存储与可观测**
```
每轮轨迹（trace：一次交互从头到尾发生了什么的完整记录）：prompt + response + 工具调用 ≈ 60 KB 压缩后
960,000 × 60 KB = 58 GB/天 = 1.7 TB/月
保留 30 天热 + 1 年冷：热 1.7 TB (S3 + 索引)，冷 20 TB Glacier
成本 ≈ $500/月   ← 便宜，所以：全量存，别采样。轨迹是 Agent 系统最有价值的资产
```

## 6. 成本建模：单位经济（Unit Economics）

Senior 必须能算出这三个数：

| 指标 | 公式 | 健康区间 |
|---|---|---|
| **$/请求** | 总基础设施成本 / 总请求数 | 与定价对比 |
| **毛利率（gross margin）** | (收入 − 变动成本 variable cost) / 收入 | SaaS ≥ 75%；AI 产品 ≥ 50% 算不错 |
| **成本占收入比（infra cost as % of revenue）** | 基础设施 / ARR | 传统 SaaS 5–15%；AI 产品 30–60% |

（**ARR** = annual recurring revenue，年度经常性收入：把当前的订阅收入按年折算出来的那个数，用来衡量订阅制生意的规模。**变动成本 variable cost** 指随用量增减的那部分成本，与之相对的是不管有没有人用都要付的固定成本。）

### AI 产品的成本结构（边际成本 marginal cost）与传统 SaaS 根本不同

```
传统 SaaS：
  边际成本 ≈ 0（多一个用户几乎不增加成本）
  → 规模化后毛利率 85%+
  → 优化重点：获客成本

AI 产品：
  边际成本 = token 成本，与使用量线性相关（甚至超线性——重度用户上下文更长）
  → 毛利率可能只有 40–60%，且**重度用户会亏钱**
  → 优化重点：单位推理成本 + 用量与定价的对齐
```

**这带来的架构后果：**
1. **必须做用量计量（usage metering）**（见 [`03-saas-platform/02-billing-and-metering.md`](../03-saas-platform/02-billing-and-metering.md)），否则你不知道谁在亏钱
2. **必须有配额（quota）/限流（rate limiting）**，防止单个租户（tenant：共用同一套系统、但数据互相隔离的一个客户组织）吃掉整月预算
3. **模型路由（model routing：按任务难度把请求分给不同大小的模型）是核心基础设施**，不是可选项
4. **缓存的 ROI 极高**，值得为它做复杂设计

### 一个反直觉的结论

> 在 AI 产品里，**降低 p99 延迟和降低成本常常是同一件事**。
> 因为两者都指向：更短的上下文、更少的轮次、更高的缓存命中（cache hit rate）、更小的模型。
> 而在传统系统里，这两者经常冲突（加缓存/加副本降延迟，但增成本）。

## 7. 估算中最常见的 6 个错误

| 错误 | 后果 | 修正 |
|---|---|---|
| **容量**维度只算平均，不算峰值 | 上线即挂 | 机器数 / 连接数 / 带宽 / 单机上限：永远乘峰谷比，并说出你的假设 |
| **累计量**维度却用了峰值（同一个错误的反面） | 月存储、月账单、日志量高估一个峰谷比倍数，据此做出错误的裁剪决策 | 月/年累计量用**均值**。判据：这个数是"最忙那一秒要扛住的"还是"一整月加起来的"？见 [§1 六步法](#1-估算的黄金流程) 的对照表 |
| 按 100% 利用率算机器数 | 延迟爆炸 | 除以 0.6–0.7 |
| 忘记副本和多环境 | 成本低估 3× | ×副本数 ×(prod+staging) |
| 忘记出网流量费（egress cost） | 云账单惊喜 | 跨 AZ $0.01/GB，出网 $0.05–0.09/GB |
| 忽略元数据/索引开销 | 存储低估 2× | 逻辑数据 ×3–5 |
| 用逻辑数据量估 IOPS | 完全脱节 | 要按访问模式估：读放大（read amplification）、写放大（write amplification，一次逻辑写引发多次实际写，见 [00-concepts §11](00-concepts.md)） |

**关于跨 AZ 流量**：一个每秒传 100 MB 跨 AZ 的服务 = 100 MB/s × 2.6M s/月 × $0.01/GB ≈ **$2,600/月**，仅流量费。这经常比计算成本还高，是 Cell 架构（cell-based architecture，AZ 内闭环）的重要动机。

## 这一章的三句话

1. **估算的价值不在那个数字，在那句"我假设峰谷比是 3×"。** 一个说得出全部假设的错答案，比一个说不出来源的对答案有用得多 —— 因为前者可以被别人当场推翻并修正，后者只能被相信或不信。
2. **利用率不是一把线性的尺子：从 65% 推到 90%，你省下的是四分之一的机器，换回来的是非线性上涨的排队延迟**（单服务台按 `1/(1−ρ)` 是 3.5 倍；16 核按 M/M/c 均值只有 1.3 倍，但真实服务时间重尾、核间有锁与 GC 争用，实际落在两者之间，而 p99 比均值恶化得更快）。所以容量规划的默认答案就是 60–70%，跑得更满需要专门论证（批处理可以，在线服务不行）。
3. **在 AI 产品里，成本必须和架构在同一张纸上算完。** token 是随用量线性甚至超线性增长的变动成本，"先做出来、以后再优化成本"这条传统 SaaS 经验在这里会直接把毛利率吃穿 —— 前缀缓存、上下文长度、轮次上限是设计决策，不是上线后的调优项。
