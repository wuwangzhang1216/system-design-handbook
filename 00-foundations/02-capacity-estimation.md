# 02 · 容量估算与成本建模

> Senior 和 Mid 的分水岭之一：能不能在 3 分钟内，用几个数字把"要多少机器、多少钱、瓶颈在哪"算出来，并且知道自己的误差范围。

---

## 1. 估算的黄金流程

```
业务量  →  QPS  →  单请求资源  →  机器数  →  成本
   ↓         ↓          ↓            ↓         ↓
 DAU/MAU   峰谷比   CPU/内存/IO   利用率上限  $/月
```

**六步法：**

1. **写下已知量**（DAU、每人每天动作数、数据保留期）
2. **算平均 QPS**：`DAU × 人均次数 / 86400`
3. **算峰值 QPS**：平均 × 峰谷比（peak-to-average ratio；Web 通常 2–3×，秒杀 flash sale 10–100×）
4. **算单请求成本**（CPU ms / 内存 / IO 次数 / 网络字节）
5. **算机器数**：`峰值QPS × 单请求CPU / (核数 × 目标利用率)`，目标利用率（target utilization）取 **60–70%**（留头部空间 headroom 给尾延迟）
6. **加乘数**：副本数 × 冗余 × 环境数

**永远说出你的假设（state your assumptions）**。面试官不在乎你算的是 87 台还是 100 台，在乎你有没有说"我假设峰谷比 3×"。

## 3. 排队论（queueing theory）：为什么 80% 利用率（utilization）是危险的

### Little's Law

```
L = λ × W
在系统中的请求数 = 到达率 × 平均停留时间
```

用法举例：
> 目标 p50 延迟 100 ms，峰值 5000 QPS
> → 并发在途请求数（in-flight requests）L = 5000 × 0.1 = **500**
> → 如果每个请求占一个线程，需要 500 个线程（→ 该用异步/协程了）
> → 如果每个请求占 2 MB 内存，需要 1 GB 常驻

### M/M/1 排队延迟（queueing delay）公式

```
W = S / (1 − ρ)        ρ = 利用率, S = 服务时间
```

| 利用率 ρ | 延迟放大倍数（latency amplification） |
|---|---|
| 50% | 2× |
| 70% | 3.3× |
| 80% | 5× |
| 90% | **10×** |
| 95% | **20×** |
| 99% | **100×** |

**这就是"CPU 才 80% 为什么这么慢"的答案。**

**工程结论**：
- 稳态（steady state）目标利用率 **60–70%**
- 超过 80% 必须自动扩容（autoscaling），且扩容速度要快过流量增长
- 批处理（batch）系统可以跑到 90%+（不在乎延迟），在线服务（online serving）不行

### 通用可扩展性定律（USL）—— 比 Amdahl 更实用

```
C(N) = N / (1 + α(N−1) + βN(N−1))
       α = 竞争（串行部分）， β = 一致性开销（跨节点协调）
```

关键洞察：**β > 0 时，吞吐（throughput）会先升后降**。加机器会让系统变慢。

典型症状：
- 分布式锁竞争（lock contention） → β 大
- 每个节点都要和其他所有节点同步（全网状 full mesh） → β ∝ N²
- 数据库连接数随应用节点线性增长 → 打爆 DB

**面试可用**：
> "我不会无脑说'水平扩展（horizontal scaling）'。这个设计里，写路径要经过一个全局序号生成器，那就是 α 项；如果再加跨节点的两阶段提交（two-phase commit），β 项会让扩展在 20 节点左右见顶。所以我先把这两个去掉。"

## 4. 完整估算示例 A：一个协作文档 SaaS

**需求**：类 Notion 的产品，目标 500 万 MAU。

**Step 1 — 用户与活跃度**
```
MAU = 5M，DAU/MAU = 0.3  →  DAU = 1.5M
人均每天：打开 20 个文档，编辑 5 个文档，每个编辑产生 200 次按键
```

**Step 2 — QPS**
```
读：1.5M × 20 / 10⁵         = 300 QPS  平均
写（编辑操作）：
   1.5M × 5 × 200 / 10⁵     = 15,000 ops/s 平均  ← 注意！
峰值（3×）：读 900，写 45,000 ops/s
```
👉 **第一个洞察**：按键级别的写入量比"文档保存"高 3 个数量级（order of magnitude）。这直接否决了"每次编辑写一次 DB"的设计。

**Step 3 — 修正设计**
```
按键 → 客户端本地缓冲 200ms → 批量成一个 op batch
       → WebSocket 送到协作服务（内存中的文档 session）
       → 每 2s 或每 100 ops 落一次盘
落盘写入：45,000 / 100 = 450 TPS   ✅ 单个 Postgres 集群扛得住
```

**Step 4 — 连接数**
```
同时在线：DAU × 在线时长占比 = 1.5M × (30min / 24h) ≈ 31,000 并发 WebSocket
每连接内存 ~40 KB（含缓冲区） → 1.2 GB
单机 50k 连接是安全值 → 需要 ~1 台（但为 HA 至少 3 台，跨 AZ）
```
👉 **第二个洞察**：连接不是瓶颈，**文档会话的内存驻留**才是。热文档要有会话亲和性路由（session affinity routing）。

**Step 5 — 存储**
```
文档数 = 5M 用户 × 50 文档 = 250M 文档
平均 20 KB       → 5 TB
操作日志（保留 30 天用于回溯）：
   45,000 ops/s × 100 B × 2.6M s/月 = 11.7 TB/月  ← 太大
   → 压缩 + 快照后只保留 op 摘要，或降到 7 天保留
索引 + 副本 3 份 → 主存储约 20 TB
```

**Step 6 — 成本粗算**
```
计算：协作服务 6 × c6i.4xlarge   ≈ $3,500/月
      API 服务 20 × c6i.2xlarge  ≈ $6,000/月
存储：20 TB gp3                   ≈ $1,600/月
数据库：Aurora 3 实例 r6g.4xlarge ≈ $5,000/月
CDN + 出网流量                    ≈ $3,000/月
                                  ────────────
                                   ~$19,000/月
÷ 5M MAU = $0.0038/MAU/月
```
👉 **第三个洞察**：如果定价 $10/用户/月、付费转化（paid conversion）3%，收入 = 5M × 3% × $10 = $1.5M/月，基础设施占收入 1.3%，**健康**。

## 5. 完整估算示例 B：一个 AI Agent 平台（现代重点）

**需求**：给开发者提供云端编码 Agent，1 万个日活开发者。

**Step 1 — 会话与轮次**
```
DAU = 10,000
人均每天 8 个 Agent 会话，每会话平均 12 轮（含工具调用）
总轮次 = 10,000 × 8 × 12 = 960,000 轮/天  ≈ 11 轮/s 平均，33 轮/s 峰值
```

**Step 2 — Token 量（这才是钱）**
```
每轮：输入 ~25,000 token（含代码上下文、历史）
      输出 ~800 token
日输入 token = 960,000 × 25,000 = 2.4 × 10¹⁰ = 240 亿 token/天
日输出 token = 960,000 × 800    = 7.7 亿 token/天
```

**Step 3 — 缓存的决定性作用**
```
Agent 的多轮对话中，前缀高度重复（系统提示 + 工具定义 + 历史）
假设前缀缓存命中率 85%：
  未命中输入：240亿 × 0.15 = 36 亿
  命中输入：  240亿 × 0.85 = 204 亿（价格约为 1/10）

成本（按 $3/M 输入、$0.3/M 缓存读、$15/M 输出）：
  未命中：3,600 M × $3   /M = $10,800/天
  缓存读：20,400 M × $0.3/M = $6,120/天
  输出：  770 M × $15    /M = $11,550/天
                            ───────────
                             $28,470/天 ≈ $854k/月
```
👉 **第一个洞察**：**没有前缀缓存（prefix caching）的话，输入成本会是 $72,000/天**，即多花 $1.6M/月。前缀缓存不是优化，是生死线。

👉 **第二个洞察**：$854k/月 ÷ 10,000 DAU = **$85/开发者/月**。如果你卖 $20/月，你在烧钱。必须：
- 降低每轮上下文（更精准的检索 retrieval，而非把整个仓库塞进去）
- 用更小的模型做规划/分类，只在难任务上用大模型
- 限制轮次上限（turn limit）、加超时

**Step 4 — 沙箱容量**
```
并发会话数 = 11 轮/s × 平均会话时长 180s / 12 轮 ≈ 165 并发会话（Little's Law）
峰值 3× → ~500 并发沙箱
每沙箱 2 vCPU / 4 GB → 1000 vCPU / 2 TB 内存
按 60% 利用率 → 需要 ~1700 vCPU ≈ 27 × c6i.8xlarge ≈ $20,000/月
```
👉 **第三个洞察**：沙箱计算成本($20k)只有模型成本($854k)的 **2.3%**。优化方向要放对地方 —— 别去抠容器启动时间，去抠 token。

**Step 5 — 存储与可观测**
```
每轮轨迹（trace）：prompt + response + 工具调用 ≈ 60 KB 压缩后
960,000 × 60 KB = 58 GB/天 = 1.7 TB/月
保留 30 天热 + 1 年冷：热 1.7 TB (S3 + 索引)，冷 20 TB Glacier
成本 ≈ $500/月   ← 便宜，所以：全量存，别采样。轨迹是 Agent 系统最有价值的资产
```

## 6. 成本建模：单位经济（Unit Economics）

Senior 必须能算出这三个数：

| 指标 | 公式 | 健康区间 |
|---|---|---|
| **$/请求** | 总基础设施成本 / 总请求数 | 与定价对比 |
| **毛利率（gross margin）** | (收入 − 变动成本 variable cost) / 收入 | SaaS ≥ 75%；AI 产品 ≥ 50% 算不错 |
| **成本占收入比（infra cost as % of revenue）** | 基础设施 / ARR | 传统 SaaS 5–15%；AI 产品 30–60% |

### AI 产品的成本结构（边际成本 marginal cost）与传统 SaaS 根本不同

```
传统 SaaS：
  边际成本 ≈ 0（多一个用户几乎不增加成本）
  → 规模化后毛利率 85%+
  → 优化重点：获客成本

AI 产品：
  边际成本 = token 成本，与使用量线性相关（甚至超线性——重度用户上下文更长）
  → 毛利率可能只有 40–60%，且**重度用户会亏钱**
  → 优化重点：单位推理成本 + 用量与定价的对齐
```

**这带来的架构后果：**
1. **必须做用量计量（usage metering）**（见 [`03-saas-platform/02-billing-and-metering.md`](../03-saas-platform/02-billing-and-metering.md)），否则你不知道谁在亏钱
2. **必须有配额（quota）/限流（rate limiting）**，防止单个租户（tenant）吃掉整月预算
3. **模型路由（model routing）是核心基础设施**，不是可选项
4. **缓存的 ROI 极高**，值得为它做复杂设计

### 一个反直觉的结论

> 在 AI 产品里，**降低 p99 延迟和降低成本常常是同一件事**。
> 因为两者都指向：更短的上下文、更少的轮次、更高的缓存命中（cache hit rate）、更小的模型。
> 而在传统系统里，这两者经常冲突（加缓存/加副本降延迟，但增成本）。

## 7. 估算中最常见的 6 个错误

| 错误 | 后果 | 修正 |
|---|---|---|
| 只算平均，不算峰值 | 上线即挂 | 永远乘峰谷比，并说出你的假设 |
| 按 100% 利用率算机器数 | 延迟爆炸 | 除以 0.6–0.7 |
| 忘记副本和多环境 | 成本低估 3× | ×副本数 ×(prod+staging) |
| 忘记出网流量费（egress cost） | 云账单惊喜 | 跨 AZ $0.01/GB，出网 $0.05–0.09/GB |
| 忽略元数据/索引开销 | 存储低估 2× | 逻辑数据 ×3–5 |
| 用逻辑数据量估 IOPS | 完全脱节 | 要按访问模式估：读放大（read amplification）、写放大（write amplification） |

**关于跨 AZ 流量**：一个每秒传 100 MB 跨 AZ 的服务 = 100 MB/s × 2.6M s/月 × $0.01/GB ≈ **$2,600/月**，仅流量费。这经常比计算成本还高，是 Cell 架构（cell-based architecture，AZ 内闭环）的重要动机。

## 面试官会追问

1. 你这个峰谷比 3× 是怎么来的？如果有秒杀活动呢？
2. 为什么目标利用率是 65% 不是 85%？
3. 你的写入 QPS 是多少？单个 Postgres 撑得住吗？撑不住的临界点在哪？
4. 加一倍机器能不能扛一倍流量？哪里会先撞墙？
5. 这个系统一个月多少钱？最大的一项是什么？怎么砍掉 30%？
6. （AI 场景）一个重度用户（power user）一个月消耗多少钱？你的定价能覆盖吗？
