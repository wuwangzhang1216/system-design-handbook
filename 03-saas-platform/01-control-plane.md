# 01 · 控制面与 Cell 架构

> 控制面全挂时数据面必须还能收钱。这一条不成立，后面所有设计都是装饰。
> Cell 化不提升可用性，它只降低爆炸半径（blast radius）和缩短恢复时间 —— 别把这两件事混为一谈。
>
> **阅读分层**：§1–§5 是 Core；§6 之后是进阶落地。文中的容量、时延和控制器参数是示例起点，必须用自己的负载与故障演练重新标定。

## 读这一章之前

**你在工作中遇到过这个**

你们的配置中心挂了 90 秒。前 60 秒风平浪静，第 61 秒开始全站 500 ——
每个 API 实例都在进程内缓存租户路由表，缓存有效期正好 60 秒，到点集体失效、集体去拉、集体拉不到、集体崩。
复盘会上你解释不清一件事：控制面的可用性目标写的是 99.9%，数据面写的是 99.99%，
为什么那个目标更低的组件挂 90 秒，能把目标更高的组件打死 4 分钟。

**这一章要回答的问题**

1. 控制面整整挂 30 分钟，存量客户还能不能正常读写、还能不能继续收钱？靠什么保证？
2. "开通一个租户"跨了 5 个以上外部系统，第 5 步失败了怎么收场？哪些步骤根本不能回滚？
3. 8 个 cell，爆炸半径是不是 1/8？为什么这个答案会被扣分？
4. 自动扩缩容为什么会把系统越调越震荡？要加哪几个阻尼？

**本章新引入的术语**

| 术语 | English | 一句话定义 |
|---|---|---|
| 控制面 / 数据面 | control plane / data plane | 负责改变系统"应该是什么样"的那一半（开通、配额、路由表）/ 负责处理最终用户请求的那一半 |
| 静态稳定 | static stability | 依赖挂掉时，系统靠手上已有的信息按当前状态继续工作，不需要为此发起任何新的依赖调用 |
| 期望态 / 观测态 | desired state / observed state | 你声明它"应该是什么样" / 探测到它"现在实际是什么样" |
| 协调循环 | reconciliation loop | 一个不停比较期望态与观测态、并把现实往期望态推的后台循环 |
| 电平触发 / 边沿触发 | level-triggered / edge-triggered | 看**当前状态**决定该做什么（丢一个事件只是晚点收敛）/ 看**变化事件**决定该做什么（丢一个事件就永远错） |
| 漂移 | drift | 现实偏离了期望态，通常是因为有人绕过控制面手工改了东西 |
| 最后一份好配置 | last-known-good | 最后一次成功加载并验证过的配置，落盘保存；拿不到新配置时就一直用它 |
| 爆炸半径 | blast radius | 一次故障最多能波及多大比例的租户 / 流量 / 收入 |
| Cell 架构 | cell-based architecture | 把一个装 `T` 个租户的系统，复制成 `K` 套互不依赖的完整副本；均匀分布只是理想情况，每套约装 `T/K` 个租户 |
| 围栏 / 纪元号 | fencing / epoch | 给"谁是当前归属方"配一个只增不减的编号，带着旧编号来的写入一律被拒绝 |
| 紧急旁路 | break-glass | 一条绕开控制面正常逻辑、直接改底层存储的、全程留审计的应急运维通道 |
| 死区 / 滞回 | deadband / hysteresis | 指标落在两个阈值之间时控制器什么都不做，以免在阈值附近来回抖动 |

## 1. 控制面 / 数据面：定义与那条铁律

| 维度 | 控制面（Control Plane） | 数据面（Data Plane） |
|---|---|---|
| 职责 | 改变系统的**期望状态（desired state）**：开通（provisioning）、扩缩、配额（quota）、路由表、密钥轮换（key rotation：定期换掉正在使用的密钥或证书，且新旧两把必须有一段同时有效的重叠期） | 处理**最终用户请求**：读写、推理、投递 |
| QPS 量级 | 10⁰–10² | 10³–10⁶（差 **100–10,000×**） |
| 可用性目标 | 99.9%（月停 43 分钟） | 99.99%+（月停 4.3 分钟） |
| 延迟预算（latency budget） | 秒级、甚至分钟级可接受 | p99 毫秒级 |
| 变更频率 | 高（每天多次发布） | 低、保守、金丝雀（canary：先把新版本只放给极小一部分流量或租户，观察指标没问题再逐步扩大） |
| 一致性需求 | **强一致（strong consistency）**（配置不能脑裂 split-brain：网络一断，两边都以为自己是权威、各自接受写入，见 [00-concepts §5](../00-foundations/00-concepts.md#5-副本分片分区--三个被混用的词)） | 最终一致（eventual consistency）通常可接受 |
| 挂掉的后果 | 不能开通/改配置，**存量业务不受影响** | **收入立刻归零** |

**铁律（static stability，[AWS Builders' Library](https://aws.amazon.com/builders-library/static-stability-using-availability-zones/) 的原始表述）：**

> 数据面在处理请求时，**不得发起任何对控制面的同步调用**。控制面只能通过"提前把结果推/拉到数据面本地"来影响数据面。

自检清单（任何一条为"是"，你的数据面就已经被控制面绑架）：

1. 请求路径上有没有"查一下这个租户属于哪个分片"的**远程调用**？
2. 有没有"每次请求向配额服务确认剩余额度"？
3. 有没有"启动时从配置中心拉配置，拉不到就 crash loop"？
4. 证书/密钥是不是**到期前**才去控制面换？
5. 扩容出来的新实例，能不能在控制面不可用时完成初始化？

**静态稳定的三个实现层次**（成本递增，可靠性递增）：

| 层次 | 做法 | 控制面挂掉时的行为 |
|---|---|---|
| L0 缓存 | 数据面进程内缓存路由表/配额，TTL 60s（TTL = 这份缓存的存活时间，到点自动作废、必须重新去拉） | TTL 到期后失效 → **假的静态稳定** |
| L1 兜底（fallback） | 缓存 + **last-known-good 落盘**，控制面不可达时永久用旧值 | 用陈旧配置继续服务，正确性降级但可用 |
| L2 预置（pre-provisioning） | 容量、IP、证书、连接池**预先超配（over-provisioning）**，不做运行时决策 | 完全不受影响；代价是常态多花 20–40% 资源 |

生产建议：**路由与授权走 L1，容量走 L2**。L0 是最常见的自欺欺人 —— TTL 一到，故障就从"控制面挂"升级成"全站挂"。

## 2. 声明式协调循环（Reconciliation Loop）

命令式 API（imperative API，`createTenant()`）的问题：**中途失败后系统处于未定义状态**，重试不安全，且没人知道"现在应该是什么样"。声明式（declarative）的做法是把"应该是什么样"写下来，然后让一个循环不停地把现实拉向它。

### 期望态存哪

| 存法 | 适用 | 代价 |
|---|---|---|
| 关系库单表（`desired_state` JSONB + `version`） | **绝大多数 SaaS 控制面的正确答案** | 需要自己做 watch（LISTEN/NOTIFY 或轮询） |
| etcd / Consul | 需要 watch 语义、租约、低延迟 | 运维成本高；不适合大对象 |
| Kubernetes CRD | 你已经在 K8s 上，且资源天然是 K8s 对象 | 把 SaaS 租户模型塞进 K8s 会在 ~10⁴ 对象量级撞 apiserver 与 etcd 上限 |
| Git（GitOps） | 变更要人审、变更频率低 | 不适合租户自助开通这种高频路径 |

（表里四个词：**watch** = 向存储订阅"这个键一变就通知我"，省掉轮询；**租约 lease** = 一个必须定期续期的持有凭证，持有者死了它就自动到期、位置自动让出来；**CRD** = 把你自己的资源类型注册进 Kubernetes，让它像内置对象一样被声明和协调；**GitOps** = 期望态就是 Git 仓库里的文件，合并 PR 即发起变更。）

**关键**：期望态和观测态**必须分表/分字段存**，永远不要让 reconcile 把观测结果写回期望态 —— 那会产生自激反馈（positive feedback loop）：现实漂到哪儿，目标就跟着漂到哪儿，系统再也回不去了，而监控上看永远显示"已收敛"。

### 版本三元组

```
spec.generation          单调递增，用户每次改期望态 +1
status.observedGeneration 最后一次成功 reconcile 处理的 generation
resourceVersion          乐观并发控制令牌（CAS 用）
```

`observedGeneration < generation` ⟺ **有待处理的变更**。这一个不等式就是你控制面的核心 SLI。

### 幂等（idempotent）的 reconcile（伪代码）

```python
def reconcile(key: str) -> Result:
    # 1. 读期望 + 观测（同一事务快照，避免读到撕裂状态）
    spec, status, rv = store.get(key)          # rv = resourceVersion
    if spec is None:                            # 已被删除
        return finalize(key)                    # 清理外部资源后摘 finalizer

    # 2. 纯函数计算差异 —— 这一步不能有副作用，才能单测
    plan = diff(desired=spec, observed=probe_reality(key))
    if plan.is_empty():
        store.cas_update(key, rv, status.with_(
            observedGeneration=spec.generation, phase="Ready"))
        return Result(requeue_after=DRIFT_SCAN_INTERVAL)   # 30–300s

    # 3. 每步都必须幂等：先查后建，或用带 idempotency key 的 API
    for step in plan.steps:                     # 有序、可中断、可重入
        if step.already_done():                 # 语义级检查，不是"我记得做过"
            continue
        try:
            step.apply(idem_key=f"{key}:{spec.generation}:{step.name}")
        except Terminal as e:                   # 400 类：重试无意义
            store.cas_update(key, rv, status.failed(step.name, e))
            emit_event(key, "ReconcileFailed", e)
            return Result(requeue=False)        # 等人工或等 spec 变更
        except Transient as e:                  # 429/5xx/超时
            return Result(requeue_after=backoff(key))   # 见下

    store.cas_update(key, rv, status.with_(
        observedGeneration=spec.generation, phase="Ready"))
    return Result(requeue_after=DRIFT_SCAN_INTERVAL)
```

（代码里两个词先说清楚：**finalizer** 是挂在对象上的一个"我还有外部资源没清理完，先别真删"的标记 —— 清理干净后把它摘掉，对象才真正消失；没有它，用户一删对象，云上那些已经建好的资源就变成没人认领的孤儿。**`requeue_after`** 是"过 N 秒把我自己重新放回工作队列"，它就是下面第 1 条说的那个周期全量扫描。）

四条必须遵守的规则：

1. **Level-triggered，不是 edge-triggered。** 事件只用来"提示该看一眼了"，绝不携带增量语义。丢一个事件的后果必须只是"晚 30 秒收敛"，而不是"永远不收敛"。所以**周期全量扫描（drift scan）是必需的**，不是冗余。
2. **`already_done()` 必须是语义检查**（"数据库里有没有这个 schema"），不是状态位检查（"我在 status 里记过"）。后者在控制面自己崩溃重启后就失效了。
3. **幂等键（idempotency key）必须稳定标识一次业务步骤。** 控制器最方便的做法是从 `(资源 key, generation, step)` 派生；随机 UUID 也可以，但必须在首次调用前写入持久状态并由所有重试复用。每次重试生成新键才是最常见的 bug（详见 [02-billing-and-metering.md](02-billing-and-metering.md) §4）。
4. **区分 Terminal 与 Transient**。把 400 当 500 重试，会让一个坏租户的坏配置永久占满你的 worker。

### 退避（backoff）与并发控制

```
指数退避（抄 controller-runtime 的默认值就够用）：
    base = 5ms, factor = 2, max = 1000s, 全程叠加 ±20% jitter
全局限速：令牌桶 10 qps / burst 100 —— 防止 10 万个对象同时"惊群"到下游 API
Per-key 串行：同一个 key 同一时刻只有一个 reconcile 在跑（工作队列去重）
全局并发：worker 数按下游 API 配额倒推，典型 4–32
```

（**令牌桶 token bucket**：桶里按固定速率往里放令牌，每个请求出发前取走一个，取不到就等或被拒；桶容量决定了允许多大的瞬时突发。**惊群 thundering herd**：大量客户端在同一时刻做同一件事 —— 缓存同时过期、定时任务整点触发、控制面重启后全量对象一起入队 —— 把下游瞬间打满；抖动 jitter 就是专门用来打散它的。）

**为什么必须 per-key 串行**：两个 reconcile 并发跑同一个租户，会产生"创建了两套资源、只记住一套"的孤儿泄漏（orphaned resources）。工作队列的去重语义（同一 key 在队列中只保留一份）是这个模型的核心，不是优化。

### 观测：三个必须有的指标

| 指标 | 含义 | 告警线 |
|---|---|---|
| `reconcile_lag`（p99） | `now - spec.updated_at`，对 `observedGeneration < generation` 的对象 | > 5 分钟 |
| `drift_detected_total` | 全量扫描发现的漂移（drift：现实和期望态对不上）数 | 突增 = 有人在绕过控制面手改 |
| `reconcile_error_total{type=terminal}` | 卡死的对象数 | > 0 且持续 = 有租户开通不了 |

## 3. 租户开通（Provisioning）：一个必须能回滚的分布式事务（distributed transaction）

开通不是一次 API 调用，是一个 6–12 步的 **Saga**（把一个跨系统的长事务拆成若干个可以各自提交的步骤，任何一步失败就按相反顺序执行前面每一步的**补偿动作**；因为跨系统没有统一的回滚，见 [`02/02 §2`](../02-architecture-patterns/02-event-driven-and-cqrs.md#2-saga跨服务事务的现实解法)），跨越 5 个以上外部系统。

```
状态机（存在 tenants.phase）：
  Pending ──▶ Provisioning ──▶ Seeding ──▶ Verifying ──▶ Active
                  │               │            │            │
                  ▼               ▼            ▼            ▼
              Failed ◀────── Rollback ◀────────┴──── Suspended ──▶ Deprovisioning ──▶ Purged
                                                        (欠费/违规)      (T+30 天硬删)
```

| # | 步骤 | 幂等做法 | 补偿动作（compensating action） | 失败常见原因 |
|---|---|---|---|---|
| 1 | 分配 tenant_id + 选 cell | 用请求的 `idempotency_key` 查已有分配 | 释放 cell 配额预留 | cell 满 |
| 2 | 创建 DB schema / namespace | `CREATE SCHEMA IF NOT EXISTS` | `DROP SCHEMA CASCADE` | 连接池/权限 |
| 3 | 建 KMS 数据密钥 | 用固定别名 `tenant/{id}/dek` 查后建 | **不删，标记 pending_delete 30 天** | 配额（KMS key 数有硬上限） |
| 4 | 写路由表（tenant → cell） | upsert | 删除路由项 | — |
| 5 | 建计费账户 | 透传 `idempotency_key` 到计费系统 | 作废账户 | 计费系统 429 |
| 6 | 播种默认数据/索引 | 按 `(tenant, seed_version)` 记录 | 删除 schema 即可 | 慢，需异步 |
| 7 | 建 IdP 连接 / SCIM | 外部 API 通常**不幂等**，需先 list 后 create | 删除连接 | 外部系统最不可靠的一环 |
| 8 | 冒烟验证（smoke test） | 用真实数据面路径打一次读写 | — | **这一步最常被省略，也最该有** |

（表里几个缩写：**KMS** 是云上的密钥管理服务；**DEK**（data encryption key）是真正用来加密这个租户数据的那把密钥，它本身又被 KMS 里的主密钥加密保管 —— 所以"删掉 DEK"等于让该租户的全部密文永久不可读，这既是 crypto-shredding 的基础，也正是第 3 步的补偿只敢"标记"不敢真删的原因。**IdP** 是企业的身份提供方（Okta / Entra 之类）；**SCIM** 是让 IdP 把员工账号自动同步进你系统的那套标准协议。）

**三条工程结论：**

- **密钥和审计日志永远不做同步补偿删除**。合规要求它们比租户活得久。补偿只能"标记"，实际清除走独立的延迟删除流程（典型 30 天）。
- **步骤 7 这类不幂等的外部 API，必须在自己这一侧维护 `(tenant, external_system, external_id)` 映射表**，先查表再调用。指望对方支持幂等键是运气。
- **步骤 8 的冒烟验证要走完整的数据面路径**（经过 router、经过认证、经过限流），而不是直连数据库。开通失败中约一半是"资源都建好了但路由没生效"。

## 4. Cell 架构（Cell-Based Architecture）

单元化（cellularization）的本质：**把一个有 `T` 个租户的系统，变成 `K` 个互不依赖的完整部署单元**。`T/K` 只是均匀分布时的平均值；真实系统必须按流量、用户数和收入分别计算。参考 [AWS Guidance for Cell-Based Architecture](https://github.com/aws-solutions-library-samples/guidance-for-cell-based-architecture-on-aws/blob/main/README.md) 与 re:Invent ARC312（链接与产品状态以阅读时官方页面为准）。

```
                       ┌─────────────────────────────┐
   客户端 ───────────▶ │  Cell Router（薄、无状态）    │ ◀── 租户→cell 映射
                       │  唯一职责：查映射 → 转发/重定向 │     （只读副本 + 本地缓存
                       └───┬─────────┬─────────┬─────┘      + last-known-good 落盘）
                           │         │         │
        ┌──────────────────┘         │         └──────────────────┐
        ▼                            ▼                            ▼
┌───────────────┐          ┌───────────────┐           ┌───────────────┐
│    CELL-1     │          │    CELL-2     │           │    CELL-N     │
│  LB→App→DB    │          │  LB→App→DB    │           │  LB→App→DB    │
│  Cache/Queue  │          │  Cache/Queue  │           │  Cache/Queue  │
│  租户 1..2000  │          │  租户 2001..  │           │      ...      │
│               │          │               │           │               │
│ 完全自治：     │          │  ✗ 不与 CELL-1 │           │               │
│ 挂了不影响别人 │          │    共享任何状态 │           │               │
└───────────────┘          └───────────────┘           └───────────────┘
   名义租户半径 ≈ 1/K           ✗ 无跨 cell 同步依赖         ✗ 无跨 cell 调用
        │                                                        │
        └──────── 控制面（开通/迁移/部署编排）在带外，不在请求路径 ┘

⚠ 唯一的全局单点是 Router 与 Router 背后的映射存储。
   ⇒ 映射必须能被数据面本地缓存并在控制面挂掉时继续用（§1 的 L1）。
```

### 分区键（Partition Key）：cell 架构的成败点

⚠️ 这里的"分区"是**把数据切开分给不同 cell** 的那个意思，和 CAP 里的"网络分区"毫无关系 —— 两者的英文都是 partition，是全书最容易混的一对词（见 [00-concepts §5](../00-foundations/00-concepts.md#5-副本分片分区--三个被混用的词)）。

AWS 的原话立场很硬：**要选能最小化跨 cell 交互的分区键**；需要复杂映射的服务只是把问题**转移给映射服务**；需要跨 cell 交互的服务会在 cell 之间**制造依赖**。

| 分区键 | 适用 | 撞墙条件 |
|---|---|---|
| `tenant_id` | B2B SaaS 的默认答案 | 出现"共享工作区""跨组织审批"时立刻破功 |
| `user_id` | C 端 | 任何社交/协作关系都是跨 cell 的 |
| `workspace_id` / `org_id` | **协作型产品的正确答案**（把协作单元本身当分区单元） | 用户属于多个 workspace 时，用户级设置需要单独处理 |
| `region + tenant_id` | 有数据驻留要求 | cell 数量 = 区域数 × 每区 cell 数，运维面膨胀 |
| 哈希（无业务语义） | 均匀，简单 | **无法为大租户单独隔离，无法做租户级迁移**，通常是错的 |

**事后改分区键 = 全量数据迁移。** 这是 cell 架构里最贵的错误，在决定的那天就要把"三年后的协作场景"想清楚。如果业务天然存在跨租户协作：要么把协作对象本身作为分区单元，要么**接受该子系统不 cell 化**（例如把"跨组织通知"做成一个独立的、非单元化的全局服务，并给它单独的可用性预算）。

### 爆炸半径量化 —— 不要用 1/N 糊弄面试官

```
名义爆炸半径  = 1 / N                                   （租户均匀分布的假设）
加权爆炸半径  = max_i ( cell_i 的流量 / 总流量 )          ← 这才是要报的数
用户加权半径  = max_i ( cell_i 的 MAU / 总 MAU )
收入加权半径  = max_i ( cell_i 的 ARR / 总 ARR )          ← 向 CFO 汇报用这个
```

真实租户分布是幂律（power law）的：**top 1% 租户常占 30–50% 流量**。8 个 cell 的名义半径是 12.5%，但如果最大租户独占一个 cell 的 60% 容量，那个 cell 的收入加权半径可能是 25%。

**Cell 数量的选择公式：**

```
K ≥ ceil(1 / 可接受的名义半径)                     ← 这是 cell 数的下界，不是实际保障
cell 最小规格 ≥ 最大单租户峰值 × 安全系数(1.5–2)     ← 规格下界由最大租户给
实际半径 = max(流量占比, MAU 占比, ARR 占比等业务权重)  ← 必须用装箱结果复算
运维成本 ≈ O(K)：部署时长、演练次数、监控面板、on-call 认知负担
```

⚠ **cell 化最常见的死结**：某个巨型租户的峰值已经超过了单个 cell 的规格上限 —— 它装不进任何 cell。解法只有两个：给它开专属 cell（silo），或者在产品层拆分它的工作负载。**没有第三个解法。**

AWS 的起步策略也是这个意思：**先做少量大 cell，等自动化成熟后再逐步缩小 cell**。先切 32 个 cell 的团队，通常会死在部署编排上。

### Router 三形态

| 形态 | 机制 | 延迟 | 关键风险 |
|---|---|---|---|
| **负载均衡型** | Router 在关键路径上代理每个请求 | +1 跳（1–5ms 同区） | **Router 变成新的全局单点（single point of failure）**，它挂了 = 全挂 |
| **转发型** | 只在首次连接时返回 cell 端点，之后客户端直连 | 稳态 0 | 需要客户端 SDK 逻辑；迁移时需要"驱逐"（eviction）机制 |
| **DNS 型** | `tenant-a.api.example.com` → cell 的 IP | 0 | 最简单可靠；但 **DNS TTL 决定了迁移/故障切换的最小时间**（60s TTL ≠ 60s 生效，客户端会无视 TTL） |

**选型主张**：面向浏览器/第三方的公共 API 用**负载均衡型**（客户端不可控），并把 router 做成一个只读、无依赖、能用陈旧映射工作的东西；面向自家 SDK 的高吞吐路径用**转发型**。

> **面试金句**：
> "我会把 cell router 设计成一个只读的、可以用过期数据工作的东西。它启动时从对象存储拉一份租户→cell 的全量映射快照，落盘，之后靠增量流更新。控制面全挂时它继续用磁盘上那份快照 —— 代价是新开通的租户在控制面恢复前访问不了，而这是我愿意付的代价：**开通失败影响的是明天的收入，路由失败影响的是今天的全部收入**。"

## 5. 跨 Cell 迁移

租户迁移是 cell 架构的税。没有可靠的迁移，你会在半年内因为"某个 cell 满了"而瘫痪。

```
阶段             写入真相源       读              回滚成本
──────────────────────────────────────────────────────────────
1 预热            旧 cell          旧 cell         0
  全量 snapshot + CDC 追增量；CDC offset 只有在新侧事务提交后才推进
2 持续复制/修复     旧 cell          旧 cell         低
  新写通过 outbox/事务日志复制到新侧；失败进入可重放 repair log，影子读比对
3 切读             旧 cell          新 cell         低
  仍以旧侧为写入真相源；不一致的 key 立即回旧侧并排入 durable repair
4 切写             新 cell          新 cell         高
  短暂冻结并排空旧写；确认 CDC watermark 追平后原子提升 route_epoch
5 回滚窗口          新 cell          新 cell         高
  向旧侧做同样可重放的反向复制；旧侧只用于受控回滚，不能同时接收独立写
6 收尾             新 cell          新 cell         不可逆
  关闭反向复制；按保留与合规策略归档/删除旧副本
```

（表里两个词：**CDC**（change data capture）= 直接读源库的事务日志，把行级变更源源不断地搬到新 cell，见 [`01/03`](../01-building-blocks/03-messaging-and-streams.md)；**影子读 shadow read** = 把线上读请求复制一份也打到新 cell，结果只拿来比对、不返回给用户。）

**版本栅栏（fencing）是第 4 步的关键**：切写瞬间必须保证旧 cell 上没有“飞行中”的写。路由映射带单调递增的 `route_epoch`；**存储写入必须原子校验 `tenant_id + target_cell + route_epoch`，只接受等于当前 epoch 的写**，不能只在 Router 校验，也不能接受“更大的任意 epoch”。旧请求拿到 `409 STALE_EPOCH` 后刷新路由，并用原业务幂等键重试。冻结窗口内先停止分配新写、排空旧写、追平 CDC watermark，再在同一个受一致性保护的映射事务中提升 epoch。没有存储侧 fencing 与 durable repair log，“应用同时写两个库”只能把部分失败变成静默分叉。

**冻结窗口（freeze window）的量级**：p99 写事务时长 × 3 + 路由传播时间。对典型 OLTP 是 **1–5 秒**；如果你的系统里有长事务或长连接（WebSocket、SSE、Agent 会话），冻结窗口会被拉到分钟级 —— 这时要么做优雅排空（drain：先不再往它上面分配新请求，等已有请求和长连接自然结束，再真正下线），要么接受这些连接被断开重连。

## 6. Cell 级部署与金丝雀

Cell 化真正的红利在这里：**部署本身变成了可以分批的、爆炸半径可控的操作**。

```
波次   目标                     观察时长    通过条件
──────────────────────────────────────────────────────
W0    sandbox cell（无真实租户）  30 min    合成流量全绿
W1    canary cell（内部+志愿租户） 24 h      覆盖完整日周期（含夜间批处理）
W2    1 个生产 cell               4 h       SLI 无回归
W3    N/4 个 cell                 2 h       ——
W4    剩余                        ——        ——
```

**bake time（新版本上线后“静置观察”、不推进下一批的时长）要覆盖相关业务周期与足够样本**。日常流量可至少覆盖峰谷，定时任务、月结和时区边界则要靠定向测试/合成探针并跨过对应周期；“固定 24 小时”既可能不足，也可能对低风险变更过度。W1 的时长应由风险和可观测证据决定。

**回滚的第一原则：恢复路径应比继续扩大影响更快、更确定。** 回滚不应依赖重新构建；上一版镜像/配置应预先存在并演练。单 cell < 5 分钟、全量 < 30 分钟可作为示例目标，实际值由 SLO、数据兼容性与部署规模确定。

⚠ **数据库迁移打破了这个模型**：schema 变更不能按 cell 回滚（每个 cell 有自己的库，但代码是同一份）。解法是六步法的扩展/收缩模式（expand/contract，见 [05-release-engineering.md](05-release-engineering.md)）—— 任何一次发布中，**代码必须同时兼容变更前后的两个 schema 版本**。

## 7. 控制面自己挂了会怎样（必答题）

面试官问这题时，在等的不是"我们有 3 副本高可用"，而是**分级的降级（graceful degradation）清单**。

| 能力 | 控制面挂时 | 实现要求 |
|---|---|---|
| 存量租户读写 | ✅ 完全正常 | 路由映射本地落盘（L1） |
| 现有 API key 认证 | ✅ 正常 | JWT（一段自带签名的令牌，服务端用公钥当场就能验真伪并读出里面的租户与权限）本地验签，公钥缓存 ≥ 24h；不要每次调 introspection（每次都反过来问认证服务"这个 token 现在还有效吗"） |
| 限流/配额 | ✅ 用本地令牌桶（token bucket）降级 | 本地桶 + 周期同步；控制面挂 = 停止同步，按最后一次配额继续跑 |
| 自动扩缩 | ⚠ 冻结在当前容量 | 这就是为什么容量要走 L2（预留） |
| 新租户开通 | ❌ 排队 | 请求进持久队列（durable queue），恢复后按幂等键重放（replay） |
| 配置变更 | ❌ 排队 | 同上 |
| 密钥轮换 | ⚠ 有窗口 | 证书剩余有效期 **≥ 控制面最坏恢复时间 × 3**；典型：90 天证书在剩 30 天时开始轮换 |
| 计费出账（invoicing） | ✅ 事件继续落盘 | 计量（metering）事件只依赖数据面本地磁盘 + 消息总线（见下一篇） |

**控制面自身的 HA 设计**：

- 控制面的状态存储用**单一强一致的库**（Postgres/Spanner/etcd），不要为了"高可用"做成最终一致 —— 配置脑裂比配置不可写危险得多。
- 控制面**可以**是单区域的。这是一个合法且常见的选择：数据面多区、控制面单区 + 跨区异步备份 + RTO 30 分钟。前提是 §1 那条铁律成立。
- 控制面必须有**紧急旁路（break-glass）**：一条不经过控制面正常逻辑、直接改底层存储的、有审计的运维通道。没有它，控制面的 bug 会变成不可恢复的事故。

## 8. 配置分发：推还是拉

| 维度 | 推（Push） | 拉（Pull） |
|---|---|---|
| 传播延迟（propagation delay） | 秒级 | 轮询周期（5–60s）或 long-poll 后秒级 |
| 控制面负载 | O(变更数) | O(实例数 / 周期)，**10 万实例 × 30s 轮询 = 3,300 QPS 常态压力** |
| 新实例启动 | 需要注册 + 等推送 | **天然正确**（启动即拉） |
| 控制面挂掉 | 已推的还在，新实例拿不到 | 靠 last-known-good 落盘 |
| 扇出（fan-out）风险 | **一次坏配置瞬间打穿全部实例** | 轮询天然错峰，且易于按比例灰度（progressive rollout） |

**主张：拉 + 内容寻址（content-addressed）+ 长轮询（long polling）。** 具体形态：

```
控制面写：  s3://config/{env}/bundle-{sha256}.json.zst   （不可变）
           s3://config/{env}/pointer.json → {"version":"sha256:ab3f…","rollout":{"cell-3":100,"cell-4":10}}
数据面读：  每 15s 带 ETag GET pointer.json（命中 304，几乎零成本）
           版本变化 → 拉 bundle → 校验签名 → 校验 schema → 原子替换 → 写本地 last-known-good
回滚：      把 pointer 指回上一个 sha256。**回滚是改指针，不是重新发布配置。**
```

（三个词：**内容寻址 content-addressed** = 文件名就是文件内容的哈希，内容一改文件名必然改 —— 于是同一个名字永远对应同一份字节，缓存和回滚都不再有歧义。**长轮询 long polling** = 客户端发一个请求，服务端先挂着不返回，直到有变化或到超时才回，于是用普通 HTTP 拿到了接近推送的时效。**ETag / 304** = 服务端给资源的当前版本一个标识，客户端下次带着它来问，没变就只回一个 304、正文一个字节都不传。）

四条硬要求：

1. **配置必须版本化且不可变**。"改一下线上那个值"是配置事故的标准起手式。
2. **配置必须过 schema 校验和签名**。数据面拿到不合法配置时要**拒绝加载并保留旧配置**，而不是加载后崩溃。配置格式错误导致的全站宕机是行业里最经典的故障类型之一。
3. **灰度按 cell/ring 做，不按随机比例做**。随机比例的 10% 会均匀地打到所有 cell，等于没有爆炸半径控制。
4. **配置变更要和代码发布走同一套金丝雀纪律**。绝大多数团队对代码发布有 5 道关卡，对配置变更有 0 道 —— 而配置事故的频率更高。

## 9. 容量控制回路的稳定性

自动扩缩是一个负反馈控制系统（negative feedback control loop）。绝大多数生产上的"自动扩缩把系统搞挂了"，根因是**控制周期短于系统响应时间**，形成了正反馈震荡（oscillation）。

```
关键时间常数：
  T_s  采样/决策周期
  T_a  执行生效时延 = 调度 + 拉镜像 + 启动 + 预热 + 进 LB
        容器（镜像已缓存）        5–30 s
        VM / 新节点              60–180 s
        GPU 节点（含权重加载）    3–10 min   ← 见 04-ai-agent-systems/01-llm-serving-infra.md
不要把稳定条件简化成 `T_s ≳ 2–3 × T_a`：采样可以远短于 `T_a`，否则会错过突发；真正需要约束的是**动作节奏**。在上一次扩缩动作尚未可观测地生效前，不发出方向相反的动作；扩缩 cooldown / stabilization horizon 至少覆盖实测 `T_a`，并把 pending capacity 计入下一次决策。
```

`T_a` 这段空窗就是**冷启动（cold start）**：从"决定扩容"到"新实例真的能接流量"之间的时间，由拉镜像、进程启动、缓存/权重预热、健康检查通过、进 LB 这几段串起来。
**它是结构性的，不是可以优化掉的** —— 这一节剩下的全部内容，都是在处理"决策比生效快得多"这一个事实。

**必须有的四个阻尼机制：**

| 机制 | 参数（可直接抄） | 作用 |
|---|---|---|
| **死区（deadband）/ 滞回（hysteresis）** | 示例起点：扩容阈值 70%、缩容阈值 40%，中间不动 | 消除阈值附近的抖动；阈值须按 workload 压测 |
| **冷却窗口（cooldown window）** | 示例：扩容动作去重窗口覆盖实例可见前的主要阶段；缩容稳定窗口可从 300–600s 起压测（具体默认值随控制器版本而变） | 不重复计算 pending capacity；缩容比扩容更保守 |
| **信号平滑（signal smoothing）** | 对指标做 EWMA（指数加权移动平均：越新的采样权重越大，于是既平滑又不迟钝，α≈0.2）或取滚动窗口的 **p95 而不是瞬时值** | 抑制毛刺触发 |
| **速率限制（rate limiting）** | 单次最多 ±30% 或 ±N 实例；设死 `min/maxReplicas` | 防止一次误判把集群拉到天上（或归零） |

HPA 常见配置会设置约 10% 的 tolerance（具体默认值与可配置性以所用 Kubernetes 版本为准），即目标附近不动作。这本身就是一个死区。自研控制器时忘了加死区，是震荡的高频原因。

**GPU 推理服务的特殊结论**：`T_a` 是 3–10 分钟，而流量尖峰的上升沿是秒级。**这意味着 LLM 服务在结构上无法靠自动扩缩追流量。** 正确的组合是：预留容量（reserved capacity，L2 静态稳定）+ 请求队列 + 准入控制（admission control：队列里的等待时间已经超过阈值就直接拒绝新请求）/ 负载卸载（load shedding：优先拒掉低优先级流量，保住高优先级的，见 [`00/01 §6`](../00-foundations/01-fundamentals.md#6-背压backpressure没有它系统就会雪崩cascading-failure)）+ 降级到小模型。把 HPA 当作 LLM 容量方案是一个会在第一次上热搜时暴露的错误。

**扩缩容与计费的耦合**：自动扩缩的目标函数应该写成成本约束下的 SLO 满足，而不是纯利用率。一个实用的护栏（guardrail）是给每个 cell 设 `max_hourly_spend`，控制回路在接近上限时**先降级功能再拒绝扩容**，而不是无声地把账单翻倍。

## 10. 什么时候不要这么做

| 情况 | 别做 | 做什么 |
|---|---|---|
| 租户 < 100，单区域，团队 < 15 人 | 不要 cell 化 | 单个部署单元（deployment unit）+ 良好的分片键（shard key：决定一行数据落到哪个分片的那个字段，见 [00-concepts §5](../00-foundations/00-concepts.md#5-副本分片分区--三个被混用的词)）设计。cell 化的固定成本（部署编排、迁移工具、N 套监控）在这个规模下是纯负担 |
| 业务天然跨租户协作 | 不要强行按 tenant_id 分 cell | 按协作单元分；或该子系统不 cell 化 |
| 只是想"提高可用性" | 不要用 cell 化当理由 | **AWS 官方文档没有做"cell 化 ⇒ 更高 SLA"的推导**。它承诺的是爆炸半径和恢复时间。不要在 SLA 承诺里写"因为 cell 化所以 99.99%" |
| 期望态频繁被外部改写 | 不要用 reconcile 循环 | 如果外部系统会持续改动你管理的资源，reconcile 会和它打架（flapping：两个系统互相把对方的改动改回去，无限来回，两边的日志都显示"我在正常工作"）。先解决所有权问题 |
| 需要毫秒级生效的配置 | 不要用拉模型 | 那不是配置，是数据。走数据面的正常路径（消息总线/数据库） |
| GPU 密集服务 | 不要指望 HPA | 预留 + 队列 + 卸载 |

**反模式（anti-pattern）速查：**

1. **控制面进入数据面关键路径。** 最隐蔽的形式是"每次请求查一下租户配置"，看起来是本地 Redis，实际上 Redis 的数据由控制面同步 —— 控制面挂了 60 秒后 TTL 过期，全站 500。
2. **把 reconcile 写成有状态的增量处理。** "收到 update 事件 → 只改变化的字段"。丢一个事件就永久不一致，且无法自愈。
3. **一个 cell 里放"共享服务"。** 一旦 cell-1 里的某个服务被 cell-2 调用，你就不是 cell 架构了，你是一个有额外部署复杂度的单体。
4. **cell 之间复制数据。** Cell 是完整独立副本，不是分片 + 复制。要复制就说明分区键选错了。
5. **用随机比例做配置灰度。** 见 §8。
6. **缩容和扩容用同一个冷却窗口。** 缩错的代价远大于扩错。
7. **没有迁移工具就上 cell 架构。** 第一个 cell 满的那天你会发现自己没有退路。迁移工具必须和 cell 架构**同期**建设，而不是"以后再说"。
8. **控制面没有 break-glass 通道。** 控制面的 bug 会变成不可恢复事故。

---

## 这一章的三句话

1. **控制面挂掉只该影响明天的收入，不该影响今天的收入。** 数据面在请求路径上对控制面的任何一次同步调用，都是在抹掉这条界限 —— 而最隐蔽的那种同步调用长得像"读一下本地 Redis"。
2. **带 TTL 的缓存不是静态稳定，它只是把故障推迟到 TTL 到期的那一秒，还顺手把"控制面挂了"升级成"全站挂了"。** 真正的静态稳定必须能用一份过期的、落盘的 last-known-good 无限期工作下去。
3. **Cell 化不自动提高可用性，它把“全挂”换成“一个部署单元挂”。** `1/K` 只是租户均匀时的名义值；真正要报的是流量、MAU 与 ARR 加权后的最大 cell 占比，而且迁移工具必须已经可用。

## 面试官会追问

1. 定义控制面和数据面的边界。你的数据面现在有哪几处同步依赖控制面？怎么去掉？
2. 控制面完全不可用 30 分钟，逐项说明哪些能力受影响、哪些不受影响。
3. reconcile 循环为什么必须是 level-triggered？丢一个事件会怎样？
4. 两个 worker 同时 reconcile 同一个租户会发生什么？你怎么防？
5. 租户开通到第 5 步失败了，怎么回滚？哪些步骤不能补偿删除，为什么？
6. 你有 8 个 cell，爆炸半径是多少？（→ 答 1/8 的直接扣分，要问租户分布）
7. 一个租户大到装不进任何 cell，怎么办？
8. 跨 cell 迁移怎么保证不丢写？fencing 是怎么做的？
9. 配置推还是拉？10 万个实例的场景下各自的成本是多少？
10. 自动扩缩把系统搞震荡了，你怎么定位和修？给出具体参数。
