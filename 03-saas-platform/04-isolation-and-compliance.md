# 04 · 隔离（isolation）与合规（compliance）

> 合规不是发布前补的一份文档，是一组**在架构上不可逆的约束**。
> 如果你的"删除用户数据"要靠人工跑 SQL，你的"数据驻留"只覆盖数据库不覆盖日志，那你没有合规，你只有一张过期的报告。

---

## 读这一章之前

**你在工作中遇到过这个**

一个欧洲客户在采购的最后一轮问"我们的数据会不会离开欧盟"。你说不会 —— 数据库、对象存储、备份都在法兰克福。
合同签完三个月后，他们的 DPO 拿着一张 Sentry 截图来问：为什么一条带着客户姓名和邮箱的错误堆栈，出现在一个部署在美国的错误追踪服务里。
你回去数了一遍：日志、指标、错误追踪、事务邮件、支持工单、LLM 推理端点 —— 六个系统全在美国，而且没有任何一个，在当初画那张架构图时被画进去过。

**需要先懂的概念**

| 概念 | 一句话 | 详见 |
|---|---|---|
| 副本 / 备份 / 快照 | 同一份数据的多个完整拷贝；备份和快照是你无法逐行遍历、却真实存在的那几份 | [00-concepts §5](../00-foundations/00-concepts.md) |
| 缓存与命中率 | 把算过的结果暂存在快的地方；命中率既决定它值多少钱，也决定它挂掉时后端要扛几倍流量 | [00-concepts §11](../00-foundations/00-concepts.md) |
| 租户隔离的四个级别 | 独立实例 / 独立库 / 独立 schema / 共享表加 tenant_id —— 隔离越强，成本越高 | [02/03 §1](../02-architecture-patterns/03-multi-tenancy.md) |
| 控制面 / 数据面 | 改变系统期望状态的那一半 vs 处理最终用户请求的那一半 | [03/01 §1](01-control-plane.md) |
| 事件与重放 | 事件可以被重新消费一遍来重建下游状态，这是"删除要传播到派生数据"能成立的前提 | [01/03](../01-building-blocks/03-messaging-and-streams.md) |

**这一章要回答的问题**

1. 客户要求"数据不出欧盟"，你的系统里哪些地方会违反它 —— 而它们通常一个都不在架构图上？
2. 用户行使删除权，主库好办，7 份快照和跨区备份里的那一份怎么删？你怎么向他**证明**删干净了？
3. 静态加密到底防住了谁、没防住谁？既然它挡不住最常见的泄露路径，为什么还必须开？
4. 共享 prefix cache 能带来数十倍的首字延迟改善，为什么跨租户还是要默认关掉它？这个决定该由谁拍板？

**本章新引入的术语**

| 术语 | English | 一句话定义 |
|---|---|---|
| 数据驻留 | data residency | 数据必须存放或处理在某个国家/地区之内的合同或法律约束 |
| PII / PHI | personally identifiable information / protected health information | 能定位到具体某个自然人的信息 / 受美国 HIPAA 保护的健康信息 |
| 派生数据 | derived data | 从原始数据算出来的副产品（搜索索引、向量、报表、缓存）；删掉原始数据它不会自己消失 |
| 信封加密 | envelope encryption | 用一把不出安全硬件的密钥，去加密另一把真正用来加密数据的密钥 |
| KEK / DEK | key encryption key / data encryption key | 前者只用来加密后者；后者才直接加密业务数据 |
| 字段级加密 | field-level encryption | 在应用里把单个字段加密后再存库，数据库自始至终只看到密文 |
| 盲索引 | blind index | 把字段的固定哈希存到另一列，用它支持等值查询，同时不暴露原值 |
| 密钥销毁式删除 | crypto-shredding | 销毁密钥，让所有密文（包括你根本遍历不到的备份）在同一瞬间变成不可解密的字节 |
| 墓碑事件 | tombstone | 一条"这个东西被删了"的事件，广播给所有持有派生数据的下游，让它们各自清理并回执 |
| WORM 存储 | write-once-read-many | 写进去之后，在保留期内任何人（包括最高权限账号）都无法修改或删除 |
| 侧信道 | side channel | 不直接读数据，而是从耗时、顺序、资源占用这类间接现象反推出内容的攻击方式 |
| DSAR | data subject access request | 个人依法要求你列出"你手上关于我的全部数据"的请求 |

## 1. 把合规翻译成架构约束

审计师问的每一句话，背后都是一个架构组件。**先建组件，证据是副产品**；反过来做（先写策略再补实现）会在每次审计前重复付出人力成本。

**三个可量化的判据**（用来判断你是"真合规"还是"纸面合规"）：

1. **删除 SLA**：从收到删除请求到所有副本（含备份、索引、派生数据 derived data）不可恢复，需要多久？能否**自动**产出完成回执？
2. **数据流图（data flow diagram）的完整性**：能否在 5 分钟内列出某个租户的 PII 经过的**全部**系统，包括第三方？
3. **审计证据的可查询性**：审计师问"2026-03-14 谁访问了租户 X 的数据"，多久能回答？是查日志还是查产品功能？

答不上来的那一条，就是你下一个季度的工程重点。

## 2. 数据驻留与区域化架构

**数据驻留（data residency）不是一个开关，是三个独立开关**：**存储在哪 / 处理在哪 / 缓存在哪**。合同和架构图都要分开画。

```
                ┌────────────── 全局层（最小元数据集）──────────────┐
                │ directory:      hash(email) → home_region         │
                │ slug_registry:  org_slug / custom_domain → region │
                │ billing_index:  tenant_id → region, plan          │
                │ ⚠️ 不含 PII 明文、不含任何业务数据                  │
                └───────────────────┬──────────────────────────────┘
                                    │ 只在注册 / 登录 / 路由时读
     ┌──────────────────────────────┼──────────────────────────────┐
     ▼                              ▼                              ▼
┌── EU (Frankfurt) ──────┐  ┌── US (Virginia) ───┐  ┌── AP (Tokyo) ────┐
│ 主库 / 对象存储        │  │ …                  │  │ …                │
│ 搜索索引 / 向量索引    │  │                    │  │                  │
│ 审计日志 / 备份 / 数仓 │  │                    │  │                  │
│ KMS（EU 独立 KEK）     │  │ KMS（US 独立 KEK） │  │                  │
│ LLM 推理端点（区域内） │  │                    │  │                  │
└────────────────────────┘  └────────────────────┘  └──────────────────┘
```

### 三个必须解决的工程问题

**(a) 用户如何被路由到自己的 region？**
登录时要先知道 region 才能路由，但 region 存在用户记录里 —— 鸡生蛋。解法是一个**全局目录（global directory）**：`hash(email) → home_region`。只存**哈希**（HMAC，密钥在 KMS），不存明文邮箱，这样全局层本身不构成跨境传输 PII。

**(b) 全局唯一性怎么办？**
`org_slug`、自定义域名、邮箱这类需要全局唯一（globally unique）的标识符，无法在每个 region 独立分配。两条路：

| 方案 | 做法 | 代价 |
|---|---|---|
| **中心化 claim 服务** | 一个全局的唯一性登记表，注册时两阶段：先 claim（TTL 10 min 的预留），成功后在 region 内创建 | 全局层成为注册路径上的依赖；需要清理过期 claim |
| **把 region 编进标识符** | `acme.eu.app.com`、`tenant_eu_a1b2` | 用户体验差；跨区迁移会改 URL；但**完全无全局依赖** |

**默认选中心化 claim 服务**，因为它只在注册这一个低频路径上，且可以做到"全局层挂了不影响已有租户"。

**(c) 跨区功能怎么处理？**
"和另一个 region 的用户协作"、"全局搜索"、"全公司 dashboard" 这类需求，唯一诚实的答案是：**要么不做，要么把它明确降级成"只跨区传元数据不传内容"**。任何在跨区通道上传业务内容的设计，都会在第一次 DPIA（Data Protection Impact Assessment，数据保护影响评估：GDPR 要求在高风险的数据处理上线之前做的一份书面风险评估）评审时被打回。

> **反模式**：把 region 做成部署参数而不是数据模型的一部分。等到第一个欧洲大客户要求 EU-only 时，你会发现日志、指标、错误追踪（Sentry）、邮件服务、支持工单系统全都在美国 —— 这些系统里全是 PII。**数据流图要在写第一行代码之前画。**

## 3. 加密：三层，各自解决不同的威胁

| 层 | 防谁 | 现状 | 成本 |
|---|---|---|---|
| **传输加密（encryption in transit，TLS 1.3）** | 网络窃听、中间人（man-in-the-middle） | 已是默认；内网也要（零信任）；mTLS 用于服务间 | 忽略不计 |
| **静态加密（at-rest）** | 磁盘被物理拿走、云厂商运维误操作 | 云盘/对象存储默认开；**它挡不住"应用被攻破"这个真实威胁** | 忽略不计 |
| **字段级 / 应用层加密（field-level encryption）** | 数据库被拖库（data exfiltration）、DBA 越权、云厂商内部人 | 真正有价值的一层，但代价大 | **高** |

**关键认知**：静态加密（EBS/S3 加密）在合规问卷上打勾很容易，但它对最常见的泄露路径（SQL 注入、越权 API、凭证泄露）**完全无效** —— 因为应用有权解密。真正提升安全等级的是字段级加密 + 密钥与应用分离。

### 字段级加密的真实代价

| 能力 | 明文 | 确定性加密（deterministic） | 随机化加密（randomized） |
|---|---|---|---|
| 等值查询（equality query） | ✅ | ✅（但泄露频率分布） | ❌ |
| 范围查询（range query）/ 排序 | ✅ | ❌ | ❌ |
| 模糊搜索 | ✅ | ❌ | ❌ |
| 唯一约束 | ✅ | ✅ | ❌ |
| 抗频率分析（frequency analysis） | — | ❌ | ✅ |

**实用折中：盲索引（blind index）**。存 `HMAC(key, normalize(value))` 到一个单独的索引列，用于等值查询；真实值用随机化加密存另一列。范围查询就放弃 —— 需要范围查询的字段（时间戳、金额）通常不是需要字段级加密的字段。

> 保序加密（OPE）和"可搜索加密"在生产里基本是陷阱：它们泄露的信息量足以在有辅助数据集时重建明文。**不要在这上面创新。**

## 4. 密钥管理：信封加密（envelope encryption）、BYOK/HYOK、轮换（key rotation）

**KMS**（Key Management Service）是云上托管的密钥管理服务，**HSM**（Hardware Security Module，硬件安全模块）是一台专用的密码硬件。两者的共同点是这一节的前提：**密钥可以在里面参与加解密运算，但密钥材料本身永远不被导出**。

```
KMS / HSM
  └─ KEK（Key Encryption Key，每租户或每区域一把，永不离开 HSM）
       └─ DEK（Data Encryption Key，加密后与数据同行存储）
            └─ ciphertext
```

**信封加密的意义在于轮换成本**：

| 轮换对象 | 操作 | 复杂度 | 耗时（100 万条记录量级） |
|---|---|---|---|
| **KEK** | 重新包裹所有 DEK | O(DEK 数量) | 秒~分钟 |
| **DEK** | 重新加密所有数据 | O(数据量) | 小时~天 |

⇒ **DEK 的粒度（granularity）决定了一切**。每租户一把 DEK 是甜点（sweet spot）：轮换成本可控，且**撕掉一把 DEK 就等于删除一个租户的全部数据**（见 §5）。每记录一把 DEK 只在极高敏感场景（医疗影像、支付凭证）才值。

**轮换节奏**（合规常见要求，非法律强制）：KEK 每年，DEK 每 1–3 年或事件驱动（怀疑泄露、员工离职、租户要求）。**做不到就不要写进政策文档** —— 审计师会要证据。

### BYOK / HYOK / 租户密钥

| 模式 | 密钥物理位置 | 客户能单方面吊销吗 | 你的可用性风险 | 谁会买 |
|---|---|---|---|---|
| **平台托管（platform-managed）**（默认） | 你的 KMS | 否 | 无 | 90% 客户 |
| **BYOK** | 你的 KMS，但密钥材料由客户导入 | 有限（要走你的流程） | 低 | 中大型企业 |
| **CMK / 客户账户密钥** | **客户自己的云 KMS**（跨账户授权） | ✅ 是 | **高**：客户误撤权限 = 该租户全站不可用 | 金融、医疗 |
| **HYOK / External Key Store** | 客户自建 HSM，每次解密都要回调 | ✅ 是 | **极高**：客户 HSM 的可用性成为你的 SLA 上限；每次解密加 5–50ms | 极少数，但单价最高 |

**工程结论**：BYOK 是性价比最高的档位 —— 满足了大多数采购问卷，且密钥仍在你的可用性域（availability domain）内。**上 HYOK 之前先算清楚**：它把你的 p99 和可用性绑到客户的基础设施上，且必须有本地缓存 DEK 的策略（缓存多久 = 客户吊销后你还能读多久，这个数字要写进合同）。

## 5. Crypto-shredding：把"删除"变成一个可执行、可证明的操作

**问题**：GDPR Art.17 要求删除，但你的数据在主库、只读副本（read replica）、7 份快照、跨区备份、搜索索引、向量索引、数仓、CDN、第三方 SaaS 里。物理删除是不可能完成的任务。

**解法**：每租户（或每用户）一把 DEK。删除 = **销毁 DEK**。所有密文在同一瞬间变成不可解密的随机字节，包括你根本无法遍历的备份。

```
DELETE tenant:acme
  ├─ ① 撕 DEK（KMS schedule_key_deletion，7–30 天等待期后不可逆）
  │    ⇒ 主库 / 备份 / 快照 / 对象存储 一次性全部失效
  ├─ ② tombstone 事件广播 → 派生数据消费者
  │    ├─ 搜索索引（Elasticsearch）：delete_by_query
  │    ├─ 向量索引：删 namespace / 按 tenant_id 过滤删除
  │    ├─ 数仓：分区删除 + 重跑受影响的物化视图
  │    ├─ CDN：purge by surrogate key `tenant-acme`
  │    └─ 第三方：调各家删除 API（有的没有 API —— 提前查）
  ├─ ③ 每个消费者回 ACK，编排器收齐后产出**删除完成回执**
  └─ ④ 审计日志本身**保留**（法定义务优先于删除权），但脱敏
```

### 五个最常被忘掉的地方

1. **Embedding 是派生 PII**。一段包含姓名和病史的文本的向量，虽然不可直接读，但可被反演（model inversion）到相当程度。**必须进删除清单。**
2. **搜索索引里存了原文的 `_source`**。删主库不删索引 = 数据还在。
3. **日志与错误追踪**（Sentry / Datadog）里的 request body。默认保留 15–90 天，且通常在另一个区域。
4. **第三方模型侧的 prompt cache**（见 §8）。这是你控制不了的一段，必须**写进 DPIA 而不是假装不存在**。
5. **审计日志**。它不能删（法定保留期），但它也是 PII 载体 —— 正确做法是审计日志用**独立的密钥体系**，字段级脱敏（redaction），保留期到了统一销毁。

> **面试金句**：
> "客户说'删除我的数据'，我第一件事是问'删除哪一层'。我们的答案分三层给：控制面 24 小时内标记不可访问；数据面靠 crypto-shredding —— 撕掉该租户的 DEK，主库、7 份快照、跨区备份在同一秒全部变成不可解密的字节，这是我们唯一能对**备份**做出的诚实承诺；派生数据（搜索索引、embedding、数仓）走独立的 tombstone 队列，SLA 30 天并有机器生成的完成回执。唯一不能承诺立即清除的是第三方模型侧的加密 prompt cache，上限约 24 小时 —— 这一条我们写进 DPIA 和 DPA，而不是藏起来。"

## 6. 审计日志：产品功能，不是 debug 日志

**第一条纪律：审计日志必须与应用日志物理分离。** 应用日志会采样、会因为成本被砍保留期、会被工程师随手改格式。审计日志是**合规证据 + 企业客户要买的产品功能**，它不采样、不丢、schema 有版本、有独立的保留策略。

### 必记字段（缺一项就会在事故复盘时后悔）

| 字段 | 说明 |
|---|---|
| `event_id` | 全局唯一，幂等去重用 |
| `ts` + `trace_id` | 时间 + 与分布式追踪关联 |
| `actor` | 谁执行（user / service_account / **agent**） |
| `on_behalf_of` | **代表谁**（Agent 场景必需，对应 RFC 8693 的 `act`/`sub`） |
| `tenant_id` | 分区键 |
| `action` + `resource` | 动作 + 资源（含类型与 ID） |
| `decision` + `reason` | allow/deny + **依据哪条关系/策略**（授权决策要落审计！） |
| `source_ip` / `user_agent` / `region` | 来源 |
| `before` / `after` | 变更类事件的前后值（敏感字段脱敏或只存哈希） |
| `outcome` | success / failure / partial |

### 不可篡改性（tamper-evidence）

```
h_0 = H(genesis)
h_n = H(h_{n-1} ‖ canonical(record_n))     ← 哈希链
每小时把 h_head 锚定到独立系统（另一账号的 WORM 桶 / 时间戳服务）
```

存储用 **S3 Object Lock（compliance mode）** 或等价物：**在保留期内连 root 都无法删除**。这是"不可篡改"唯一能通过审计的实现方式；应用层的"只读表"不算。

### 保留期（retention period）与查询性能

| 场景 | 常见保留期 |
|---|---|
| SOC 2 证据 | ≥ 1 年（通常 13 个月覆盖审计窗口） |
| HIPAA | **6 年** |
| 金融类 | 5–7 年 |
| 产品功能（客户可查） | 90 天热 + 更长冷 |

查询模式几乎永远是 `(tenant_id, time_range, [actor|resource])`。⇒ **按 `tenant_id` 分片 + 按月分区 + 列存（columnar storage）**（ClickHouse / Iceberg + 查询引擎）。热数据 90 天在线，冷数据落对象存储。
**容量估算（capacity estimation）**：每条审计事件约 1–2 KB（含 before/after 可到 5 KB）。1 万租户 × 平均 500 事件/天 × 1.5 KB ≈ **7.5 GB/天 ≈ 2.7 TB/年**（压缩后约 1/8）。这个数量级下不要用 Postgres 存审计日志。

## 7. 合规要求 → 架构组件映射表

这张表是本篇的核心交付物。左边是审计师/客户问卷的原话，右边是你必须已经有的东西。

| 合规要求 | 典型出处 | 架构组件 | 可提交的证据 |
|---|---|---|---|
| 最小权限（least privilege）/ 访问控制 | SOC 2 **CC6.1**、ISO 27001:2022 **A.5.15**、HIPAA §164.312(a)(1) | 集中式 PDP（ReBAC/ABAC）+ JIT 提权（just-in-time elevation）+ 默认拒绝（default deny） | 授权决策日志、角色→权限矩阵导出 |
| 用户去配置 | SOC 2 CC6.2/CC6.3 | **SCIM 端点** + token TTL ≤15 min + 会话版本号 | SCIM 事件日志 + 失效时间分布 |
| 变更管理（change management） | SOC 2 **CC8.1**、ISO A.8.32 | PR 强制审批 + CI 门禁 + 部署标记 + 不可绕过的流水线 | commit → PR → 部署记录的关联链 |
| 加密（传输/静态） | HIPAA §164.312(a)(2)(iv)、ISO A.8.24 | TLS 1.3 + KMS 信封加密 + 字段级加密（PHI/PII） | KMS 配置快照、TLS 扫描报告 |
| 审计与监控 | SOC 2 **CC7.2**、HIPAA §164.312(b) | 独立审计日志 + 哈希链 + WORM + 告警规则 | 日志样本 + 保留策略 + 篡改检测报告 |
| 数据删除权 | GDPR **Art.17** | Crypto-shredding + tombstone 编排器 + 完成回执 | 删除工单的 SLA 报表 |
| 数据可携权（data portability） | GDPR **Art.20** | 结构化导出 API（JSON/CSV，含派生数据说明） | 导出样例 |
| 数据主体访问（DSAR） | GDPR **Art.15**（1 个月，可延 2 个月） | 跨系统的 PII 索引 / 数据目录 | DSAR 响应时长统计 |
| 泄露通知（breach notification） | GDPR **Art.33（72 小时）**、HIPAA（**60 天**） | 事件响应流程 + 完整数据流图 + 影响面查询能力 | 演练记录、事件时间线 |
| 子处理者（subprocessor）披露与变更通知 | GDPR **Art.28** | 供应商登记表 + DPA 归档 + 变更前 ≥30 天通知机制 | 公开的 subprocessor 列表页 + 通知记录 |
| 跨境传输（cross-border transfer） | GDPR Ch.V（SCCs / 充分性认定） | Region 路由 + 全局层只存哈希 + 传输影响评估 | 数据流图 + TIA 文档 |
| 数据驻留承诺 | 客户合同 | 存储/处理/缓存**三个独立开关** + 区域化推理端点 | 区域配置导出 |
| 业务连续性（business continuity） | SOC 2 **A1.2**、ISO A.5.29 | 跨区备份 + 定期恢复演练（recovery drill，**演练才算证据**） | 恢复演练报告（RTO/RPO 实测值） |
| 漏洞管理（vulnerability management） | SOC 2 CC7.1、ISO A.8.8 | 依赖扫描（dependency scanning）+ SBOM + 分级 SLA + KEV 优先 | 漏洞老化报告 |
| **AI 透明度** | **EU AI Act Art.50** | 与 AI 交互的显式告知 + 合成内容（synthetic content）机器可读标记 | UI 截图 + 水印（watermarking）实现说明 |
| **AI 留痕（audit trail）** | EU AI Act（记录保存）+ SOC 2 审计师新期望 | 模型版本 / prompt 模板版本 / 检索文档 ID / 工具调用参数与结果 / 授权决策 **全落审计日志** | 单次会话的完整可复现 trace |
| **AI 人工监督（human oversight）** | EU AI Act Art.14、Five Eyes 指南 | 高影响动作**静态清单** + 审批链路 + 审批记录 | 清单文档 + 审批日志 |
| **AI 供应商管理** | GDPR Art.28 + 审计师期望 | 模型供应商 DPA + ZDR 条款 + 区域承诺 | 合同条款摘录 |

**注意**：SOC 2 在 2026 年**没有出 AI 专章** —— AICPA 现行仍是 2017 TSC + 2022 修订的 points of focus，五大准则未变。变化的是**审计师的期望**：模型注册表（model registry）访问控制、模型/prompt 变更留痕、供应商 DPA、持续控制监控（continuous control monitoring），都是按现有准则的解释来要的。

## 8. AI 相关合规：2026 年真正在动的那部分

### 8.1 EU AI Act 的实际时间表

Digital Omnibus 于 2026-05 达成临时政治协议并经理事会确认，推迟了部分义务。**关键在于哪些没被推迟**：

| 义务 | 原定 | 现状 |
|---|---|---|
| GPAI（通用模型）义务 | 2025-08-02 起适用 | **已生效**；委员会**调查与罚款权自 2026-08-02** |
| **Article 50 透明度**（与 AI 交互告知、合成内容标记） | 2026-08-02 | **不变**；存量系统水印宽限至 2026-12-02 |
| Annex III 独立高风险 | 2026-08-02 | 推迟至 **2027-12-02** |
| Annex I 嵌入型高风险 | 2027-08-02 | 推迟至 **2028-08-02** |

> **反模式**："AI Act 被推迟了，2026 可以不管。" 只有高风险被推迟。Article 50 和 GPAI 罚款权都在 2026-08-02。
> ⚠️ 在正式刊登 Official Journal 之前，这些日期仍可能微调 —— **落地前查 [European Commission 官方页面](https://digital-strategy.ec.europa.eu/en/policies/regulatory-framework-ai)**。

### 8.2 把 PII 送给第三方模型：四条路径

| 路径 | 做法 | 合规成本 | 质量代价 | 何时选 |
|---|---|---|---|---|
| **不送** | PII 字段在进 prompt 前替换成占位符（placeholder），输出后再回填 | 低 | 中：模型看不到真实实体，某些推理会失效 | 默认起点 |
| **脱敏/假名化（pseudonymization）后送** | NER + 规则识别 → 一致性假名（同一实体映射到同一假名） | 中：需要维护映射表（本身是 PII） | 低~中 | 大多数场景的甜点 |
| **原样送 + 合同保障** | DPA（Data Processing Agreement，数据处理协议）+ ZDR（Zero Data Retention：供应商承诺不留存你送进去的内容）+ 区域内处理 + 子处理者披露 | 中：谈判周期长，但技术上最简单 | 无 | 有企业合同、供应商配合 |
| **本地/私有部署模型** | 自建推理栈或云厂商私有端点 | 高（见下） | 通常有：开源模型能力差一档 | 数据绝对不可出域（医疗、政务、军工） |

### 8.3 供应商侧的三个"以为是这样其实不是"

**(a) "ZDR = 零留存"** —— 错。OpenAI 的零数据保留会排除 abuse monitoring 中的客户内容并强制 `store=false`，但**仍会存储加密的 prompt cache tensors，最长 24 小时**；被 CSAM 扫描标记的图像/文件输入仍会保留。这一条必须写进你的数据流图和 DPIA。

**(b) "存储在 EU = 在 EU 推理"** —— 错，这是两个分开的承诺。OpenAI 可选**存储区域 10 个**（US、EU、AU、CA、JP、IN、SG、KR、UK、UAE），但**"区域内处理"只有 US / EU / UAE 三个**（2026-07 口径）。合同里必须分别写死。
**区域化是有价签的**：Anthropic 的 `inference_geo: "us"` 是 **1.1×** 全项加价；OpenAI 对 2026-03-05 后发布模型的区域化处理是 **+10%**（2026 年中量级，随时变动）。

**(c) "自建推理栈天然多租户安全"** —— 错，且这是本节最重要的一条。

### 8.4 KV cache：最大的性能杠杆，也是最大的跨租户泄露面

[PROMPTPEEK（NDSS 2025）](https://www.ndss-symposium.org/wp-content/uploads/2025-1772-paper.pdf) 实证：共享 prefix cache 造成的**服务顺序/时序侧信道（side channel）**可以逐 token 重建他人的 prompt。

- 已知 prompt 模板时成功率 **99%**；反推模板本身 **98%**；**无任何背景知识 95%**。
- 已知模板时约 **60 次请求**即可套出性别/年龄/体重/身高这类属性。
- 攻击面覆盖 vLLM、SGLang（主要目标）、LightLLM、DeepSpeed；已向厂商披露，ByteDance 已确认该侧信道。

**这与"prefix cache 是 2026 最大的单点性能杠杆"直接冲突**（命中率 hit rate 提升可带来数十倍 TTFT（time to first token：从发出请求到模型吐出第一个 token 的等待时间）改善）。手册的立场是把这个张力显式写出来，而不是假装可以两全：

```
结论：同租户内共享 prefix cache（保留大部分收益）
      跨租户默认关闭（放弃跨租户系统提示共享带来的那部分收益）
      系统提示前缀中禁止出现密钥、PII、租户标识以外的任何敏感内容
```

代价是真实的：跨租户共享的系统提示前缀往往是命中率最高的那部分。**你在这里买的是隔离，卖的是钱和延迟** —— 把这笔账算给业务方看，而不是替他们决定。

**多租户推理的补充措施**：AWS Lambda **Tenant Isolation Mode（GA 2025-11-19）** 是同类思路的产品化 —— 执行环境（Firecracker microVM）**永不跨租户复用，同租户内仍复用**，所以可以安全地缓存租户级配置与凭据。但注意它把冷启动（cold start：请求到达时没有现成可用的热执行环境，必须先把沙箱、依赖、模型权重加载起来，这段额外等待就是冷启动）次数从 O(并发) 变成 **O(租户 × 并发)**：**隔离是免费的，冷启动不是。**

## 9. 数据分类分级（data classification）与 DLP

分级的意义在于：**每一级对应一组自动施加的技术控制**，而不是一张让人自觉遵守的表。

| 级别 | 例子 | 强制控制 |
|---|---|---|
| **L0 Public** | 文档、定价页 | 无 |
| **L1 Internal** | 内部指标、非敏感日志 | 需登录；不出组织 |
| **L2 Confidential** | 客户业务数据、合同 | 租户隔离 + 静态加密 + 访问审计 + 禁止进入非生产环境 |
| **L3 Restricted** | PII / PHI / 支付凭证 / 密钥 | L2 + **字段级加密** + 独立 DEK + 出口 DLP + 禁止进入日志/第三方模型（除非走 §8.2 路径） |

**DLP 的现实**：
- 出口侧正则对**结构化标识符**有效（信用卡 Luhn 校验、SSN、AWS key 前缀），对自由文本 PII 召回率（recall：真正存在的敏感内容里，被成功抓出来的那个比例）低。
- ⇒ **分类必须在写入时打标，而不是在出口时猜**。schema 上标注字段级别，ORM/序列化层根据级别自动决定"能否进日志/能否进 prompt/能否跨区"。
- 最有效的单条控制不是 DLP 引擎，是**结构化日志的字段白名单（field allowlist）** —— 只有显式标记为可记录的字段才进日志，默认不记。

## 10. 渗透测试（penetration test）与漏洞响应

**年度第三方渗透测试**是 SOC 2 与企业采购问卷的标配。多租户 SaaS 的测试范围必须**显式包含租户越权（cross-tenant access）**：

- IDOR（Insecure Direct Object Reference，不安全的直接对象引用）：把 URL 里的 `tenant_id`/`project_id` 换成别人的，服务端没校验归属就返回了
- 串谋（collusion）：租户 A 的低权限用户 + 租户 B 的邀请链接
- 授权绕过（authorization bypass）：直接调内部 gRPC、绕过网关
- **Agent 场景新增**：提示注入导致的跨租户数据访问、MCP server 的凭证隔离

**漏洞响应 SLA**（写进政策并用工单系统度量）：

| 严重度（severity） | 修复 SLA | 触发 |
|---|---|---|
| Critical（CVSS ≥9.0 或已在 [CISA KEV](https://www.cisa.gov/known-exploited-vulnerabilities-catalog)） | **24–72 小时**，必要时紧急发布 | 立即成立事件 |
| High（7.0–8.9） | 7 天 | 排入当前迭代 |
| Medium（4.0–6.9） | 30 天 | 排期 |
| Low | 90 天 / 下次大版本 | 记录 |

**KEV（Known Exploited Vulnerabilities，CISA 维护的"已被实际利用"漏洞清单）优先于 CVSS（Common Vulnerability Scoring System，一套 0–10 的漏洞严重度打分标准）**：一个 CVSS 7.5 但已进 KEV 的漏洞，比一个 CVSS 9.8 但无公开利用的更紧急。

**必备物**：`security.txt`、公开的漏洞披露政策（含 safe harbor 条款）、SBOM（Software Bill of Materials，软件物料清单：列出你的制品里所有依赖及其版本的机器可读文件；SPDX/CycloneDX 是两种通行格式）、依赖扫描进 CI 并对新增 Critical **阻断合并**。

## 11. 什么时候不要这么做（反模式 anti-pattern）

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| **"数据驻留 = 数据不出境"** | 存储合规了，日志/指标/推理/缓存全在别处 | 存储/处理/缓存三个独立开关，分别画图分别写合同 |
| **"ZDR 意味着零留存"** | 加密 prompt cache 仍留 ≤24h，标记文件仍保留 | 写进 DPIA，别在客户问卷里说"零留存" |
| **"vLLM/SGLang 天然多租户安全"** | PROMPTPEEK 已在 SGLang 上实证 | 跨租户 prefix cache 默认关闭 |
| **加密一切字段** | 查询能力归零、性能塌方、密钥管理复杂度爆炸 | 只对 L3 做字段级加密，其余靠访问控制 |
| **物理删除实现"删除权"** | 备份删不掉，永远无法证明完成 | Crypto-shredding + tombstone 传播 |
| **crypto-shredding 忘了派生数据** | embedding / 搜索索引里数据还在 | 删除清单从**数据流图**生成，不是拍脑袋列 |
| **审计日志和应用日志混在一起** | 被采样、被砍保留期、被改 schema | 物理分离 + WORM + 不采样 |
| **留痕按"够用就行"设计** | 第一次审计/事故时发现关键字段没记 | 按"**未来一定会被审计**"设计：模型版本、prompt 版本、检索文档 ID、工具参数与结果、授权决策全落库 |
| **HYOK 卖给第一个提要求的客户** | 你的 SLA 上限被绑到客户的 HSM | 先算延迟与可用性账，DEK 缓存时长写进合同 |
| **合规当作发布前的一次性任务** | 每次审计重复付人力，控制会漂移 | 持续控制监控：把证据采集做成定时任务 |
| **在非生产环境用生产数据** | 最常见的实际泄露原因，且必被审计发现 | 合成数据（synthetic data）/ 假名化导出流水线 |

## 这一章的三句话

1. **合规不是发布前补的一份文档，是一组在架构上不可逆的约束。** 判断你是真合规还是纸面合规只要问三个数：删除 SLA 多久、能不能在 5 分钟内列全一个租户的 PII 流经的所有系统、审计证据是靠人查日志还是点一个产品功能 —— 答不上来的那条就是下个季度的工程重点。
2. **对备份，你唯一能做出的诚实删除承诺是 crypto-shredding。** 物理删除跨不过快照和跨区备份，而销毁 DEK 能让所有你根本遍历不到的拷贝在同一秒失效 —— 代价是 DEK 的粒度必须一开始就按租户切好，事后再切等于重新加密全部数据。
3. **隔离和性能在跨租户 prefix cache 这一处是硬冲突，没有两全。** 你的工作不是替业务方选一个，而是把"跨租户共享每月能省多少钱"和"PROMPTPEEK 已实证的重建成功率"算成两个数摆到桌面上 —— 然后把结论写进 DPIA，而不是写进某个人的记忆里。

## 面试官会追问

1. 客户要求"数据不出欧盟"。列出你系统里所有会违反这一条的地方 —— 至少说出 8 个，包括你不直接控制的。
2. 用户行使删除权。你的删除链路是什么？备份里的数据怎么办？你怎么向客户**证明**删干净了？
3. 为什么静态加密（EBS/S3 加密）对最常见的泄露路径几乎无效？那它为什么还是必须开？
4. BYOK 和 HYOK 的区别是什么？HYOK 会怎样影响你的 SLA？你会在合同里写死哪个数字？
5. 审计日志为什么不能和应用日志放一起？"不可篡改"你打算怎么实现，怎么向审计师证明？
6. 你要把用户输入送给第三方 LLM。列出合规上必须先落地的四件事。
7. 多租户共享 prefix cache 有什么已被证实的风险？你怎么在性能和隔离之间取舍，这个取舍谁来拍板？
8. EU AI Act 在 2026 年对你的系统有哪些**已经生效**的义务？哪些被推迟了？
9. SOC 2 Type II 和 Type I 的区别是什么？为什么"演练报告"比"演练计划"值钱？
