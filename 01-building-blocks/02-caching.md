# 02 · 缓存：从 CPU 到 CDN 到 KV Cache

> 缓存是唯一能同时降低延迟和成本的手段，也是最容易引入正确性 bug 的手段。
> "计算机科学只有两个难题：缓存失效（cache invalidation）和命名。"

## 读这一章之前

**你在工作中遇到过这个**

你给商品详情接口加了一层 Redis，命中率 96%，DB 的 QPS 从 3000 掉到 120，所有人都很满意。
三周后的凌晨两点，一次批量预热让几万个 key 的过期时间落在了同一秒，它们一起失效，
DB 连接池在 200 毫秒内打满，接口全线 504，持续四分钟。
恢复之后更难受：缓存是空的，每个请求都要回源，DB 又被打死一次 ——
系统再也回不到那个"命中率 96%"的稳态，只能靠人工限流一点点把它喂回去。

**需要先懂的概念**

| 概念 | 一句话 | 详见 |
|---|---|---|
| 缓存在优化什么 | 把查过/算过的结果放到更快更近的地方，代价是数据会旧 | [00-concepts §11](../00-foundations/00-concepts.md) |
| 命中率的非线性 | 命中率 90% 的缓存挂掉，数据库瞬间承受的是 10 倍流量，不是 10% | [00-concepts §11](../00-foundations/00-concepts.md) |
| 强一致 / 最终一致 | 写完之后别人是不是立刻能读到新值，还是"过一会儿就对了" | [00-concepts §6](../00-foundations/00-concepts.md) |
| 幂等 | 同一个操作做多次，效果和做一次相同 | [00/01 §5](../00-foundations/01-fundamentals.md) |
| 背压与有界队列 | 处理不过来时要当场拒绝，而不是无限排队等着一起死 | [00/01 §6](../00-foundations/01-fundamentals.md) |
| 三个数量级 | 进程内内存 ~100 ns、同 AZ 网络 ~0.5 ms、磁盘/跨洲 ~10–100 ms | [00/01 §1](../00-foundations/01-fundamentals.md) |

**这一章要回答的问题**

1. 数据更新时，到底是删缓存还是写缓存？先动 DB 还是先动缓存？剩下那个关不掉的竞态窗口怎么办？
2. 一个 QPS 5 万的热 key 在过期的那一毫秒里会发生什么？不加分布式锁能不能解决？
3. 整个 Redis 集群挂掉的那一秒，我的数据库靠什么活下来？为什么它挂了之后还"自己好不了"？
4. 命中率 95% 听起来很健康，为什么 DB 还是很累？我到底该盯哪个指标？
5. LLM 的前缀缓存对我组装上下文的**顺序**提了什么硬约束？违反了会怎样？

**本章新引入的术语**

| 术语 | English | 一句话定义 |
|---|---|---|
| 回源 | origin fetch | 缓存里没有这份数据，只好到后面那个权威来源（数据库 / 源站）真正取一次 |
| 陈旧 | staleness | 缓存里的值和权威来源已经不一样了；差了多长时间就叫多陈旧 |
| 旁路缓存 | cache-aside | 由应用代码自己先查缓存、没有再查库并回填；缓存组件本身不知道数据库的存在 |
| 缓存失效 | cache invalidation | 数据在权威来源变了之后，把缓存里那份旧的删掉或标记作废 |
| 负缓存 | negative caching | 把"这个键查出来是空的"这件事本身也缓存起来，免得同一个不存在的键反复打到数据库 |
| 缓存踩踏 / 惊群 | cache stampede / thundering herd | 同一个键失效的瞬间，大量并发请求同时发现未命中、同时去回源 |
| 相关过期 | correlated expiry | 一大批键的过期时刻被设成了同一个点，于是它们在同一秒集体失效 |
| 单飞 | single-flight | 同一个键的并发回源只真正执行一次，其余请求在原地等这一次的结果 |
| 返回陈旧值 | serve stale | 明知值已过期仍先把它返回给用户，同时在后台异步刷新 |
| 淘汰策略 | eviction policy | 内存装不下时，按什么规则决定踢掉哪个键 |
| 扫描污染 | scan pollution | 一次性的全量扫描把只会用一次的数据灌进缓存，把真正的热数据挤出去 |
| 前缀缓存 | prefix caching / KV cache reuse | 两次 LLM 请求开头的 token 完全一样时，复用第一次算出的中间结果，跳过这段重复计算 |

## 1. 缓存层级全景

```
┌─────────────────────────────────────────────────────────────┐
│ 浏览器缓存 / Service Worker      TTL: 分钟~天    命中 = 0 网络 │
├─────────────────────────────────────────────────────────────┤
│ CDN / 边缘缓存                   TTL: 秒~天      命中 = 10ms  │
├─────────────────────────────────────────────────────────────┤
│ API 网关缓存 / 反向代理           TTL: 秒        命中 = 1ms   │
├─────────────────────────────────────────────────────────────┤
│ 应用进程内缓存（本地 LRU）        TTL: 秒        命中 = 100ns │
├─────────────────────────────────────────────────────────────┤
│ 分布式缓存（Redis/Memcached）     TTL: 分钟      命中 = 0.5ms │
├─────────────────────────────────────────────────────────────┤
│ 数据库 buffer pool                              命中 = 100ns │
├─────────────────────────────────────────────────────────────┤
│ 磁盘 / 对象存储                                  = 0.1–50ms  │
└─────────────────────────────────────────────────────────────┘
```

（**Service Worker**：浏览器里常驻的一段脚本，能拦截页面自己发出的请求并直接用本地存的副本回答，页面代码毫不知情。）

**设计原则：越靠近用户越好，但一致性越难。**

**关键判断**：进程内缓存（L1，每个应用进程在自己内存里各存一份）+ Redis（L2，所有进程共用的那一份）的两级结构，能把 Redis 的 QPS 降 90%，但引入了**每个进程副本可能不一致**的问题。适用于：读极热、可容忍数秒陈旧（staleness）、值不大的数据（配置、feature flag（不发版就能开关某个功能的配置项）、租户元数据、汇率）。

## 2. 缓存模式

### Cache-Aside（旁路缓存）—— 90% 的场景用这个

```python
def get_user(uid):
    v = cache.get(f"user:{uid}")
    if v is not None:
        return v                    # 命中
    v = db.query(uid)               # 未命中，回源
    cache.set(f"user:{uid}", v, ttl=300)
    return v

def update_user(uid, data):
    db.update(uid, data)            # 1. 先更新 DB
    cache.delete(f"user:{uid}")     # 2. 再删除缓存（不是更新！）
```

**两个必须记住的规则：**

**规则 1：更新时删除缓存，而不是写入缓存。**
> 因为并发下"写缓存"会产生这个序列：
> `A 读DB得v1 → B 写DB为v2 → B 写缓存v2 → A 写缓存v1` → 缓存永久是脏的 v1。
> 而"删除"是幂等的（idempotent），最坏情况是多回源（origin fetch）一次。

**规则 2：先更新 DB，再删缓存（Cache-Aside 顺序）。**
> 反过来（先删缓存再更新 DB）的问题：删完缓存后、更新 DB 前，另一个读请求把旧值回填进缓存 → 长期脏数据。

⚠️ **即便如此，先更新 DB 再删缓存仍有一个极小概率的竞态（race condition）**：
```
读请求 A：缓存未命中 → 读 DB 得 v1  ────────────────┐
写请求 B：           更新 DB 为 v2 → 删缓存         │
读请求 A：                                    ← 写入缓存 v1（脏）
```
这要求 A 的"读 DB"和"写缓存"之间跨越了 B 的整个写操作 —— 概率很低（读通常比写快），但在高并发下会发生。

**彻底的解法（按成本递增）**：
1. **给缓存加短 TTL**（最实用）—— 脏数据最多存活 TTL 时长
2. **延迟双删（delayed double delete）**：更新 DB → 删缓存 → 等 500ms → 再删一次
3. **订阅 binlog/CDC 来失效缓存**（CDC = change data capture：订阅数据库自己的变更日志 —— MySQL 的 binlog、Postgres 的逻辑复制槽 —— 把每一次行级改动变成一条事件，见 [03](03-messaging-and-streams.md)）—— 单一失效来源，最可靠，生产推荐
4. 版本号/CAS 写缓存（CAS = compare-and-swap：写的时候带上"我读到的是第几版"，版本对不上就整个写失败，见 [00-concepts §7](../00-foundations/00-concepts.md)）

### Write-Through / Write-Behind

| 模式 | 写路径 | 特点 |
|---|---|---|
| **Write-Through** | 应用 → 缓存 → 同步写 DB | 缓存永远最新；写延迟高 |
| **Write-Behind** | 应用 → 缓存 → 异步批量写 DB | 写极快；**缓存挂了会丢数据** |
| **Refresh-Ahead** | 临近过期时后台主动刷新 | 消除冷启动（cold start：缓存刚起来是空的，这段时间几乎每个请求都要回源）毛刺；可能刷新无人访问的键 |

**Write-Behind 的合法使用场景**：可容忍丢失的高频计数（浏览量、点赞数）。用 Redis 累加，每 10 秒批量 flush 到 DB —— 把 10 万 TPS 变成 100 TPS。
（这个 100 是怎么来的：**DB 的写次数不再取决于点赞次数，只取决于有多少个不同的计数器。** 假设热度集中在约 1,000 个条目上，
10 秒里不管来了 100 万次点赞，最后也只是 1,000 行各写一次 → 1,000 ÷ 10 秒 = 100 TPS。**这就是"合并写"的全部原理：把写放大从"按事件"变成"按键"。**）

## 3. 三大经典故障：穿透、击穿、雪崩

> ⚠️ **英文面试警告**：「穿透 / 击穿 / 雪崩」这套三分法是中文技术社区的产物，**英文工程界没有对应术语**。
> 直译成 cache penetration / breakdown / avalanche，英语母语面试官听不懂 —— avalanche 尤其糟，
> 它在英文里没有任何技术含义。正确说法见下面每一节标注的英文，它们各自是独立的、真实存在的术语。

| 中文 | ❌ 别说 | ✅ 英文该说 |
|---|---|---|
| 缓存穿透 | cache penetration | **queries for non-existent keys**；解法叫 **negative caching** |
| 缓存击穿 | cache breakdown | **cache stampede** / **thundering herd**（这两个是标准术语） |
| 缓存雪崩 | cache avalanche | 大量同时过期 → **synchronized/correlated expiry**；缓存集群挂 → **cascading failure** |

### 缓存穿透（queries for non-existent keys）：查不存在的键

```
攻击者用随机 UUID 查询 → 缓存永远不命中 → 全部打到 DB
```

**对策**：
1. **缓存空值（negative caching）**：`cache.set(key, NULL_SENTINEL, ttl=60)` —— 简单有效，注意 TTL 要短，且要能被写入路径正确失效
2. **布隆过滤器（Bloom filter）**：把所有存在的 key 放进 BF，查询前先问 BF。BF 说"不存在"就 100% 不存在。
   - 1 亿个 key，误判率（false positive rate） 1% → 需要 ~120 MB
     （怎么算的：BF 的空间只取决于**键数 × 每键位数**，而每键位数只取决于你要的误判率 —— 1% 对应约 **9.6 bit/键**，
     10% 是 4.8 bit，0.1% 是 14.4 bit。所以 1e8 × 9.6 bit = 9.6e8 bit ÷ 8 ≈ 120 MB。**注意它和 key 本身多长完全无关。**）
   - 缺点：**不支持删除**（要用 Counting BF 或定期重建）
3. **参数校验 + 限流（rate limiting：给某个来源单位时间内允许通过的请求数设上限，超出的直接拒绝）**：非法格式的 ID 直接拒

### 缓存击穿（cache stampede / thundering herd）：热点 key 过期瞬间

```
一个 QPS 5 万的热 key 过期 → 同一毫秒 5 万个请求同时回源 → DB 瞬间崩
```
这就是 **Cache Stampede / Thundering Herd**。

**对策（按推荐度）：**

**a) 单飞（Single-flight / 请求合并）** —— 最优雅
```go
// 同一个 key 的并发回源只执行一次，其余等待结果
var g singleflight.Group
v, err, _ := g.Do(key, func() (interface{}, error) {
    return db.Query(key)
})
```
注意：这只在单个进程内合并。多进程还需要分布式锁（distributed lock：一个所有进程都认的外部标记，同一时刻只有拿到它的那个进程可以做某件事，见 [05](05-consensus-and-coordination.md)）或下面的方法。

**b) 概率提前过期（probabilistic early expiration，XFetch）** —— 无锁（lock-free），我的首选
```python
# 存储时同时记录计算耗时 delta 和写入时间
value, delta, expiry = cache.get_with_meta(key)
if value is None or (time.now() - beta * delta * math.log(random.random())) >= expiry:
    value = recompute()   # 只有极少数请求会提前触发
    cache.set_with_meta(key, value, delta=elapsed, ttl=T)
return value
```
效果：**在过期前，请求会以逐渐增大的概率提前刷新**，避免所有人在同一时刻撞墙。beta 默认 1.0，越大越早刷新。

**c) 永不过期 + 后台刷新**：逻辑过期时间存在 value 里，发现逻辑过期就异步触发刷新，当前请求返回旧值（serve stale）。**保证永远有值可返回**（可用性优先）。

**d) 分布式锁**：只让一个请求回源，其余轮询等待。可行但增加延迟和复杂度，且锁本身要处理超时。

### 缓存雪崩（correlated expiry / cascading failure）：大量 key 同时过期 / 缓存集群挂

**成因 1：TTL 同时到期**（比如启动时批量预热（warm-up：在真实流量到来之前，主动把一批数据先灌进缓存），全设 300s）
> 对策：**TTL 加随机抖动（jitter）** `ttl = base + random(0, base * 0.1)`

**成因 2：缓存集群整体不可用**
> 这是最危险的：DB 平时只承担 5% 的流量，缓存挂了瞬间要承担 100% → 立刻崩溃，且崩溃后缓存无法预热 → **无法自愈（self-heal）**。

**对策（必须提前设计）：**
1. **本地缓存兜底**（fallback，L1）：即便 Redis 全挂，热数据仍有 L1 命中
2. **回源限流（load shedding：主动丢弃一部分请求，用"少数人失败"换"系统不死"，它是背压的一种，见 [00/01 §6](../00-foundations/01-fundamentals.md)）**：给 DB 的回源路径加严格的并发上限（如 100 并发），超出的请求直接返回降级值/错误。**宁可拒绝 90% 也不要让 DB 崩**
3. **熔断（circuit breaker：某个下游连续失败到一定比例就干脆暂时不再调它、直接快速失败，冷却一段时间后再放几个探测请求试水，见 [`05-reliability/03`](../05-reliability/03-resilience-patterns.md)） + 降级（graceful degradation：明确定义地少做一些事，而不是整体报错）**：DB 压力过大时返回静态默认值
4. **缓存集群多可用区（multi-AZ） + 分片（sharding）**，避免单点全挂

**面试金句**：
> "缓存的可用性设计里，最重要的一条是：**缓存挂掉时数据库必须能活下来**。所以回源路径上必须有并发限制，而不是让所有 miss 都直通 DB。我会给回源加一个信号量（semaphore：一个计数器，最多允许 N 个请求同时进入这段逻辑，满了的直接被拒），容量按 DB 能承受的连接数设，满了就返回降级响应。"

## 4. 热点 Key（Hot Key）

**问题**：某个 key（明星发微博、爆款商品）的 QPS 达到几十万，**单个 Redis 分片扛不住**（单实例上限约 10–15 万 QPS）。

**发现**：
- Redis `--hotkeys` / `MONITOR` 抽样
- 客户端侧统计本地 key 频率，上报
- 代理层（Twemproxy/Envoy）做统计

**对策**：

| 手段 | 做法 | 代价 |
|---|---|---|
| **本地缓存** | 检测到热 key 后，客户端进程内缓存 1–5 秒 | 短暂不一致 |
| **Key 打散（spread the key）** | `hotkey:shard_{0..9}`，读时随机选一个 | 写要更新 10 份 |
| **只读副本（read replica）** | 热 key 走多个只读副本 | 复制延迟（replication lag：从副本落后主副本的时间，这段时间里从它读到的是旧值，见 [00-concepts §6](../00-foundations/00-concepts.md)） |
| **预计算（precompute：提前把结果算好存起来，而不是等请求来了现算） + CDN** | 把热内容推到 CDN | 只适合可公开缓存的内容 |

## 5. 缓存淘汰策略（eviction policy）

| 策略 | 说明 | 适用 |
|---|---|---|
| LRU | 淘汰最久未用 | 通用默认 |
| **LFU** | 淘汰访问频率最低 | 有稳定热点时**优于 LRU** |
| **W-TinyLFU** | 频率草图（frequency sketch） + 分段 LRU | **当代最优**，Caffeine/Ristretto 采用 |
| FIFO / Clock | 便宜 | 内核页缓存 |
| **S3-FIFO** | 三队列 FIFO，2023 新提出 | 简单且接近 W-TinyLFU 的命中率 |

**LRU 的致命弱点：扫描污染（缺乏 scan resistance —— "抗扫描"指的是"一次性的全量扫描不会把热数据挤出去"这个性质，LRU 恰恰不具备）。**
> 一次全表扫描或批处理任务会把所有热数据挤出缓存。W-TinyLFU 用一个 Count-Min Sketch（一个固定大小的计数表，用很少的内存近似统计每个 key 被访问了多少次；会高估、不会低估）记录访问频率，只有当新 key 的频率**高于**将被淘汰的 key 时才准入（admission policy：决定"这个 key 配不配进缓存"，而不是只决定"该踢谁"） —— 一次性扫描的 key 进不来。

**Redis 的 maxmemory-policy**：
- `allkeys-lru`：通用缓存
- `volatile-lru`：只淘汰设了 TTL 的（用于缓存+持久数据混存，但**混存本身是反模式（anti-pattern）**）
- `allkeys-lfu`：有明显热点时
- `noeviction`：Redis 作为数据库时（写满会报错）

⚠️ **不要在同一个 Redis 实例里混放"缓存"和"不能丢的数据"**（如分布式锁、会话）。淘汰策略无法同时满足两者。分实例。

## 6. CDN 与边缘缓存

### 缓存键（cache key）的设计是 CDN 的核心

```
默认缓存键 = 协议 + 域名 + 路径 + 查询串
问题：?utm_source=xxx 会让每个营销链接产生一份独立缓存 → 命中率崩塌
```

**必做的规范化（normalization）**：
- 剔除无关查询参数（utm_*、fbclid、gclid）
- 排序查询参数
- `Vary` 头要克制（`Vary` 告诉缓存"这个响应的内容随哪些请求头而变"，列进去的头每多出一种取值，就多出一份独立缓存）：`Vary: Accept-Encoding` 可以，`Vary: User-Agent` 会把缓存打成碎片

### 关键 HTTP 头

```http
Cache-Control: public, max-age=60, s-maxage=3600, stale-while-revalidate=86400, stale-if-error=604800
```

| 指令 | 含义 |
|---|---|
| `max-age` | 浏览器缓存时长 |
| `s-maxage` | **CDN/共享缓存（shared cache）**时长（覆盖 max-age） |
| `stale-while-revalidate` | 过期后仍可返回旧内容，同时后台刷新 → **消除回源毛刺** |
| `stale-if-error` | 源站（origin：CDN 背后那台真正生成内容的服务器，也就是回源的目的地）挂了时继续返回旧内容 → **免费的可用性** |
| `private` | 禁止 CDN 缓存（含用户数据时必须） |
| `immutable` | 内容永不变（配合内容哈希文件名） |

**`stale-while-revalidate` + `stale-if-error` 是被严重低估的两个指令。** 它们把 CDN 从"加速器"变成了"可用性层"：源站宕机 7 天，用户仍能看到内容。

### 缓存失效

| 方式 | 延迟 | 说明 |
|---|---|---|
| TTL 到期 | TTL | 最简单，最可靠 |
| Purge by URL | 秒级 | 精确但要知道所有 URL |
| **Surrogate Key / Cache Tag** | 秒级 | **最强**：给响应打标签（如 `product-123`, `tenant-acme`），一次 purge 所有相关内容 |
| 版本化 URL（cache busting） | 立即 | `/assets/app.a3f9b2.js` —— 静态资源的标准做法，配 `immutable` |

**架构建议**：动态内容用 **Surrogate Key**。文章更新时 purge `article-42`，所有包含它的页面（列表页、首页、RSS）一并失效。

## 7. LLM 时代的新缓存层

这是 2024–2026 最重要的缓存演进。

### a) Prompt 前缀缓存（KV Cache Reuse）—— 最重要

Transformer 推理时，每个 token 的 Key/Value 张量可复用
（**Key/Value 张量**：模型每读进一个 token，都会为它算出一组中间结果并一直留在显存里，后面每生成一个新字都要回头查这些结果。
你可以就把它当成"模型为前面每个 token 建的索引"—— 这就是 **KV cache**，也是这一节标题里那个 KV。
关键性质：**第 N 个 token 的 KV 只取决于它前面的内容**，所以只要开头那段一模一样，这段 KV 就原样能用）。如果两个请求有相同前缀，前缀部分的 KV 可以直接复用，**跳过 prefill 计算**（**prefill**：把整段输入 token 一次性算出 KV 的那个阶段，和之后一个一个吐字的 decode 阶段相对；输入越长它越贵）。

```
请求 1: [系统提示 2000 tok][工具定义 3000 tok][历史 8000 tok][新问题 200 tok]
请求 2: [系统提示 2000 tok][工具定义 3000 tok][历史 8000 tok][新问题+回答 1000 tok][新问题 200 tok]
        └────────────── 13,000 token 前缀完全相同，可复用 ──────────────┘
```

**收益**：
- TTFT（time to first token：从发出请求到看见第一个字，见 [00/01 §2](../00-foundations/01-fundamentals.md)）从 2s 降到 0.3s（**5–10×**）
- 输入成本降到 1/10（各家 API 的缓存读价格约为标准输入的 10%）

**架构要求（这是设计题的考点）：**
1. **前缀必须完全相同（逐 token）**。所以：
   - 系统提示里**不能有时间戳、随机 ID、动态排序的工具列表**
   - 上下文必须**只在末尾追加**（append-only），不能在中间插入或修改
   - 一旦你"压缩历史"改写了前面的内容，**整个缓存作废**
2. **会话粘性路由（session affinity / sticky routing）**：同一会话的请求要路由到同一个推理实例（KV cache 在那台机器的显存/本地缓存里）。这让 LLM 网关变成**有状态路由** —— 请求不能再随便发给任何一台，而必须发给特定的那一台（见 [00-concepts §9](../00-foundations/00-concepts.md)）。
3. 缓存有 TTL（通常 5 分钟–1 小时），长时间空闲的会话会失效。

**设计推论**：
> Agent 系统的上下文应该组织成 `[稳定前缀（系统提示+工具）] + [只追加的历史] + [变化的当前输入]`。
> 把"检索到的文档"放在系统提示后面是错的 —— 每次检索结果不同会让缓存全废。应该放在历史的末尾。

### b) 语义缓存（Semantic Cache）

```
"如何重置密码？" 和 "密码忘了怎么办" 语义相同 → 复用同一个回答
```
实现：把 query embedding（embedding：把一段文本映射成的一串定长浮点数，意思相近的文本对应的向量在空间里也相近，见 [01 §6](01-storage-engines.md)）存入向量库，新查询相似度 > 0.95 则返回缓存答案。

⚠️ **危险**：语义相似 ≠ 答案相同。
- "北京今天天气" vs "上海今天天气"：embedding 相似度可能 0.93，但答案完全不同
- "如何取消订阅" 对不同租户的答案不同

**安全的用法**：
- 阈值设很高（0.97+）
- **必须按租户/用户/权限分区**
- 只用于**无个性化、无时效性**的问答（FAQ、文档问答）
- 缓存键要包含所有影响答案的上下文

**结论**：语义缓存的适用面比宣传的窄得多。生产中前缀缓存的 ROI 是它的 10 倍。

### c) 工具调用结果缓存

Agent 反复调用同样的工具（读同一个文件、查同一个 API）。
```
cache_key = hash(tool_name, normalized_args, tenant_id, data_version)
```
注意：**必须有 data_version 或短 TTL**，否则 Agent 会基于陈旧数据决策（比如文件已被它自己改过）。

### d) Embedding 缓存

对同一段文本重复计算 embedding 是纯浪费。`cache_key = hash(model_id + normalized_text)`，命中率通常 30–60%。**必须包含 model_id** —— 换模型后旧 embedding 不可用。

## 8. 缓存监控指标

| 指标 | 健康值 | 异常含义 |
|---|---|---|
| 命中率（hit rate） | > 90%（热数据缓存） | 下降 = 数据集变大 / TTL 太短 / 淘汰太激进 |
| p99 延迟 | < 2 ms（Redis 同 AZ） | 高 = 大 key / 慢命令 / 网络 |
| 淘汰率（evictions） | ≈ 0 | > 0 说明内存不够，命中率会持续恶化 |
| 内存碎片率（memory fragmentation ratio） | 1.0–1.5 | > 1.5 考虑重启/activedefrag |
| **回源 QPS** | 稳定 | 突增 = stampede 发生了 |
| 连接数 | < maxclients 的 70% | |

**必须监控"回源 QPS"而不只是命中率。** 命中率 95% 听起来不错，但如果总 QPS 从 1 万涨到 100 万，5% 的 miss 就是 5 万 QPS 打向 DB。

## 9. 什么时候不要用缓存

| 情况 | 理由 |
|---|---|
| 数据变更频率 ≈ 读取频率 | 命中率极低，纯增复杂度 |
| 强一致性（strong consistency：写成功后任何人任何时刻读到的都是新值，见 [00-concepts §6](../00-foundations/00-concepts.md)）要求（余额、库存扣减） | 用 DB 直读 + 索引优化 |
| 数据量小且 DB 已经在内存里 | Postgres 的 buffer pool 就是缓存 |
| 只是为了掩盖慢查询 | **先修查询/加索引**。缓存掩盖的问题在缓存失效时会加倍爆发 |

**反模式警告**：用缓存掩盖一个 3 秒的慢查询。这个系统在缓存正常时看起来很好，一旦缓存冷启动或雪崩就会彻底崩溃，且**无法恢复**（因为回源太慢，永远填不满缓存）。

## 这一章的三句话

1. **缓存的可用性设计里最重要的一条是：缓存挂掉时数据库必须能活下来。**
   所以回源路径上必须有一个明确的并发上限，而不是让所有 miss 都直通 DB ——
   一个没有回源限流的缓存，本质上是把数据库的容量按命中率打了个折再卖出去。
2. **更新数据时唯一的默认动作是"先写库、再删缓存"，理由不是它没有竞态，而是删除是幂等的、写入不是。**
   剩下那个极小概率的窗口用短 TTL 或 CDC 失效去关，而不是靠设计一个更聪明的写顺序 —— 那条路上没有正确答案。
3. **命中率是给你看的，回源 QPS 才是给数据库看的。** 总流量涨十倍时，95% 的命中率和 50% 的命中率
   对下游是同一件事；只盯命中率的监控面板会在雪崩当天显示一切正常。
