## 3. 可用性对照

| SLA | 年停机 | 月停机 | 周停机 | 典型代价 |
|---|---|---|---|---|
| 99% | 3.65 天 | 7.3 h | 1.7 h | 单机 + 备份 |
| 99.9% | 8.76 h | **43.8 min** | 10.1 min | 多 AZ + 自动故障转移（failover） |
| 99.95% | 4.38 h | 21.9 min | 5 min | + 无损发布、演练 |
| 99.99% | 52.6 min | **4.38 min** | 1 min | + 多 region、单元化（cell-based architecture）、错误预算（error budget）政策 |
| 99.999% | 5.26 min | 26 s | 6 s | 极少数系统真的需要，成本非线性爆炸 |

**串行依赖相乘**：3 个各 99.9% 的依赖串起来 = 99.7%（年停 26 小时）。
**并行冗余相补**：2 个各 99% 的独立副本 = 99.99%（前提是**故障真的独立**，同一份配置推错就不独立）。

> **口袋结论**：从 99.9% 到 99.99% 通常意味着**成本翻 2–3 倍、复杂度翻更多**。先问"停 43 分钟的业务代价是多少"，再决定要不要买这一位。

## 4. 排队论（queueing theory）三件套

### Little's Law
```
L = λ × W        在途请求数 = 到达率 × 平均停留时间
```
用法：p50 目标 100 ms、峰值 5000 QPS → 并发在途 = 500 → 500 个线程（该上异步了）或 500 × 2 MB = 1 GB 常驻。

### M/M/1 延迟放大（latency amplification）
```
W = S / (1 − ρ)      ρ = 利用率，S = 服务时间
```
| ρ | 50% | 70% | 80% | 90% | 95% | 99% |
|---|---|---|---|---|---|---|
| 延迟放大 | 2× | 3.3× | **5×** | **10×** | **20×** | **100×** |

⇒ 在线服务稳态目标利用率（target utilization） **60–70%**；>80% 必须自动扩容且扩容速度快过流量增长；批处理可以跑 90%+。

### USL（通用可扩展性定律）
```
C(N) = N / (1 + α(N−1) + βN(N−1))
       α = 串行/竞争    β = 跨节点一致性开销
```
**β > 0 时吞吐先升后降 —— 加机器会让系统变慢。** 典型 β 来源：分布式锁、全网状同步、两阶段提交（two-phase commit）、连接数随节点线性增长打爆 DB。

### 尾延迟放大（tail latency amplification）
```
扇出 N 个后端且必须等全部返回：P(至少一个慢) = 1 − (1−p)^N
```
单后端 p99 = 10 ms，扇出 100 → **63% 的请求会遇到至少一个 10 ms+ 的后端**。
对策：对冲请求（+~5% 流量，**必须幂等**）、减少扇出（fan-out）、部分结果、负载感知路由（load-aware routing）。
⚠ LLM 场景不要对冲（一次对冲 = 一次完整推理的钱），改成**超时后降级到更小的模型**。

## 5. 选型决策树

### 5.1 存储引擎
```
写入是不是远多于读？
├─ 是 ──► 需要范围扫描 / 时序？
│         ├─ 是 ──► LSM（RocksDB / Cassandra / ClickHouse / 时序库）
│         └─ 否 ──► LSM 或 追加日志 + 定期 compact
└─ 否 ──► 需要事务 + 复杂查询 + JOIN？
          ├─ 是 ──► B-Tree 系（Postgres / MySQL）  ← 默认从这里开始
          │         └─ 单实例撑不住（>2万 TPS 或 >5 TB）？
          │            └─► 先读写分离 → 再拆热点路径 → 最后才分片
          └─ 否 ──► 访问模式固定的点查？
                    ├─ 是 ──► KV（DynamoDB / Redis 持久化 / FoundationDB）
                    └─ 否 ──► 分析型宽表 ──► 列存（ClickHouse / Lakehouse）
```
**默认答案永远是 Postgres。** 只有当你能说出"它在 X 指标上撞墙（hit a scaling limit）、我实测过"时，才换。

### 5.2 缓存
```
数据变更频率 ≈ 读取频率？──► 不要缓存（命中率低，纯增复杂度）
需要强一致（余额/库存）？ ──► 不要缓存，优化查询与索引
只是为了掩盖慢查询？     ──► 先修查询。缓存掩盖的问题在雪崩时加倍爆发
        │
        ▼ 其余情况
读极热 + 可容忍数秒陈旧 + 值小（配置/flag/汇率）
        ├─ 是 ──► L1 进程内 LRU（100 ns） + L2 Redis（0.5 ms）
        └─ 否 ──► 只用 L2 Redis
                  │
                  ├─ 有明显热点 key（单片 >10 万 QPS）？──► 打散 / 本地缓存 / 只读副本
                  ├─ 存在热 key 同时过期？          ──► XFetch 概率提前刷新 或 单飞
                  └─ 存在查不存在的 key 攻击？       ──► 缓存空值（短 TTL）+ 布隆过滤器
```
**必须回答的一题**：Redis 全挂时 DB 活不活得下来？→ 回源（origin fetch）路径必须有并发上限（信号量），满了返回降级值。

### 5.3 消息与流
```
消费者需要重放历史 / 多个独立消费组？
├─ 是 ──► 日志型（Kafka / Pulsar / Kinesis）
│         └─ 需要严格分区内有序？──► 分区键 = 需要保序的实体 ID
└─ 否 ──► 只是异步解耦 + 削峰？
          ├─ 团队 <10 人、无运维经验 ──► 托管队列（SQS / Pub-Sub）← 默认
          └─ 需要延迟队列 / 优先级 / 单条 ack ──► 队列型（SQS / RabbitMQ）

跨服务的"数据库改了要通知别人"？
└─► 不要双写。用 Outbox（同事务写事件表）或 CDC（读 binlog）
```
**语义**：分布式系统没有 exactly-once 交付，只有 **at-least-once 交付 + 幂等处理 = effectively-once**。

### 5.4 一致性
```
这条链路上，用户看到旧数据的后果是什么？
├─ 资金/库存错误（不可接受）──► Serializable / Linearizable
│                              代价：跨节点共识，同 AZ ~1ms，跨 AZ 2–5ms，跨 region 60–150ms
├─ 用户困惑（改完看不到）  ──► Read-Your-Writes：会话粘性路由到主库/主副本，代价 0
├─ 顺序错乱（消息乱序）    ──► Causal：同分区有序 + 版本向量
└─ 无人察觉（feed 慢几秒）──► Eventual：随便读从库
```
**CAP 的选择是按链路做的，不是按系统做的。** 同一个系统里支付走 CP、通知走 AP 是完全正常的。

### 5.5 向量索引
```
向量数 < 1000 万 且 已经在用 Postgres？
└─► pgvector（HNSW）。不要为此引入新系统
        │
向量数 1000 万 – 10 亿？
├─ 单租户 / 少量租户 ──► 专用向量库（HNSW，内存驻留）
└─ 多租户（>1 万）  ──► 隔离范式三选一：
                        namespace（查询只能命中一个） /
                        原生 multi-tenancy（需显式创建租户） /
                        payload 过滤（过滤在图遍历内执行）
                      + 冷热分层：冷租户索引下沉对象存储，接受首查 1–3 s
        │
向量数 > 10 亿 或 内存放不下？
└─► 量化（PQ / 二值）+ 磁盘索引（DiskANN 系）；
    Matryoshka 截断到 256 维通常只损 2–3% 精度、存储降 4×
        │
需要词法精确（错误码 / SKU / 函数名 / 罕见实体）？
└─► 必须加 BM25。dense 在这类查询上系统性失效。融合用 RRF（k=60）
```

### 5.6 同步 vs 异步
```
用户是否需要在这次请求内知道结果？
├─ 是 ──► 同步
│         └─ 处理时间 > 1 s？──► 同步返回 job_id + SSE/WebSocket 推进度
│                              （不要让客户端每 100 ms 轮询：既有异步的复杂度
│                                又有同步的延迟，还多了轮询压力）
└─ 否 ──► 异步（队列 + worker）
          必备三件套：幂等键、死信队列、可观测的重试次数
```

## 6. 分片键（shard key）选择检查清单

依次问这 8 个问题，**任何一个答不上来就不要上线**：

```
□ 1. 基数够大吗？        （分片键的不同值数 ≫ 分片数 × 100）
□ 2. 分布均匀吗？        （画出真实数据的直方图，不要假设均匀）
□ 3. 最大的那个键有多大？（单个租户/用户 超过单分片容量怎么办 → 需要"专属分片"逃生舱）
□ 4. 90% 的查询能路由到单分片吗？（做不到就是分布式 JOIN，等于没分片）
□ 5. 写入热点在哪？      （自增 ID / 时间戳做分片键 = 所有写打在最后一片）
□ 6. 跨分片事务有多少？  （>5% 就要重新想分片维度）
□ 7. 租户级操作（导出/删除/迁移）在单分片内完成吗？
□ 8. 逻辑分片数够大吗？  （建议 1024+，物理库才是可变的；直接对物理库取模 = 未来全量搬迁）
```

**分片键是典型的单向门（one-way door）。** 改它 = 双写（dual write） → 回填（backfill） → 影子读（shadow read）比对 → 灰度切读 → 停双写，一个季度起步。

## 7. 韧性（resilience）配置默认值（合理起点，不是真理）

| 项目 | 默认起点 | 调整依据 |
|---|---|---|
| **连接超时** | 200–500 ms（同 region） | 略大于 p99 建连时间 |
| **请求超时** | p99.9 × 1.5，且 ≤ 上游剩余预算 | **每层只减不加**；下游超时永远 < 上游超时 |
| **重试次数** | 1–2 次（只在最外层或最内层） | 3 层各重试 3 次 = **27× 放大** |
| **退避** | 全抖动（full jitter）：`sleep = rand(0, min(cap, base × 2^n))` | base 50–200 ms，cap 2–10 s |
| **重试预算**（retry budget） | 重试量 ≤ 总请求量的 **10%** | 超预算直接放弃重试 |
| **熔断（circuit breaker）打开阈值** | 错误率 > 50% 且样本 ≥ 20 | 样本太少会误触发 |
| **熔断半开（half-open）** | 30 s 后放 1–5 个探测请求 | 探测必须幂等 |
| **隔板（并发上限）** | 按下游能承受的连接数设，不按 QPS | 信号量比限 QPS 更贴近真实资源 |
| **队列深度** | `目标并发 × 2`，且必须**有界** | 无界队列（unbounded queue） = 把 OOM 推迟到最坏时刻 |
| **负载卸载（load shedding）阈值** | 队列等待 > 100 ms 即拒绝新请求（CoDel 思想） | 保住已在途请求 |
| **健康检查** | 浅检查 5 s（存活）+ 深检查 30 s（决定摘流量） | 只测进程存活会漏掉**灰色故障（gray failure）** |
| **缓存 TTL 抖动** | `ttl = base + rand(0, base × 0.1)` | 防同时过期 |
| **幂等键（idempotency key） TTL** | 24 h – 7 d（≥ 客户端最大重试窗口） | |
| **Agent 单任务上限** | 轮次上限 + 绝对 token 上限 + wall-clock 上限，**三者同时设** | Agent 循环方差比人类会话大一个数量级 |

## 8. 2026 年 AI 数字速查

> 全部为 **2026 年中量级，随时变动**；跨厂商、跨 harness、跨版本的数字**不可横向比较**。
> 定价单位统一为 **USD / 百万 token**。

### 8.1 模型单价（按档位取量级，不是具体报价）

| 档位 | 输入 | 缓存读 | 输出 | 典型上下文 |
|---|---|---|---|---|
| **超旗舰** | ~$10 | ~$1 | ~$50 | 200K–1M |
| **旗舰** | ~$5 | ~$0.5 | ~$25–30 | 200K–1M |
| **主力** | ~$2–3 | ~$0.2–0.3 | ~$10–15 | 200K–272K |
| **小模型** | ~$0.2–1 | ~$0.02–0.1 | ~$1.2–5 | 128K–200K |
| **极小/lite** | ~$0.1–0.3 | ~$0.03 | ~$0.4–2.5 | 100K+ |

### 8.2 缓存与批处理（最重要的一张表）

| 项 | 量级 |
|---|---|
| **缓存读 ≈ 输入价的 10%** | 主流厂商现行模型；但老代际有 25% / 50% 档，**不要一律按 90% 折扣算** |
| 缓存写 | 短 TTL ~1.25× 输入价；长 TTL ~2× |
| 缓存回本点 | 短 TTL **读 1 次**回本；长 TTL **读 2 次**回本 |
| 最小可缓存前缀（minimum cacheable prefix） | **512 / 1024 / 2048 / 4096 token，按模型不同且非单调** —— 小 prompt 在高阈值模型上缓存无效**且不报错** |
| 显式 breakpoint 上限 / 回看窗口 | 最多 4 个 / 每个只回看 20 个 content block（单轮 >20 个 tool 块会**静默 miss**） |
| 缓存失效（cache invalidation）级联顺序 | tools → system → messages（改工具定义 = 全部失效） |
| **Batch 折扣** | **一律 50% off**（覆盖输入+输出），周转目标 24 h |
| Batch 内缓存命中 | best-effort，实测区间 **30%–98%**；batch 内应用长 TTL |
| **叠加极值** | batch × 缓存读 ≈ 同步未缓存价的 **1/20** |
| 上下文阶梯溢价 | 多数厂商 1M 上下文无溢价；**个别厂商 >200K 后输入 ×2、输出 ×1.5** |
| tokenizer 换代 | 新一代 tokenizer 同样文本可多产生约 **+30% token** ⇒ 跨代成本对比先跑 `count_tokens` |

**静默 cache miss 是最贵的失效模式（failure mode）**：没有异常、没有日志，只有账单。唯一可靠信号是 `cache_read_input_tokens` 恒为 0 —— **做成监控指标，不是排查手段**。

### 8.3 延迟与吞吐

| 项 | 量级 |
|---|---|
| 对话 TTFT 目标 / 理想 / 感知阈 | <1 s / <600 ms / **>2 s 用户明显感知** |
| 生产长上下文推理 SLA 模板 | mean TTFT ≤ 2.5 s、mean TPOT ≤ 20 ms |
| 单用户 decode | 30–200 tok/s |
| 大规模 MoE 服务（H200 档，wide-EP） | ~2.2k tok/s per GPU（最实用的量级锚点） |
| 自建 70B 单卡（FP8 + 连续批处理（continuous batching）） | ~400 tok/s 聚合 ≈ 34.5M tok/天 |
| KV cache 体积 | **~1 MB / token** 量级；70B FP8 / 8k tokens ≈ 1.3 GB/请求 |
| 前缀缓存（prefix caching）命中率 | 共享系统提示场景 70–90%；**agentic 多轮可跌破 20%**（工具输出插在中间打碎前缀） |
| 缓存感知路由（cache-aware routing）的极端对照 | 精确路由 vs 随机路由，P90 TTFT 可差 **两个数量级** |
| 投机解码（speculative decoding） | 低并发 ~1.7×，**高并发衰减到 ~1.0× 甚至负收益** ⇒ decode 大批场景默认关 |
| 约束解码（constrained decoding） | 后端开销 <40 µs/token，但**编译一次 20–50 ms** ⇒ 每请求换新 schema 是最坏用法 |

### 8.4 检索与 embedding

| 项 | 量级 |
|---|---|
| embedding 单价 | $0.02 – $0.15 / 百万 token |
| 常见维度 | 256 / 512 / 768 / 1024 / 1536 / 2048 / 3072（Matryoshka 可截断） |
| Matryoshka 截到 256 维 | 损 **2–3%** 精度，存储降 **4×** |
| 分块参数起点 | chunk 数百 token；上下文化每块 +50–100 token |
| 检索候选 → 重排（reranking） | 一阶段 top-100 → 重排候选 30–50 → 最终 top-20 |
| RRF | `score(d) = Σ 1/(k + rank_i(d))`，**k = 60** 行业惯例 |
| hybrid 实际增益 | 裸 RRF vs BM25 约 **+1.3% NDCG**；调参后 +7% 量级（约需 40 条标注对） |
| 生产目标线 | Recall@10 **85–91%**、MRR **>0.80** |
| 1M 文档索引体积 | dense ≈ **3 GB**；late interaction 无量化 ≈ **102 GB**；2-bit ≈ 6 GB |
| GraphRAG 成本 | 索引 **6–8×** flat RAG、运行 ~3×；**语料 <100 万 token 通常不值** |
| 2026 默认形态 | **检索 5 万–20 万 token → 长上下文模型推理**（不是二选一） |

### 8.5 Agent 运行时与成本结构

| 项 | 量级 |
|---|---|
| **Agent 成本分布** | 推理 **85–89%** / 沙箱 **11–15%** / 存储 ~0（官方算例 n=1） |
| token 放大 | 单 Agent ≈ 聊天的 **4×**；多 Agent 系统 ≈ **15×** |
| 子 Agent 摘要回传 | **1,000–2,000 token**（有损，父 Agent 无法复审原始证据） |
| 扇出配额起点 | 简单查找 1 agent / 3–10 次工具调用；对比类 2–4 子 agent；复杂研究 10+ |
| 沙箱单价 | ~$0.07 – $0.40 / 沙箱·小时（按规格与厂商，2026 量级） |
| 沙箱冷启动（cold start） | microVM ~100–200 ms；容器沙箱 1–3 s（多次工具调用会累积） |
| 托管沙箱会话硬上限 | 1 小时（入门档）– 24 小时（付费档）⇒ **长任务必须外置状态（externalize state）** |
| 编码 Agent 人均成本 | ~$13 / 活跃日、$150–250 / 月（官方口径，人群差异大） |
| 上下文清理策略参数 | trigger 3 万–10 万 input token；保留最近 3 组 tool 结果；`clear_at_least` 设 5000 **以免击穿前缀缓存** |

### 8.6 评测与安全

| 项 | 量级 |
|---|---|
| 首轮错误分析样本 | 20–50 条 trace；之后每轮 ≥100 条；连续 ~20 条无新类别即饱和 |
| 失败模式分类法规模 | 5–10 类 |
| LLM judge 起步 | 100+ 人工标注样本 + 每周维护 |
| judge-人工一致性门槛 | Cohen's kappa **≥0.6 可上线，≥0.8 强**（人-人基线只有 0.5–0.8） |
| 判官偏差量级 | 风格/冗长偏差（verbosity bias） **0.10–0.76**，位置偏差（position bias） ≤0.04 ⇒ **风格偏差是位置偏差的十倍以上** |
| 金丝雀（canary）自动回滚阈值 | 单指标回归 2–3 个百分点且持续 15–60 分钟 |
| 提示注入（prompt injection）防御现状 | 已发表防御在自适应攻击下多数 **ASR > 90%** ⇒ 概率性防御不能当边界 |
| 跨租户 KV cache 泄露 | 已被实证可逐 token 重建他人 prompt ⇒ **跨租户共享 prefix cache 默认关闭** |
| 公开 benchmark 可信度 | 8 个主流 agent 基准中 7 个被刷到接近 100% ⇒ **只能当参考，不能当门禁（release gate）** |

## 9. 成本估算公式合集

```
① 单请求成本
   $/req = (计算 + 存储 + 网络 + 第三方) / 请求数

② 机器数
   机器数 = 峰值QPS × 单请求CPU秒 / (核数 × 目标利用率 0.6~0.7) × 副本 × 环境数

③ 跨 AZ 流量费（最常被漏掉的一项）
   100 MB/s 跨 AZ × 2.6×10⁶ s/月 × $0.01/GB ≈ $2,600/月
   ⇒ 这经常比计算成本还高，是 Cell 架构（AZ 内闭环）的主要动机

④ LLM 月成本
   月成本 = 日轮次 × 30 × [ 输入tok × (1−h) × P_in
                           + 输入tok × h × P_in × 0.1        ← h = 前缀缓存命中率
                           + 输出tok × P_out ]
   ⇒ h 从 0 提到 0.85，输入项成本降到约 24%。缓存不是优化，是生死线。

⑤ 缓存回本点
   短 TTL：写 1.25× → 读 1 次即回本
   长 TTL：写 2×    → 读 2 次回本
   ⇒ 判据是"这段前缀在 TTL 内会被读几次"，不是"它有多长"

⑥ 自建 GPU 盈亏平衡
   自建单位成本 = (卡租金 + 3~5× 隐性成本) / (吞吐 tok/s × 3600 × 利用率)
   ⇒ 利用率从 100% 掉到 20%，单位成本涨 5 倍。
     对标基线必须先钉死：对标溢价旗舰 API 可能回本，对标廉价开源托管几乎不可能。

⑦ 单位经济
   毛利率 = (收入 − 变动成本) / 收入
   传统 SaaS 80–90%；AI 产品 ~50%（2026 行业量级）
   基础设施 / ARR：传统 SaaS 5–15%；AI 产品 20–60%

⑧ 重度用户测试（AI 产品必算）
   P99 用户月成本 = P99 会话数 × 每会话轮次 × 每轮 token 成本
   ⇒ 如果它 > 你的月订阅价，你的定价模型有洞
```

## 10. 面试口袋话术（10 句可复用模板）

把 `[ ]` 换成具体内容，这 10 句能覆盖一场面试里 80% 的表述需求。

**1. 澄清收尾**
> "我总结一下：一个 [读写比]、峰值 [QPS]、p99 [X ms]、可用性 [Y] 的系统，明确不做 [Z]。我按这个往下走。"

**2. 完整取舍（四段式，最重要的一句）**
> "我选 A。因为在 [具体约束] 下，A 在 [维度] 上比 B 好 [量化差距]。代价是 [具体坏处]，我接受是因为 [业务无所谓 / 有缓解]。如果 [条件] 变了，我会改用 B。"

**3. 撞墙与信号**
> "这个方案能撑到 [规模]。第一个撑不住的是 [组件]，信号是 [具体指标] 超过 [具体值]，我会在监控里设这条告警。"

**4. 可逆性（reversibility）**
> "这里唯一的单向门是 [决策]。一旦上线并有 TB 级数据，改它就是一次跨季度的迁移。所以我在这里多花时间，其余先选简单方案。"

**5. 复杂度预算（complexity budget）**
> "技术上 [X] 更合适，但这个团队只有 [N] 个人且没人运维过它。我先用 [托管方案]，等 [具体信号] 真的逼到了再迁，迁移成本我估 [时长] —— 而提前上的成本是持续的运维税。"

**6. 失败与降级（graceful degradation）**
> "[组件] 挂了的时候，[上游] 会在 [时间] 内感知到，然后降级到 [具体行为] —— 不是'尽力而为'，是明确关掉 [模块]、只返回 [内容]。"

**7. 演进分阶段**
> "v0 我用 [最简方案]，能撑到 [规模]，3 个月能上线。v1 加 [能力]。真正需要 [重方案] 是在 [规模]，那大概是第 [N] 年的事，届时我已经在 schema 里预留了 [字段]。"

**8. 承认不会**
> "我没有直接做过 [X]。但它要解决的是 [问题]，约束是 [Y]，所以机制上大概是 [C]。这和我做过的 [D] 是同一类问题。真实项目里我会先做一个 [N] 天的原型测 [指标] 再决定。"

**9. 迁移剧本（Staff 信号）**
> "改 [X] 我会走六步：双写 → 限速回填 → 影子读比对 → 差异率 <0.01% 持续 7 天 → 按 1/10/50/100% 切读 → 停双写。每一步的回滚条件是 [具体条件]。"

**10. AI 成本（AI 岗必备）**
> "这个系统的成本支配项是 [推理 / 检索 / 沙箱]，占 [百分比]。最大的旋钮是前缀缓存命中率 —— 缓存读约为输入价的 10%，命中率从 0 到 85% 能把输入成本降到约 1/4。所以上下文必须组织成'字节稳定的前缀 + 只追加（append-only）的尾巴'。"

## 11. 最后 60 秒自查

进考场前扫一眼：

```
□ 我会先花 5–8 分钟问需求，并把 SLO 写在白板左上角
□ 每个决策后我会说一句"代价是……"
□ 每个组件后我会跟一个数字（QPS / 延迟 / 容量 / $）
□ 剩 8 分钟时我无条件切到"取舍与演进"
□ 我准备了 2–3 个主动提名的深挖点，且它们是这题最难的部分
□ 我知道这个设计里哪个是单向门
□ 我能说出"什么时候不要这么做"
□ 被追问时我先展开论证，而不是先改答案
□ 不会的问题我用「承认 + 推理路径 + 类比 + 验证方式」四步答
□ （AI 题）我算了 token 成本，并说出了缓存命中率这个支配变量
```
