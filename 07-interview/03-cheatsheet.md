## 1. 延迟数字（背下来）

| 操作 | 量级 |

| 互斥锁（mutex） 加解锁（无竞争） | 17 ns |

| 机械盘寻道 | 5–10 ms |
| **LLM TTFT（中等模型）** | **200 ms – 2 s**（命中前缀缓存可降一个数量级） |
| **LLM 单 token 解码（TPOT）** | **5–30 ms**（即 30–200 tok/s） |
| **向量 ANN（100 万向量 HNSW，recall 0.95）** | **1–10 ms** |
| **一次 Agent 工具调用往返** | **50 ms – 5 s**（工具本身决定） |

## 3. 可用性对照

| SLA | 年停机 | 月停机 | 周停机 | 典型代价 |
|---|---|---|---|---|
| 99% | 3.65 天 | 7.3 h | 1.7 h | 单机 + 备份 |
| 99.9% | 8.76 h | **43.8 min** | 10.1 min | 多 AZ + 自动故障转移（failover） |
| 99.95% | 4.38 h | 21.9 min | 5 min | + 无损发布、演练 |
| 99.99% | 52.6 min | **4.38 min** | 1 min | + 多 region、单元化（cell-based architecture）、错误预算（error budget）政策 |
| 99.999% | 5.26 min | 26 s | 6 s | 极少数系统真的需要，成本非线性爆炸 |

**串行依赖相乘**：3 个各 99.9% 的依赖串起来 = 99.7%（年停 26 小时）。
**并行冗余相补**：2 个各 99% 的独立副本 = 99.99%（前提是**故障真的独立**，同一份配置推错就不独立）。

> **口袋结论**：从 99.9% 到 99.99% 往往需要消除新的共因故障、扩大冗余与演练范围，成本和复杂度是非线性的，但没有通用的 2–3 倍。先问“停 43 分钟的业务代价是多少”，再为这组依赖和恢复目标单独估价。

## 4. 排队论（queueing theory）三件套

### Little's Law
```
L = λ × W        在途请求数 = 到达率 × 平均停留时间
```
用法：**实测平均**停留时间 100 ms、峰值 5000 QPS → 平均在途约 500。若采用“一请求占一个阻塞线程”的模型，线程池与栈内存会成为约束；异步 I/O 可以减少线程占用，但不会消除这 500 个在途任务及其下游连接、缓冲区和业务状态。Little's Law 不能用 p50 或 p99 直接代替平均值。

### 利用率 → 延迟放大（latency amplification）
```
响应时间 W  = S / (1 − ρ)      ← M/M/1（单队列单服务台）
排队延迟 Wq = ρS / (1 − ρ)     ← 只有排队那段。W = Wq + S，别把两者混着说
```
| ρ | 50% | 70% | 80% | 90% | 95% |
|---|---|---|---|---|---|
| **M/M/1**（单服务台：单主库、单分片、单连接、单线程锁） | 2× | 3.3× | **5×** | **10×** | **20×** |
| **M/M/c，c=8**（8 核 / 8 worker） | 1.01× | 1.11× | 1.29× | 1.88× | 3.11× |
| **M/M/c，c=16**（16 核容器 ← 你多半是这个） | 1.00× | 1.03× | **1.10×** | **1.37×** | 1.98× |

⚠️ **别把 M/M/1 的 5× 套在多核服务上** —— 这是这一页最容易被面试官反打的一格。16 核上按模型只有 1.10×。
⇒ 在线服务稳态目标利用率（target utilization） 仍是 **60–70%**，但理由是：真实服务时间**重尾**（M/G/c 下按 `(1+CV²)/2` 再放大）、
c 个核不是 c 个独立服务台（内存带宽 / 锁 / STW GC）、80% 是**平均值**掩盖单核与单分片热点、以及要给扩容时延留头部空间。
⇒ 80% 可作为在线服务的调查/扩容候选线，而不是跨系统硬阈值；扩容要早于队列失控，批处理则可在不违反截止时间时追求更高利用率。推导见 [`00/02 §3`](../00-foundations/02-capacity-estimation.md#3-排队论queueing-theory为什么-80-利用率utilization是危险的)。

### USL（通用可扩展性定律）
```
C(N) = N / (1 + α(N−1) + βN(N−1))
       α = 串行/竞争    β = 跨节点一致性开销
```
**β > 0 时吞吐先升后降 —— 加机器会让系统变慢。** 典型 β 来源：分布式锁、全网状同步、两阶段提交（two-phase commit）、连接数随节点线性增长打爆 DB。

### 尾延迟放大（tail latency amplification）
```
扇出 N 个后端且必须等全部返回：P(至少一个慢) = 1 − (1−p)^N
```
单后端 p99 = 10 ms，扇出 100 → **63% 的请求会遇到至少一个 10 ms+ 的后端**。
对策：对冲请求（+~5% 流量，**必须幂等**）、减少扇出（fan-out）、部分结果、负载感知路由（load-aware routing）。
⚠ LLM 场景不要对冲（一次对冲 = 一次完整推理的钱），改成**超时后降级到更小的模型**。

## 5. 选型决策树

### 5.1 存储引擎
```
写入是不是远多于读？
├─ 是 ──► 需要范围扫描 / 时序？
│         ├─ 是 ──► LSM（RocksDB / Cassandra / ClickHouse / 时序库）
│         └─ 否 ──► LSM 或 追加日志 + 定期 compact
└─ 否 ──► 需要事务 + 复杂查询 + JOIN？
          ├─ 是 ──► B-Tree 系（Postgres / MySQL）  ← 默认从这里开始
          │         └─ 单实例撑不住（>2万 TPS 或 >5 TB）？
          │            └─► 先读写分离 → 再拆热点路径 → 最后才分片
          └─ 否 ──► 访问模式固定的点查？
                    ├─ 是 ──► KV（DynamoDB / Redis 持久化 / FoundationDB）
                    └─ 否 ──► 分析型宽表 ──► 列存（ClickHouse / Lakehouse）
```
**对多数事务型业务，Postgres / MySQL 是值得先验证的默认假设，不是永远正确的答案。** 先按访问模式、团队能力和约束做最小可行基线；只有当你能说出“它在 X 指标上撞墙（hit a scaling limit）、我实测过”，或需求一开始就不属于关系型事务负载时，才换。

### 5.2 缓存
```
数据变更频率 ≈ 读取频率？──► 不要缓存（命中率低，纯增复杂度）
需要强一致（余额/库存）？ ──► 不要缓存，优化查询与索引
只是为了掩盖慢查询？     ──► 先修查询。缓存掩盖的问题在雪崩时加倍爆发
        │
        ▼ 其余情况
读极热 + 可容忍数秒陈旧 + 值小（配置/flag/汇率）
        ├─ 是 ──► L1 进程内 LRU（100 ns） + L2 Redis（0.5 ms）
        └─ 否 ──► 只用 L2 Redis
                  │
                  ├─ 有明显热点 key（单片 >10 万 QPS）？──► 打散 / 本地缓存 / 只读副本
                  ├─ 存在热 key 同时过期？          ──► XFetch 概率提前刷新 或 单飞
                  └─ 存在查不存在的 key 攻击？       ──► 缓存空值（短 TTL）+ 布隆过滤器
```
**必须回答的一题**：Redis 全挂时 DB 活不活得下来？→ 回源（origin fetch）路径必须有并发上限（信号量），满了返回降级值。

### 5.3 消息与流
```
消费者需要重放历史 / 多个独立消费组？
├─ 是 ──► 日志型（Kafka / Pulsar / Kinesis）
│         └─ 需要严格分区内有序？──► 分区键 = 需要保序的实体 ID
└─ 否 ──► 只是异步解耦 + 削峰？
          ├─ 团队 <10 人、无运维经验 ──► 托管队列（SQS / Pub-Sub）← 默认
          └─ 需要延迟队列 / 优先级 / 单条 ack ──► 队列型（SQS / RabbitMQ）

跨服务的"数据库改了要通知别人"？
└─► 不要双写。用 Outbox（同事务写事件表）或 CDC（读 binlog）
```
**语义**：不要脱离边界说“有/没有 exactly-once”。Kafka 等系统能在自身事务边界内提供 exactly-once processing；一旦跨到外部数据库、邮件或支付副作用，常见实现仍是 **at-least-once 交付 + 幂等写入 / 去重 + 对账 = 端到端 effectively-once**。

### 5.4 一致性
```
这条链路上，用户看到旧数据的后果是什么？
├─ 资金/库存错误（不可接受）──► Serializable / Linearizable
│                              代价：跨节点共识，同 AZ ~1ms，跨 AZ 2–5ms，跨 region 60–150ms
├─ 用户困惑（改完看不到）  ──► Read-Your-Writes：携带提交版本/LSN；
│                              副本追上前读主库，或短期会话粘性（仅是有界延迟假设）
├─ 顺序错乱（消息乱序）    ──► Causal：同分区有序 + 版本向量
└─ 无人察觉（feed 慢几秒）──► Eventual：随便读从库
```
**CAP 的选择是按链路做的，不是按系统做的。** 同一个系统里支付走 CP、通知走 AP 是完全正常的。

### 5.5 向量索引
```
向量数 < 1000 万 且 已经在用 Postgres？
└─► pgvector（HNSW）。不要为此引入新系统
        │
向量数 1000 万 – 10 亿？
├─ 单租户 / 少量租户 ──► 专用向量库（HNSW，内存驻留）
└─ 多租户（>1 万）  ──► 隔离范式三选一：
                        namespace（查询只能命中一个） /
                        原生 multi-tenancy（需显式创建租户） /
                        payload 过滤（过滤在图遍历内执行）
                      + 冷热分层：冷租户索引下沉对象存储，接受首查 1–3 s
        │
向量数 > 10 亿 或 内存放不下？
└─► 量化（PQ / 二值）+ 磁盘索引（DiskANN 系）；
    Matryoshka 截断到 256 维通常只损 2–3% 精度、存储降 4×
        │
需要词法精确（错误码 / SKU / 函数名 / 罕见实体）？
└─► 把 BM25 / 精确索引加入候选，与 dense 做自有查询集基线；
    可从 RRF（k=60）起调，但不是固定最优参数
```

### 5.6 同步 vs 异步
```
用户是否需要在这次请求内知道结果？
├─ 是，且能在请求超时预算内完成 ──► 同步返回最终结果
├─ 是，但处理可能超过预算 ──────► 异步受理：返回 202 + job_id，
│                                  再用 SSE/WebSocket/低频轮询报告进度
└─ 否 ──► 异步（队列 + worker）
          必备三件套：幂等键、死信队列、可观测的重试次数
```

## 6. 分片键（shard key）选择检查清单

依次问这 8 个问题，**任何一个答不上来就不要上线**：

```
□ 1. 基数够大吗？        （分片键的不同值数 ≫ 分片数 × 100）
□ 2. 分布均匀吗？        （画出真实数据的直方图，不要假设均匀）
□ 3. 最大的那个键有多大？（单个租户/用户 超过单分片容量怎么办 → 需要"专属分片"逃生舱）
□ 4. 90% 的查询能路由到单分片吗？（做不到就是分布式 JOIN，等于没分片）
□ 5. 写入热点在哪？      （自增 ID / 时间戳做分片键 = 所有写打在最后一片）
□ 6. 跨分片事务有多少？  （>5% 就要重新想分片维度）
□ 7. 租户级操作（导出/删除/迁移）在单分片内完成吗？
□ 8. 逻辑分片数够大吗？  （建议 1024+，物理库才是可变的；直接对物理库取模 = 未来全量搬迁）
```

**分片键是典型的单向门（one-way door）。** 改它 = 双写（dual write） → 回填（backfill） → 影子读（shadow read）比对 → 灰度切读 → 停双写，一个季度起步。

## 7. 韧性（resilience）配置默认值（合理起点，不是真理）

| 项目 | 默认起点 | 调整依据 |
|---|---|---|
| **连接超时** | 200–500 ms（同 region） | 略大于 p99 建连时间 |
| **请求超时** | 从端到端 deadline 分配，参考无故障延迟分布与降级所需时间 | **每层只减不加**；给上游留处理/降级余量，不机械用 `p99.9 × 1.5` |
| **重试次数** | 1–2 次（只在最外层或最内层） | 3 层各重试 3 次 = **27× 放大** |
| **退避** | 全抖动（full jitter）：`sleep = rand(0, min(cap, base × 2^n))` | base 50–200 ms，cap 2–10 s |
| **重试预算**（retry budget） | 重试量 ≤ 总请求量的 **10%** | 超预算直接放弃重试 |
| **熔断（circuit breaker）打开阈值** | 例如滚动窗口错误率 >50% 且样本 ≥20 | 只是起点；按基线、错误预算和请求量校准，低流量还需连续错误条件 |
| **熔断半开（half-open）** | 30 s 后放 1–5 个探测请求 | 探测必须幂等 |
| **隔板（并发上限）** | 按下游能承受的连接数设，不按 QPS | 信号量比限 QPS 更贴近真实资源 |
| **队列深度** | 必须有界；可从 `目标并发 × 2` 压测 | 由可接受排队时间 × 到达率和内存上限共同约束 |
| **负载卸载（load shedding）阈值** | 队列等待耗尽剩余 deadline 前拒绝新请求 | 100 ms 只是案例值；目标是保住可按时完成的在途请求 |
| **健康检查** | 浅检查 5 s（存活）+ 深检查 30 s（决定摘流量） | 只测进程存活会漏掉**灰色故障（gray failure）** |
| **缓存 TTL 抖动** | `ttl = base + rand(0, base × 0.1)` | 防同时过期 |
| **幂等键（idempotency key） TTL** | ≥ 最大自动/人工重试与消息重放窗口；支付等还需长期在线 tombstone | 24 h–7 d 只适合对应重试窗口的普通 API |
| **Agent 单任务上限** | 轮次上限 + 绝对 token 上限 + wall-clock 上限，**三者同时设** | Agent 循环方差比人类会话大一个数量级 |

## 8. AI 数字速查：背变量，不背会过期的报价

> AI 的价格、上下文上限、缓存规则与 GPU 吞吐变化很快。面试前按目标厂商和模型更新一张**带日期的快照**；跨模型、跨硬件、跨并发和跨评测 harness 的数字不能直接比较。下面给的是计算框架和实验起点。

### 8.1 价格与缓存

| 要记录的变量 | 怎么用 |
|---|---|
| `P_in / P_out` | 每百万输入 / 输出 token 单价；输出通常更贵，模型分级先打输出侧 |
| `d_read / d_write` | 缓存读价、缓存写价相对普通输入价的倍数；厂商、模型、TTL 都会改变它，不能统一写成 0.1 / 1.25 / 2 |
| `min_prefix`、TTL、breakpoint 规则 | 决定“理论上有公共前缀”是否真的能命中；工具定义、system prompt 或前缀中的动态字段变化都可能截断复用 |
| Batch 折扣与完成窗口 | 只用于可延迟、可重放的路径。50% / 24 h 是某些产品的报价快照，不是协议定律 |
| 长上下文阶梯价 | 超过阈值后输入、输出、缓存价可能同时变化，估算必须按阶梯分段 |
| tokenizer 版本 | 换模型前对同一生产样本重新计数；字符数相同不代表 token 数相同 |

缓存改造前先量四个分布：**字节级前缀重叠率、TTL 内复用次数、并发到达形状、按租户拆分后的命中率**。改造后同时回归质量、权限隔离与账单；`cache_read_input_tokens`（或厂商等价字段）长期为 0 是强烈的 miss 信号，但还要区分“不满足最小前缀”和“前缀发生变化”。

### 8.2 延迟、吞吐与显存

| 项 | 正确口径 |
|---|---|
| TTFT / TPOT | 诊断时分开看 p50/p95/p99；可燃尽 SLO 写成“至少 X% 有效交互同时满足 TTFT ≤ A、TPOT ≤ B、总耗时 ≤ C”。示例阈值不能跨产品照搬 |
| Goodput | 每秒**同时满足 TTFT、TPOT、质量与错误率门槛**的请求数；GPU 利用率或总 tok/s 不能替代它 |
| 吞吐 benchmark | 固定模型版本、量化、输入/输出长度分布、batch、并发、硬件、运行时和 SLO；缺一个维度就不可复现 |
| KV cache | 按层数、KV 头数、head dimension、精度和 token 数计算；MHA/GQA/MQA/MLA 可差数量级，公式见 [`04/01 §2`](../04-ai-agent-systems/01-llm-serving-infra.md#2-kv-cache显存预算的主项公式--算例) |
| 动态批处理 | batch 上限与最大排队时间是两个旋钮；`(B−1)/λ` 只近似最老请求等攒满的时间，平均等待通常更小，实际 knee 要压测 |
| 缓存感知路由 | 比较命中收益与负载倾斜；精确粘住热点前缀可能把某台 GPU 打满 |
| 投机 / 约束解码 | 分别测低/高并发和 schema 复用率；加速倍数、编译开销都依赖实现，出现负收益就旁路 |

### 8.3 检索与 embedding

| 项 | 实验起点与判据 |
|---|---|
| 分块 | 从“一个可独立回答问题的语义单元”起步，再扫 chunk size / overlap；不是先背固定 token 数 |
| 候选漏斗 | 先召回较大候选集，再按延迟预算重排并返回；`100 → 30 → 20` 可作为首轮压测，不是标准答案 |
| Hybrid / RRF | BM25 与 dense 在自有查询集上分别做基线。RRF 的 `k=60` 是常见起点，仍要按领域与候选深度调 |
| 维度 / 量化 | 用相同语料比较 Recall@K、MRR/NDCG、索引内存和 p99；Matryoshka 截断后的质量损失不能从别的模型搬来 |
| 索引容量 | `向量数 × 维度 × 每元素字节 + 图/倒排/元数据开销`；late-interaction 还要乘每文档 token 数 |
| GraphRAG | 只有问题确实依赖多跳实体关系时才进入候选；与 flat RAG 同质量、同延迟目标比较全量构建和增量维护成本 |
| 长上下文 | 检索和长窗口可以组合，但放入多少 token 由召回、干扰、TTFT 与费用曲线决定，不存在通用的 5 万–20 万默认值 |

### 8.4 Agent 运行时、评测与安全

| 项 | 正确口径 |
|---|---|
| 成本分布 | 按 trace 归因推理、工具、沙箱、存储和出网；单 Agent 4×、多 Agent 15× 或“推理占 85%”都只是特定样本 |
| 扇出预算 | 创建子 Agent / 工具调用前预留 token、时间和美元预算；独立读评可并行，共享写要划所有权或串行合并 |
| 摘要 | 限长以控制父上下文，但必须附原始证据/产物引用，使父 Agent 能抽查；摘要长度没有统一的 1,000–2,000 token 最优值 |
| Durable execution | 状态与副作用日志外置，不押注单个沙箱寿命；平台会话上限与冷启动查当期官方规格 |
| 错误分析 | 先抽样建立失败分类，再按新类别出现率决定是否加样；“连续 20 条无新类别”只是启发式 |
| LLM judge | 用盲标样本校准，报告分类型混淆矩阵、kappa 与人—人基线；没有跨任务统一的上线阈值 |
| Canary | 阈值来自指标自然方差、样本量、错误预算与业务风险，不统一写成回归 2–3 个点 / 15–60 min |
| Prompt injection | 模型护栏做纵深；权限、参数校验、出口控制和不可逆动作审批才是确定性边界 |
| 跨租户缓存 | 除非供应商提供可验证的隔离边界并完成攻击回归，否则默认按租户分区；性能收益不能覆盖数据泄漏风险 |
| 公开 benchmark | [Berkeley RDI](https://rdi.berkeley.edu/blog/trustworthy-benchmarks-cont/) 展示 evaluator 可被利用；公开分可作外部参照，不能单独当发布门禁 |

## 9. 成本估算公式合集

```
① 单请求成本
   $/req = (计算 + 存储 + 网络 + 第三方) / 请求数

② 机器数
   机器数 = 峰值QPS × 单请求CPU秒 / (核数 × 目标利用率 0.6~0.7) × 副本 × 环境数

③ 跨 AZ 流量费（最常被漏掉的一项）
   月成本 = 跨 AZ GB/月 × 当前双向计费口径 P_xaz
   ⇒ 价格按云厂商、region 和方向查当期页面；先画哪些字节跨边界，再乘价

④ LLM 月成本
   月成本 = 日轮次 × 30 × [ 输入tok × (1−h) × P_in
                           + 输入tok × h × P_cache_read
                           + 缓存写入成本
                           + 输出tok × P_out ]
   ⇒ h 是**按 token 加权**的命中率；把当前模型的缓存读/写价代入，不硬编码 0.1

⑤ 缓存回本点
   复用 n 次后的节省 = n × (P_in − P_cache_read) − 额外缓存写入成本
   ⇒ 解“节省 > 0”的最小 n；还要把前缀整理工程成本与隔离回归算进去

⑥ 自建 GPU 盈亏平衡
   自建单位成本 = (GPU + CPU/网络 + 人力/on-call + 闲置 + 备机) /
                  满足联合 SLO 的有效 token 数
   ⇒ 先证明候选模型在同任务质量与 SLO 上可接受，再谈价格；不能拿不同质量档直接比

⑦ 单位经济
   毛利率 = (收入 − 变动成本) / 收入
   ⇒ 用自己的合同、折扣、支持和基础设施成本；行业区间不能代替产品目标

⑧ 重度用户测试（AI 产品必算）
   P99 用户月成本 = P99 会话数 × 每会话轮次 × 每轮 token 成本
   ⇒ 如果它 > 你的月订阅价，你的定价模型有洞
```

## 10. 面试口袋话术（10 句可复用模板）

把 `[ ]` 换成具体内容，这 10 句能覆盖一场面试里 80% 的表述需求。

**1. 澄清收尾**
> "我总结一下：一个 [读写比]、峰值 [QPS]、p99 [X ms]、可用性 [Y] 的系统，明确不做 [Z]。我按这个往下走。"

**2. 完整取舍（四段式，最重要的一句）**
> "我选 A。因为在 [具体约束] 下，A 在 [维度] 上比 B 好 [量化差距]。代价是 [具体坏处]，我接受是因为 [业务无所谓 / 有缓解]。如果 [条件] 变了，我会改用 B。"

**3. 撞墙与信号**
> "这个方案能撑到 [规模]。第一个撑不住的是 [组件]，信号是 [具体指标] 超过 [具体值]，我会在监控里设这条告警。"

**4. 可逆性（reversibility）**
> "这里唯一的单向门是 [决策]。一旦上线并有 TB 级数据，改它就是一次跨季度的迁移。所以我在这里多花时间，其余先选简单方案。"

**5. 复杂度预算（complexity budget）**
> "技术上 [X] 更合适，但这个团队只有 [N] 个人且没人运维过它。我先用 [托管方案]，等 [具体信号] 真的逼到了再迁，迁移成本我估 [时长] —— 而提前上的成本是持续的运维税。"

**6. 失败与降级（graceful degradation）**
> "[组件] 挂了的时候，[上游] 会在 [时间] 内感知到，然后降级到 [具体行为] —— 不是'尽力而为'，是明确关掉 [模块]、只返回 [内容]。"

**7. 演进分阶段**
> "v0 我用 [最简方案]，能撑到 [规模]，3 个月能上线。v1 加 [能力]。真正需要 [重方案] 是在 [规模]，那大概是第 [N] 年的事，届时我已经在 schema 里预留了 [字段]。"

**8. 承认不会**
> "我没有直接做过 [X]。但它要解决的是 [问题]，约束是 [Y]，所以机制上大概是 [C]。这和我做过的 [D] 是同一类问题。真实项目里我会先做一个 [N] 天的原型测 [指标] 再决定。"

**9. 迁移剧本（Staff 信号）**
> "改 [X] 我会先保留一个权威写入源并记下 CDC 位点：限速快照回填 → 持续追变更日志 → 影子读比对 → 按可隔离单元灰度切读 → 用 epoch/fencing 封住旧写入 → 停旧路径。若必须写新旧两边，也由同一份 outbox 幂等投递，不在请求线程里做裸双写。每一步的阈值、回滚条件和越过单向门后的恢复点都预先写清。"

**10. AI 成本（AI 岗必备）**
> "这个系统的成本支配项是 [推理 / 检索 / 沙箱]，占 [百分比]。最大的旋钮是前缀缓存命中率 —— 缓存读约为输入价的 10%，命中率从 0 到 85% 能把输入成本降到约 1/4。所以上下文必须组织成'字节稳定的前缀 + 只追加（append-only）的尾巴'。"

## 11. 最后 60 秒自查

进考场前扫一眼：

```
□ 我会先花 5–8 分钟问需求，并把 SLO 写在白板左上角
□ 每个决策后我会说一句"代价是……"
□ 每个组件后我会跟一个数字（QPS / 延迟 / 容量 / $）
□ 剩 8 分钟时我无条件切到"取舍与演进"
□ 我准备了 2–3 个主动提名的深挖点，且它们是这题最难的部分
□ 我知道这个设计里哪个是单向门
□ 我能说出"什么时候不要这么做"
□ 被追问时我先展开论证，而不是先改答案
□ 不会的问题我用「承认 + 推理路径 + 类比 + 验证方式」四步答
□ （AI 题）我算了 token 成本，并说出了缓存命中率这个支配变量
```
