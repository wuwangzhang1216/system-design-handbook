# 21 · 设计一个 A/B 实验平台（Design an A/B Experiment Platform）

> 这题的题面是"怎么把用户切成两半"，考的却是**如何让实验结论可信** —— 分流的正确性、指标计算的正确性，以及最难的第三件：**如何防止团队骗自己**。
> 还有一个几乎所有人都不敢说的量级事实：**实验的中位正向率只有约 10%，而 p<0.05 的显著结果里约四分之一是假的。**
> 一个不做 SRM 检查的实验平台，输出的不是结论，是**带小数点的随机数**。

## 读这道题之前

**你在工作中遇到过这个**

商详页改版实验开了 5% 流量。第 4 天早上你看板上是 CTR +0.8%、p = 0.031，截图发群里，当天推到 100%。
两周后大盘 CTR 回到基线，季度复盘时长期 holdout 给出的数字是 **−0.3%**。事后查出三件独立的事叠在一起：
① 你从第 2 天起每天早上看一次结果、看到显著就停 —— 连看 4 次把真实假阳性率从 5% 抬到约 **13%**
（重复显著性检验的经典结果：看 2 次 ≈8%、4 次 ≈13%、10 次 ≈19%、看满两周才到 §4.4 说的 0.2 量级）；
② 两组入组人数是 50.4 : 49.6，看起来"差不多"，但在几百万样本上这个偏差的 p 值远小于 0.0005，
随机化那一刻就已经坏了，而面板上根本没有这项检查；③ iOS 端有 11% 的用户缓存着旧配置，
实验停了 6 小时曝光还在涨，这部分数据混进了分析窗口。**三件事没有一件和被测的那个改版有关**，
而这个平台把它们全都算进了那个 +0.8%。

**本题新引入的术语**

| 术语 | English | 一句话定义 |
|---|---|---|
| 分流单元 | randomization unit | 抛硬币决定进哪一组的那个东西 —— 可以是用户、设备、会话，也可以是单次请求 |
| 曝光 | exposure | "这个随机化单元确实进入某组，且该处理有机会影响结果"的记录；它与分配配置、触发条件和结果事件共同构成可审计分析输入 |
| 分层与正交 | layer / orthogonality | 把流量切成若干互相独立的坐标轴，同一个用户在每层各被独立分一次组；层与层之间的分组结果统计上不相关，于是多个实验能同时跑在 100% 流量上 |
| 互斥组 | mutual exclusion group | 一组默认不让同一用户同时命中的实验；会改同一输出/决策的独立实验通常应互斥，除非它们被合并成预注册、可估交互项的 factorial design |
| 分流比例失配 | sample ratio mismatch (SRM) | 实际进入两组的样本数之比，与你设定的比例发生统计上显著的偏离（设 50:50 实际 50.4:49.6）；它说明随机化或埋点本身坏了，不是效应估偏了 |
| 最小可检测效应 | minimum detectable effect (MDE) | 在给定样本量和功效下，实验能可靠识别的最小提升；比它小的真实效果只会被当成噪声。**样本量与 MDE 是平方关系** |
| 统计功效 | statistical power | 假如效果真的存在，这次实验有多大概率把它检出来；行业默认取 80% |
| 偷看 | peeking | 实验跑到一半反复看结果、看到显著就停 —— 每看一次都相当于重新抽一次奖，真实假阳性率远高于名义上的 5% |
| 方差缩减 / CUPED | CUPED, controlled experiment using pre-experiment data | 用实验开始前就已存在、且与结果指标相关的数据（如上周人均下单数）扣掉指标的一部分方差，从而用更少样本达到同样功效 |
| 护栏指标 | guardrail metric | 不指望它变好，而是要求“劣化不超过事先定义的业务容忍边界”的指标（p99 延迟、崩溃率、退订率）；通常按单侧非劣效检验判断，而不是要求观测值一动不动 |
| 触发分析 | triggered analysis | 只在真正被实验影响到的那部分用户/会话上算指标，而不是在全量入组用户上算 —— 后者会把效应稀释掉一到两个数量级 |
| 新奇效应 / 首因效应 | novelty effect / primacy effect | 前者是用户因为"这是新的"而多点、几周后回落；后者是老用户被打断习惯、短期先跌后回。两者都让 2–4 周的实验测到一个会衰减的数字 |

**这道题的一句话本质**

> **实验平台的产品不是"分流"，是"可信的结论"。** 分流是入场券 —— 一个哈希函数、不到 0.1 个 CPU 核心就做完了；
> 分数全在**你怎么证明这个结论没被污染**，以及**你怎么在团队想要一个正向结果时挡住他们**。带着这句话往下读：
> 每见到一个组件就问一次"它是在生产结论，还是在**证伪**结论？"—— 一个健康的实验平台，后者的代码量应该更多。

## 0. 45 分钟怎么分配这道题

| 时间 | 做什么 | 这一段的得分点 |
|---|---|---|
| **0–3 min** | 问"分流单元是登录用户还是设备"、"有没有网络效应" | 这两个问题决定随机化是否成立。不问就是在赌 |
| **3–5 min** | 敲定规模（DAU、并发实验数、指标数）与非目标（不做多臂老虎机、不做因果推断研究） | 明确说"我不做 X"，把 45 分钟留给该深挖的地方 |
| **5–10 min** | 算三个数：分流计算量、曝光日志三档量级、**样本量 → 实验周期** | **样本量倒推出的"3 周"是本题的枢纽**，它直接推翻"实时看板"的存在意义 |
| **10–14 min** | 画最简版本：配置文件 + SDK 哈希分流 + 一条 SQL，说清它在什么规模撞墙 | 先给能工作的最简解。上来就画 10 个框是负分 |
| **14–20 min** | 画目标架构：配置面 / 分流 SDK / 曝光管道 / 指标引擎 / 统计引擎 / 止损回路 | 边画边说数据流，每个框写一句"它挂了会怎样" |
| **20–26 min** | 深挖一：**分流设计**（哈希 + 分层正交 + 互斥组 + 单元稳定性） | 说出"salt 必须含层 ID"和"跨登录换组"，给出污染比例 |
| **26–33 min** | 深挖二：**SRM 检测**（本题唯一的必答点） | **没讲到 SRM，这题就是不及格。**给出 p<0.0005 和灵敏度数字 |
| **33–38 min** | 深挖三：统计引擎（样本量 / 序贯 / CUPED / 多重检验）+ 护栏与自动止损 | 说出业务护栏为何默认人工，以及什么统计与治理条件下才能自动化 |
| **38–42 min** | 深挖四（主动提名）：为什么大部分实验结论是错的 | **主动提名这一节比什么都加分** —— 它证明你运营过平台而不只是造过平台 |
| **42–45 min** | 失败模式 3 条 + 撞墙信号 + 演进触发条件 | 说出可观测信号（"SRM 触发率 > 8%"），不要说"用户变多" |

**如果只剩 10 分钟**：跳过统计细节（一句"固定视界 + CUPED，偷看用 always-valid 边界"带过），把全部时间给 §4.1 和 §4.5。

## 1. 需求澄清

| # | 我会问 | 面试官通常怎么答 | 为什么决定架构 |
|---|---|---|---|
| 1 | **分流单元（randomization unit：随机化时被当作"一个独立个体"的东西）是什么？** user / device / session / account？ | "登录用户为主，未登录用设备" | 决定 §4.1 的稳定性设计，也决定统计上的独立性假设是否成立 |
| 2 | **产品有网络效应吗？**（一个用户的 treatment 会不会影响另一个用户的体验） | "社交流有，商品页没有" | 有网络效应时用户级随机化直接失效，必须换簇/时间片随机化，有效样本量掉 2–3 个数量级 |
| 3 | 规模：DAU、并发实验数、每实验指标数、维度切面数？ | 5,000 万 DAU、500 并发实验、每实验 50 指标、10 个切面 | 决定曝光日志量级与多重检验的严重程度 |
| 4 | 客户端类型？Web / 移动 App / 服务端？ | 三者都有 | 移动端**配置缓存**是最大的污染源（§4.2），Web 没有这个问题 |
| 5 | 结论延迟要多快？看板要不要实时？ | "越快越好" | **这是个陷阱回答**：实时看板会鼓励偷看，必须区分"止损用的实时"和"决策用的 T+1"（§2.3） |
| 6 | 谁有权停实验？要不要自动止损？ | "崩溃率炸了要能自动停" | 决定是否需要与配置下发解耦的 kill switch 通道 |
| 7 | 要不要支持排序/推荐模型的实验？ | "要，这是最大的用户" | ML 实验多两类污染：共生偏差与反馈回路（§4.7），普通 A/B 平台测不出来 |
| 8 | 指标定义归谁管？和 BI 报表是同一份吗？ | "……应该是吧" | 不是同一份的话，实验平台会长期陷入"两边差 2%"的对账地狱（§4.3） |

**不问就会做错方向的两个：#1 和 #2。**

- 不问 #1，你会把 `user_id` 当分流单元讲完，然后被一句"我们一半流量是未登录的"推翻整个曝光归因。
- 不问 #2，你会给一个在双边市场里**结构性错误**的方案。用户级随机化在有网络效应时不满足 SUTVA（stable unit treatment value assumption：一个个体受到的处理效应不受其他个体分组的影响）—— 这不是精度问题，是**结论符号可能反过来**。

**本文假设**：5,000 万 DAU、500 并发实验、20 个分流层、每实验 50 指标 × 10 个维度切面、Web + iOS + Android + 服务端四类接入。

## 2. 估算

### 2.1 分流的计算量：小到不该为它建一个服务

```
DAU 5,000 万 × 人均每天 40 次需要做实验判定的请求 = 20 亿次/天
  ÷ 86,400 = 23,000 req/s 均值 × 3.5（晚高峰）= 80,000 req/s 峰值
每请求遍历 20 层，每层一次哈希 + 一次条件求值 → 160 万次哈希/s
MurmurHash3 对约 40 字节输入约 20–50 ns → 0.056 core·s/s  ← 一个 CPU 核心的 6%
配置体积：500 实验 × 约 2 KB（分桶区间 + 定向条件 + 参数）= 约 1 MB，全量塞进进程内存
```

**推论 1**：对本文这种高 QPS、确定性分流，**热路径优先在调用方进程内计算**。远程分配会增加一跳延迟、容量与可用性依赖；但它并非永远错误：薄客户端无法安全执行定向规则、需要集中策略审计，或必须统一跨语言求值时，可以由边缘/服务端批量求值并缓存结果。关键是不能让每个业务请求同步依赖一个无缓存的中心服务。

**推论 2**：**不要为了标准确定性分流而预写“所有用户 × 所有实验”的分配表。** 哈希可让求值路径不依赖逐用户存储与远程读；但配置、人工覆盖、审计证据、随机化单元迁移和需要显式抽样的实验仍要持久化。保存的是必要状态与证据，不是 250 亿行笛卡尔积。

### 2.2 曝光日志：三个数字差 53 倍，整条管道的成本全在这里

**曝光（exposure）= "这个随机化单元确实进入了某实验的某个分组，并且该分组的处理有机会影响结果"**。它是 triggered analysis 的入组证据之一，还必须与分配配置、触发条件和结果事件共同审计；不能把“调用过分流函数”当曝光。三个量级：

```
A. 天真实现（入口对所有 20 层调 get_variant 各打一条）  400 亿条/天 = 6.0 TB/天
B. 触发式打点（只在分支真的改变输出时打，2.5 条/请求）   50 亿条/天 = 750 GB/天
C. 去重后（分析真正需要的粒度：unit × experiment × 日）  7.5 亿条/天 = 112 GB/天
     C 列存 + zstd 约 8× → 14 GB/天 → 5 TB/年        A : B : C = 53 : 6.7 : 1
```

**推论 3**：**A→B 的 8 倍靠打点位置（工程规范），B→C 的 6.7 倍靠去重（管道能力）。两者都省下来才有 53 倍。** 而 A 这种写法不只是贵 —— 它让**触发分析（triggered analysis：只在真正被实验影响到的那部分用户/会话上计算指标）失效**，这才是致命的（§4.3 有量化）。存储本身便宜到不值得讨论：5 TB/年 × $0.023/GB/月（2026 量级）≈ 年末月费 $115。**贵的是重算**：改一次指标口径要重跑 30 天窗口 = 1,500 亿行的 join + 聚合，钱是几百美元量级，但**墙钟时间 6–12 小时，而这段时间里旧结论还挂在所有人的页面上**。

### 2.3 样本量 → 实验周期：这才是本题真正的容量约束

每组样本量（α=0.05 双侧、power=80%，`z` 系数合并后）：**比例指标 `n ≈ 15.7 × p(1−p)/Δ²`**（p = 基线转化率，Δ = 要检出的绝对差）；**连续指标 `n ≈ 15.7 × CV²/δ²`**（CV = 变异系数，δ = 相对提升）。

| 场景 | 每组样本量 | 说明 |
|---|---|---|
| 相对 1% 提升，基线转化 5% | **约 298 万** | 本文基准场景；基线 2% 要 769 万，基线 20% 只要 63 万 |
| **相对 5%** 提升，基线 5% | 约 11.9 万 | **MDE 缩 5× → 样本 ×25**（平方关系） |
| 人均收入，CV=3 / CV=5，相对 1% | 约 141 万 / 392 万 | 重尾指标 CV 常在 3–8 ⇒ "收入指标永远不显著"是量级问题，不是运气 |

```
500 并发实验 ÷ 20 层 = 每层约 25 个实验平分流量 → 单实验约 4%
5,000 万 DAU × 4% = 每天约 200 万个被分配的独立 unit；50/50 时首日最多约 100 万/组
同一 unit 第二天再来不是新的独立样本。累计独立样本应算集合并集：
  N_t = |U_day1 ∪ U_day2 ∪ ... ∪ U_dayt|，不能把“100 万/组/天”直接相加
若历史 cohort 显示首日后每组每天新增约 50 万个此前未出现的 unit：
  → 约第 5 天达到 298 万/组，再向上取整到完整周观察周内效应
若相对 MDE 收紧到 0.5%，目标样本约 ×4；在相同新增速度下约 3–4 周
```

这里的“样本”以**随机化 unit**计数。一个用户贡献多天或多个 session 的结果时，这些观测彼此相关：可以先聚合到用户级，或用 cluster-robust / repeated-measures 方法估方差；不能把每次访问当作新的独立用户。若稳定可触达人群本身少于 298 万/组，就必须提高分配比例、放宽 MDE 或更换设计，等待不会凭空产生新样本。

**推论 4**：在本文流量、MDE 与新增独立 unit 的假设下，实验可能需要完整周到数周；原因是样本量与 MDE 近似平方关系，不只是流程慢。实时看板适合数据质量与止损，决策指标何时有分辨率要由功效与序贯设计决定，不能把“7 天”外推到所有实验（§4.4）。

### 2.4 指标计算量与结果延迟

```
指标格数 = 500 实验 × 50 指标 × 2 组 × 10 维度切面 = 50 万格
每格 6 个累加量：count / sum / sumsq（没有 sumsq 就没有置信区间）+ CUPED 协变量三项
输入：7.5 亿条去重曝光 ⨝ 25 亿条用户日指标（5,000 万用户 × 50 指标）
两条通道，两个延迟目标：
  ① 护栏 / SRM 实时：5 min 滚动窗口，端到端 p99 < 10 min   ← 用于止损
  ② 决策指标 T+1 批：02:00 起跑，2–3 h，08:00 出结果       ← 用于结论
  ③ 迟到修正：T+3 全量重算（移动端离线队列可迟到 24–72 h）
```

> **面试金句**
> "实验平台里有两条完全不同的数据通道，把它们合并是这题最贵的错误。止损通道要的是十分钟内看到崩溃率翻倍 —— 它可以脏、可以近似、可以漏 1% 的数据。决策通道要的是七天后一个能被复现、能被重算、能被审计的数字 —— 它必须等迟到数据、必须可回填。一个五分钟就刷新的决策看板不是产品特性，它是在把偷看做成默认行为。"
> "There are two completely different data paths in an experimentation platform, and merging them is the most expensive mistake you can make here. The kill path needs to see a doubled crash rate within ten minutes — it's allowed to be dirty, approximate, and to drop one percent of the data. The decision path needs a number that, seven days later, is reproducible, recomputable, and auditable — it has to wait for late events and it has to backfill. A decision dashboard that refreshes every five minutes isn't a feature; it's peeking, shipped as the default."

## 3. 高层设计

### 3.1 先给最简单能工作的版本（10 个并发实验）

```
 experiments.yaml（提交进代码库，随构建打包）
        ▼
 App 进程 ──► bucket = murmur3(exp_id + ":" + user_id) % 100
                 │ [0,50) → control，[50,100) → treatment
                 └─► exposure(user_id, exp_id, variant, ts) 写日志
                                     ▼
                     每天一个 SQL：exposure ⨝ events GROUP BY exp_id, variant
                     两比例 z 检验，手算置信区间，贴进周会文档
```

**它能撑到哪**：10 个并发实验、单端产品。撞墙信号有三个，任一出现就走 v1：
两个实验开始改同一个 UI 区域（没有互斥机制）；或改一次实验要发一次版（配置随构建下发）；或有人问"这个结论可信吗"而你除了 p 值答不出别的（**没有 SRM，你不知道自己在不在污染中**）。

### 3.2 目标架构（500 并发实验，5,000 万 DAU）

```
 ┌── 控制面（低 QPS，强一致）────────────────────────────────────┐
 │  Experiment Console ──► Config Store(PG) ──► 配置编译器          │
 │    实验定义 / 分层分配 / 互斥组 / 定向条件      产出不可变快照      │
 │                                          config_version = 单调递增 │
 └────────────┬──────────────────────────────┬──────────────────────┘
              │ ① 全量配置（拉，30 s 轮询/长轮询）│ ② kill switch（推，秒级）
              ▼                                ▼
   ┌────────────────────────────────────────────────────┐
   │  分流 SDK（进程内，四端同源：Go / Java / TS / Swift）  │
   │   for layer in 20 层:                               │
   │       b = murmur3(layer.salt + ":" + unit_id) % 10000│
   │       variant = layer.lookup(b) → 定向条件求值        │
   │   曝光打点：只在"分支真的改变了输出"处调 log_exposure   │
   └───────────┬────────────────────────────────────────┘
               │ exposure（含 config_version、unit_id、exp_id、variant）
               ▼
        Kafka: exposure ──┬──► 实时流（5 min 窗口）──► 护栏聚合 + SRM 早检
                          │                              │ 越界 → 止损回路 ②
 业务事件（点击/下单/崩溃）─┴──► 对象存储（按 event_time 分区，Iceberg）
                                        │
                                        ▼
                          指标引擎（T+1，可重算，不做增量）
                            去重 → 触发过滤 → 用户日聚合 → 组内累加量
                                        ▼
                          统计引擎：SRM 门 → 方差缩减 → 检验 → 多重校正
                                        ▼
                          结果 API / 看板（SRM 未过 → 指标区整体屏蔽）
```

**数据流的四条边界**：

1. **控制面与数据面物理隔离**：控制面挂了，SDK 用最后一份缓存配置继续跑（fail-static：不可用时冻结在最后已知状态，而不是清空或放行）；数据面挂了，实验照常生效，只是没有结论。**反过来是灾难** —— 配置服务不可用时若降级成"全部走对照组"，全站会立刻产生 SRM 且不可逆。
2. **曝光事件证明处理真正生效，确定性哈希证明应分到哪组。** 平台可以从曝光物化 assignment audit 表，也可以为显式抽样实验保存分配记录；但热路径不需要先查一张“所有人在哪组”的数据库。分析前必须核对哈希/分配配置与实际曝光是否一致。
3. **指标是可重算的，不是增量更新的**。每天全量重算 N 天窗口，代价是多烧一份计算，换回迟到数据能正确回填、口径变更能被追溯 —— 增量表一旦被迟到数据污染就没办法修。
4. **SRM 是一道门，不是一个指标**：它在统计引擎的最前面，不过就不往下算。

## 4. 深挖

### 4.1 分流设计：哈希、分层、互斥组

**基本形式是一行：`bucket = murmur3_32(layer.salt + ":" + unit_id) % 10000`。三个决定，每一个都能单独扣分：**

**① salt 必须包含层 ID（或实验 ID），不能全站共用一个哈希。** 如果所有实验都用 `hash(user_id) % 100`，同一用户在不同实验会反复落到相同桶位，造成跨实验分组相关，使一个实验的处理与另一个实验的处理混杂。这里应称为**相关分配/混杂**；carryover 则是旧处理停止后仍残留的行为或状态效应，需要 washout、重置状态、换 salt 或长期 holdout 处理，不能只靠哈希独立消除。

**② 分桶粒度 10000，不是 100。** 100 桶时最小分配单位是 1%，而金丝雀阶段需要 0.1%；更要命的是 SRM 的检测分辨率 —— 分桶越粗，人数比本身的离散噪声越大，你会分不清是粒度问题还是真的污染。

**③ 分流单元必须跨会话稳定，且与用户身份绑定。** 这是最常见的污染源：

```
未登录 unit = device_id ──hash──► treatment ──用户登录──► unit = user_id ──hash──► control
                                                                    ↑ 同一个人换组了
假设 30% 的会话跨越登录边界、换组概率约 50%
  → 实验期内约 15% 的用户既暴露过 treatment 又暴露过 control
  → ① 效应估计被稀释（这些人是"混合处理"）② 稳定处理假设被破坏；但若换组在两侧恰好对称，SRM 仍可能不触发
```

正确做法二选一：**（a）登录时把 `device_id` 的分流单元 sticky 写进用户档案，此后一律用它**；**（b）全站统一使用一个跨登录稳定的匿名 ID**（登录只是给它贴标签，不改变它）。方案 a 需要一次写、能兼容存量；方案 b 更干净但要求所有客户端同时改造。

**分层（layer）与正交** —— 一个用户的分流状态是 20 个互相独立的坐标，每层一个：

```
  层 0（首页排序）  │████ exp_A 40% ████│██ exp_B 20% ██│░░ 空闲 40% ░░│
  层 1（搜索召回）  │██ exp_C 20% ██│██████ exp_D 50% ██████│░ 30% ░│
  层 2（结算页 UI） │███████ exp_E 100% ███████████████████████████│
  ...
  层19（推送策略）  │████ exp_Z 30% ████│░░░░░░░ 空闲 70% ░░░░░░░░░░░│

  层内互斥：一个用户在一层里只可能命中一个实验（桶区间不重叠）
  层间正交：salt 不同 ⇒ 20 次哈希互相独立 ⇒ 层 0 的 A 组在层 1 里仍是 20/50/30 分布
```

**正交性是要被检验的，不是被假设的**：任取两层做 2×2 列联表卡方检验，所有层对的 p 值应近似均匀分布。**p 值在 0 附近堆积 = salt 设计有问题**（最常见的原因是 salt 只用了自增的实验 ID，哈希对小整数输入的雪崩效应不足）。而**互斥组（mutual exclusion group）**判据只有一条 —— **两个实验会改同一个渲染输出或同一个决策，就必须同层**。改同一个结算按钮的两个实验放在不同层，"层间正交"救不了你：用户看到的是叠加后的界面，两个实验测到的都是叠加效应。

| 分配策略 | 每实验可用流量 | 交互效应风险 | 何时用 |
|---|---|---|---|
| 单层（全站互斥） | 100% ÷ 并发实验数 → 500 个实验各 0.2% | 零 | 并发实验 < 10 |
| **分层 20 层** | 100% ÷ 每层实验数 → 约 4% | 低但非零 | 本文；主流做法 |
| 临时重叠且无层/互斥治理 | 100% | 高且不可控 | 不要用于生产判决 |

分层的代价是**交互效应（interaction effect）不一定为零，而分层机制不会自动告诉你它发生了**。对高风险层对应事先定义交互项并监测，而不是相信正交就等于没有业务交互。例外是**有意设计的 factorial experiment**：多个因子可以同时随机化来估主效应和交互效应，但要预注册设计、保证各组合有足够样本，并用匹配的统计模型分析；它不是“随便把两个冲突实验放到不同层”。

### 4.2 配置下发与生效：客户端缓存是最大的污染源

| 方案 | 生效延迟 | 崩了会怎样 | 代价 |
|---|---|---|---|
| 每请求查配置中心 | 0 | **全站阻塞或全站降级** | +1 跳 p99、配置中心成为全站单点 |
| **进程内缓存 + 30 s 轮询/长轮询**（服务端） | 1–30 s | fail-static，用旧配置继续跑 | 需要版本号 + 心跳上报"我在用哪个版本" |
| App 冷启动拉一次 | **一次会话，可长达数天** | 同上 | **这是最大的污染源** |

**移动端的具体病灶**：App 启动时拉一次配置，用户不杀进程就永远不刷新。实验已经在控制台停掉三天，客户端仍在按旧配置执行 —— 现象是"实验已停但曝光还在涨"。三个必须做的事：

1. **曝光事件里必须带 `config_version`。** 指标计算时按"该版本属于本次实验的有效版本集合"过滤 —— 没有这个字段，你无法把铺开期的混合数据从分析窗口里切掉。
2. **配置带 TTL（如 30 min），并在任意一次业务 API 响应里搭车下发当前版本号**，客户端发现落后就异步拉取。不要为配置刷新单独建一条轮询 —— 它会在启动风暴时把配置服务打死。
3. **kill switch 与配置走两条通道。** 止损是秒级要求，配置是分钟级要求；合并意味着"停实验"的生效延迟被"下发全量配置"绑架。kill switch 的三个硬要求（默认值安全、路径上没有新依赖、可在配置服务不可用时生效）见 [`05-release-engineering.md`](../03-saas-platform/05-release-engineering.md) §2.4。

**生效延迟会混合 eligibility 与版本窗口，但不必然制造 SRM**：若拿到新配置的客户端仍对 control/treatment 对称哈希，组比可能正常；若配置到达与平台、版本、处理分支或曝光成功率相关，才可能出现 SRM。即使没有 SRM，把旧配置与新配置混在同一分析窗口也会改变实验总体，仍需隔离。

> **规则**：分析窗口的起点应由**预先定义的配置覆盖率阈值 + 稳定窗口**决定，不是点击启动的时刻。移动端很难真正“100% 铺满”，因此平台要按端/版本记录 `config_version` 收敛，冻结纳入规则，并把覆盖不足人群单独报告。

### 4.3 曝光日志与指标管道：去重、迟到、口径

**打点位置比打点格式重要一百倍。曝光必须打在"用户真的会看到差异"的那一行代码上，而不是分流函数被调用的那一行。**

```
❌ 请求入口：for exp in all_experiments: v = get_variant(exp); log_exposure(exp, v)
✅ 触发处：   if should_render_empty_state:
                  v = get_variant("new_empty_state")
                  render_empty_state(v)                 # control 和 treatment 都会渲染
                  log_exposure("new_empty_state", v)    # 两组都在同一触发点、同一时机打点
```

量化代价。某实验只改"搜索无结果页"，而只有 3% 的会话会走到那里：全量曝光下整体效应 = 真实效应 × 3%，相对提升被稀释 **33 倍**；样本量与 MDE 是平方关系，于是样本需求 **×33² = 1,089 倍** —— 7 天能出结论的实验变成 21 年。

**推论 5**：**触发分析不是一个优化项，它是这类实验能不能做的分水岭。**

曝光处理要分清三件不同的事：**消息重投、分组一致性、分析粒度**。把 `variant` 或 `event_date` 塞进一个“万能去重键”，会把同一用户跨组的问题藏成两条合法记录。

| 层 | 键 / 约束 | 它保证什么 | 失败时怎么做 |
|---|---|---|---|
| 传输幂等 | 稳定的 `exposure_event_id`（同一次曝光重试沿用） | 同一消息重投只入一次 | 重复丢弃；不能每次重试生成新 UUID |
| **分组一致性** | `UNIQUE(unit_id, experiment_id)`，行内保存 observed variant、首次曝光时间与 config version | 一个分析窗口内一个 unit 只属于一个 variant | 若后来出现不同 variant，标记 crossover、隔离该实验并诊断；不能按 variant 分成两行后当正常数据 |
| 日级物化 | `(unit_id, experiment_id, event_date)`，建立在已通过一致性检查的 assignment 上 | 降低日常 join 成本 | 只是派生表；样本量仍按 distinct unit，不把多天当独立样本 |

同一用户后续的点击、session、收入等**结果事件不应被去重掉**；它们要按预定义窗口聚合到随机化 unit，或用能处理组内相关的方差估计。上游 LRU/窗口去重可以省网络与计算，但最终正确性来自稳定事件 ID、assignment 唯一约束和可重算原始日志（见 [`13-ride-hailing.md`](13-ride-hailing.md) §4.3）。

**迟到（late arrival）**：按 **event_time 分区**（不是 processing_time）。watermark 只是事件时间进度估计，用来触发窗口的首次结果；它按各分区延迟分布和 idle-partition 策略标定，**不负责定义“还能迟到多久”**。本题另设 `allowed_lateness = 24 h`，并让窗口状态在首次出结果后至少保留这段修正期；超过状态保留期的事件进入原始日志/侧输出，由可审计回填重算，因此 T+1 的结果仍可在 T+3 被修正。迟到超过 24 h 的曝光占 **0.1–0.5% 量级**，听起来可以丢 —— **但它们不是随机分布的**，弱网、低端机、境外用户占绝大多数。丢弃它们等于把一个人群系统性地从实验里删掉，而这个人群恰恰最可能对性能类改动有相反的反应。这就是指标引擎必须**可重算**（全量重跑 N 天窗口，而不是往聚合表上增量累加）的成本理由。

**口径统一**：指标定义必须活在**指标层 / 语义层**（一份定义，实验平台和 BI 报表都读它，见 [`05-data-platform.md`](../02-architecture-patterns/05-data-platform.md) §6）。否则你会永久停在"实验平台算的 CTR 比 BI 高 2%"的对账地狱里 —— 而且每次对账都会发现是第三种口径。定义的三要素是**分析单元、聚合方式、时间窗口**，其中分析单元藏着本题最常见的统计 bug：

> **当分析单元 ≠ 随机化单元时（按 user 随机化、按 session 算 CTR），朴素方差公式会系统性低估方差 2–5 倍**，因为同一个用户的多个会话不独立。准确的倍数是**设计效应 `1 + (m−1)ρ`**（m = 人均会话数、ρ = 组内相关系数）—— 它**以 m 为上界**，只有在 ρ→1（同一用户的会话行为完全一致）时才等于人均会话数，实际业务里 ρ 通常在 0.2–0.6，所以 m=6 时倍数是 2–4 而不是 6。低估方差 ⇒ 置信区间偏窄 ⇒ p 值虚低 ⇒ **假阳性暴涨**。正确做法是 **delta method**（把"比率的方差"用一阶泰勒展开还原到用户级：`Var(X/Y) ≈ (1/μ_Y²)Var(X) − (2μ_X/μ_Y³)Cov(X,Y) + (μ_X²/μ_Y⁴)Var(Y)`）或用户级 bootstrap。自建平台十有八九漏了这一步。

### 4.4 统计引擎：样本量、序贯、CUPED、多重检验

**① 事前样本量与 MDE 必须是门禁信息，而是否拒绝要看治理策略。** 平台在创建时算出“以当前流量分配，检出相对 X% 需要几天”；对明显不可辨识的设计可阻止启动，也可以要求审批、提高分配比例或改成探索性研究。不能用一个固定“90 天”阈值替代业务成本判断。

**② 偷看（peeking）与序贯检验。** 固定视界检验（fixed-horizon test：样本量事先算好、只在终点看一次）如果每天看一次连续看 14 天，名义 α=0.05 的实际一类错误率会升到 **0.2 量级** —— 也就是说"每五个不该上线的实验，就有一个在中途某一天显著过"。

| 方法 | 能随时停吗 | 代价 | 现状 |
|---|---|---|---|
| 固定视界 | ❌ 只能看终点 | 无 | 默认；但没人真的忍住不看 |
| **always-valid inference / GAVI** | ✅ 任意时刻 | 同样本下功效更低，等价于多要 15–30% 样本 | Eppo 用 Howard et al. 2021 的 GAVI（[来源](https://arxiv.org/pdf/1512.04922)） |
| **corrected-alpha（CAA）** | ✅ 预定的若干个检查点 | 同上量级 | Statsig 的做法（[来源](https://docs.statsig.com/experiments/advanced-setup/sequential-testing)） |

既然团队一定会看，就把“能看”做成统计上合法的。序贯方法是常见选项之一，但不是所有平台或指标的默认；额外样本、边界和功效损失依具体方法、检查频率与指标分布而变，表中的 15–30% 只能作为该来源/场景的量级。

**③ CUPED（Controlled-experiment Using Pre-Experiment Data：用实验前协变量扣掉一部分可预测方差）**：`Y_adj = Y − θ·(X − μ_X)`，其中 `θ = Cov(X,Y)/Var(X)`，`X` 必须在处理前确定，`μ_X` 用与分组无关的方式估计。校验包括：预实验协变量两组平衡、没有处理后泄漏、交叉拟合/估计方式符合分析计划、调整后方差确实下降。CUPED 不要求样本里两组的调整后均值相等；它要求处理效应估计在随机化下保持无偏。

**诚实的数字**：厂商口径常说"方差降 20–50%、样本减半"。Microsoft ExP 自己的口径是：R²=0.4 时**中位有效流量倍数只有 1.66×**（功效 +22%），且**某个产品面 >68% 的指标倍数 ≤1.05×**（[Deep Dive Into Variance Reduction, 2022-11-15](https://www.microsoft.com/en-us/research/group/experimentation-platform-exp/articles/deep-dive-into-variance-reduction/)）。

> **不要在验证前把 CUPED 的收益写进容量模型。** 它必须按指标测量 effective traffic multiplier 才能计入排期。新用户通常没有“同一用户的历史指标”，所以这类协变量不给收益；但仍可能使用随机化前已存在且不受处理影响的设备、地区或注册来源等协变量。能否有效要验证，不能一概写成完全无效。

**④ 多重检验。** 一个实验 50 个指标，α=0.05 时"至少一个显著"的概率 = `1 − 0.95⁵⁰ = 92%`。再乘 10 个维度切面 = 500 次检验 —— "总体不显著，但在 Android 新用户上 +5% 显著"这句话**几乎必然出现在每一个实验里**。分层校正，三类指标三种待遇：

| 指标类 | 数量 | 校正方式 | 理由 |
|---|---|---|---|
| 主指标（OEC） | **1 个** | 不校正 | 事前声明，只有它能决定上不上线 |
| 次要指标 | 20–50 | **BH-FDR**（控制假发现比例） | 用于解释机制，不用于决策 |
| 护栏指标 | 5–10 | 预先定义可容忍劣化 `δ_guard`，做单侧非劣效/劣化检验，并纳入多重与序贯控制 | 把“统计上不等于 0”与“业务上不可接受”分开 |

**不要在 50 个指标上用 Bonferroni**（α 变成 0.001，功效直接崩掉）。也不要以为"p<0.05 就是 5% 假阳性"—— 在实验正向率约 8% 的先验下，显著结果里的假阳性比例（贝叶斯 FDR）约 **26%**（§4.7 展开）。

### 4.5 SRM 检测：本题唯一的必答点

**SRM（sample ratio mismatch：实际观测到的各组样本量之比，与实验设计的分配比例发生了统计上显著的偏离）。**

检验就是一个卡方拟合优度检验（chi-squared goodness-of-fit），H0 是"观测比例 = 设计比例"：

```sql
-- 每个实验、每个分析窗口都跑一次；输入是去重后的曝光表
SELECT experiment_id, SUM(POWER(observed - expected, 2) / expected) AS chi_sq
FROM (SELECT experiment_id, variant, COUNT(DISTINCT unit_id) AS observed,
             SUM(COUNT(DISTINCT unit_id)) OVER (PARTITION BY experiment_id)
               * designed_ratio AS expected
      FROM exposure_dedup WHERE event_date BETWEEN :start AND :end
      GROUP BY experiment_id, variant, designed_ratio) t
GROUP BY experiment_id;   -- chi_sq > 12.116 (df=1, p<0.0005) → 门禁不通过
```

**公开资料常见 p < 0.0005（Microsoft）或 p < 0.001（Kohavi）这样的保守起点**，但它们不是标准常数。平台仍要按变体数、检查频率、实验数量与告警用途控制多重/序贯错误；不能只把 0.0005 写死就宣称控制了 family-wise error。LinkedIn 约 10% triggered 实验、Microsoft 约 6% 触发 SRM 是特定时期与平台的公开快照，用来说明问题并不少见，不是你的基线目标。

**灵敏度有多高（能重算的）**：50/50 实验、总样本 n，触发阈值处的人数偏差是 `d = √(3.03 n)` —— `n = 20 万 → d ≈ 778 → 50.39%/49.61% 触发`；`n = 200 万 → d ≈ 2,461 → 50.12%/49.88%`；`n = 2,000 万 → d ≈ 7,782 → 50.04%/49.96%`（灵敏度按 `1/√n` 变化）。

**这个灵敏度用于捕捉很小的分配/观测不对称。** 但不要把 SRM 的“人数比例偏差 0.12%”与业务指标 MDE 的“转化相对变化 1%”直接比较：两者量纲和抽样分布不同。SRM 阈值应按预期比例、样本量、检查频率和多重检验策略设定；业务指标的 MDE 则来自效果与方差。两道门都要有功效分析，但不存在“SRM 灵敏度数值必须小于 MDE”的通用公式。

**六类根因，按发生频率排（这张表就是诊断清单）**：

| # | 根因 | 典型现象 | 定位方法 |
|---|---|---|---|
| 1 | 分流单元不稳定（跨登录换组、SDK 版本哈希实现不一致） | 全局 SRM，登录用户切面尤其严重 | 按"是否跨过登录"切分 SRM |
| 2 | **触发条件依赖 treatment**（treatment 更慢/更容易崩，用户在打点前就跳走了） | SRM 与页面性能指标同向 | 按"曝光打点前的漏斗步骤"逐级检查 |
| 3 | 曝光打点不对称（两个分支代码路径不同，一条漏打） | 某组曝光量整体偏低且比例稳定 | 代码 diff + 按 SDK 版本切分 |
| 4 | 数据管道过滤规则不对称（bot 过滤、去重、迟到丢弃） | SRM 只在最终表出现，流式表正常 | 逐级比对各阶段的行数比 |
| 5 | 配置铺开速度不一致；或实验重启但没重置分析窗口 | SRM 只在前几小时出现，或在重启时刻阶跃 | 按小时切分看是否收敛；对齐 `config_version` 变更时刻 |
| 6 | 跨实验复用桶位导致相关分配，或旧处理存在 carryover | 结论对上一实验/历史处理敏感 | 前者检查 salt 与联合分组表；后者检查 washout、残留状态和分时效应，二者不要混为同一根因 |

**诊断的通用方法是二分法**：把观测/期望人数与 SRM 统计量沿平台、版本、国家、小时和漏斗阶段切开，找偏差从哪一段开始。大多数真实 SRM 来自具体不对称，但检验本身仍有预设的一类错误率；频繁重复检查、稀疏切片或随机波动都可能产生假阳性。找不到根因时应保留门禁、核对多重/序贯口径并复现实验数据，不能断言“一定只是还没切对维度”。

> **面试金句**
> "SRM 应作为发布判决的硬门禁，而不只是黄条告警。它说明分配、触发曝光或数据处理至少有一处与设计比例不一致；在根因解释并修复前，效应估计不可信。页面可以保留诊断数据，但不能继续给出‘建议上线’。"
> "SRM should gate launch decisions rather than appear as a passive warning. It indicates that assignment, triggered exposure, or data processing is inconsistent with the planned allocation. Until the cause is understood and resolved, the effect estimate is not decision-grade. Diagnostics may remain visible, but the platform must not recommend launch."

### 4.6 护栏指标与自动止损

**护栏指标（guardrail metric：你不指望它变好、但绝不能让它变差的指标）分两类，待遇完全不同**：

| 类别 | 例子 | 延迟 | 噪声 | 能否自动止损 |
|---|---|---|---|---|
| **运维/信任类** | 崩溃率、错误率、p99 延迟、SRM、曝光量骤降、指标缺失率 | 分钟级 | 低 | ✅ **可以** |
| **业务/组织类** | 收入、留存、退订率、会话数 | 天–周级 | 高 | 默认人工；只有预注册的序贯决策、标签已成熟且代价明确时才可自动化 |

**为什么业务指标默认不自动止损，用数字说**：若把 `500 实验 × 10 护栏 × 每 10 min` 当成 72 万个相互独立、每次都用 α=0.001 的检验，朴素上界是 **720 次假拒绝/天**；真实检查彼此相关，因此不能把 720 当准确预测，但它足以说明“重复看固定阈值”不可用。收入等标签还会迟到和回补。若确需业务自动止损，要预注册单侧非劣效边界、使用合法序贯方法、控制跨指标错误率、等待标签成熟，并设置人工复核/可逆开关。

**自动止损的触发条件应是联合条件**，例如：`合法的序贯边界越界 ∧ 最小样本/事件数满足 ∧ 数据新鲜度达标 ∧ 指标在白名单 ∧ kill switch 可逆`。连续 3 个窗口和 N 万曝光只能作为待标定的场景起点，不是通用常数。运维指标通常比延迟业务指标更适合自动化；业务/质量指标并非永远不能自动执行，但需要更严格的设计与成熟标签。

**分级放量（ramp）**：`1% → 5% → 10% → 25% → 50%` 是本文高流量、可快速回滚场景的示例，不是固定阶梯。起点和档位要由爆炸半径、最小事件数、关键租户/ring、标签成熟时间与回滚速度决定；推进应 **validation-gated 而不是只按时间**（[GrowthBook, 2026-05-29](https://www.growthbook.io/insights/canary-releases-ai-models-what-changes-vs-traditional-software)）。低流量产品在 1% 跑 48 小时若只有约 200 次交互，不能声称已验证质量；可在安全门通过后扩大档位来获得分辨率，而不是“算不出就无条件跳级”。**止损路径**走独立 kill switch，并在配置服务不可用时仍可生效。

### 4.7 为什么大部分实验结论是错的

这一节没有架构，只有事实。**它是这道题里区分"造过平台"和"运营过平台"的地方。**

**① 基础比率低 ⇒ 显著结果里的假发现比例可能远超 5%。** 实验正向率：Microsoft 约 33%、Bing/Google 10–20%、Airbnb 约 8%，行业中位约 10%。先验成功率 8% 时，p<0.05 的显著结果中约 **26%** 是假阳性（贝叶斯 FDR：`0.92×0.025 / (0.08×0.8 + 0.92×0.025)`，其中 0.025 是双侧 α 里“方向为正”的那一半、0.8 是功效；若把双侧 0.05 全部计入则约 **42%**）。这些数字依赖先验与功效，只用于解释概念。“p<0.05 就是 5% 错误率”混淆了一类错误率与显著结果中的假发现比例。**平台必须先保证结论可信，再追求多、快、省**；吞吐不能补偿错误的随机化和分析。

**② 多重检验 + 偷看 + 事后切片三者叠加，外加团队内部的发表偏倚。** §4.4 算过：50 指标 × 10 切面 = 500 次检验，"某个切面显著"是必然事件；而不显著的实验不写文档、不进复盘、不进知识库，三个月后组织记忆里只剩下赢的那些。两个解法都是架构性的：**事后切片的结果默认标记为探索性、不能作为上线依据、必须显示校正后 p 值**；**实验结论由平台自动归档，无论结果如何，且"未得出结论"是一个一等状态**。

**③ 新奇效应与首因效应。** 新奇效应（用户因为“这是新的”而多点，几周后回落）与首因效应（老用户被打断习惯，短期指标先跌后回）都会让 2–4 周实验测到会变化的效应。长期 holdout 是校准累计增量和长期衰减的重要方法，但不是唯一手段；还可用分时效应曲线、延长随访、复现实验和预注册的早期/成熟期窗口。长期 holdout 自身也有机会成本、合规和总体漂移问题。

**④ ML 实验独有的污染：共生偏差（Symbiosis Bias, WWW 2025）。** A/B 两组的模型**共享同一份训练数据池**：A 组产生的探索数据被用去训练 B 组的模型，直接违反 SUTVA 的 "no hidden treatments"。**SRM 检测不到它，分层也挡不住它 —— 污染发生在离线训练管道里，而不是在线分流里。** 缓解三选一，代价都是每组能用的训练数据变少：cluster-randomized（有效样本量从用户数降到簇数）／**data-diverted**（两组训练数据物理隔离，每组数据减半、模型本身变弱）／user-corpus co-diverted（用户与物料池同时分流，实现最复杂）。

**⑤ 离线指标和线上 KPI 的关系是要标定的，不是给定的。** RecSys 2025 在 2,650 万次曝光、5 个测试组上实测：`Recall@20 → CTR` 的系数是 **0.8985（p<1e-4）**，而 `Recall@20 → CVR` 是 **−0.204（p=0.0174，负相关）**（[arXiv 2507.09566](https://arxiv.org/html/2507.09566)）。同一个离线指标，对两个线上指标一正一负。**所以"离线涨了就该上线"在推荐系统里是错的，而且是符号级的错。**

### 4.8 权限、隐私与审计：实验平台也是生产变更平台

Full Stack 开发者最容易把实验平台理解成“一个带图表的 feature flag”。实际上它同时持有用户定向条件、生产配置和行为结果，权限边界必须先于统计功能设计：

1. **最小权限与职责分离**：创建者可以写草稿，指标 owner 审核口径，生产 approver 批准分流与 ramp，operator 才能执行紧急停用。高风险实验与 100% 放量至少需要双人审批；任何人都不能在结论出来后静默改主指标或分析窗口。
2. **定向字段 allowlist**：SDK 只接收实验需要的属性；敏感属性、精确位置和自由文本默认不可用于定向。控制台与结果 API 展示聚合，不向普通实验者导出原始 `unit_id`。跨系统 join 使用受控的伪名标识，并按地域与用途限制访问。
3. **小群体保护**：维度切片低于最小 cohort 大小时抑制或合并，避免通过多次查询反推出个人。阈值要依据隐私模型和法规设定，而不是把一个固定人数当全球规则。
4. **保留与删除**：分别定义原始曝光、派生 assignment、指标聚合和审计日志的保留期；用户删除/撤回同意要能传播到可识别明细与后续重算。长期审计可保留不可逆聚合或依法需要的最小证据，而不是无限期保留全量行为。
5. **不可抵赖的变更记录**：保存谁在何时修改 salt、分配比例、定向条件、指标版本、分析窗口与 kill switch，以及审批人与生效版本。配置包应签名/校验，SDK 拒绝未知或回退版本；审计日志自身要限制读取并防篡改。

这些约束不会改变哈希公式，却决定一次“5% → 50%”究竟是可审计发布，还是无人负责的生产改动。

### 4.9 什么时候这整套方案是错的

| 场景 | 为什么本文方案错 | 应该做什么 |
|---|---|---|
| **DAU < 10 万，转化基线 < 5%** | 检出相对 5% 提升需 11.9 万/组（基线 5%）到 31 万/组（基线 2%）—— 全站流量全给一个实验也要 1–2 周，而实际上它只能拿到其中一部分，量级就是"一个月一个实验" | 只做大改动（MDE 设到 20%+）；排序类改动用交错实验做筛选；其余改动做定性研究 + 前后对比，别假装在做 A/B |
| **有网络效应的产品**（社交流、双边市场）；**供给侧改动**（定价、排序位次、库存分配） | 用户级随机化违反 SUTVA：treatment 通过好友泄漏到 control，或两组抢同一份供给此消彼长。**结论符号可能反过来** | 簇随机化（按社群/地理）或 switchback（时间片轮换：整个系统在时间片上交替使用 A 和 B）。代价是有效样本量从"用户数"掉到"簇数/时间片数"，通常降 2–3 个数量级 |
| **B2B / 企业客户产品** | 分流单元是账号，N = 几百 —— 统计功效根本不存在 | 分阶段 rollout + 事前事后 + 定性访谈。**明确说"这不是实验"** |
| **排序模型的日常迭代** | 每个候选模型都占 4% 流量跑 3 周，一年只能试 17 个版本 | 上交错实验 lane 做筛选（50–100× 样本效率），**但只当筛选器**：交错与 A/B 的方向一致率只有 82%、相关系数 0.6（[arXiv 2508.00751](https://arxiv.org/abs/2508.00751)），且在集合级优化场景会给出**相反**结论 |
| **强监管场景**（金融定价、医疗、招聘） | 事后切片 + 偷看在这里不只是统计问题，是合规问题；差别定价在部分辖区违法 | 预注册（pre-registration：分析方案在开跑前冻结）、固定视界、禁止事后切片、保留完整审计链 |

**一条通用判据**：当"跑一个实验所需的时间"超过"产品迭代周期"时，A/B 就不再是决策工具，而是决策的阻塞项 —— 此时正确的动作是**降低 MDE 要求或换筛选层**，而不是缩短实验时间。缩短实验时间只会让你更快地得到错误答案。

## 5. 失败模式

| 故障 | 影响 | 检测信号 | 应对 / 降级到什么 |
|---|---|---|---|
| 配置服务不可用 | 若 fail-open 到"全走对照组"→ **全站 SRM，且不可逆** | 配置拉取错误率、`config_version` 分布离散度 | **fail-static**：SDK 冻结在最后一份缓存配置；配置带本地持久化，进程重启也不丢 |
| 客户端缓存旧配置 | 实验已停但曝光仍在涨；分析窗口混入停用后的数据 | 停用后 N 小时的曝光衰减曲线 | 曝光带 `config_version` 并在分析时过滤；kill switch 走推送；配置 TTL 30 min |
| 某个变体的代码路径 panic | 该组用户数下降 → SRM；同时错误率上升 | SRM p 值 + 该变体错误率联合 | 自动止损（运维类护栏白名单内）；SRM 门禁屏蔽结论 |
| 曝光管道积压 | 决策指标延迟；**护栏止损同时失明** | 曝光事件端到端延迟 p99、consumer lag | 护栏走独立低延迟通道，不与全量日志共享管道；积压时优先保护栏 |
| 埋点变更导致某字段静默缺失 | 指标在部分人群上悄悄失真且**不报任何错** | **列级数据质量监控**（空值率 / 分布 / distinct count）| Uber D3 的真实事故：某费用组件在美国主要城市 **10% session 中缺失、持续 45 天**，靠人工发现，模拟影响约 **0.23% gross booking**（[来源](https://www.uber.com/us/en/blog/d3-an-automated-system-to-detect-data-drifts/)）。列级监控把 TTD 从 45 天降到平均 2 天 |
| 四端 SDK 哈希实现不一致 | 同一用户在客户端与服务端被分到不同组，归因错乱 | 跨端一致性抽样比对（同 unit_id 的 variant 是否一致） | 分流逻辑做成共享测试向量（同一组 10 万个 unit_id 的期望分桶），四端 CI 必须全绿 |
| 时区边界 / Bot 与内部员工流量 | 首尾两天样本被切错；bot 占 1–5% 且在两组间分布不均 | 首尾日曝光量与中间日的比值；排除前后的 SRM p 值变化 | 分析窗口按"完整本地日"对齐，首尾不完整日整天剔除；bot 单独排除，**排除规则对两组逐字对称**且版本化 |
| 迟到数据翻转结论 / 口径变更 | T+1 显著、T+3 不显著；历史结论与新结论不可比 | 同一实验历次重算的符号一致性；指标定义版本号 | watermark 关闭前结论标记 preliminary，决策在其之后；结果绑定 `metric_definition_version`，口径变更触发重算与标记 |

## 6. 演进路线

```
v0  10 个并发实验，单端。experiments.yaml 随构建下发；SDK 哈希分流；每天一个 SQL。
    → v1 触发条件（任一）：两个实验开始改同一个 UI 区域；或改配置要发版；
      或有人问"这结论可信吗"而你只能答 p 值（没有 SRM = 不知道自己在不在污染中）

v1  50–100 个并发实验，多端。配置中心 + 拉取式下发；分层（先 5 层）；曝光日志表；
    固定视界统计；**SRM 硬门禁**。
    → v2 触发条件：偷看导致的假阳性被业务发现（"上周还显著的怎么没了"）；
      或 T+1 指标回算跑不完一晚；或实验排队等流量（层内实验数 > 30）

v2  500 个并发实验 ← 本文。20 层 + 互斥组；触发式打点 + 三层去重；可重算指标引擎；
    序贯检验 + CUPED；多重检验分层校正；运维类护栏自动止损；指标层统一口径。
    → v3 触发条件：**SRM 触发率 > 8%**（分流或打点有系统性问题，先修再扩）；
      或排序类实验排队 > 4 周；或交互效应被实际观测到（同一决策的两个实验落在不同层）

v3  交错 lane（两层分流：先切 A/B vs interleaving，再切具体 lane，50–100× 样本效率，
    **只当筛选器**）+ 长期 holdout（数月，校准累计增量）+ 簇/switchback 随机化。
    信号：产品进入双边市场，或"所有实验累计增量"与大盘实际增长长期对不上。
```

## 7. 常见错误答法

| mid-level 会怎么答 | 为什么掉分 | 正确的说法 |
|---|---|---|
| 「用 `user_id % 100` 分组」 | 两个独立错误：① 所有实验共用桶位会造成跨实验分组相关；②自增 `user_id` 与注册时间等属性相关，直接取模不具备合格哈希的均匀与雪崩性质。carryover 是旧处理的残留效应，要另行处理 | "用经过跨语言测试向量验证的哈希，如 `murmur3(layer_salt + ':' + unit_id) % 10000`。salt 隔离层/实验；桶数按最小分流粒度选择，10000 只是支持 0.01% 桶位的常见例子。" |
| 「分流结果存数据库，请求时查」 | 预写 250 亿行并让每个请求远程读，会引入不必要的延迟与全站依赖 | "标准分流在本地按配置确定性计算；持久化配置、审计、人工覆盖和必要的显式 assignment，不预写用户×实验笛卡尔积。薄客户端可由边缘批量求值并缓存。" |
| 「p<0.05 就上线」 | 暴露四件事一件都没想：没有 SRM 门禁、没有多重检验校正、没有触发分析、没意识到偷看会把一类错误率抬到 0.2 量级。而且"p<0.05 = 5% 假阳性"本身就是错的 —— 先验 8% 时显著结果里约 26% 是假的 | "SRM 是硬门禁，不过就不出指标。主指标一个、事前声明、不校正；次要指标走 BH-FDR；护栏单侧宽松。要随时看就上 always-valid 边界，多花 15–30% 样本买合法性。" |
| 「做个实时看板，指标秒级刷新」 | 把止损通道和决策通道合并了。秒级刷新的决策指标 = 把偷看做成默认行为；而且迟到数据保证了实时值必然与最终值不一致，团队会看到结论反复横跳并因此不信任平台 | "两条通道：护栏走 5 分钟流式，端到端 p99 < 10 min，用于自动止损；决策指标走 T+1 可重算批处理，watermark 关闭前标记 preliminary。看板上直接不显示未达最小样本量的决策指标。" |
| 「曝光就在请求入口统一打一遍」 | 曝光量放大 8 倍（400 亿 vs 50 亿/天）是小事；致命的是触发分析失效 —— 一个只影响 3% 会话的实验，效应被稀释 33 倍，样本量需求 ×1089，7 天的实验变成 21 年 | "曝光打在分支真的改变了输出的那一行。这不是省钱，是这类实验能不能做的分水岭。" |

## 自测

遮住上文，你能不能说出：

1. **salt 里为什么必须含层 ID？** 不含会怎样？（否则跨实验复用桶位，分组结果相关、处理容易混杂；它解决的不是旧处理残留，carryover 还需 washout/状态重置等机制）
2. **SRM 的告警阈值是多少？为什么不是 0.05？** 总样本 200 万时多大的偏差会触发？（p<0.0005~0.001；因为每个实验每天都跑，要控 family-wise error；200 万时 50.12%/49.88% 即触发）
3. **曝光日志的三个量级差多少倍？** 分别靠什么手段拿掉？（400 亿 / 50 亿 / 7.5 亿，53:6.7:1；触发式打点拿掉 8×，三层去重拿掉 6.7×）
4. **MDE 缩小 5 倍，样本量变几倍？** 这个关系推出了什么架构结论？（25 倍，平方关系 ⇒ 实验周期是 2–3 周而非几天 ⇒ 决策指标不需要实时，实时只用于止损）
5. **哪些护栏适合自动止损？业务护栏什么时候也可以？**（分钟级、低噪声、可逆的运维/信任类最适合；收入/留存默认人工，但在预注册序贯边界、标签成熟、多重控制、最小样本和可逆执行均满足时可以自动化）
