# 03 · 案例：设计多租户向量检索服务（10 万租户）

> 这道题真正考的不是 ANN 算法，是**长尾（long tail）**：99% 的租户贡献不到 15% 的向量，却贡献 99% 的索引对象、元数据行和固定成本。
> 谁把"每个租户一个 HNSW 索引"当默认答案，谁在第 8 分钟就已经输了。

---

## 1. 需求澄清（前 5 分钟必须问出来的东西）

| 问题 | 为什么决定架构 |
|---|---|
| 租户规模分布？最大租户多少向量？ | 决定是否需要**租户内分片**；决定长尾策略 |
| 检索延迟 SLO？分不分租户档位？ | 决定能不能做冷启动（cold start）分层。**冷启动必须写进 SLO，不能藏** |
| 写入是批量导入还是持续增量？ | 决定段（segment）结构与 compaction 策略 |
| 需要过滤吗？除 tenant 外还有几维？ | 决定 pre/post/filter-aware 的选择 |
| 召回率（recall）目标？有没有客观 ground truth？ | 没有 ground truth 就没法调旋钮，只能凭感觉 |
| embedding 模型多久换一次？ | 这是**最贵的一条约束**，见 §6 |
| 合规要求？数据驻留（data residency）/ BYOK / 删除权（right to erasure）？ | 决定段文件加密粒度与是否允许共享段 |

**本文锁定的假设**：10 万租户，文本 chunk 检索，p95 ≤ 300 ms（不含 rerank）/ ≤ 450 ms（含 rerank），召回目标 Recall@10 ≥ 0.90，写入以持续增量为主，需要 tenant + 若干元数据过滤。

## 2. 规模估算：长尾是这道题的地基

租户规模服从重尾分布（heavy-tailed，近似 Zipf）。用四档建模：

| 档位 | 租户数 | 平均向量数 | 小计 | 占比 |
|---|---|---|---|---|
| 微型（免费/试用） | 90,000 | 3,000 | 2.7 亿 | 4.8% |
| 小型 | 9,000 | 60,000 | 5.4 亿 | 9.6% |
| 中大型 | 900 | 200 万 | 18 亿 | 32.1% |
| 巨型 | 100 | 3,000 万 | 30 亿 | 53.5% |
| **合计** | **100,000** | — | **≈ 56 亿** | 100% |

**第一条推论**：`99,000` 个租户（99%）只装了 `8.1 亿` 向量（14.4%）。而 `1,000` 个租户装了 85.6%。
⇒ **架构必须按档位分治（divide and conquer）**。用同一套机制服务这两端，一定在某一端翻车。

### 内存账（决定一切）

按 [`01-building-blocks/01-storage-engines.md`](../01-building-blocks/01-storage-engines.md) 的公式，HNSW 每向量内存 ≈ `d × 4 + M × 2 × 4` 字节：

| 方案 | 每向量 | 56 亿向量总量 | 月成本（内存 ≈ $6/GB，2026 年中量级，随时变动） |
|---|---|---|---|
| 1536 维 float32，M=32 | 6.4 KB | **35.8 TB** | ≈ $220,000 —— **直接出局** |
| MRL 截 512 维 float32，M=16 | 2.2 KB | 12.3 TB | ≈ $75,000 |
| 512 维 **int8** 量化，M=16 | 640 B | **3.6 TB** | ≈ $22,000 |
| 512 维 **binary**（1 bit/维）+ 原向量 rerank | 192 B | 1.07 TB | ≈ $6,600 |

Matryoshka（MRL）截断到 256–512 维通常只损 **2–3%** 精度、存储降 4×（2026 量级）；int8 标量量化（scalar quantization）再降 4×，配 top-100 用全精度向量重排（rerank）可把损失基本补回。

> **面试金句**
> "在 56 亿向量这个量级上，索引结构的选择远不如**每向量字节数**重要。1536 维 float32 到 512 维 int8 是 10× 的成本差，而召回只掉 2–3 个百分点 —— 前者决定我要不要建这个系统，后者可以用重排补回来。所以我的第一个设计决策是量化方案，第二个才是索引类型。"

### 第二条推论：冷热分层（hot/cold tiering）省的不是字节

按"日活租户 8%"估算，`8,000` 个活跃租户里几乎必然包含**全部 1,000 个大租户**（他们天天在用）。
⇒ 热向量 ≈ 48 亿 + 少量小租户 ≈ **总量的 87%**。

**冷热分层几乎省不到内存。** 它省的是：90,000 个微型租户的**索引对象数、元数据行、后台合并任务、监控时间线、备份对象**。
这是完全不同的一笔账 —— 见 §5 与 §8。

## 3. 高层架构

```
                         ┌──────────────── 控制面（Control Plane）────────────────┐
                         │  租户注册表 / 段清单(manifest) / 路由表 / 版本状态机     │
                         │  Postgres + 定期快照到 S3，数据面可缓存 5 分钟          │
                         └───────────────┬──────────────────────────────────────┘
                                         │ 拉取（不在关键路径）
   Query ──► API GW ──► Router ──────────┴──► Search Node (N 台)
             (authn,     (tenant→shard,          ├─ L0: 内存 HNSW（可写段）
              tenant_id   查 manifest)           ├─ L1: mmap 段（本地 NVMe，4–8 TB/台）
              来自 token)                        └─ L2: 对象存储段（S3，全量真相）
                                                       ▲
   Write ──► Ingest ──► Kafka(tenant 分区) ──► Indexer ─┘  seal / compact / GC
                                       └──► Embedding Worker（批量，可用 Batch API 省 50%）
```

**四个不可动摇的边界**：

1. **控制面不进关键路径**。路由表在数据面缓存；控制面挂了，已知租户继续可查，只是新租户开不了。
2. **对象存储是唯一真相**。搜索节点是可丢弃的缓存，重建靠拉段而不是重建索引。
3. **段（segment）不可变（immutable）**。写入 = 追加新段；删除 = 墓碑位图（tombstone bitmap）；更新 = 删 + 插。这与 LSM 完全同构（见 `../01-building-blocks/01-storage-engines.md`）。
4. **tenant_id 只能来自认证凭据**，绝不接受请求体参数。见 §7。

## 4. 深挖一：索引组织 —— 这道题的核心分叉

### 三种范式

| 范式 | 做法 | 优点 | 撞墙条件 |
|---|---|---|---|
| **A. 每租户独立索引**（silo） | 一个租户一个 HNSW/collection | 过滤退化成"选哪个索引"，ANN 质量不受影响；删租户 = 删文件 | **索引对象数爆炸**。10 万个索引 × 固定开销（fixed overhead）2–10 MB（图头、ID 映射、arena、后台线程）= **200 GB–1 TB 纯开销**，超过微型租户向量本身（量化后仅 ~170 GB） |
| **B. 共享索引 + 过滤**（pool） | 全库一个大索引，`tenant_id` 作 payload 过滤 | 索引对象少，内存利用率高，小租户零固定成本 | **过滤选择性（filter selectivity）极低时 ANN 退化**。一个 3,000 向量的租户占全库 0.00005%，图遍历几乎每一步都被过滤掉，`ef_search` 要开到几千才能凑够 top-10 |
| **C. 分组共享**（bridge，正解） | 小租户合并进"多租户合并段"，段内**按 tenant 分组建图**；大租户独立段 | 兼得两端 | 分组边界要跟着租户成长动态迁移，需要控制面协调 |

### 为什么 post-filter 在多租户里是错的

```
全库 56 亿向量 → ANN 取 top-1000 → WHERE tenant_id='acme' → 剩 0 条
```
`acme` 的 3,000 个向量出现在全局 top-1000 里的概率约 `3000/5.6e9 × 1000 ≈ 5×10⁻⁴`。
**post-filter 在多租户场景下不是"慢"，是"返回空结果"**。这条必须能脱口而出。

### 正确做法：过滤感知 + 租户物理分组

两个必须同时具备的能力：

1. **过滤在图遍历内部执行**（filter-aware traversal），而不是遍历完再筛。
2. **同租户向量在存储上物理相邻**，让低选择性过滤退化成**顺序扫描（sequential scan）**而不是随机 IO（random IO）。

工程对照（数字来自厂商文档，**上线前必须以官方 limits 页复核并压测**）：

- **Qdrant**：`tenant_id` 建 payload index 并标记为租户键（[多租户指南](https://qdrant.tech/documentation/guides/multiple-partitions/)），使同租户点在存储上聚簇（co-locate）；`hnsw_config.payload_m` 为分组单独建边，`full_scan_threshold` 控制"候选集小于阈值就直接暴力扫"的切换点。
- **Weaviate**：[原生 multi-tenancy](https://docs.weaviate.io/weaviate/manage-collections/multi-tenancy)，每 tenant 一个 shard，支持 `ACTIVE/INACTIVE/OFFLOADED` 三态 —— 这直接是 §5 的冷热分层原语。
- **Pinecone**：namespace，**每次查询只能命中一个 namespace**。
- **pgvector**：RLS + `tenant_id`，只适合几十到几百租户量级。

> ⚠️ 各类 2026 年对比文里的"Pinecone 10 万 namespace / Cloudflare Vectorize 5 万 namespace"之类的上限**未经一手核实且厂商在改**。**namespace 数量爆炸是多租户向量库最常见的翻车点**，选型评审必须把这一条列为阻塞项（blocker）。

### 被忽略的最优解：微型租户根本不需要 ANN

3,000 个 512 维 int8 向量 = **1.5 MB**。SIMD 暴力（brute-force）点积 ≈ 150 万次乘加，单核 **< 1 ms**，且 `Recall = 1.0`。

```
if tenant.vector_count <= FLAT_THRESHOLD:   # 经验取 10,000–50,000
    return brute_force_topk(segment, q, k)  # recall 1.0，无图内存，无 compaction
else:
    return hnsw_search(segment, q, k, ef_search)
```

**90% 的租户走这一条分支。** 它们不需要 HNSW 图（省 40% 内存）、不需要 compaction、不需要 ef 调参、删除立即生效。
把 `FLAT_THRESHOLD` 当成一个可调的产品参数，随硬件（SIMD 宽度、内存带宽）上调。

## 5. 深挖二：冷热分层

### 分层与延迟

| 层 | 介质 | 容量 | 命中延迟 | 单价（2026 年中量级，随时变动） |
|---|---|---|---|---|
| L0 可写段 | 堆内存 | GB 级 | < 1 ms | — |
| L1 热段 | mmap + page cache | 单机 4–8 TB NVMe | 2–15 ms | ~$0.10–0.15/GB/月 |
| L2 冷段 | 对象存储 | 无限 | **150 ms–2 s（首查）** | ~$0.023/GB/月 |

**段格式必须能直接 mmap 查询**（图与向量都是定长、按偏移寻址、无指针），不能"反序列化后重建索引"。
100 万向量重建 HNSW 要**几分钟**；mmap 一个 640 MB 段只要一次顺序读。turbopuffer、LanceDB、Vespa 这类"对象存储原生"的设计，核心就是这个约束。

### 加载延迟推算

```
段大小 = 向量数 × 640 B
  3,000 向量  →   1.9 MB → S3 GET ~30 ms + mmap ~10 ms  ≈  50 ms
 60,000 向量  →    38 MB → 单流 ~90 MB/s → ~420 ms；8 路并行 → ~120 ms
200 万向量    →   1.3 GB → 必须分片并行拉，16 路 → ~1.5 s（这类租户不该被卸载）
```

**卸载策略（offload policy）**：只卸载"向量数 < 20 万 且 连续 7 天无查询"的租户。大租户永不卸载 —— 卸载它们省下的钱远小于把 p95 打成 2 秒的代价。

### 把冷启动写进 SLO

```
档位 A（付费/活跃）：p95 ≤ 300 ms，常驻 L1
档位 B（免费/沉睡 >7 天）：首查 p95 ≤ 2 s，之后 30 分钟内驻留 L1
```
**不要试图对所有租户承诺同一个数字然后偷偷祈祷。** 分档承诺是诚实的，也是可售卖的（"专业版含索引常驻"）。

### 预热（warm-up）与惊群（thundering herd）

- **可预测的预热**：按租户的历史活跃时段 + 本地时区，在工作日 08:45 批量拉起。命中率提升的收益远高于预热成本。
- **惊群防护**：搜索节点全量重启后，所有租户同时打 S3。S3 单前缀约 **5,500 GET/s**，且你会被限流成雪崩。
  对策与 `../01-building-blocks/02-caching.md` 里的"回源（origin fetch）限流"完全同构：
  1. 段路径前缀**散列打散（spread / shard the key）**（`s3://idx/{hash(tenant)[:2]}/{tenant}/{seg}`）
  2. 加载路径加**信号量（semaphore）**（如单机 32 并发），超出的查询排队并返回 `Retry-After`
  3. 同段的并发加载做 **single-flight** 合并
  4. 节点重启走**滚动重启（rolling restart）+ 预热探针**，预热未完成不进 LB

## 6. 深挖三：写入路径

### 增量插入：LSM 化

HNSW 支持增量插入，但**图质量随插入顺序退化**，且删除只能软删（soft delete）。所以写入按 LSM 组织：

```
写入 → L0 内存平坦段（暴力可查，无图）
      → 满 64 MB 或 5 分钟 → seal 成不可变段（建图 + 量化）→ 上传 S3
      → 后台 compaction：L0 ≤ 4 段，逐层 10× 放大
查询 = 扇出所有活跃段 → 各取 top-k' → 全局归并 top-k
```

**段数直接乘进查询延迟**。段数从 4 涨到 20，p95 大约翻倍。所以 compaction 落后是一个必须告警的指标（`segments_per_tenant_p99 > 8` 报警）。

### 删除：墓碑与 over-fetch

软删除用 roaring bitmap 记录被删的内部 ID，查询时过滤。代价是**返回不足 k**：

```
over_fetch_k = ceil(k / (1 - deleted_ratio)) + safety_margin
```
- 墓碑率 10%：影响可忽略
- 墓碑率 **30%**：召回率开始明显下降，且内存里还压着 30% 的死向量
- ⇒ **墓碑率 > 20% 触发段重建**，或按段的 `deleted_bytes / total_bytes` 排 compaction 优先级

⚠️ 陷阱：租户执行"清空知识库再重导"会瞬间制造 100% 墓碑率并塞满 compaction 队列。**对"整租户重建"提供专门的 API 路径**（直接 seal 新段 + 原子切换（atomic swap）manifest + 删旧段），不要让它走普通删除路径。

### embedding 版本升级：这道题最贵的一节

**先算钱。** 56 亿 chunk × 平均 512 token = **2.87 万亿 token**。按 [voyage-context-4](https://blog.voyageai.com/2026/06/29/voyage-context-4/) 的 $0.12/1M（2026 年中量级，随时变动）：

```
2.87e12 / 1e6 × $0.12 ≈ $344,000  —— 一次全量重建
```
再加上重建期间**两份索引并存**的内存/存储翻倍。

> **面试金句**
> "换 embedding 模型的一次性成本是 34 万美元加一次全量双写（dual write）。所以这不是一个工程决定，是一个需要 VP 签字的决定。我会在架构上做三件事让它可行：per-tenant 版本切换、按活跃度排队的懒重建、以及一个能在切换前用离线 recall 对比新旧模型的评测集 —— 因为**新模型未必更好**，而这笔钱花出去是不可退的。"

不停服重建（zero-downtime rebuild）的六步（与 `../03-saas-platform/05-release-engineering.md` 的 schema 迁移六步法同构）：

```
1. 双写      新写入同时进 v1 与 v2 索引（只对已进入迁移队列的租户）
2. 回填      按优先级队列 backfill：先 5 个内部租户 → 小租户抽样 → 大租户
             用 Batch API（三家均 50% off）+ prompt cache，成本可再降一半
3. 影子读    v1 返回结果给用户；同时查 v2，离线比对 Recall@10 / NDCG@10 重叠度
4. 灰度切    per-tenant 元数据 `active_embedding_version: v2`，1% → 10% → 100%
5. 观察      线上指标：点击率、无结果率、rerank 后 top-1 变化率。留 ≥ 7 天
6. 回收      确认无回滚需求后删 v1 段（保留 manifest 记录以备审计）
```

关键：**切换粒度是租户，不是全局**。任何时刻可以把单个租户切回 v1，代价是 O(1) 的元数据写。
关键 2：**查询侧必须带版本**。`query_embedding` 用哪个模型算，由租户的 `active_embedding_version` 决定 —— 用 v1 的 query 向量查 v2 的索引，结果是纯噪声，而且**不会报错**。这是这类迁移最阴险的 bug，必须在段头写入 `model_id` 并在查询时断言。

## 7. 深挖四：查询路径

### 延迟预算（latency budget）分解（p95，含 rerank 目标 450 ms）

| 阶段 | 预算 | 备注 |
|---|---|---|
| 认证 + 路由 + manifest 查表 | 5 ms | manifest 本地缓存，miss 时 +20 ms |
| Query embedding | 40 ms（API）/ 8 ms（本地小模型） | **最容易被忽略的一段**；可缓存，命中率 30–60% |
| 段加载（热） | 0 ms | 冷则 150 ms–2 s，走档位 B |
| BM25 检索 top-50 | 12 ms | 与 ANN 并行 |
| ANN 检索 top-100 | 8–25 ms | `ef_search` 是唯一运行时旋钮 |
| RRF 融合 | < 1 ms | `score(d) = Σ 1/(60 + rank_i(d))` |
| Rerank（cross-encoder，50 候选） | **100–200 ms** | 端到端最大单项 |
| 取回原文 + 序列化 | 15 ms | |
| **合计** | **≈ 200 ms（无 rerank）/ 400 ms（含）** | 留 10% 余量 |

**Rerank 占了近一半预算。** 所以它必须是可开关的：低延迟档关掉，质量档打开。头部 reranker 延迟在 **~190 ms（Jina v3 档）到 ~600 ms（Voyage 2.5 / Cohere 档）** 区间（第三方 2026 测评口径，跨 harness 不可直接横比）。

### 召回 / 延迟旋钮

| 旋钮 | 方向 | 代价 |
|---|---|---|
| `ef_search` 64 → 256 | 召回 ↑ 数个百分点 | 延迟约 2–3× |
| `nprobe`（IVF） | 同上 | 同上 |
| over-fetch k → 3k 后重排 | 补墓碑与量化损失 | 内存带宽 |
| 量化 int8 → binary | 内存 ↓ 4× | 必须配全精度重排，否则召回崩 |
| rerank 候选 30 → 100 | NDCG ↑ | 延迟线性增长 |

**先定召回目标，再反推旋钮，最后看延迟够不够。** 反过来做（先卡延迟再看召回）会得到一个没人知道好不好用的系统。

### 混合检索（hybrid search）是默认，不是加分项

纯 dense 在**错误码、SKU、函数名、罕见实体、受控词表（controlled vocabulary）**上系统性失效 —— embedding 会把 `ERR_4021` 映射到"错误码语义邻域"从而召回错误对象。BM25 在这里不可替代。

但要诚实：**裸 RRF 相对 BM25 只有约 +1.3% NDCG，调优（alpha/权重 + 领域适配 domain adaptation，约需 40 条标注 query-relevance 对）后约 +7.5%**（2026 实测口径）；领域越窄绝对增益越小（专利检索绝对增益仅 +0.0094 NDCG@100）。
**"打开 hybrid 开关就有 26–31% 提升"的说法未见可核对的原始实验，不要对客户承诺。** 详见 `../04-ai-agent-systems/02-context-engineering-and-rag.md`。

### 不要为了"看起来先进"上多向量（multi-vector）

ColBERT / late interaction 在 1M 文档上：dense ≈ 3 GB，**无量化 late interaction ≈ 102 GB**，2-bit ≈ 6 GB。在 56 亿向量的多租户场景，这个乘数是灾难性的。要上就必须同时上 PLAID 或 [MUVERA](https://arxiv.org/html/2405.19504)（FDE，Weaviate 1.31 起是 `Encoding.muvera(...)` 一个配置开关）。

## 8. 深挖五：隔离与安全

### 跨租户泄露（cross-tenant leakage）的七条真实路径

| # | 路径 | 防御 |
|---|---|---|
| 1 | 应用层忘了加 `tenant_id` 过滤 | **引擎内强制**：查询接口不接受"无 tenant 约束"的调用形态 |
| 2 | `tenant_id` 来自请求体，被客户端篡改 | **只从认证凭据派生**，见下方代码 |
| 3 | post-filter：结果被滤掉，但**耗时/命中数**泄露他人数据分布 | 用 filter-aware；对返回计数做粗粒度化 |
| 4 | 共享 embedding 缓存，key 未含 tenant | `cache_key = hash(model_id, tenant_id, normalized_text)` |
| 5 | 语义缓存跨租户命中 | 语义缓存**必须按租户分区**（见 `../01-building-blocks/02-caching.md` §7b） |
| 6 | rerank 批处理跨租户混批，结果错配 | 混批可以，但候选必须携带 tenant 标签并在返回时断言 |
| 7 | 段文件路径可枚举 / 错误消息带别人的段名 | 段路径加 HMAC；错误消息只回不透明 request_id |

```python
# 错的：tenant 是入参
def search(tenant_id: str, q, k): ...          # 调用方少传一次 = 全库泄露

# 对的：tenant 是能力（capability），从已验证的 principal 推导
def search(ctx: AuthContext, q, k):
    scope = ctx.tenant_scope()                  # 从 JWT aud/claims 派生，不可伪造
    if scope is None:
        raise Forbidden                         # 没有 scope 就没有查询，不存在"全库查"这个形态
    return engine.search(q, k, partition=scope.tenant_id,
                         acl_filter=scope.doc_acl)   # ACL 也进引擎，不在应用层后过滤
```

**文档级权限（document-level permission）也必须进引擎。** "先 ANN 取 100 条再按用户 ACL 过滤"和 post-filter 是同一个错误：一个只能看 0.1% 文档的用户会拿到 0 条结果。把 ACL 编成 payload（`allowed_groups: [...]`）在遍历时过滤，或对高选择性 ACL 单独建分组段。

**加密与删除权**：BYOK 租户的段用其 DEK 加密（段级，不是行级），**这类租户不能进合并段**（合并段无法按租户单独销毁密钥）。GDPR 删除权的可执行版本是"删掉这个租户的所有段对象 + 销毁 DEK"，而不是"发一批 delete 请求等 compaction"。

## 9. 成本模型：长尾租户的固定成本（fixed cost）才是杀手

按 §2 的量化方案（512 维 int8，3.6 TB 全量），一个 2026 年中量级的月度账（随时变动）：

| 项 | 用量 | 月成本 |
|---|---|---|
| L1 内存/NVMe（热 25% + page cache） | ~900 GB RAM + 12 TB NVMe | $5,400 + $1,600 |
| L2 对象存储（全量 + 版本） | 4.5 TB | $105 |
| 搜索计算（峰值 5k QPS，40 核心机 × 12） | — | $6,800 |
| 索引/compaction 计算 | — | $2,200 |
| Embedding（增量写入，非重建） | 8 亿 token/月 | $96 |
| Rerank API（30% 查询开启） | — | $1,900 |
| 跨 AZ 流量 + 备份 + 可观测 | — | $3,000 |
| **合计** | | **≈ $21,100/月** |

**天真的算法**：$21,100 / 100,000 = **$0.21/租户/月**。这个数字会误导所有人。

**正确的拆法**：

```
边际成本（微型租户）：
   存储 3,000 × 640 B = 1.9 MB × $0.023/GB      ≈ $0.00004
   查询（月 50 次 × 暴力扫 1.5 MB）              ≈ $0.0002
   ───────────────────────────────────────────────────────
   合计                                          ≈ $0.0003 / 月

固定成本（每个租户，不管用不用）：
   控制面元数据行 + 索引 + 备份                  ≈ $0.01
   监控时间线（10 条指标 × 高基数标签）          ≈ $0.04   ← 最大的一项
   段对象 + manifest 的 S3 PUT/LIST 请求         ≈ $0.02
   后台任务调度 / 健康检查 / 生命周期作业        ≈ $0.03
   ───────────────────────────────────────────────────────
   合计                                          ≈ $0.10 / 月
```

⇒ **70,000 个免费租户 = $7,000/月 纯固定成本，超过了全部对象存储 + embedding + rerank 的总和。**

**对策（按 ROI 排序）**：

1. **监控降采样（downsampling）**：免费租户不打 per-tenant 时间线，只打分桶直方图。这一条通常砍掉 40% 固定成本。
2. **超级合并段**：1,000 个微型租户装进一个段对象，manifest 里按 tenant 记录 offset 区间。段对象数从 90,000 降到 90。
3. **深度归档（deep archive）**：连续 90 天无查询 → 段合并进归档对象 + 控制面行标记 `dormant`，唤醒延迟承诺 30 s（写进免费档条款）。
4. **免费档配额**：向量数上限 5,000、QPS 上限 1，超出即提示升级。**免费档的成本必须有硬天花板（hard cap）**，否则单个滥用租户能吃掉整个免费额度预算。

## 10. 什么时候不要这么做

| 情况 | 该做什么 |
|---|---|
| 租户 < 500 且总向量 < 500 万 | **pgvector + RLS + `tenant_id` 复合索引**。别建这个系统，它的运维成本会吃掉你两个工程师 |
| 语料是单仓库/数百个文本文件 | 直接给 Agent 文件系统工具（grep/glob）。小规模下它质量更好，且零索引成本。**但企业级异构语料上纯词法检索（lexical search）会崩** |
| 每租户文档 < 1,000 且模型上下文够 | 全量塞进 prompt + prefix cache，比建检索基础设施更快更便宜。**前提是知识库稳定**，一更新缓存全失效 |
| 只有一个巨型租户 | 那不是多租户问题，是分片问题。别引入 tenant 抽象 |

**六条反模式（anti-pattern）**：

1. **给每个租户建 HNSW 图**。10 万个图的固定开销超过数据本身。
2. **post-filter 多租户**。不是慢，是返空。
3. **相信对比文里的 namespace 上限**。厂商在改，必须查官方 limits 页 + 压测。
4. **以为冷热分层能省内存**。它省的是租户数，不是字节；省字节的是量化。
5. **在应用层做 ACL 后过滤**。与 post-filter 同源的错误。
6. **换 embedding 模型不先算重建成本**。34 万美元不是"顺手升级一下"。

## 11. 失败模式与演进

| 失败模式 | 信号 | 应对 |
|---|---|---|
| 巨型租户单段超过单机内存 | 单租户段 > 60% 机器内存 | **租户内分片（intra-tenant sharding）**：按 `hash(doc_id) % N` 切片，查询扇出（fan-out）+ 归并；这是尾延迟放大（tail latency amplification）场景，N 别超过 8 |
| 冷启动风暴（全节点重启） | S3 5xx/503 激增、p99 飙到 10 s | 前缀散列 + 加载信号量 + single-flight + 滚动预热 |
| Compaction 与查询争 CPU | compaction 期间 p99 抖动 2× | compaction 独占 cgroup 配额；或把 compaction 移到独立节点，产物写 S3 |
| 墓碑爆炸 | `deleted_ratio > 0.3` | 整租户重建走专用路径；对普通删除做速率限制 |
| Embedding 服务限流 → 写入积压 | Kafka lag 持续增长 | 写入侧背压（backpressure）到 API（返回 429 + `Retry-After`），**不要无声堆积**；批量导入走 Batch API |
| 查询侧 embedding 模型与索引版本错配 | 召回率断崖但**无报错** | 段头写 `model_id`，查询时断言相等；这是最阴险的一类 bug |
| 租户成长跨档但仍在合并段 | 单租户在合并段占比 > 30% | 控制面检测 + 自动"晋升"到独立段（后台重建 + 原子切 manifest） |

### 演进路线

```
v0  0–1,000 租户 / < 500 万向量
    pgvector + RLS，一个 Postgres。不引入新组件。

v1  1,000–1 万租户 / < 2 亿向量
    专用向量库单集群 + tenant payload index + 过滤感知搜索。
    此时开始需要：段化写入、混合检索、rerank。

v2  1 万–10 万租户 / 数十亿向量   ← 本文
    控制面/数据面分离 + 对象存储原生段 + 冷热三层 + 量化 + 分档 SLO。
    撞墙信号：索引对象数 > 3 万、manifest 查询 p99 > 50 ms、
              冷加载 p95 > 3 s、固定成本占比 > 30%。

v3  巨型租户 silo + cell 化
    单个 cell 服务 ~2 万租户，cell 之间不共享数据；
    合规/驻留租户走独立 cell。爆炸半径 ≤ 1/N（见 ../03-saas-platform/01-control-plane.md）。
```
