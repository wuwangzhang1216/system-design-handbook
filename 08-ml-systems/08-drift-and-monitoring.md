# 08 · 漂移检测与 ML 监控
> ML 系统坏掉的方式不是 500，是 200 —— 每个请求都成功返回，只是答案一天比一天差。
> 你的 APM 面板对这件事结构性失明：它测的东西里根本不包含"预测对不对"。

---

## 读这一章之前

**你在工作中遇到过这个**

你的支付风控模型上线半年，面板一直全绿：HTTP 错误率 0.00%，p99 42 ms，GPU 利用率 55%，半年零告警。
季度复盘时风险团队甩出数字：过去 6 周欺诈拦截率从 91% 掉到 78%，多赔出去约 40 万美元。
根因是 App 一次埋点重构让 `device_age_days` 在 12% 的会话里变成 null，
而特征管道按"缺失就填训练集中位数"的约定把它填成了 180 天 ——
于是这批真正的新设备在模型眼里全是"用了半年的老设备"，风险分被系统性压低。
从埋点发版到有人发现隔了 41 天，这 41 天里没有任何一条告警，因为**缺失率这一列从来没被监控过**，
而填充之后的特征分布看起来非常正常。

**需要先懂的概念**

| 概念 | 一句话 | 详见 |
|---|---|---|
| p50 / p99 与尾部 | 排序后处在某个百分位的值；平均值会把局部损坏平均掉 | [00/00 §3](../00-foundations/00-concepts.md#3-为什么平均值是骗人的p50--p90--p99) |
| SLI / SLO / 燃尽率告警 | 请求成功/延迟常转成“好事件 ÷ 有效事件”；新鲜度、容量等也可用 gauge/分布。多窗口多燃尽率适合有错误预算的事件型 SLO | [05/01 §1 §6](../05-reliability/01-slo-and-error-budget.md#1-sli优先写成-好事件--有效事件) |
| 指标基数 | 每多一个标签维度，时间序列数按乘法涨，成本也按乘法涨 | [05/02 §2](../05-reliability/02-observability.md#2-指标基数是最容易失控的成本变量) |
| 训练/服务偏斜 | 同一个特征在训练侧和服务侧算出来的值不一样；五种成因各有指纹和检测手段 | [06 §2](06-feature-and-data.md#2-训练服务偏斜五种成因各自的检测手段) |
| 样本量与统计功效 | "多大把握、检出多大差异、需要多少样本"三者互锁，定死两个就定死第三个 | [07 §4](07-model-quality-and-experimentation.md#4-样本量与统计功效先算再决定要不要做这个实验) |
| LLM 侧的静默降级 | KV cache 打满时 vLLM 不返回 429，只是悄悄抢占重算，错误率仍是 0 | [04/01](../04-ai-agent-systems/01-llm-serving-infra.md) |

**这一章要回答的问题**

1. 错误率 0.00%、延迟不变、面板全绿，模型却已经坏了 —— 你到底靠什么信号发现它？多久能发现？
2. PSI 报了 0.31，该不该叫醒人？该不该重训？为什么这两个问题的答案可以是"都不"？
3. 标签要 90 天才回来，这 90 天里你监控什么？无标签的性能估计能不能信？
4. 自动重训该不该做？如果做，哪几道闸门是一道都不能省的？
5. 推荐系统的训练数据是它自己写出来的，怎么让它不越跑越窄？这件事要花多少钱？

**本章新引入的术语**

| 术语 | English | 一句话定义 |
|---|---|---|
| 数据漂移 | data drift / covariate shift | 线上输入特征的分布和基线不一样了，但"同样的输入该给什么答案"这条规律没变 |
| 概念漂移 | concept drift | 同一个输入对应的正确答案变了 —— 模型学的那条映射本身过期，输入分布可以一动不动 |
| 标签延迟 | label delay | 从做出一次预测，到拿到"这次预测到底对不对"的真值，中间隔的那段时间 |
| 代理指标 | proxy metric | 真标签没回来之前先用的可观测量，要求滞后短、且与真标签的相关性经过实测标定 |
| 群体稳定性指数 | PSI (Population Stability Index) | 按基线的分位数把一个特征切成固定的桶，比较两个时期落进各桶的比例，加权求和成一个数 |
| 对抗验证 | adversarial validation | 训一个分类器专门去区分"这条样本来自基线还是来自当前"，它区分得越准说明两批数据差得越远 |
| 校准 | calibration | 模型打 0.7 分的那批样本里真实正例比例是不是也接近 70%；分布没变而校准坏掉是概念漂移的典型信号 |
| 预测熵 | prediction entropy | 单次预测的概率分布有多"平"；一批预测集体变平 = 模型对当前这批输入普遍没把握 |
| 曝光偏差 | exposure bias | 训练数据里只有系统曾经展示过的东西，没展示过的永远不产生任何标签 |
| 退化反馈回路 | degenerate feedback loop | 模型的输出变成下一轮的训练数据，把自己原有的偏好越放越大，最后收敛到只推很少几样东西 |
| 选择性标签 | selective labels | 只有被系统放行的样本才会产生标签，被拒的那部分永远不知道真相 |

## 1. 静默降级：为什么面板全绿而模型已经死了

普通服务的故障信号是**离散的、自暴露的**：调用超时会抛异常，schema 对不上会反序列化失败，
每一步都会改变 HTTP 状态码或延迟。ML 推理不会 —— 给它任何输入，它都会返回一个格式合法的分数。
**"这个分数是错的"不是一个运行时事件，它不产生任何异常。**

```
普通服务故障：信号离散、自暴露
   上游挂 ──► 连接超时 ──► 5xx ──► 告警触发        总耗时 T+30s
                │
                └─ 每一环都改变了状态码或延迟

ML 质量退化：信号连续、自洽
   埋点改了 ──► 12% 会话该列为 null ──► impute 成中位数 ──► 模型照常打分 ──► 200 OK
                                                                   │
   错误率 0.00% ─── p99 42ms ─── QPS 平稳 ─── GPU 55% ──────────────┘  面板全绿
                                                                   │
                        欺诈拦截率 91% → 78%（6 周，最后靠人复盘发现）
```

这不是某一家的特例，是这类系统的结构性特征，四类独立材料给出同一结论：

- **Uber**：training-serving skew、概念漂移、上游数据问题
  "can cause degradations in customer experience without throwing off any production alarms" ——
  所以他们把监控明确拆成 operational（可用性/延迟/吞吐）与 **prediction-level（score distribution、calibration、entropy）**
  两层（[Uber, 2025-10-30](https://www.uber.com/us/en/blog/raising-the-bar-on-ml-model-deployment-safety/)）。
- **Uber D3 的真实事故**：某个费用组件在美国主要城市 **10% 的 session 中缺失，持续 45 天**，
  期间没有任何服务级告警，靠人工发现；事后模拟影响约 **0.23% gross booking**，量级是数千万美元
  （[Uber D3, 2023-02-23](https://www.uber.com/us/en/blog/d3-an-automated-system-to-detect-data-drifts/)）。
- **LLM 服务侧同构**：vLLM 的 KV cache 打满时不会返回 429，而是静默抢占并重算，
  表现为 p99 抬升、错误率恒为 0，必须专门监控 `vllm:num_preemptions_total`（详见 [04/01](../04-ai-agent-systems/01-llm-serving-infra.md)）。
- 公开 AI 事故复盘的**中位检测时间约在"天"这个量级（有二手统计给到 ~4.5 天，可信度低，只当量级看）** ——
  等发现时，干净回滚的窗口通常已经关闭：这期间产生的日志已经被下一轮训练吃进去了。

> **面试金句**
> 「运维指标是给系统看的，预测分布是给模型看的。一个 ML 系统可以在错误率 0%、p99 完全不变的情况下彻底坏掉 ——
> 所以模型监控是**第二套栈**，不是 APM 面板上多加几块板子。」
> *"Ops metrics tell you the service is up. They tell you nothing about whether the model is still right.*
> *An ML system can be completely broken at a 0% error rate — that's why model monitoring is a second, separate stack,*
> *not a few extra panels bolted onto your APM dashboard."*

## 2. 数据漂移 vs 概念漂移：这条界必须画清楚

把一次预测看成 `X → Y`，只有三个分布会变，它们的可检测性完全不同：

| 变化类型 | 变的是什么 | 典型成因 | 无标签能否检出 | 模型还准吗 |
|---|---|---|---|---|
| **数据漂移**（covariate shift） | `P(X)` 变，`P(Y\|X)` 不变 | 新渠道流量、新国家上线、App 改版、上游数据 bug | **能**（PSI/KS/JS/对抗验证都是干这个的） | 可能仍然准（如果新区域在训练分布覆盖内） |
| **标签漂移**（label / prior shift） | `P(Y)` 变，`P(X\|Y)` 不变 | 欺诈团伙集中作案、大促期间转化率整体抬升 | 部分（预测分布均值会动） | 阈值和校准先坏，排序可能还好 |
| **概念漂移**（concept drift） | `P(Y\|X)` **本身变了** | 欺诈手法换代、用户偏好迁移、竞对上线新功能、政策变化 | **原理上不能** | 直接坏，且越用越坏 |
| **训练/服务偏斜**（skew） | 训练与服务的**实现**不一致 | 离线 SQL 与线上 Go/C++ 两套实现、impute 逻辑不同 | 能（但必须**对训练基线**比） | 上线第一天就已经坏了 |

**为什么概念漂移更危险，答案是一句话：它可以在输入分布完全不变的情况下发生。**
欺诈团伙换了一套手法，设备指纹、金额分布、时段分布可以和上个月一模一样 ——
所有基于 `P(X)` 的检测器（PSI、KS、JS、对抗验证）在原理上都看不见它，
因为它们从头到尾没有用过 `Y`。能提供概念漂移证据的包括真标签、经验证的代理指标，以及**标签回流后**计算的校准；
（预测分数 0.7 那一桶的真实正例率是不是还在 0.7 附近 —— 但它同样要等标签）。

**同样重要的反方向澄清：漂移不等于性能下降。**
一个模型完全没用到的特征漂移到 PSI=0.8，对线上毫无影响。
2025–2026 的行业口径已经从"报警即行动"退到"漂移只是线索"：
**drift without eval impact is a false alarm, and it burns your on-call.**
所以第 3 节讲怎么测，第 6 节讲**测出来之后凭什么才允许它叫醒人**，这是两件事。

**skew 和 drift 回答不同问题。** skew 拿线上实际值与训练/回放值比；drift 最好维护双参照：冻结的训练/发布 reference 发现累计偏移，上一窗口或季节模型发现短期异常。Google Vertex AI 的产品界面把 skew 与 drift 分开
（[Google Cloud](https://cloud.google.com/blog/topics/developers-practitioners/monitor-models-training-serving-skew-vertex-ai)）。
只做 drift 的系统会漏掉一整类问题：**部署第一天就存在的实现差异** —— 因为它每天都和昨天一样，永远不产生 delta。
skew 的五种成因、各自的指纹和检测手段（逐列精确匹配率 / 差值均值 / 差值 P99）在 [06 §2](06-feature-and-data.md#2-训练服务偏斜五种成因各自的检测手段)，
本章只负责"它上线之后有没有变坏"这一半。

## 3. 检测方法：适用面、阈值经验值、误报特征

| 方法 | 适用数据类型 | 输出与量纲 | 阈值经验值 | 主要误报来源 / 撞墙条件 |
|---|---|---|---|---|
| **PSI** | 数值（分桶后）、低基数类别 | 无上界的正实数 | `<0.1` 忽略 / `0.1–0.2` 调查 / `>0.2` 行动 | 阈值源自信用评分行业经验，**不是统计推导**；桶数和桶边界一变，数值就变 |
| **KS 检验** | 连续数值，单变量 | D 统计量 + p 值 | 传统看 `p<0.05` | **样本 >50,000 行/batch 时几乎每个 batch 都报**：p 值随 n 单调趋 0，必须配效应量 |
| **JS 散度** | 数值（Vertex AI 默认用它） | 有界、对称。⚠️ **上界取决于对数底**：log₂ 时是 `[0,1]`，自然对数时是 `[0, ln2≈0.693]` —— 抄阈值前必须确认库用的是哪个底 | Vertex AI **默认告警阈值 0.3**，可 per-feature 覆盖 | 有界这一点让它比 KL 好用；对小概率桶不敏感，长尾变化会被吃掉 |
| **KL 散度** | 数值/类别 | 无上界、不对称 | 无公认阈值 | 基线里为 0 的桶会让它发散到 ∞，必须平滑；不对称意味着 A→B 和 B→A 不是一个数 |
| **L∞ 距离** | 类别（Vertex AI 默认用它） | `[0,1]` | 同上，默认 0.3 | 只看差最大的那一类；十个类各动 5% 它读数很小 |
| **Wasserstein 距离** | 连续数值 | 与特征同量纲 | 按特征标定（如"平均移动了 3 天"） | **可解释性最好**：读数直接是"分布平均搬了多远"；对量纲敏感，换单位就换阈值 |
| **对抗验证** | 多变量、混合类型 | AUROC `[0.5, 1.0]` | `0.5` 无漂移 / `>0.7–0.8` 可区分 / `≈1.0` 强漂移 | 能抓多元联合分布的变化（每个边缘分布都没动，联合关系变了）；**官方明确警告 AUROC 不能直接翻译成性能影响**，且比 PCA 法更吃数据 |
| **PCA 重建误差** | 多变量数值 | 重建误差均值 | 偏离参考集 **±3σ** | 对特征相关结构的破坏敏感；PCA 本身要在基线上拟合并冻结 |
| **预测分布 / 熵；有标签后的校准** | 模型输出 +（ECE 需要标签） | 分数分位数、ECE、熵 | 按模型标定 | 无标签时只能看分数/熵并作为线索；校准必须等标签或可靠代理到达 |

（对抗验证的标准实现是 LightGBM + 交叉验证 AUROC；PCA 与 CBPE 的口径见
[NannyML multivariate drift](https://nannyml.readthedocs.io/en/stable/how_it_works/multivariate_drift.html)。
Vertex AI 的监控频率**默认 24 小时、最小 1 小时**，并提供 `--prediction-sampling-rate` 降采样控成本。）

**PSI 的实现里有一个几乎人人踩过的 bug**：桶边界必须冻结在基线上。

```python
# 正确：桶边界来自基线，之后永久冻结（连同 baseline 一起版本化存起来）
edges = np.quantile(baseline, np.linspace(0, 1, 11))      # 10 桶，等频
edges[0], edges[-1] = -np.inf, np.inf                     # ← 见下方"错误三"，这一行不能省
p, _ = np.histogram(baseline, bins=edges); p = p / p.sum()
q, _ = np.histogram(current,  bins=edges); q = q / q.sum()
eps = 1e-6                                                 # 空桶必须平滑，否则 log 发散
p, q = p / p.sum(), q / q.sum()                            # clip 之前先归一
p, q = np.clip(p, eps, None), np.clip(q, eps, None)
psi = float(np.sum((q - p) * np.log(q / p)))

# ❌ 错误一：每次都按 current 自己的分位数重新切桶 → q 恒为均匀的 10%，读数跨天不可比
# ❌ 错误二：只保留“上周线上数据”滚动窗口并替换冻结 baseline → 缓慢漂移被吞掉
#           一个每周挪 1% 的缓慢漂移可以走完全程而 PSI 从不越线（温水煮青蛙）
# ❌ 错误三（最隐蔽）：直接用 np.quantile 的首尾当外边界 → np.histogram 会把
#           current 里落在 [min(baseline), max(baseline)] 之外的样本**静默丢弃**。
#           而"出现了基线里从没有过的极端值"恰恰是最该报警的一类漂移，
#           不加 ±inf 的实现会在最需要它的时候读数纹丝不动。
```

类别特征还要多一条：**必须留一个 `__other__` 桶收纳基线里没见过的新枚举值**。
上游新上线一个 `channel = "tiktok_live"`，没有兜底桶的实现要么抛异常，要么把它静默丢掉 ——
后者更糟，那正是你最想被告知的一次变化。

**多重检验是漂移告警噪声的第一来源，而且它是可以算出来的。**
200 个特征、每个每天跑一次 α=0.05 的检验，**期望 10 个假阳性/天**；
如果改成每小时跑一次，`200 × 24 = 4,800` 次检验/天 → **期望 240 个假阳性/天**。
没有 Benjamini-Hochberg 之类的 FDR（false discovery rate：控制"报出来的告警里有多大比例是假的"，
而不是控制每一次检验各自的犯错概率）校正，这套系统在第二周就会被静音。
**工程结论：报效应量（PSI / Wasserstein），不要报 p 值；p 值只用来排序，不用来触发。**

## 4. 没有标签的那段时间里，你监控什么

标签延迟是 ML 监控的**硬下界**，它决定了"最快多久能给出一个确定的结论"：

| 场景 | 标签延迟量级 | 这段时间里唯一可用的东西 |
|---|---|---|
| CTR / 点击 | 秒–分钟 | 几乎不用代理，直接看真值 |
| 电商转化（含归因窗口） | 1–30 天 | 加购率、详情页停留、下单率 |
| 支付欺诈（chargeback 回流） | 数天–90 天 | 人工复核抽样命中率、拒付预警、规则引擎重合度 |
| 信贷违约 | 6–24 个月 | 首期逾期（vintage 早期指标）、评分分布与校准 |
| 保险理赔 / 临床预测 | 数月–数年 | 只能靠代理与专家抽检 |

**标准解法是双环监控**，快环负责"值不值得看"，慢环负责"到底对不对"：

```
                    ┌───────── 快环（分钟–小时）──────────┐
   线上预测 ──┬────►│ 输入质量 · 特征漂移 · 预测分布/校准/熵 │──► 疑似退化：打标、限流、通知，但不下结论
              │     └──────────────────────────────────────┘
              │                                                     ▲
              │     ┌───────── 慢环（天–月）────────────┐            │ 标签到齐后回填 true / false
              └────►│ 真标签回流 → 真实 AUC / 精确率 / 损失 │──────────┘  用来重新标定快环的阈值
                    └───────────────────────────────────┘
```

**代理指标必须标定，不能凭直觉选。** RecSys 2025 在 OTTO 上做了个体级回归标定，
实测 `Recall@20 → CTR` 系数 **0.8985（p<1e-4）**，而 `Recall@20 → CVR` 是 **−0.204（p=0.0174，负相关）**
（[arXiv 2507.09566](https://arxiv.org/html/2507.09566)，2,650 万次曝光、5 个测试组）。
**选错代理指标比没有代理指标更糟** —— 后者只是瞎，前者会让你朝反方向踩油门。

**无标签性能估计（CBPE / DLE）能用，但它的前提正好排除了你最担心的情况。**
NannyML 的 CBPE 显式假设：① 概率良好校准；② 输入没有向未见区域的协变量偏移；③ **没有概念漂移**；④ 样本足够大。
概念漂移下 CBPE **系统性高估**性能（[NannyML 文档](https://nannyml.readthedocs.io/en/stable/how_it_works/performance_estimation.html)、
[arXiv 2505.05295](https://arxiv.org/html/2505.05295v1)）。
一句话记住：**它在你最需要它的那一刻最不可靠。** 正确用法是"在已确认无概念漂移的窗口里补齐性能曲线"，
而不是"用它替代标签"。

**第三条路是花钱买标签：定量抽样送人工标注。**
要检出精确率从 90% 掉到 85%（Δ=5pp）、双侧 α=0.05、power=80%，
按标准双比例公式 `n ≈ 2 · (z_{α/2}+z_β)² · p̄(1−p̄) / Δ² = 2 × 7.849 × 0.875 × 0.125 / 0.05²`
自算得 **每组约 690 条**；每天抽 700 条送标注，你就有了一条**延迟 1 天、成本固定**的性能曲线 ——
在标签要 90 天的业务里，这经常是唯一能在一周内下结论的手段。

**风控还有一个额外坑：选择性标签。** 被模型拒掉的申请永远不会产生"其实他会不会违约"的真值，
于是模型对自己拒绝区的错误**在数学上不可观测**。唯一解法是**放行一小撮随机样本**（reject inference 的实验版），
代价是这部分的坏账是确定要吃的 —— 这是一笔必须写进预算的、买"可观测性"的钱。

## 5. 监控分层：四层各自的告警时延

```
        监控层         典型指标                        检测延迟   归因能力   "模型真坏了"的证据力
   ┌─ 输入/数据层   null 率·越界率·schema·上游作业 SLA   分钟      最强       弱
   │                                                             (直指某列)
   ├─ 特征层       PSI/JS·缺失率·在线-离线 parity        小时–天    强         中
   │
   ├─ 模型层       score 分布·校准·熵·各类别占比         分钟–小时  中         中
   │
   └─ 业务层       CTR·转化·拦截率·GMV                   天–周      最弱       最强
        └────────────────────────────────────────────────────────────────►
              快而不准（会误报）  ←─────────────────►  准而不快（会来不及）
```

**这四层不是让你选一层，它们的快慢和准确度是反着的，所以必须同时上。**

| 层 | 该有的指标（举例） | 告警时延 | 为什么不能只靠它 |
|---|---|---|---|
| **输入/数据层** | 每列 null 率、越界率、类型错误率、distinct count、外键一致性、上游分区是否按时到达 | 分钟级 | 只知道数据坏了，不知道模型受不受影响（很多列模型根本没用） |
| **特征层** | top-K 重要特征的 PSI/JS、缺失率、**在线-离线 parity**（同一 key 同一时刻两边取值是否一致） | 小时–天 | 漂移 ≠ 退化；且完全看不见概念漂移 |
| **模型层** | 分数分布分位数、预测熵、各类别占比、拒绝/降级率、模型版本×特征版本一致性；校准在标签回流后更新 | 分钟–小时（校准受标签延迟约束） | 分布可以不变而结果全错；无标签时不能声称测到真实校准 |
| **业务层** | CTR、转化率、欺诈拦截率、人均 GMV、投诉率 | **天–周** | 最准，但慢到没法当告警；且被大促、季节、竞对活动污染 |

**业务层慢，本质上不是工程问题，是统计问题。**
基线 CTR 5%、要检出相对 1% 的变化（5.00% → 5.05%），按双比例公式自算需要**约 298 万用户/组**；
如果你每天入组 30 万独立用户/组，那就是 **10 天**才有统计分辨率 —— 而且复访会让累积独立用户次线性增长，
实际常需要朴素估算的 1.5–2 倍。**没有任何监控工程能把这个数变短**，
你只能靠上面三层去争取那 10 天里的信息（完整的样本量与功效算法见 [07 §4](07-model-quality-and-experimentation.md#4-样本量与统计功效先算再决定要不要做这个实验)）。

**Uber D3 的数字说明了输入层的性价比**：300+ Tier-1 数据集、**100,000+ monitors**（1,000+ 数据集 × 50+ 列），
用 Prophet 做时序基线 + 保守告警上下界；fact 表告警**精确率 95.23%**，
其 2023 文章报告在 Uber 当时的事故/平台口径下，把这类事故的检测时间从 **45 天降到平均 2 天（20×）**
（[Uber D3](https://www.uber.com/us/en/blog/d3-an-automated-system-to-detect-data-drifts/)）。这是厂商历史快照；本团队应从当前 TTD 基线、告警精度与覆盖列数设目标。
**列级数据质量监控比模型监控更早触发，也更容易归因** —— 如果预算只够做一层，先做这层。

**第五个观测面是影子模型。** 把线上流量复制一份喂给候选模型、输出不返回用户，
就能在完全没有标签的情况下，直接比较新旧两个模型的**预测分布**差异 —— 这是本章唯一一个"主动制造对照组"的监控手段。
Uber 2025-10-30 的公开材料称其当时把 shadow 做成默认前置并覆盖 **>75% 的关键在线用例**；这是采用度快照，不是通用覆盖目标。影子增量成本约为 `镜像比例 × 候选路径成本`，还受特征复用、日志采样、异步资源池和候选模型大小影响；只有 100% 镜像且两条路径成本相近、完全独立时，总成本才接近 2×。
它能证明什么、不能证明什么见 [07 §9](07-model-quality-and-experimentation.md#9-影子部署能证明什么不能证明什么)，一句话版本：
**它测不了任何业务指标**，因为预测不返回给用户就没有反馈闭环。

**基数会先炸掉你的账单。** 200 个特征 × 10 个分桶 × 20 个切片维度 = **40,000 条时间序列/模型**；
50 个生产模型就是 **200 万条**。指标基数是可观测性成本的重要驱动之一；采样率、保留期、日志正文、直方图桶和查询扫描量同样影响成本（[05/02 §2](../05-reliability/02-observability.md#2-指标基数是最容易失控的成本变量)），
所以切片维度必须显式白名单（通常只留：模型版本、大区、渠道、新老用户），
而不是"把所有维度都打上去以后再说"。

## 6. 告警怎么定：漂移告警天生高误报

漂移告警的假阳性率高，有四个叠加的原因，且它们都不是"调个阈值"能解决的：
**多重检验**（§3 那 240 个/天）、**样本量放大 p 值**、**季节性与营销活动**、
以及最根本的一条 —— **模型不用的特征漂移了也会报**。

降噪按性价比排序，四招：

1. **改成联合条件触发**：`漂移 ∧（性能或代理指标下降）` 才算事件。这是 2025–2026 的主流口径，
   单独的漂移信号降级为"线索"，只进面板不进 oncall。
2. **按特征重要性加权**：只有 top-10~20 重要特征（用模型自己的 SHAP/gain 排序，随模型版本更新）
   才有资格进告警规则，剩下的进周报。这一步通常能砍掉 80% 以上的候选告警。
3. **报效应量 + FDR 校正**，不报 p 值（§3）。
4. **多窗口确认**：短窗（1h）负责快，长窗（24h）负责稳，两个都超才触发 ——
   这是 SLO 多窗口多燃尽率告警的直接移植（[05/01 §6](../05-reliability/01-slo-and-error-budget.md#6-多窗口多燃尽率告警multi-window-multi-burn-rate-alerting)）。

| 档位 | 触发条件（示例） | 响应 | 典型信号 |
|---|---|---|---|
| **page（叫醒人）** | 输入层硬失败 ∧ 影响 >1% 流量 | 15 分钟内 | top-10 特征缺失率从 0.1% 跳到 5%；特征服务超时率 >1%；**模型版本与特征管道版本不匹配** |
| **ticket（工作时间）** | 漂移 ∧ 代理指标下降，连续 2 个窗口 | 1 个工作日 | 重要特征 PSI>0.2 且代理 CTR 跌 2%；校准误差翻倍 |
| **面板 / 周报** | 单纯漂移、低重要性特征 | 不打断任何人 | 第 47 重要的特征 PSI=0.25；新枚举值出现 |

**还要有一个专门关告警的机制。** Uber 的做法是跑一个 diagnosis job **自动关掉预测误差高的噪声 monitor**，
并让人工标注 true / false alert 回流去调整基线 —— 在 100,000+ monitors 的规模下，
"谁来删 monitor"和"谁来加 monitor"是同等重要的岗位职责。

**反直觉但被反复验证的一条：guardrail 指标不要太多。**
每多一个自动阻断指标，假阳性率就抬一截 → 好模型被自动回滚 → 团队失去信任 → **最后把自动回滚整个关掉**。
这条失败路径的终点比"没有 guardrail"更糟，因为你还以为自己有。

## 7. 何时重训：定期、触发式，还是别重训

| 策略 | 触发条件 | 优点 | 代价 / 撞墙条件 |
|---|---|---|---|
| **定期重训** | 固定周期（日/周/月） | 实现简单、可预算、可预排队列 | 在缺乏评估门禁时**会周期性地把更差的模型推上线**；周期选错则要么烧钱要么滞后 |
| **触发式** | 性能或代理指标跌破阈值 | 对真实退化自动响应，不浪费算力 | 依赖健壮监控；**会漏掉阈值之前的缓慢侵蚀**；标签慢的业务根本触发不了 |
| **事件驱动** | 上游 schema 变更、大促、新区域上线、政策调整 | 抓住已知的分布突变点 | 需要人把"什么算事件"列出来，永远列不全 |
| **不重训** | — | 零成本、零风险 | 只在 `P(Y\|X)` 稳定的物理/工业场景成立；用户行为类模型不适用 |

**周期不该拍脑袋，应该回测出来**：把过去 12 个月切成滚动窗口，模拟"如果每 N 天重训一次，性能曲线长什么样"，
选出**性能损失可接受的最大 N**（[Evidently 的方法论](https://learn.evidentlyai.com/ml-observability-course/module-4-designing-effective-ml-monitoring/when-to-retrain-ml-models)）。
这条曲线通常很平：从每周降到每天，性能只多 0.3pp，训练成本却是 7 倍 —— **回测的价值主要是让你敢于减少重训**。

再叠一条硬约束：**旧模型至少保留 `标签回流周期 + 检测延迟 + 一个完整重训周期` 这么久**
（这是可推导的下界，具体保留时长没有公开共识数据；保留成本怎么算见 [02 §5](02-model-lifecycle.md#5-保留策略与成本一个必须自己算一遍的算例)）。
否则你在确认新模型更差的那一天，会发现能回滚的目标已经被清理掉了。

**回滚不是把版本指针拨回去。** 模型 artifact 回滚到 X 天前，它就要去面对特征存储里**训练时并不存在的"未来"特征** ——
版本不匹配、静默劣化，而不是报错。所以可回滚的单位是**不可分割四元组**：
`权重 + 特征/预处理管道版本 + 依赖锁（容器 digest）+ 配置`。只回滚其中一半，是把一个问题变成两个
（完整的回滚机制见 [09 §4](09-model-deployment.md#4-模型回滚--代码回滚)）。

## 8. 自动重训是不是好主意

先说结论：**"监控 → 重训 → 直接上线"这条闭环，在 2026 年仍然没有一家公开材料建议你做。**
Uber 的自动回滚触发器至今**全部挂在运维指标上**（error rate / latency / CPU-GPU 利用率），
质量指标是"监控"而非"自动回滚"（[Uber, 2025-10-30](https://www.uber.com/us/en/blog/raising-the-bar-on-ml-model-deployment-safety/)）——
不是因为他们做不到，而是因为**质量信号还不够快、不够干净到能自动决策**。

**下面 6 条是一份高门槛检查表，而不是法规式充分条件。** 低风险、可快速回滚且已证明稳定的链路可在满足这些原则后考虑自动晋升；高影响决策即使技术条件满足，也可能因政策/合规保留人工闸门。

1. **标签回流周期 < 检测延迟 + 一个重训周期**。标签 90 天回来的业务，自动重训只是自动地学过时的东西。
2. **标签的产生不被模型自己影响**，或者你有随机曝光流量可以做无偏纠正（见 §9）。
3. **有 golden dataset 做硬门禁**：一份人工维护、覆盖已知关键场景与历史事故的固定集合，
   新模型不过就不允许出闸 —— 且它**不能**来自会被漂移污染的线上采样（门禁的分层设计见 [09 §3](09-model-deployment.md#3-双层门禁技术护栏立即判--质量指标延迟判)）。
4. **有自动回滚，且回滚单位是 §7 那个四元组**。
5. **有最小数据量门槛与训练数据质量门禁**：上游数据质量检查不通过时，重训任务必须**拒绝启动**而不是照常跑。
6. **重训频率高到人工确认成本不可接受**（一天多次值得自动化；一周一次不值得 —— 让人点一下更便宜也更安全）。

**不满足这些条件时，自动重训的三种典型事故：**

**(a) 脏数据被固化进权重。** 上游 bug → 重训把 bug 学成"规律" → 你回滚模型，
下一次自动重训又把它学回来。**规则：修数据之前禁止重训**，
所以数据质量检查必须是重训流水线的前置门，而不是事后看板。

**(b) 反馈回路把偏好放大成坍塌。** 推荐场景：只推热门 → 用户只消费热门 → 训练数据更热门 → **长尾坍塌**；
风控场景：拒得越多 → 拒绝区标签越少 → 模型对自己的拒绝越自信。
**自动重训是这个回路的加速器** —— 手工重训每月一次，回路每月转一圈；自动重训每天一次，它每天转一圈。
而这类退化在 AUC / CTR 上短期是**上升的**，必须靠 §9 那组分布形状指标才看得见
（度量口径见 [arXiv 2509.00109](https://arxiv.org/pdf/2509.00109)、[Mansoury et al., CIKM 2020](https://arxiv.org/pdf/2007.13019)）。

**(c) 攻击面从模型扩到数据。** 全自动链路意味着谁能影响你的线上日志，谁就能影响你下周的权重。

> **面试金句**
> 「自动重训不是把训练自动化了，是把'今天的脏数据写进下周的权重'这件事自动化了。
> 判据只有一条：**你能不能自动回滚它。不能自动回滚，就不要自动上线。**」
> *"Auto-retraining doesn't automate training — it automates baking today's data bug into next week's weights.*
> *My rule is simple: if you can't auto-roll it back, don't auto-ship it. Ship the retrain, gate the promote."*

**折中的标准形态是"自动重训 + 人工放行"**：训练、评测、影子部署全自动，
**只有"晋升为线上主模型"这一步需要人点确认**，且金丝雀必须是 validation-gated（每一档流量都等到有统计分辨率才推进）
而不是 time-gated（按排班表定时推进 —— 那不是统计方法，只是日程表），判据见 [09 §1 §2](09-model-deployment.md#1-为什么服务的金丝雀判据搬到模型上会失效)。

## 9. 反馈回路：你的训练数据是模型自己写的

```
        ┌──────────────────── 曝光偏差闭环 ─────────────────────┐
        ▼                                                       │
   模型打分 ──► 排序 ──► 只展示 Top-10 ──► 用户点/不点 ──► 日志 ──┘
        ▲                                                       │
        └──────────── 下一版训练数据（只含被展示过的）◄──────────┘

   从未被展示的物品：0 曝光 → 0 正样本 → 下一版模型对它更没信心 → 更不展示
   位置偏差叠加：同一物品放第 1 位与第 10 位的 CTR 差数倍，
                 模型会把"我把它排在前面"错学成"它本来就好"
```

这个闭环的统计本质是 **MNAR（missing not at random：数据的缺失本身取决于它的取值，
所以直接拿观测到的部分做统计一定有偏）**：把"没被观测到"当成负反馈，
就等于把"我没给你看"记成了"你不喜欢"。
**纠偏手段**（位置偏差建模 / IPW / 受控探索 / 随机曝光日志）属于数据采集侧，四种做法与各自的代价见
[07 §10](07-model-quality-and-experimentation.md#10-反馈采集曝光日志的完整性与随机流量的必要性)。本节只回答监控侧的那一半问题：
**这个回路正在收紧的时候，你的仪表盘上会先动哪一格。**

**答案很反直觉：主指标会先变好。** 退化反馈回路的早期表现是 AUC 和 CTR 一起上升 ——
模型把流量集中到它最有把握的那一小撮物品上，短期命中率当然更高。
等到 CTR 掉下来，长尾供给通常已经流失了，这不是回滚模型能修的。
所以必须专门监控下面这类**分布形状指标**，且它们要和主指标画在同一张图上：

| 退化形态 | 发生在哪 | 主指标的假象 | 该监控的指标 | 健康判据 |
|---|---|---|---|---|
| **热门坍塌**（popularity collapse） | 推荐 / 信息流 | CTR 短期上升 | 长尾覆盖率、平均热度排名、DivRatio | 与季节性/产品目标基线相比不能持续越过护栏；不要求曲线绝对平坦 |
| **拒绝区盲区**（selective labels） | 风控 / 授信 | 通过率下降、坏账率"改善" | 拒绝率、随机放行桶的实际坏账率 | 随机桶坏账率与模型预测坏账率的偏离 |
| **分数自我强化** | 级联多模型（召回→粗排→精排） | 各级单独的离线指标都在涨 | 相邻两级输入分布的 L2-norm deviation、RS-score（推荐系统偏差研究里的标准度量） | 上一级输出分布的月度漂移应该有界 |

**随机曝光的成本是可以算清楚的，所以它是产品决策而不是算法决策。**
设随机桶让该桶 CTR 从 5% 掉到 2%（与 [07 §10](07-model-quality-and-experimentation.md#10-反馈采集曝光日志的完整性与随机流量的必要性) 给的"随机流量转化率低 30–60%"同一量级），
桶占 1% 流量，则大盘 CTR 的相对损失 = `1% × (5%−2%) / 5% = 0.6%`。
**这 0.6% 买到的是三件在别处买不到的东西**：无偏的离线评估集、debias 训练样本、以及对模型盲区的持续曝光。
Booking.com 明确表示保留了 exploration budget，但**未披露具体比例** —— 这是本章明确的"未找到公开数据"项，面试里别编一个数。
另外还有一层污染：A/B 两组共享同一份训练数据池会产生**共生偏差**，让"做个 A/B 验证一下"这个动作本身也不干净，
详见 [07 §2](07-model-quality-and-experimentation.md#2-离线-在线鸿沟六类成因逐条给应对)。

## 10. 什么时候不要这么做（反模式清单）

| 反模式 | 为什么错 | 该怎么做 |
|---|---|---|
| 给全部 200 个特征都建漂移 monitor 并接 oncall | 每天 10–240 个假阳性（§3），两周内被全员静音 | 只有 top-K 重要特征进告警，其余进周报 |
| 用 KS 检验在大 batch 上做告警 | `n>50,000` 时几乎必报，p 值失去意义 | 报效应量（PSI/Wasserstein）+ FDR 校正 |
| 把 PSI 0.2 当成普适真理 | 它是信用评分行业的经验值，不是统计推导 | 每个特征在历史平稳期上重标定自己的阈值 |
| 漂移单独触发重训或 oncall | 模型不用的特征漂移完全无害 | 联合条件：漂移 ∧ 性能/代理下降 |
| 只做 drift，不做 skew | drift 即使有双基线也不验证训练/服务实现逐值一致 | skew 对训练/回放值逐条比，且上线前就跑一次（[06 §2](06-feature-and-data.md#2-训练服务偏斜五种成因各自的检测手段)） |
| 疑似概念漂移时用 CBPE 估性能 | CBPE 显式假设无概念漂移，此时**系统性高估** | 只在已确认无概念漂移的窗口用；否则花钱买标签 |
| 没有随机流量就上 IPW / debias | 没有 propensity 分母，权重是拍出来的 | 先建随机桶，再谈 debias |
| 拿 APM 的固定阈值套 ML 指标 | 自然流量周期内误报，又漏掉渐进漂移 | 冻结训练/发布 reference 用于累计偏移；另建季节性/近期基线（如 Prophet）捕捉短期异常，二者都保留 |
| 监控里没有"模型版本 × 特征管道版本"这一维 | 最贵的事故是版本错配，而它在任何单一维度上都看起来正常 | 把版本对当作一等标签打在所有 ML 指标上 |
| 照抄 2024 年的监控选型对比表 | **WhyLabs 已于 2025 年停运**（被 Apple 收购，whylogs/langkit 开源继续）；**SageMaker Model Monitor / Clarify 自 2026-07-30 起不向新客户开放** | 选型表每年重做；把"厂商还在不在"当作第一道筛选 |

还有一条不写进表里的：**不要在没有基线的时候上线监控**。
基线数据集（reference set）必须和训练集同源、冻结、版本化，并且和模型 artifact 一起存 ——
临时拿"上周的线上数据"当基线，等于用一个可能已经病了的东西当健康标准。

## 这一章的三句话

1. **ML 系统的失败是 200 不是 500，所以你需要两套监控栈，而不是一套加几块面板。**
   运维指标和预测质量指标测的是两件正交的事：Uber 的费用组件缺失在 10% 会话里持续 45 天，
   没触发任何服务告警 —— 任何"我们的 APM 很完善"的说法都和这件事无关。
2. **漂移是线索，不是判决；概念漂移需要标签或经验证代理提供证据，校准本身也依赖标签。**
   PSI/KS/JS/对抗验证从头到尾没用过 `Y`，它们在原理上看不见 `P(Y|X)` 的变化；
   所以告警必须是"漂移 ∧ 性能下降"的联合条件，单独的漂移只配进周报。
3. **自动重训的门槛不是"能不能自动训"，而是"能不能自动回滚"。**
   全自动链路会把上游脏数据固化成权重（修数据之前重训只会把 bug 学得更牢），
   也会把曝光偏差放大成长尾坍塌 —— 而后者在 AUC 和 CTR 上短期是**上升**的，
   等主指标掉下来已经来不及。默认形态是训练自动化、晋升按风险设门禁；低风险且可快速回滚的成熟链路可自动晋升，高影响链路保留人工/政策审批。

## 面试官会追问

1. 你的模型已经坏了但错误率是 0.00%、p99 没变，你靠哪个信号最先发现？这个信号的检测延迟是多少？
2. 数据漂移和概念漂移的区别是什么？哪些检测方法在原理上抓不到概念漂移，为什么？
3. PSI 报了 0.31，你会做什么？什么情况下你什么都不做？
4. 200 个特征、每小时跑一次漂移检验，你每天会收到多少个假阳性？怎么把它降下来？
5. 标签要 90 天才回来，这 90 天你怎么知道模型是好是坏？无标签性能估计（CBPE）什么时候不能信？
6. 监控分四层，各自的告警时延是多少？为什么业务指标最准却不能拿来当告警？
7. 你会做自动重训吗？给我你的判据；如果做，哪几道闸门不能省？
8. 推荐系统的训练数据是它自己产生的，你怎么打破这个回路？随机曝光流量要付多少钱，这笔钱买到了什么？
