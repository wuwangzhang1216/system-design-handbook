# 01 · ML 系统与普通系统的根本差别

> 普通系统坏掉的方式是抛异常，ML 系统坏掉的方式是返回 200 OK。
> 你为前者建的全部监控、测试和发布流程，对后者都是失明的。

---

## 读这一章之前

**你在工作中遇到过这个**

你的排序服务上线八个月没触发过一次告警：可用性 99.97%，p99 42 ms，5xx 率 0.01%，SLO 面板全绿。
第 45 天产品同学问你为什么某几个城市的转化率在缓慢下滑，你回查才发现：三个月前 App 的一次埋点改版
让某个费用字段在约 10% 的 session 里变成了 null，你的特征管道把 null 填成了 0，模型照常打分、照常返回 200。
Uber 公开过同一类事故的完整数字 —— 某个 fare component 在美国主要城市 **10% 的 session 中缺失、持续 45 天**，
模拟出的业务影响是 **gross booking 下降 0.23%**（折合数千万美元），**全程没有任何一条服务级告警被触发**
（[Uber D3, 2023-02-23](https://www.uber.com/us/en/blog/d3-an-automated-system-to-detect-data-drifts/)）。

**需要先懂的概念**

| 概念 | 一句话 | 详见 |
|---|---|---|
| SLI / SLO / 错误预算 | SLI 的唯一正确形式是 `好事件 / 有效事件`；SLO 是你对它承诺的目标值 | [05/01 §1](../05-reliability/01-slo-and-error-budget.md) |
| p50 / p99 与尾延迟放大 | 平均值骗人；一个请求要等最慢的那个下游，扇出越宽尾巴越长 | [00-concepts §3](../00-foundations/00-concepts.md)、[00/01 §7](../00-foundations/01-fundamentals.md) |

| 批处理 / 流处理 / CDC | 数据从业务库流到分析侧的三条路径，以及"事件时间"和"处理时间"的区别 | [02/05 §1 §3](../02-architecture-patterns/05-data-platform.md) |
| 数据契约与 CI 门禁 | 把上游"不会乱改 schema"的口头约定变成能挡住合并的自动检查 | [02/05 §4](../02-architecture-patterns/05-data-platform.md) |
| 渐进式交付 | 金丝雀 / 蓝绿 / 影子，以及"部署 ≠ 发布" | [03/05 §1 §3](../03-saas-platform/05-release-engineering.md) |

**这一章要回答的问题**

1. 为什么一个 ML 服务可以在所有运维指标全绿的情况下已经坏了三个月？我该补哪一套监控？
2. 完整生命周期里，Inference Engineer 负责哪一段？和 ML Engineer / Data Engineer 的接口上签的是什么合同？
3. 模型没有确定的期望输出，那单元测试到底测什么？CI 里能挂什么硬门禁、不能挂什么？
4. ML 服务的 SLO 该怎么写？为什么"可用性 99.9% + p99 < 50 ms"是一个**不完整**的 SLO？

**本章新引入的术语**

| 术语 | English | 一句话定义 |
|---|---|---|
| 离线指标 / AUC | offline metric / AUC | **离线指标**：不放线上、只在历史日志上重放算出来的模型质量分。**AUC** 是其中最常用的一个：随机抽一个正样本和一个负样本，模型给正样本打分更高的概率 —— 0.5 等于瞎猜，1.0 是完美排序。全书凡是"离线 AUC 涨了"的说法，指的都是这个数（口径与陷阱见 [08/07 §1.2](07-model-quality-and-experimentation.md)） |
| 训练/服务偏斜 | training-serving skew | 同一个特征，训练时算出来的值和线上服务时算出来的值不一样，模型在线上看到的输入和它学习时看到的不是一回事 |
| 特征穿越 / 数据泄露 | data leakage | 训练样本里混进了"标签发生那一刻还不存在"的信息，离线指标虚高，上线必然打回原形 |
| 时点正确性 | point-in-time correctness | 构造训练集时，每一行的特征只允许用标签时刻及之前可见的数据算出来 |
| 数据漂移 | data drift | 输入的分布 P(X) 变了，但"给定输入应该输出什么"的规律 P(Y\|X) 没变 |
| 概念漂移 | concept drift | 规律本身变了：同样的输入，正确答案已经不是原来那个了 |
| 静默降级 | silent degradation | 服务不报错、延迟不变、状态码全是 200，但预测质量在持续下滑 |
| 反馈回路 | feedback loop | 模型的输出改变了用户能看到什么，进而改变了下一轮训练数据，模型开始自己教自己 |
| 级联模型 | model cascade | 上游模型的输出是下游模型的输入，上游的偏差被下游吸收、放大并固化 |
| 校准 | calibration | 模型说"70% 会点击"的那批样本，实际点击率是不是真的接近 70% |
| 特征日志 | feature logging | 线上打分那一刻，把**实际喂给模型的那个特征向量**原样落盘，下一轮训练直接用这份日志当样本来源 |
| 影子部署 | shadow deployment | 把线上真实请求复制一份喂给新模型，但**不把它的结果返回给用户** |
| 黄金数据集 | golden dataset | 一份人工确认过标签、长期冻结的小样本集，任何模型上线前必须在它上面跑出结果并与历史逐条比对 |

## 1. 普通系统的行为写在代码里，ML 系统的行为写在数据里

普通后端服务的行为是 `f(代码版本, 输入)`。你 `git diff` 就知道行为变没变；没人动它，它明年还是这个行为。

ML 服务的行为是 `f(代码版本, 权重, 特征值的当下分布, 上游数据管道的当下语义)`。
后面三项**每天都在变，而且不经过任何一次 code review**。三条推论直接决定了这本章后面所有内容：

**推论 1：变更单位不是 git commit，是一个不可分割的四元组。**
`权重 + 特征/预处理管道版本 + 依赖锁（容器 digest）+ 配置`。
把版本指针指回三天前的权重，而特征管道还是今天的 —— 这个模型会遇到它训练时根本不存在的特征列，
产生**静默劣化而不是报错**。业界给这个失效模式的名字是"特征时间旅行"，公开材料里的原话是
*"rolling back just one part of the system creates new failures instead of solving the problem"*。

**推论 2：质量会自然衰减，不需要任何人碰它。** 用户行为在变、竞品在变、商品池在变、欺诈手法在变。
一个八个月没人动过的排序模型，它的效果一定不如上线那天 —— 差别只在于衰减速度和你有没有测到。

**推论 3：同一份代码在不同数据上是不同的系统。** 你在 A 租户/A 国家验证过的模型行为结论，
不能迁移到 B。这是多租户 ML 平台最贵的一课：**代码复用是真的，行为复用是假的。**

规模感：Uber 的 Michelangelo/Palette 平台公开口径是 **20,000+ 特征、5,000+ 生产模型、峰值 1,000 万次实时预测/秒**
（[Uber, 2024-05-02](https://www.uber.com/us/en/blog/from-predictive-to-generative-ai/)）。
这个规模下"每个模型手工盯着"在物理上不可能 —— 这就是为什么 ML 平台的核心产出是**自动化的一致性与监控**，
而不是"支持更多模型结构"。

| 维度 | 普通后端服务 | ML 推理服务 |
|---|---|---|
| 行为的来源 | 代码 | 代码 + 权重 + 特征值 + 上游管道语义 |
| 同样输入的输出 | 确定、可断言 | 随重训与特征刷新而变，且常常没有"正确答案" |
| 变更单位 | git commit / 镜像 tag | 四元组：权重 + 特征管道 + 容器 digest + 配置 |
| 没人动它会怎样 | 一直正常 | 质量随时间衰减 |
| 坏掉时你看到什么 | 5xx / 超时 / 堆栈 | **200 OK，p99 不变，业务指标慢慢掉** |
| 回滚 | 换镜像 tag，秒级确定 | 换四元组；只回一半会制造第二个故障 |
| 测试的期望值 | `assert f(x) == y` | 没有 ground truth，只能断言分布、不变量、相对表现 |
| 发布推进的门槛 | 时间（烤 30 分钟没事就推进） | **样本量**（要够统计分辨率才能推进） |
| 判定"这次变更是好是坏" | 分钟级 | 小时到数月（取决于标签延迟） |

## 2. 生命周期与三个角色的边界

```
        ┌───────────── Data Engineer ─────────────┐┌──── ML Engineer ────┐
        │                                          ││                     │
  [业务库/埋点]                                     ││                     │
        │                                          ││                     │
        ▼                                          ││                     │
   ①采集/CDC ──► ②事实表(带事件时间) ──► ③特征定义 ─┼┼► ④训练 ──► ⑤离线评估 │
        │              │                    │      ││     │         │      │
        │              │                    │      ││     ▼         ▼      │
        │              │                    │      ││  ⑥模型注册(registry) │
        │              │                    │      │└─────────┬───────────┘
        │              │                    │      │          │
        │              │            ┌───────┴──────┴──┐       ▼
        │              │            │ 特征物化(在线KV) │  ⑦打包/编译/warmup ◄── Inference
        │              │            └───────┬─────────┘       │            Engineer
        │              │                    │                 ▼               │
        │              │                    │          ⑧影子 → 金丝雀 → 全量   │
        │              │                    │                 │               │
        │              │                    ▼                 ▼               │
        │              │            ⑨在线特征取数 ─────► ⑩在线推理服务 ────► 用户
        │              │                    │                 │               │
        │              │                    └────► ⑪特征日志 + 预测日志 ◄──────┘
        │              │                                      │
        │              │                          ⑫双环监控(服务腿/质量腿)
        │              │                                      │
        │              └──────────── ⑭ 训练集回流 ◄─── ⑬标签回流(延迟 天~年)
        │                                                     │
        └──────────────── ⚠ 反馈回路：⑩的输出决定了用户看到什么，
                            于是决定了 ⑬ 收到什么标签，于是决定了 ④ 学到什么
```

> 📖 **读图要点**：注意 ⑨ 在 Inference Engineer 的框里而 ③ 在 ML Engineer 的框里 ——
> **"特征怎么定义"和"线上怎么把它取出来"分属两个人，训练/服务偏斜就长在这条缝里**。
> 另外注意 ⑪ 那条从 ⑩ 指回 ⑭ 的边：它是唯一一条能把偏斜归零（而不是"检测到偏斜"）的边。
> 最后看最下面那条 ⚠ 虚线 —— 它不是数据流，是**因果流**，图上其余所有箭头都不表达它。

| 角色 | 拥有的阶段 | 交付物 | 对下游签的合同 |
|---|---|---|---|
| **Data Engineer** | ①② | 带事件时间、可回放的原始事实表 | schema 冻结 + 列级数据质量 SLA（空值率、P50/P99、distinct count、外键一致性） |
| **ML Engineer** | ③④⑤⑥ | 模型 artifact + 特征定义 + 训练集构造逻辑 | **时点正确**的训练集；离线指标 + golden dataset 结果；模型卡与血缘 |
| **Inference Engineer** | ⑦⑧⑨⑩⑪⑫ | 在线服务 + 特征日志 + 双指标 SLO | **在线算出的特征值 == 训练时算出的值，且这件事可度量**；p99 与吞吐；预测分布监控与自动回滚 |

**边界上的三个扯皮点，以及正确的归属：**

1. **线上特征值和离线对不上** → 归 **Inference Engineer**。理由不是"谁的锅"，是**只有在线侧能落 feature logging**：
   离线侧永远只能"重算一遍"，重算就意味着又跑了一次可能有 bug 的实现。
2. **上游埋点改了 schema** → 归 Data Engineer，但 Inference Engineer 必须有**列级数据质量监控**当第二道防线。
   Uber 的 D3 系统用 **300+ Tier-1 数据集、100,000+ monitors**，把这类问题的平均检测时间从 **45 天压到 2 天（20×）**，
   fact 表告警精确率 95.23%（[Uber D3](https://www.uber.com/us/en/blog/d3-an-automated-system-to-detect-data-drifts/)）。
3. **质量掉了但延迟没变** → **由 Inference Engineer 发现**（预测分布/校准监控在你手里），**由 ML Engineer 修**。
   这一条如果分不清，结果就是"模型效果掉了"变成一个没有人负责的状态。

## 3. "模型只占 5% 代码"：Hidden Technical Debt 及其工程含义

Sculley 等人的 *Hidden Technical Debt in Machine Learning Systems*（NIPS 2015，
[原文](https://papers.nips.cc/paper_files/paper/2015/hash/86df7dcfd896fcaf2674f757a2463eba-Abstract.html)）里那张图，
是这个方向被引用最多的一张图：

```
┌──────────────┬──────────────┬───────────────────────┬──────────────┐
│ Configuration│ Data         │                       │  Monitoring  │
│              │ Collection   │   ┌───────────────┐   │              │
├──────────────┤              │   │   ML  Code    │   ├──────────────┤
│  Machine     ├──────────────┤   └───────────────┘   │   Serving    │
│  Resource    │  Feature     │                       │   Infra      │
│  Management  │  Extraction  ├───────────┬───────────┤              │
├──────────────┴──────────────┤ Analysis  │  Process  ├──────────────┤
│    Data Verification        │  Tools    │  Mgmt     │  (glue code) │
└─────────────────────────────┴───────────┴───────────┴──────────────┘
              ▲                                              ▲
              └──── Data Engineer 的战场            Inference Engineer 的战场 ────┘
```

> 📖 **读图要点**：中间那个 `ML Code` 盒子的面积就是全部信息 —— 它周围的每一个盒子都需要一个 owner，
> 而其中 `Serving Infra` / `Monitoring` / `Configuration` / `Machine Resource Management` 四个是 **Inference Engineer 的**。

⚠️ **诚实标注**：论文本身**没有给出"5%"这个百分比**，它给的是一张面积对比图；"5%" 是后来流传的口径。
这不影响结论，但你在面试里说"论文说只有 5%"是可以被抓的。

论文列出的债务里，对 Inference Engineer 最致命的是这四条：

- **CACE / 纠缠（entanglement）**：*Changing Anything Changes Everything*。改动任何一个输入特征，
  所有权重都会重新分配 —— **不存在"只改这一个特征"的局部改动**。工程含义：任何特征变更都必须走完整发布流程，
  不能因为"只是加一个特征"就跳过影子和金丝雀。
- **未声明的消费者（undeclared consumers）**：别的团队直接读了你的预测结果当他们的特征。
  你换模型，他们的模型跟着劣化，而**你不知道他们存在**。工程解法：预测输出必须走带 schema 的正式通道
  （消息主题 / 注册过的表），禁止裸落一张公共表任人 `SELECT`。
- **纠正级联（correction cascade）**：模型 A 效果不好，于是套一个模型 B 修正 A 的输出；后来又套 C。
  从此改 A 会同时打断 B 和 C，于是没人敢改 A。这就是级联模型的误差累积在组织层面的形态。
- **胶水代码与管道丛林（glue code / pipeline jungle）**：把数据从一种形状搬到另一种形状的代码量，
  在真实系统里通常是模型代码的一到两个数量级。

**推论**：ML 平台的 ROI 全部来自消灭上面这四条，而不是"支持更多模型结构"。
面试里如果你只讲模型结构和算子优化，你答的是 ML Engineer 的题。

## 4. ML 系统特有的失败模式清单

这张表是本章的核心。**它们的共同特征是：系统完全正常工作，没有任何一条会触发传统告警。**

| 失败模式 | 你会看到什么 | 根因 | 检测手段 | 结构性兜底 |
|---|---|---|---|---|
| **训练/服务偏斜** | 离线指标好、上线掉；无告警 | 同一个特征有两套实现（离线 SQL / 在线 Go-C++），语义会漂 | 用 request id 把训练侧与服务侧特征 join 起来，每日算**精确匹配率 / 差值均值 / 差值 P99** | **feature logging 当训练集主来源** —— 这是唯一能把偏斜归零而不是"检测"的方案 |
| **特征穿越** | 离线 AUC 持续变好，线上不动甚至退化 | 训练集用了标签时刻之后才存在的数据；或回填窗口（24h）与线上窗口（5min）不一致 | 强制 AS OF join（按主键匹配 + 取 ≤ 标签时间戳的最新值）；比对回填窗口与在线 TTL | 时点正确性做成训练集构造的**唯一入口 API**，不允许手写 join |
| **静默降级** | 200 OK、p99 不变、业务指标缓慢下滑 | 上游列缺失 / 口径变化 / 漂移 / 默认值兜底比例上升 | 预测**分数分布 + 校准 + 熵**；列级数据质量监控 | 双环监控（见 §6） |
| **反馈回路** | 长尾覆盖率下降、热度集中度上升，短期指标反而更好看 | 模型输出决定用户看到什么，于是决定下一轮训练数据 | 长尾覆盖率、平均热度排名、DivRatio、L2-norm deviation | **常驻的随机/探索流量**（没有它，IPW、无偏离线评估、debias 训练全都做不了） |
| **级联误差累积** | 端到端指标掉，但每一跳单独看都正常 | A→B→C 串联，A 的分布变化被 B 当成正常输入吸收 | 每一跳记录输入分布；端到端联合监控 | 限制级联深度；**禁止"上一个新模型去纠正老模型"** |
| **回滚制造新故障** | 回滚后指标不回升，甚至继续掉 | 老权重遇到训练时不存在的"未来"特征（特征时间旅行） | 部署前 diff 新旧模型的特征集合与管道版本 | 四元组回滚；用 alias/pointer 层部署，服务代码里**不写死版本号** |
| **warmup 未完成就进 LB** | 金丝雀第一批用户 p99 爆炸，被误判成"新模型变慢" | CUDA graph capture 典型 **30–60 s**，一次性初始化开销落在首批真实请求上 | 就绪探针必须包含 warmup | 抄 Triton 的 `ModelWarmup`：声明一组 warmup 请求（含 batch size 与迭代次数），**全部成功才标记 READY** |
| **告警疲劳 → 关掉自动回滚** | 好模型被自动回滚，团队随后把自动回滚关了 | guardrail 指标堆太多，假阳性率线性上升 | 统计"回滚记录里误回滚的比例" | **guardrail 指标做减法**，这是反直觉但被反复验证的建议 |

**两个阈值的现实**（用于设计监控，不要照抄）：

- **PSI**（population stability index：把分布切成若干桶，逐桶比较两个分布的占比差异，得到一个越大越不一样的标量）
  的行业惯例是 `<0.1 无需关注 / 0.1–0.2 需调查 / >0.2 显著漂移需行动`。
  ⚠️ 这来自信用评分行业的经验值，**不是统计推导**，必须按你的每个特征重新标定。
- **KS 检验在样本 >50,000 行/batch 时基本每批都会报漂移** —— 大样本下任何微小差异都显著。
  所以 2025–2026 的口径已经从"报警即行动"退回"**漂移只是线索**"：
  告警条件应该是 **漂移 ∧ 性能（或代理指标）下降** 的联合条件。
  Vertex AI 的 skew 检测默认告警阈值是 **0.3**，监控频率**默认 24 小时、最小 1 小时**
  （[Google Cloud](https://cloud.google.com/blog/topics/developers-practitioners/monitor-models-training-serving-skew-vertex-ai)）—— 注意这个频率量级，
  它意味着**你不可能靠漂移检测做秒级止损**。

⚠️ **skew 和 drift 的基线不同，这是最常见的混淆**：**skew 对训练集基线比，drift 对上一个时间窗比。**
只做 drift 会漏掉"部署第一天就存在"的管道实现差异 —— 因为它从第一天起就稳定地错着，时间窗之间毫无变化。

## 5. 为什么 ML 系统的测试不同：没有确定的期望输出

普通系统的测试是 `assert f(x) == y`。ML 系统里 `y` 是什么？大多数时候没人知道，
而且"知道"要等标签回流 —— 欺诈是数天，保险理赔是数月到数年。所以测试形态必须换成四类：

| 测试类型 | 断言什么 | 能不能做成 CI 硬门禁 |
|---|---|---|
| **管道等价性测试** | 同一份输入，离线特征代码与在线特征代码算出的值逐位相等（或 `\|diff\| < ε`） | ✅ **必须是硬门禁**。这是偏斜唯一的确定性防线 |
| **黄金数据集回归** | 200–2,000 条冻结样本的预测与上一版逐条 diff，超阈值挡住 | ✅ 硬门禁。注意它测的是"有没有明显坏掉"，不是"好不好" |
| **不变量 / 蜕变测试**（metamorphic test：不断言输出是什么，而断言"输入这样变，输出应该那样变"） | 年龄 +1 岁，风控分不应跳变 20 分；标题多一个空格，排序分变化应 < ε；单调性特征方向不能反 | ✅ 硬门禁，但要容忍非确定性，用区间不用等号 |
| **分布断言 / 数据契约** | 空值率 < x%、取值域、预测分数均值与分位在参考区间内 | ✅ 硬门禁（挡的是数据不是模型） |
| **"模型准不准"** | — | ❌ **根本不属于 CI**。它属于线上实验 |

**离线指标只配当筛选器，不配当判据 —— 这句话有实测数字支撑：**

- RecSys 2025 在 OTTO 数据上做了个体级回归标定（2,650 万次曝光 / 5 个测试组）：
  `Recall@20 → CTR` 的系数是 **+0.8985（p < 1e-4）**，而 `Recall@20 → CVR` 的系数是
  **−0.204（p = 0.0174，负相关）**（[arXiv 2507.09566](https://arxiv.org/html/2507.09566)）。
  **同一个离线指标对两个业务指标符号相反。**
- Meta 的 Mosaic 系统给了另一种刻度感：离线 NE 变化 **−0.03% ~ −0.37%**，对应线上 A/B **+0.10% ~ +0.28%**
  （[arXiv 2607.24015, 2026-07-27](https://arxiv.org/html/2607.24015v1)）。
  **离线的 Δ 和线上的 Δ 不在一个刻度上，不要拿离线的提升幅度去预测线上。**

于是评测必须是一条三段漏斗：

```
  离线指标            交错 / 反事实评测            A/B + 长期 holdout
 ─────────────►      ─────────────────────►      ────────────────────►   全量
  分钟级              数天，50–100× 样本效率        数周~数月
  只有否决权          方向一致率仅 82%              唯一判据
  （便宜、只用于剪枝） （筛选器，不是判决器）        （贵，且正向率只有 ~10%）
```

> 📖 **读图要点**：注意每一层写的是**权限**而不是精度 —— 第一层"只有否决权"意味着离线指标变差可以直接毙掉，
> 但离线指标变好**不构成任何上线理由**；三层的箭头都是单向的，没有任何一层可以跳过后面直接到"全量"。

几个必须知道的数字（它们决定你的实验平台要多大）：

- **交错实验**（interleaving：把两个排序模型的结果交叉混排进同一个列表给同一个用户看，直接比较用户点了谁的，
  详见后续章节）效率：Netflix **>100×**、Thumbtack **~100×**（400 vs 40,000 样本达到 90% 一致率）、Airbnb **~50×**。
  但 Airbnb 的 KDD'25 论文同时给了反例：29 组配对里相关系数只有 **0.6**、**方向一致率 82%**
  —— 约 **1/5 的结论和 A/B 相反**（[arXiv 2508.00751](https://arxiv.org/abs/2508.00751)）。
- **A/B 的样本量下界**（标准双比例公式自算，α=0.05 双侧、power=80%）：基线转化率 5%、要检出**相对 1%** 的提升，
  需要 **≈ 298 万用户/组**。MDE 缩小 5 倍，样本量 **×25**。
- **实验正向率**：Microsoft ~33%、Bing/Google 10–20%、Airbnb ~8%，中位约 **10%**。
  这决定了实验平台的目标是"多、快、省"，不是"准"。
- **`p < 0.05` 不等于 5% 假阳性**：先验成功率 8%、功效 80% 时，显著结果的假阳性率约 **26%**（贝叶斯 FDR，只数"方向为正"那一半误判；双侧全计则约 42%。口径推导见 [07 §6](07-model-quality-and-experimentation.md)）。
- **SRM**（sample ratio mismatch：分流比例说好 50/50，实际落进两组的人数比显著偏离，说明分流或埋点坏了）
  发生率：LinkedIn 约 10% 的 triggered 实验、Microsoft 约 6%。
  告警阈值用 **p < 0.0005 ~ 0.001**（远严于 0.05），**SRM 触发时任何指标结论都不可信，必须禁止展示。**

## 6. ML 系统的 SLO：延迟 + 质量，两条腿

一个把所有请求都返回常数 `0.5` 的排序服务：可用性 100%、p99 1 ms、错误率 0。
**它能通过你现在写的所有 SLO。** 这就是为什么 ML 的 SLO 必须有两条腿。

**关键设计约束不是"多加几个指标"，而是：这两条腿的判定延迟差 3–5 个数量级。**
服务腿秒级可判，所以可以挂自动回滚；质量腿小时到天级可判，所以只能挂人工闸门。
Uber 公开的自动回滚触发器**全部是运维指标**（error rate / latency / CPU-GPU 利用率击穿阈值），
质量指标目前是"监控"而非"自动回滚"
（[Uber, 2025-10-30](https://www.uber.com/us/en/blog/raising-the-bar-on-ml-model-deployment-safety/)）——
这不是他们做得不够，是**质量信号还不够快到能自动决策**。

| 层 | SLI（`好事件 / 有效事件`） | 目标（示例，必须自校准） | 判定延迟 | 能触发什么 |
|---|---|---|---|---|
| 服务 | 非 5xx 请求 / 总请求 | 99.9% | 秒 | **自动回滚** |
| 服务 | p99 端到端打分延迟 | < 50 ms（在线排序典型预算：特征取数 ~15 ms + 推理 + 其余） | 秒 | **自动回滚** |
| 服务 | **降级率** = 用默认特征值兜底的请求 / 总请求 | < 0.5% | 秒 | **自动回滚** |
| 数据 | 关键特征空值率（逐特征） | 偏离参考基线 > 3σ 告警 | 分钟 | 告警 |
| 数据 | 特征新鲜度（事件时间到可读时间） | 按特征分三档：日级批 / 分钟级流 / 请求时计算 | 分钟 | 告警 |
| 数据 | **在线-离线特征精确匹配率** | > 99%（Coinbase 公开口径 99%） | 天 | **阻止发布** |
| 预测 | 分数分布 PSI vs 训练基线 | <0.1 / 0.1–0.2 / >0.2 三档 | 小时 | 告警（**必须与性能下降联合**） |
| 预测 | 校准误差、预测熵 | 相对上周的偏移量 | 小时 | 告警 |
| 业务 | 代理指标（CTR / 加购率） | 金丝雀期不劣于 control | 小时–天 | 人工闸门 |
| 业务 | 真实性能（等标签到齐） | 按业务定 | 天–月 | 人工闸门 |

**"好事件"的定义是 ML SLI 的全部难点。** 直觉写法 `预测正确的请求 / 总请求` 是不可用的 ——
大部分时刻你不知道对不对。正确做法是拆成**当下可判定的代理**：

- `返回了非降级预测的请求 / 总请求`
- `特征完整度 ≥ 95% 的请求 / 总请求`
- `预测分数落在 [参考分布 ±3σ] 内的请求 / 总请求`

**标签延迟决定了"多久能出结论"的物理下界。** 欺诈标签数天、保险理赔数月到数年、临床预测可能数年。
标准解法是**双环监控**：实时环用代理指标（要求"滞后短 + 与目标高相关"），延迟环在标签到齐后跑真实性能。

> **面试金句**
>
> "ML 服务的 SLO 如果只写延迟和可用性，那么一个永远返回 0.5 的服务能拿满分。我会把它写成两条腿：
> 服务腿 —— 可用性、p99、降级率 —— 秒级可判，自动回滚挂在它上面；质量腿 —— 分数分布、校准、
> 在线离线特征一致率 —— 判定要小时到天，所以它只能卡人工闸门。这里真正的设计决策不是多加指标，
> 而是承认这两条腿的判定延迟差了三到五个数量级，因此它们能触发的动作根本不是一回事。"
>
> "If your ML service SLO is just latency and availability, then a service that always returns 0.5 passes
> with flying colors. So I split it in two. The ops leg — availability, p99, degraded-response rate —
> you can call in seconds, so that's what auto-rollback hangs off. The quality leg — score distribution,
> calibration, online-offline feature parity — takes hours to days before you'd bet on it, so it gates
> humans, not robots. The real design call isn't adding more metrics. It's admitting those two legs are
> three to five orders of magnitude apart in how fast you can trust them, so they can't trigger the same
> kind of action."

## 7. 哪些是普通系统设计问题，哪些才是真正的 ML 问题

这一节是本章最实用的部分。**ML 系统设计题里大约 70% 实际考的是普通分布式系统能力**，
但候选人常常在那 70% 上花光时间，然后在 30% 上暴露。

**这些看起来像 ML 问题，其实是普通系统设计问题：**

| 题面 | 它其实是 | 用什么解 |
|---|---|---|
| "推理服务扛不住 QPS" | 容量与批处理 | 水平扩 + 动态组批 + **按队列深度而不是 CPU 利用率扩缩容**（CPU 利用率是饱和指标，延迟劣化后才涨） |
| "在线特征取数太慢" | 分布式存储的扇出问题 | 延迟由**往返次数**决定，不是特征个数：10 个特征分散在 5 个 feature view = **5 次串行 RTT**。Redis 同 entity 共享一个 hash key → 恒 1 次，p50 600–700 µs / p99 2.5–3.0 ms；DynamoDB p50 3–4 ms / p99 20–25 ms（Tecton 口径） |
| "模型加载太慢" | I/O 与镜像分发 | 顺序是**镜像 > 权重并行读 > 编译缓存**。8B 冷启动的镜像+权重+编译三段从 ~11 min 优化到 ~26 s（含 CUDA graph capture 的端到端是 ~12 min → ~35 s，口径见 [08/03 §2](03-model-loading-and-warmup.md)），主项是 image pull 5–6 min + layer extract 3–4 min，**权重只占小头**（[BentoML, 2025-05-08](https://www.bentoml.com/blog/25x-faster-cold-starts-for-llms-on-kubernetes)） |
| "多个模型版本共存 / 切流" | 发布工程 | alias/pointer 层 + 蓝绿 / 金丝雀，见 [03/05 §3](../03-saas-platform/05-release-engineering.md) |
| "GPU 利用率低" | 调度与资源共享 | time-slicing / MPS / MIG，**按信任域选**：跨租户只能 MIG（且**只有 A100/A30/H100/H200 一线有 MIG，Ada 系 L4/L40/L40S 没有**，没有就只能整卡独占），MPS 会崩溃连坐 |
| "模型服务挂了怎么降级" | 弹性模式 | 熔断 + 默认值 / 上一版模型兜底，见 [05/03](../05-reliability/03-resilience-patterns.md) |

**这些才是真正的 ML 问题 —— 它们的共同特征是"系统完全正常工作时问题正在变严重"：**

| 问题 | 为什么普通系统设计救不了 |
|---|---|
| **训练/服务偏斜** | 两边代码都"正确"，两边都不报错。这是**语义等价性**问题，不是可靠性问题；再多的重试、熔断、副本都没用 |
| **特征穿越** | 系统运行完美，错的是训练集的**时间语义**。它甚至不发生在线上 |
| **反馈回路** | 系统越"正常工作"，问题越严重 —— 它是被成功放大出来的 |
| **离线指标不代表线上** | 没有任何工程手段能把 82% 的方向一致率变成 100%。这是认识论上界，不是实现质量问题 |
| **静默降级** | **不存在可以报警的事件**。你必须先定义"什么算不正常"，才有东西可监控 |
| **标签延迟** | 物理约束（理赔标签就是要几个月）。加机器、加副本、加缓存都不改变它 |

> **判据**：如果一个问题在"把机器加到无限多、网络延迟降到 0"之后仍然存在，它就是真正的 ML 问题。

## 8. 什么时候不要这么做 / 反模式

| 反模式 | 为什么坏 | 撞墙信号 |
|---|---|---|
| **一上来就建 feature store** | 三条判据不全中就是净负债：(a) 在线路径要 <50 ms 拿到跨多实体的特征；(b) 特征被 ≥3 个团队/模型复用；(c) 存在有状态时间窗聚合 | 一个团队、一个模型、批量打分 —— 一张宽表就够了 |
| **把后端服务的 SLO 直接抄给 ML 服务** | 质量腿缺失，静默降级永远不触发告警 | 上线半年零告警，但业务指标缓慢下滑 |
| **照抄服务金丝雀的 25% 起步 + 定时推进** | 在有统计分辨率之前就暴露 1/4 用户。模型金丝雀应 **1–5% 起步**且 **validation-gated 而非 time-gated** —— 按时间推进不是统计方法，只是排班表 | 低流量产品用 1% 流量跑 48 小时，可能只积累了 ~200 次交互（[GrowthBook, 2026-05-29](https://www.growthbook.io/insights/canary-releases-ai-models-what-changes-vs-traditional-software)） |
| **只回滚模型权重** | 特征时间旅行；把一个问题变成两个 | 回滚后指标不回升，甚至继续掉 |
| **漂移告警直接触发重训** | 模型忽略的特征上漂移完全无害；KS 在 >50,000 行/batch 时几乎每批必报 | oncall 被烧穿，然后所有人把这条告警静音 |
| **"监控 → 自动重训 → 直接上线"闭环** | 缺评估门禁时会把更差的模型推上线，并**把反馈回路固化** | 长尾覆盖率单调下降、热门集中度单调上升 |
| **多加 guardrail 指标求安全** | 假阳性率上升 → 好模型被误回滚 → 团队索性关掉自动回滚。**方向是反的** | 回滚记录里误回滚占多数 |
| **用无标签性能估计替代真标签** | CBPE / DLE 这类方法**显式假设"没有概念漂移"**，而概念漂移恰恰是破坏校准的那个东西 → 系统性高估。**它在你最需要它的时候最不可靠** | 估计出来的性能一直很好，真标签到齐后打脸 |
| **上一个新模型去"纠正"老模型的输出** | correction cascade，从此没人敢动老模型 | 改一个模型需要同时协调三个团队排期 |
| **把预测结果裸落一张公共表任人 SELECT** | undeclared consumers：你换模型会打断你不知道存在的下游 | 换模型后收到来自陌生团队的故障单 |
| **上 ML 之前没试过规则** | 规则引擎能到 90% 效果时，ML 的真实成本是**第二套监控 + 实验平台 + 特征一致性流水线 + 影子部署的 2× 算力** | 团队里没有人能回答"这个模型比上一版规则好多少" |

**关于影子部署的边界**（因为它最常被误用成"验证过了就能上线"）：

| 影子部署能验证 | 影子部署**不能**验证 |
|---|---|
| 延迟 / 稳定性 / 不崩 | **用户体验与业务影响** |
| 预测一致性（prediction parity） | CTR / 转化 / 留存 —— **预测不返回给用户，就没有反馈闭环** |
| 输入分布是否错配 | 任何需要"不同预测导致不同结果"的效应 |
| 成本（**确定是 2×**：双份推理 + 双份特征拉取 + 双份日志） | — |

## 这一章的三句话

1. **ML 系统坏掉的默认方式是 200 OK。** 你现有的全部监控都是为"报错"设计的，而 ML 的失效不报错 ——
   所以"第二套预测级 + 数据级监控"不是加分项，是准入条件；没有它，你的系统能坏 45 天而面板全绿。
2. **模型版本不是权重的版本，是"权重 + 特征管道 + 依赖锁 + 配置"这个不可分割四元组的版本。**
   只回滚其中一项不叫修复，叫制造第二个故障 —— 老权重会撞上它训练时不存在的特征，并且静默地劣化。
3. **ML 系统设计题里 70% 考的是普通分布式系统能力，30% 才是 ML 问题，而分级发生在那 30%。**
   判据很简单：把机器加到无限多、网络延迟降到 0 之后仍然存在的问题，才是真正的 ML 问题。

## 面试官会追问

1. 你的推荐服务可用性 99.99%、p99 40 ms，SLO 面板全绿。我怎么知道模型没坏？你会加哪三个指标，判定延迟各是多少？
2. 训练/服务偏斜和数据漂移的区别是什么？各自拿什么当基线比？只做其中一个会漏掉什么？
3. 你要回滚一个上线三天的排序模型。除了把版本指针指回去，还要回滚什么？只回权重会发生什么？
4. ML 系统的单元测试测什么？哪些能做成 CI 硬门禁，哪些**不能**，为什么？
5. 离线 AUC 涨了 3 个点，你敢不敢上线？你需要额外看到什么才敢？
