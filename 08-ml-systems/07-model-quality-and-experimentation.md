# 07 · 模型质量：离线评测、在线实验与影子部署

> 离线指标只配当筛子，不配当判决；而绝大多数团队把 A/B 测试跑成了"每天早上看一眼，显著就发布"的抽奖机。

---

## 读这一章之前

**你在工作中遇到过这个**

你的搜索排序模型离线 NDCG@10 涨了 2.1%，你开 5% 流量跑 A/B，第 4 天早上看面板：CTR +0.8%，p = 0.031，
你截图发群里，当天推到 100%。两周后大盘 CTR 回到基线，季度末的长期 holdout 显示这个模型实际是 **−0.3%**。
复盘查出三件事叠在一起：① 你每天早上都看一次结果，看到显著就停 —— 连看 4 次把真实假阳性率从 5% 抬到约 **13%**
（重复显著性检验的经典量级：2 次 ≈8%、4 次 ≈13%、10 次 ≈19%，连看两周才到 §6 说的 20–30%）；
② 实验组和对照组的入组用户数是 50.4 : 49.6，SRM 早就告诉你随机化坏了，但面板上没这个检查；
③ 剩下那点真实增量是新奇效应，两周后归零。**这三件事没有一件和模型有关。**

**需要先懂的概念**

| 概念 | 一句话 | 详见 |
|---|---|---|
| p50 / p99 与长尾 | 平均值会掩盖少数人的极差体验；实验的延迟护栏必须看分位数，且分位数不能取平均 | [00-concepts §3](../00-foundations/00-concepts.md) |
| 排队论与单位经济 | "每天能入组多少独立用户"决定实验要跑多久，这是容量估算而不是统计问题 | [00/02](../00-foundations/02-capacity-estimation.md) |
| 训练/服务偏斜 | 离线算特征和线上算特征是两套代码、两套执行语义，天然会漂 | [08/06](06-feature-and-data.md) |
| 影子 → 金丝雀 → 全量 | 新版本先只算不返回，再小比例真放量，最后全量 | [04/06 §8](../04-ai-agent-systems/06-evaluation-and-observability.md) |
| SLO 与错误预算 | 护栏指标的阈值不该拍脑袋定，应该挂在已有的 SLO 上 | [05/01](../05-reliability/01-slo-and-error-budget.md) |
| 单向门 / 双向门 | 能低成本回滚的决定可以快，不能回滚的必须慢 —— 全量发布是单向门 | [00/03](../00-foundations/03-tradeoff-framework.md) |

**这一章要回答的问题**

1. 离线 AUC 涨了、线上不涨，到底有几种成因？每一种的**症状**长什么样、怎么单独排除？
2. 要检测 1% 的 CTR 提升，我需要多少样本、要跑多久？这个数字为什么大到让大多数实验根本没意义？
3. 为什么排序实验必须按用户分流、不能按请求分流？请求级分流在什么场景下反而是对的？
4. 交错实验（interleaving）宣称比 A/B 快 50–100 倍，那为什么不能用它做最终判决？
5. 影子部署到底能证明什么？它能不能替代 A/B？

**本章新引入的术语**

| 术语 | English | 一句话定义 |
|---|---|---|
| 时间序划分 | temporal split / out-of-time split | 训练集只取某个时间点之前的日志、测试集只取之后的，用来模拟"上线后要面对没见过的未来" |
| GAUC | grouped AUC | 先在每个用户（或每次请求）**内部**算一次 AUC，再按曝光数加权平均；它衡量"同一屏里谁该排前面"，而全局 AUC 衡量"所有人所有物品混在一起谁该排前面" |
| 最小可检测效应 | minimum detectable effect (MDE) | 给定样本量和显著性要求下，实验能可靠识别的最小提升；比它更小的真实效果会被当成噪声 |
| 统计功效 | statistical power | 假如效果真的存在，这次实验有多大概率把它检出来；行业默认取 80% |
| 分流单元 | randomization unit | 抛硬币决定进哪一组的那个东西 —— 可以是用户、会话，也可以是单次请求 |
| 分流比例失配 | sample ratio mismatch (SRM) | 实际进入两组的样本数之比显著偏离你设定的比例（如 50:50 实际是 50.4:49.6），说明随机化或埋点本身坏了 |
| 偷看 | peeking | 实验跑到一半反复看结果，看到显著就停 —— 每看一次都相当于重新抽一次奖，真实假阳性率远高于名义上的 5% |
| CUPED | CUPED, controlled experiment using pre-experiment data | 用实验开始前就已存在、且与结果指标相关的数据（如上周人均下单数）把指标方差扣掉一部分，从而用更少样本达到同样功效 |
| 护栏指标 | guardrail metric | 不指望它变好、只要求它别变坏的指标（p99 延迟、崩溃率、退订率）；它变坏时无论主指标涨多少都不发布 |
| 交错实验 | interleaving | 把两个排序模型的结果混成**一个**列表给同一个用户看，比较用户点的位置是谁贡献的 |
| 影子部署 | shadow deployment（流量侧也说 traffic mirroring） | 把线上真实请求复制一份喂给新模型，新模型的输出只落日志、不返回给用户 |
| 位置偏差 | position bias | 排在前面的物品天然被点得多，与它本身好不好无关；不校正就会把"曾经排第一"学成"应该排第一" |

## 1. 离线评测：划分错了，后面全白做

### 1.1 时间序数据不能随机划分

推荐、排序、风控、时序预测的日志都是**时间序**的。随机划分（random split）会让训练集里出现测试集时间点**之后**发生的事：
同一 session 的后半段、同一用户当天更晚的点击、当天全量日志算出来的"用户 7 日点击率"。模型于是在训练时见到了未来。

```
随机划分（错）：
  时间 ────────────────────────────────────────────────────►
  日志  ▓░▓▓░▓░░▓▓░▓▓░░▓░▓▓░░▓░▓░▓▓░░▓▓░▓░░▓▓░▓░▓░░▓▓░▓░
        ▓ = train    ░ = test
        └─► 训练样本和测试样本在时间上互相穿插，模型见过"未来"

时间序划分（对）：
  时间 ────────────────────────────────────────────────────►
  日志  ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓|░░░░|■■■■■■■■
        └──── train  D-30 … D-4 ───┘ gap └─ test D-1 … D0 ─┘
                                    D-3 … D-2：挖空，等标签回流
```

**那条 gap 是关键，且几乎所有人第一次都不会留。** 标签有回流延迟：电商下单可能 30 分钟，
退货标签 7–15 天，欺诈标签数天，保险理赔数月至数年（[Uber 的口径](https://www.uber.com/us/en/blog/raising-the-bar-on-ml-model-deployment-safety/)，2025-10-30）。
训练集末尾那几天的负样本里混着"其实会转化但还没转化"的样本，直接训练等于往标签里注噪声。
**gap 宽度 = 标签成熟期的 P95**，不是平均值。

**撞墙信号**：离线 AUC 高得反常（比如 CTR 模型 > 0.85）、把某个特征去掉后 AUC 掉超过 0.05 —— 大概率是穿越（leakage），不是这个特征真的强。

### 1.2 指标选对了，也只是"选对了筛子"

| 指标 | 衡量什么 | 什么时候会骗你 |
|---|---|---|
| AUC | 全局排序：随便抽一正一负，正样本分更高的概率 | 线上只关心**同一次请求内**的相对顺序。全局 AUC 涨可能只是"活跃用户 vs 沉默用户"更可分了，与排序无关 |
| **GAUC** | 请求/用户内部的排序 | 更贴近线上，但对曝光少的用户方差极大，必须按曝光数加权 |
| NDCG@K | 带位置折扣的排序质量 | 折扣函数是你**假设**的用户注意力衰减，不是实测的 |
| Recall@K | 召回阶段有没有把好东西捞进候选集 | 与下游转化可能**负相关**，见下 |
| LogLoss / NE | 概率是否校准（预测 0.3 的那批样本是不是真有 30% 转化） | 排序对了但校准偏了，竞价类业务（广告出价）会直接算错钱 |

**离线指标的天花板有实测数字。** RecSys 2025 的 OTTO 研究在 **2,650 万次曝光 / 5 个测试组**上做个体级回归，
标定"离线指标 → 线上 KPI"的系数（[arXiv 2507.09566](https://arxiv.org/html/2507.09566)，2025-07）：

- Recall@20 → CTR：系数 **0.8985**（p < 1e-4），正相关且强
- Recall@20 → CVR：系数 **−0.204**（p = 0.0174）—— **负相关**。召回更多"会被点"的东西，转化反而掉
- OD@20（一种多样性指标）→ CVR：系数 **1.2608**（p = 0.008）

结论不是"Recall 没用"，而是：**离线指标到业务 KPI 的映射本身是一个需要定期用线上数据重新标定的模型**，
不是一条你可以背下来的常识。团队换了业务面、换了流量结构，系数会变号。

## 2. 离线-在线鸿沟：六类成因，逐条给应对

| # | 成因 | 症状（怎么单独认出它） | 应对 | 代价 |
|---|---|---|---|---|
| 1 | **离线/在线特征不一致** | 拿同一条线上请求的特征快照重算离线特征，两边逐字段比对，差异 > 0 | **feature logging**：在线请求时把实际用到的特征值原样落盘，训练时只 join 标签，不做离线回溯拼接 | 日志量翻数倍；特征快照的存储与保留期是真金白银 |
| 2 | **特征穿越 / 泄露** | 去掉某特征离线掉大、线上无感 | 时间序划分 + gap + point-in-time join | 训练数据构造复杂度上一个台阶 |
| 3 | **冰山效应（曝光偏差）** | 对见过的样本排序没变，对没曝光过的物品打分显著更高；线上新品/长尾占比一升，指标就掉 | 对**随机/探索流量**样本上采样；上线初期用系数 `a` 融合新旧模型分数并逐步放大 `a` | 必须长期保留一条随机流量（§10），这条流量的转化天然更差 |
| 4 | **指标口径不对齐** | 全局 AUC 涨、GAUC 平 | 用 GAUC / 请求内指标做选型判据 | 无 |
| 5 | **系统延迟本身是一个 treatment** | 新模型 p99 比旧模型高 40 ms，A/B 测出来的是"模型质量 + 延迟惩罚"的和 | 把延迟设成**护栏指标**，并在实验里额外跑一组"旧模型 + 人为注入同等延迟"来拆分两者 | 多一个实验组，样本量需求变成 1.5 倍 |
| 6 | **反馈回路（退化闭环）** | 上线数周后长尾覆盖率、平均热度排名单调恶化，短期指标却是正的 | 监控 L2-norm deviation / 长尾覆盖率 / DivRatio；探索流量 + 多样性配额 | 短期主指标会被压低 1–3% 量级 |

**还有一类几乎没人排除的：共生偏差（Symbiosis Bias）。**
A/B 两组的算法**共享同一份训练数据池** —— A 组的探索数据喂养了 B 组的模型，
这直接违反了 A/B 测试的基本假设 SUTVA（stable unit treatment value assumption：一个用户的结果只取决于他自己被分到哪组，
不取决于别人被分到哪组）。WWW 2025 给了三种缓解设计：cluster-randomized、data-diverted、user-corpus co-diverted
（[arXiv 2309.07107](https://arxiv.org/abs/2309.07107)）。代价很实在：data-diverted 会让每组的训练数据变少，
模型本身就变弱 —— 你在用"实验更干净"换"两个模型都更差"。

> **面试金句**
> "离线指标是筛子，不是判决。我们的规矩是：离线只用来砍掉明显更差的候选，任何上线决策必须有在线证据。
> 排序类改动先跑交错实验拿方向 —— 一天、几个百分点流量就够；但交错和 A/B 的方向一致率只有 82%，
> 所以它永远是筛选器，最终判决还是用户级 A/B 加长期 holdout。"
>
> "Offline metrics are a filter, not a verdict. We only use them to kill the obviously worse candidates —
> nothing ships on offline numbers alone. For ranking changes we run interleaving first: one day and a couple
> percent of traffic gets you a direction. But interleaving only agrees with A/B about 82% of the time,
> so it stays a screener. The final call is always a user-level A/B plus a long-term holdout."

## 3. 分流：为什么排序实验必须按用户分

```
请求级分流（排序实验里是错的）：
  用户 u 第 1 次搜索 → treatment ranker → 列表偏"新"
  用户 u 第 2 次搜索 → control   ranker → 列表偏"旧"
  用户 u 第 3 次搜索 → treatment ranker → 又偏"新"
  ├─ 用户侧：他看到的是两个模型混出来的产品，行为不代表任何一个模型
  ├─ 统计侧：同一用户的多次请求高度相关，按请求算方差会**低估**真实方差
  │          → 标准误偏小 → p 值虚小 → 假阳性率远高于 5%
  └─ 指标侧：留存、次日回访、人均 GMV 这类指标在请求级**根本没有定义**

用户级分流（正确）：
  bucket = hash(user_id ⊕ "search_ranker_v7") % 1000
  bucket ∈ [0,499]   → control
  bucket ∈ [500,999] → treatment
  同一用户永远落同一侧；跨天、跨设备（登录态）一致
  ⊕ salt 的作用：换一个实验就换一个 salt，否则不同实验的分桶完全重合，
                  两个实验的效果会永久纠缠在一起
```

**请求级分流在什么时候是对的**：被测的效果不跨请求、且用户感知不到差异。典型是**推理侧的性能实验** ——
换推理引擎、改 batch 参数、换量化精度，只要输出等价，按请求分流能用极小样本量测出延迟和成本差异。
一旦改动会**改变返回内容**，就必须回到用户级。

**SRM 是唯一一个"触发即全部作废"的检查。** 你设 50:50，实际入组 1,004,312 : 995,688 —— 看起来只差 0.43%，
但在这个样本量下这是 **p ≈ 1e-9** 的事件（自算：`χ² = 2×4,312²/10⁶ = 37.2`，df=1 ⇒ 双侧 p ≈ 1.1e-9）。行业实测发生率不低：LinkedIn 约 **10%** 的 triggered 实验、Microsoft 约 **6%** 有 SRM。
告警阈值行业惯例是 **p < 0.0005**（Microsoft）或 **p < 0.001**（Kohavi 默认），远严于 0.05 ——
因为每个实验都要跑这个检查，必须控 family-wise error。
**SRM 触发时禁止展示任何指标结论**，这必须是平台的硬门禁，而不是面板上一行小字。
常见根因：treatment 侧多一次重定向导致埋点丢失、bot 过滤规则对两组不对称、实验生效点在某个会 fallback 的服务后面。

## 4. 样本量与统计功效：先算，再决定要不要做这个实验

二元指标（CTR、转化率）的每组样本量：

```
n_每组 ≈ 2 · (z_{α/2} + z_β)² · p(1−p) / Δ²

  α = 0.05 双侧 → z_{α/2} = 1.96
  power = 80%   → z_β     = 0.8416
  (1.96 + 0.8416)² = 7.849        ← 把这个系数背下来
  p = 基线转化率，Δ = 绝对提升 = p × 相对提升
```

**一个完整算例。** 你的搜索 CTR 基线 5%，产品要你证明 **相对 1%** 的提升（即 5.00% → 5.05%）：

```
Δ = 0.05 × 0.01 = 0.0005
p(1−p) = 0.05 × 0.95 = 0.0475
n = 2 × 7.849 × 0.0475 / (0.0005)² = 0.745655 / 2.5e-7 ≈ 2,982,620   → 约 298 万 / 组
```

**换算成天数**：日活 200 万，但只有搜索场景的用户会入组，每天新入组独立用户约 40 万（20 万/组）。
298 万 ÷ 20 万 = **15 天（朴素估算）**。但复访会让"累积独立用户"次线性增长 —— 第 5 天入组的很多人第 1 天已经入过组了 ——
经验上要乘 **1.5–2×**，所以真实是 **22–30 天**。

**这个数字才是设计题的真正答案**：不是"跑一周看显著性"，而是"要么接受一个月，要么改需求"。三条出路：

| 出路 | 新的样本量 | 新的天数 | 代价 |
|---|---|---|---|
| 把 MDE 从 1% 放宽到 2% | 74.6 万 / 组（÷4） | 4 天朴素 / 6–8 天实际 | 真实的 1.5% 提升会检不出来，你会把好模型判死 |
| 上 CUPED（有效流量 1.66×） | 180 万 / 组 | 9 天朴素 / 14–18 天实际 | 需要预实验期数据 + 协变量工程，见 §5 |
| 换成交错实验（排序场景） | 数千 session | 1 天 | 只能回答"哪个 ranker 更受偏好"，不能回答业务问题，见 §8 |

**MDE 与样本量是平方关系，这是全章最该记住的一条**：MDE 缩小 5 倍，样本量 ×25。

| 基线转化率 | 检测**相对 1%** 提升所需 | 检测**相对 5%** 提升所需 |
|---|---|---|
| 2% | ≈ 769 万 / 组 | ≈ 31 万 / 组 |
| 5% | ≈ 298 万 / 组 | ≈ 11.9 万 / 组 |
| 10% | ≈ 141 万 / 组 | ≈ 5.7 万 / 组 |
| 20% | ≈ 63 万 / 组 | ≈ 2.5 万 / 组 |

（以上均为按上式自算，α=0.05 双侧 / power 80%。）

**连续指标（人均收入、人均时长）要用变异系数 CV = 标准差/均值 代入**：`n ≈ 2 · 7.849 · CV² / δ²`（δ 为相对效应）。
重尾指标的 CV 常在 **3–8**：CV=3 检测相对 1% 需 **≈141 万/组**，CV=5 需 **≈392 万/组**。
所以人均 GMV 这类指标在中小流量产品上**根本测不动** —— 正确做法是缩尾（winsorize，把超过 P99.9 的值截断到 P99.9）
把 CV 压下来，并明确写进指标定义，而不是每次实验临时决定。

**最小运行时长是独立于样本量的约束，两个都要满足：**

1. **至少一个完整周（7 天）**。周内效应（工作日 vs 周末的用户构成完全不同）会让任何截断在周三的实验产生系统性偏差。
2. 有月度周期的业务（发薪日、月末冲量）**至少 14 天**。
3. 涉及用户习惯改变的改动，新奇效应通常要 **2 周以上**才衰减（§7）。

**样本量够 ≠ 可以停；反过来也成立**：跑满 30 天但只入组 5 万用户的实验从第一天起就注定失败，这类实验最该在**设计阶段**被杀掉。

## 5. CUPED：能省多少样本，别信厂商口径

CUPED 用实验**开始之前**就已存在的协变量 X（最常用：同一用户在预实验期的同一指标）来扣掉方差：

```
Y_adj = Y − θ · (X − E[X])            θ = Cov(Y, X) / Var(X)
Var(Y_adj) = Var(Y) · (1 − ρ²)        ρ = corr(Y, X)
```

因为 X 在随机化**之前**就采集了，它必然与分组独立 —— 所以 CUPED 是**一致估计量**，不以偏差换方差。

**收益的诚实口径**：厂商普遍宣称"方差降 20–50%、样本减半"。Microsoft 实验平台自己公布的数字要低得多
（[ExP: Deep Dive Into Variance Reduction](https://www.microsoft.com/en-us/research/group/experimentation-platform-exp/articles/deep-dive-into-variance-reduction/)，2022-11-15）：
R² = 0.4 时**中位有效流量倍数只有 1.66×**（功效 +22%）；在某个产品面上 **超过 68% 的指标倍数 ≤ 1.05×**（几乎白做），
另一个面上 **超过 55% 的指标倍数 > 1.2×**。

**工程结论**：不能把"CUPED 让样本减半"写进容量模型。正确做法是**按指标逐个测出 effective traffic multiplier 并存下来**，
实验设计时用这个指标自己的倍数算天数。

**上线前的校验只有一条，必须自动化**：调整后指标的**方差必须下降，且均值保持一致**。均值也变了说明协变量选错了
（它和分组不独立 —— 最常见的错误是拿了实验期内的数据当协变量），这是 CUPED 唯一的致命错误。

## 6. 多重检验与 p-hacking

**三个独立的坑，会叠加。**

**a) p < 0.05 不是 5% 假阳性。** 假阳性率取决于先验成功率。行业实测的实验正向率：Microsoft ~33%、Bing/Google 10–20%、
Airbnb ~8%，中位约 10%。**先验成功率 8% 时，一个 p < 0.05 的显著结果约有 26% 的概率是假的**（贝叶斯 FDR）。

> **口径必须写清楚，否则你自己复算会对不上**：这 26% 的算法是 `FDR = (1−π)·α₁ / [π·power + (1−π)·α₁]`，
> 取 π=0.08、power=0.8、**α₁=0.025**（双侧 0.05 里只有"方向为正"的那一半会被当成"我赢了"上线）
> ⇒ `0.92×0.025 / (0.08×0.8 + 0.92×0.025) = 0.023/0.087 ≈ 26%`。
> 若把双侧 0.05 全部计入（连"显著变差"也算一次误判），同样的先验下是 **≈42%**。
> 两个数都对，取决于你数的是哪种错误 —— 面试里报数字之前先说口径。
这条数字应该印在实验平台首页 —— 它解释了为什么"上线的实验加起来涨了 30%，大盘没动"。

**b) 多指标 = 多次抽奖。** 一个实验看 40 个指标、α = 0.05，期望有 **2 个**指标假阳性显著。
Bonferroni（α / m）在 m = 40 时把阈值压到 0.00125，过于保守、会杀掉真实效果。
生产上的做法是**分层**：1 个主指标不校正；一组次要指标用 Benjamini-Hochberg 控 FDR（false discovery rate：
控制"被判为显著的结论里有多大比例是假的"，而不是控制"犯任何一次错的概率"）；护栏指标反向使用 ——
护栏是"证明没变坏"，所以对护栏要**降低**显著性门槛（宁可误报也不能漏报）。

**c) 偷看（peeking）是最常见、也最容易被合理化的一个。** 固定样本量的 t 检验的 5% 是"在预定终点检验一次"的保证。
每天看一次、看到显著就停，连看两周，真实假阳性率会到 20–30% 量级。

**正确解法不是"不许看"，而是换检验方法。** 序贯检验（sequential testing）已成为新一代实验平台的默认：
[Statsig 用 corrected-alpha approach](https://docs.statsig.com/experiments/advanced-setup/sequential-testing)，
Eppo 用 Howard et al. 2021 的 GAVI（always-valid inference），Spotify 公开比较过多种序贯框架。
**代价**：序贯检验在同等功效下需要比固定样本量多约 **10–30%** 的样本 —— 你是在用样本量买"随时可以看、随时可以停"的权利。
这笔交易在大多数团队是划算的，因为它把"偷看"从违规变成了合法操作。

## 7. 护栏指标与效应的时间形状

**护栏指标（guardrail metric）的定义是"不许变坏"，不是"希望变好"。** 三类：

| 类别 | 例子 | 阈值怎么定 |
|---|---|---|
| 信任类 | SRM、缓存命中率异常、埋点丢失率 | 触发即作废，不看主指标 |
| 系统类 | p99 延迟、错误率、崩溃率、单请求成本 | 挂在已有 SLO 上（[05/01](../05-reliability/01-slo-and-error-budget.md)），不要为实验另定一套 |
| 用户类 | 退订率、举报率、7 日留存、长尾覆盖率 | 用历史波动的 ±2σ 起步，逐季校准 |

**反直觉的一条：护栏指标不要太多。** 每加一个护栏都在加假阳性率；护栏一多，好模型会被频繁自动回滚，
团队的应对不是修护栏而是**关掉自动回滚** —— 你最终得到的是零护栏。
（[GrowthBook 的同一结论](https://www.growthbook.io/insights/canary-releases-ai-models-what-changes-vs-traditional-software)，2026-05-29。）
经验区间是主指标 1 个 + 护栏 5–8 个，超过就该问"这一个是不是可以并进另一个"。

**新奇效应（novelty effect）与首因效应（primacy effect）是两个方向相反的时间形状**：
新奇效应 = 用户因为"这是新的"而多点，短期虚高、几周内衰减；首因效应 = 用户因为不熟悉新交互而少用，
短期虚低、随熟练度回升。**两者都无法用延长同一个实验来解决** —— 延长只是把它们平均进结论里。

**唯一能破它们的是长期 holdout**：常驻保留一小撮用户（通常 1–5%）永远不接收新功能，持续数月
（[arXiv 2102.12893](https://arxiv.org/pdf/2102.12893)，2021-02）。它还有第二个更值钱的用途：
**校准"所有实验累计增量"与大盘实际增长的差值** —— 这个差值几乎总是正的，也就是说你们上报的收益总和被高估了。

## 8. 交错实验：排序场景的 50–100 倍效率，以及它测不了的东西

交错实验把两个 ranker 的结果混成一个列表，让**同一个用户**同时看到两者的贡献 ——
每个用户既是实验组又是对照组，用户间的巨大异质性被消掉了，方差因此塌了一到两个数量级。

```
control ranker A:  a1  a2  a3  a4  a5
treat.  ranker B:  b1  b2  b3  b4  b5
                    │
                    ▼  team draft：每轮抛硬币决定谁先选，已被选过的去重
交错后的列表 I  :  a1  b1  b2  a2  a3  b3  ...
归属            :  A   B   B   A   A   B
用户点击        :  ✓       ✓       ✓
本次 session 记分:  A:2                 B:1        → A 胜
                    └── 统计量是"胜/负/平"的配对比较，不是人均指标
```

**效率数字（各厂一手口径）**：Netflix **>100×**（[Netflix TechBlog](https://netflixtechblog.com/interleaving-in-online-experiments-at-netflix-a04ee392ec55)）、
Thumbtack **~100×**（**400 个样本 vs A/B 的 40,000 个**才能达到 90% 一致率）、
Airbnb **~50×**（一天的数据 + 一小部分流量就能检出负向转化影响，同样的结论 A/B 要数周）。

**但它是筛选器，不是判决器。** Airbnb 在 KDD '25 公开了 29 组配对实验的结果
（[arXiv 2508.00751](https://arxiv.org/abs/2508.00751)，2025-08）：交错与 A/B 的相关系数只有 **0.6**，
**方向一致率 82%** —— 约 **1/5 的结论看反**。同一篇论文给了明确的失效边界：

| 交错测不了 | 为什么 |
|---|---|
| **集合级（set-level）优化** | 一个只优化次要目标、对转化中性的 treatment ranker，在混合列表里被用户挑走了 control 的高概率物品 → 交错**系统性低估** treatment，结论与 A/B 相反 |
| 搜索结果还喂给别的页面元素时（如地图视图） | 混排污染了下游模块的输入，测的已经不是原来那个系统 |
| **连续值指标**（收入、人均 GMV） | 交错的统计量是配对的"谁被点得多"，没有人均金额这个量 |
| **留存、长期效果** | 需要用户长期处在同一个 treatment 下，交错的定义就排除了这件事 |

**工程实现要点**：Airbnb 用**两层分流架构** —— 先切"常规 A/B 域 vs 交错域"，再在交错域内切到具体的 interleaving lane；
一次搜索**并行调用**两个 ranker 再合并结果。代价直接可见：**交错域的每次搜索都要跑两遍排序**，
这一层的 CPU/GPU 成本是 2×，并且两个 ranker 的延迟取 max 而不是 avg。

**反事实评测（counterfactual evaluation）是交错的补充**：每次搜索生成两个 ranker 的结果但**只展示一个**，
另一个只记录 —— 避免混排污染体验。Airbnb 同一篇论文给的效率：OEC ~**15×**、win-loss τ ~**23×**、gain 估计量 τ_g ~**100×**，
与 A/B 的相关性 **0.65**。

## 9. 影子部署：能证明什么，不能证明什么

```
                      ┌──────────────► 生产模型 v1 ──► 返回给用户
  请求 ──► 特征拉取 ──┤                                    │
              │       └── 复制 ──► 影子模型 v2 ──► 只落日志 ✗ 不返回
              │                        │
              └────────────────────────┴──► 双份特征拉取 + 双份日志写入
```

**做法**：在服务入口或 sidecar 处复制请求，同步或异步调用影子模型，两边的输入/输出/延迟全部落盘，离线做逐请求比对。
Uber 把 shadow 作为**默认前置门**，覆盖 **>75% 的关键在线用例**（计划 2025 H2 到 100%），
分两种形态：Endpoint shadowing（可配流量比例 + 自定义校验）和 Deployment shadow（默认全自动，聚焦 prediction drift）
（[Uber, 2025-10-30](https://www.uber.com/us/en/blog/raising-the-bar-on-ml-model-deployment-safety/)）。

**成本是确定的 2×**：两遍推理 + 两遍特征拉取 + 两份日志。这是唯一没有争议的成本项，必须提前预算。
如果影子跑异步且不共享特征拉取结果，成本还会更高。

| 影子**能**验证 | 影子**不能**验证 |
|---|---|
| p50/p99 延迟、吞吐、GPU 显存占用 | **任何业务指标**：CTR、转化、留存 |
| 崩溃、OOM、超时、依赖不可用 | 用户体验变化 |
| 输出分布（分数分布、类别分布、熵、校准） | 需要"不同预测导致不同结果"的任何效应 |
| 与生产模型的预测一致性（prediction parity） | 反馈回路（预测不返回 → 没有闭环） |
| 输入分布错配 / 特征缺失 | 长期效果 |
| 单请求成本 | — |

**最常见的误解**："影子跑了两周没问题，可以直接全量了。"
影子只是"不会崩、分布没歪"的证明，它对业务指标一无所知 —— 因为预测**没有返回给用户，就不存在反馈闭环**。
影子的正确位置是金丝雀**之前**的那道门，不是 A/B 的替代品。

**影子的第二个价值常被忽略**：它是**唯一**能在不影响用户的前提下测出"新模型在真实流量分布下的资源画像"的手段。
压测用的是合成流量，分布必然偏 —— 真实流量的长尾请求（超长 query、异常大的候选集）才是打爆显存的那批。

## 10. 反馈采集：曝光日志的完整性，与随机流量的必要性

**隐式信号 vs 显式信号**：

| | 隐式（点击、播放时长、停留、下单） | 显式（评分、点赞、举报） |
|---|---|---|
| 量级 | 每天亿级 | 每天万级，稀疏 3–4 个数量级 |
| 偏差 | 位置偏差、曝光偏差、诱饵标题 | 自选择偏差（只有极满意/极不满的人会点） |
| 用途 | 训练主力 | 校准、护栏、离线评测的"金标准"子集 |

**曝光日志的完整性是训练数据的地基，而它坏掉时不会报错。**
Uber 的真实事故：App 的一次埋点变更导致某个 fare component 在美国主要城市 **10% 的 session** 中缺失，
**持续 45 天**，期间**没有任何服务级告警**（错误率、延迟、可用性全绿），靠人工发现；
模拟影响约 **0.23% 的 gross booking**，折合"数千万美元"级（[Uber D3](https://www.uber.com/us/en/blog/d3-an-automated-system-to-detect-data-drifts/)，2023-02-23）。
教训只有一条：**列级数据质量监控（空值率、分布、外键一致性）比模型监控更早触发**，
这类"部分损坏"永远不会触发服务级告警。Uber D3 把这类问题的平均检测时间从 **45 天压到 2 天（20×）**，
fact 表告警精确率 95.23%。完整的监控分层见 [08/08](08-drift-and-monitoring.md)（那一章讲数据质量、漂移与何时重训）。

**无偏训练数据的四种手段**（成本递增）：

1. **随机曝光日志 / RCT 样本**：一小比例流量完全随机排序，用于无偏评估与训练上采样。
2. **受控探索**：随机 item 注入、多样性配额、ε-greedy 或 bandit。
3. **倾向性加权（IPW, inverse propensity weighting）**：按"这条样本被曝光的概率"的倒数重新加权，把被系统压制的样本权重放大；
   拿不到精确 propensity 时用随机桶的日志近似。
4. **位置偏差建模**：把 position 作为独立特征或独立塔训练，serving 时把它固定成同一个位置。

**曝光偏差在统计上是 MNAR + PU 问题**（MNAR = missing not at random：数据缺失与它本身的取值有关；
PU = positive-unlabeled：你只有正样本和"未观测"，没有真负样本）。
把"未观测"当负反馈会系统性地压制长尾 —— 热门 item 的曝光量比长尾高几个数量级，观测到的正反馈天然偏向热门。

**随机流量的成本必须写进预算，且它是产品级决策而不是算法决策。** Booking.com 明确保留了 exploration budget，
但**未披露具体比例**（这一点没有公开数据，别在面试里编一个数）。可以给的推理是：
随机流量的转化率通常比正常流量低 30–60%，所以 1% 的随机流量约等于 0.3–0.6% 的直接收入损失 —— 这是买"能做无偏评估"的门票钱。
**没有这条流量，IPW、无偏离线评估、debias 训练全部无法落地**，而且这件事**不能事后补**：你需要的是历史随机日志。

## 11. 实验最常见的五个错误

1. **跑之前不算功效。** 一个从设计上就只能入组 5 万用户的实验，跑三个月也得不出结论。
   **修法**：实验平台强制填 MDE 和基线，自动算出天数；算出来 > 60 天的直接拒绝创建。
2. **偷看 + 显著就停。** 真实假阳性率 20–30% 量级。**修法**：默认开序贯检验，接受 10–30% 的样本量溢价；
   或者锁死终点，中途面板只显示护栏和 SRM，不显示主指标。
3. **不检查 SRM。** 6–10% 的实验有 SRM，而它一旦触发，**所有**指标结论都不可信。
   **修法**：p < 0.0005 的硬门禁，触发时面板直接遮住主指标，不给"我看一眼没关系"的余地。
4. **用请求级分流做排序实验。** 方差被低估，p 值虚小，同时用户看到自相矛盾的产品。
   **修法**：分流单元写进实验配置且不可事后改；平台对"改动会影响返回内容"的实验类型禁用请求级。
5. **拿短期实验的结论去外推长期。** 新奇效应两周内衰减到零，而绝大多数实验只跑 1–2 周。
   **修法**：常驻 1–5% 的长期 holdout，季度对账"实验累计增量 vs 大盘实际增量"。

**第六个（不算在五个里，但杀伤力最大）**：在流量不足以支撑任何有意义 MDE 的产品上，
正确的动作是承认实验不可行、改用交错/反事实/人工评估，而不是跑一个功效 20% 的 A/B 然后假装它有结论。

## 12. 什么时候不要这么做（反模式）

| 情况 | 为什么这么做是错的 | 该做什么 |
|---|---|---|
| 日入组用户 < 1 万 **/组**，还要测相对 1% 的提升 | 需要 298 万/组 ⇒ 朴素 300 天，算上复访的次线性增长是 450–600 天 —— 实验只是拖延决策的仪式 | 交错实验 / 反事实评测 / 专家评估 + 影子验证不崩 |
| 用影子部署的"预测一致性"当上线判据 | 一致性高说明新模型没什么变化，正是"不该上线"的信号；一致性低它也不告诉你哪个更好 | 影子只做"不崩 + 分布没歪"的门禁 |
| 用交错实验测收入、留存、多样性 | Airbnb 已给出集合级优化下**结论相反**的实例 | 这几类指标必须回落到用户级 A/B |
| 加到 15 个护栏指标以求"更安全" | 假阳性率累积 → 好模型被自动回滚 → 团队关掉自动回滚 → 零护栏 | 主指标 1 个 + 护栏 5–8 个，其余降级为"监控但不阻塞" |
| 把 CUPED 的"样本减半"写进容量规划 | Microsoft 自测中位只有 1.66×，某些指标面 68% 的指标几乎无收益 | 逐指标测出并存下 effective traffic multiplier |
| 每个实验都自建一套指标口径 | 两个实验的"CTR"定义不同，结论无法横向比较，也无法做累计增量对账 | 指标定义收敛到指标平台，实验只能引用不能重定义 |
| 模型换代时把评测集也换了 | 新旧模型的数字不可比，你测的是评测集的差异 | 评测集独立于模型版本演进；换评测集时必须同时重跑旧模型 |

**最大的反模式是把实验平台当"发布审批流"。** 实验的价值在于**它有权说不**。
一个 90% 的实验都被发布的平台，等于没有平台 —— 行业实测的正向率中位只有 **10%** 左右。
如果你的通过率远高于这个数，先怀疑 SRM 检查、功效计算和多重检验校正是不是全都没做。

---

## 这一章的三句话

1. **离线指标唯一合法的用途是剪枝，任何上线决策都必须有在线证据。**
   RecSys 2025 在 2,650 万次曝光上实测出 Recall@20 与 CVR 是**负相关**（系数 −0.204）——
   "离线指标 → 业务 KPI"是一个需要定期用线上数据重新标定的模型，不是一条可以背下来的常识。
2. **实验的可信度先于实验的结论：SRM、功效、多重检验校正这三件事没做，主指标涨多少都不该看。**
   先验成功率 8% 时，一个 p < 0.05 的显著结果有 26% 的概率是假的；再叠上偷看和 40 个指标，
   你的面板显示的是噪声的形状，不是模型的效果。
3. **交错实验快 50–100 倍但会看反 1/5，影子部署成本翻倍但对业务指标一无所知 —— 它们都是门禁，不是判决。**
   把评测做成"离线剪枝 → 交错/反事实定方向 → 用户级 A/B 定结论 → 长期 holdout 对账"这四段漏斗，
   任何一层都不能单独放行。
