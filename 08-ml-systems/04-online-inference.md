# 04 · 在线推理：批处理、准入与队列

> GPU 忙不等于系统在干活。没有准入控制的推理服务，过载时会把 100% 的算力用来计算已经没人要的结果。

---

## 读这一章之前

**你在工作中遇到过这个**

你的商品排序模型跑在 A10G 上，Triton 的动态批处理开着 `max_batch_size=64`、`max_queue_delay=50ms`，单批前向
40 ms，服务上限就是 `64 / 40ms = 1600 QPS`。平时 800 QPS，p99 92 ms，一切正常。大促当天流量涨到 2400 QPS ——
只超了 1.5 倍。队列没有上限（Triton 的 `max_queue_size` 默认不设），每秒净积压 800 个，
**60 秒后队列里躺着 4.8 万个请求，排队时延 30 秒**。而上游网关超时是 300 ms：算出来的每一个结果都早已被上游
丢弃，GPU 却一直 100% 忙。你把实例扩了 3 倍，5 分钟内毫无好转 —— 新实例只是更快地处理过期请求。
最后是把整个服务重启、清空队列才恢复的。

**需要先懂的概念**

| 概念 | 一句话 | 详见 |
|---|---|---|
| Little's Law | 并发 = 吞吐 × 延迟；用它从延迟目标反推队列该有多深 | [00-concepts §2](../00-foundations/00-concepts.md) |
| 排队论与利用率 | 利用率 80% 时排队时延已是服务时间的 5 倍，90% 是 10 倍 | [00/02 §3](../00-foundations/02-capacity-estimation.md) |
| 分位数不能相加 | 各段 p99 加起来不等于端到端 p99，通常远大于它 | [00-concepts §3](../00-foundations/00-concepts.md) |
| 背压与 load shedding | 处理不过来时当场拒绝，而不是无限排队等着一起死 | [00/01 §6](../00-foundations/01-fundamentals.md) |
| 连续批处理（LLM 侧） | 每个 decode step 之后重新组批，而不是等整批跑完 | [04/01 §3](../04-ai-agent-systems/01-llm-serving-infra.md) |
| SLO | 你对外承诺的服务指标，如"p99 ≤ 120 ms"，以及超了怎么办 | [05/01](../05-reliability/01-slo-and-error-budget.md) |

**这一章要回答的问题**

1. 这个预测该在线算、近线算、还是昨晚就该算好？三个判据分别是什么，边界在哪？
2. `max_batch_size` 和 `max_queue_delay` 各自换的是什么？为什么把 delay 调大在饱和时**一定**是亏的？
3. 输入变长时，padding 浪费和分桶带来的排队延迟怎么换算？分几个桶划算？
4. 过载时该拒绝谁、什么时候拒绝、队列该多深？为什么 FIFO 在过载时反而是最差的选择？

**本章新引入的术语**

| 术语 | English | 一句话定义 |
|---|---|---|
| 在线推理 / 批量推理 | online / batch inference | 前者在请求到达时才算一次前向并直接回给这次调用；后者离线一次性给一大批实体算好写进存储，线上只查表 |
| 动态批处理 | dynamic batching | 服务端把短时间内到达的多个独立请求攒成一个张量，一次前向算完再拆开返回 |
| 凑批窗口 | max queue delay | 攒批时最多愿意等多久；到了这个时间就算没凑满也立刻发车 |
| 分桶 | bucketing | 按输入长度把请求分到几个区间，同区间的才组批，减少补齐浪费 |
| 补齐浪费 | padding waste | 一批里长度不一时短的要补到最长那条，补出来的部分算了但没用 |
| 准入控制 | admission control | 在请求真正进入处理之前判断"要不要收"，收不下就当场返回拒绝 |
| 及早丢弃 | early drop / deadline-aware dropping | 请求出队时先看还剩多少时间预算，来不及就直接丢，不浪费一次前向 |
| 队头阻塞 | head-of-line blocking | 队伍最前面那个慢请求把后面所有人都堵住，哪怕后面的本来很快 |
| 有效吞吐 | goodput | 每秒完成**且满足延迟 SLO** 的请求数；与吞吐的差额就是白烧的算力 |

## 1. 在线、近线、还是离线：先回答这个

**绝大多数"必须在线推理"的需求经不起追问。** 推荐系统里的 user embedding、item embedding、长期画像、
商品质量分全都可以昨晚算好；真正必须在请求那一刻算的，只有拿到本次候选集之后的 **排序（ranking）** 那一层，
和依赖"本次会话前几秒行为"的实时特征。分清这件事，GPU 账单通常能砍一半以上。

| 判据 | 在线 | 近线（事件触发、异步写存储） | 离线批量 |
|---|---|---|---|
| **结果必须多新** | 依赖本次请求内容（候选集、query、上下文） | 依赖分钟级事件（刚下单、刚点了什么） | T+1 / 小时级足够 |
| **延迟预算** | 端到端 p99 通常 50–300 ms | 无请求路径延迟，只有新鲜度 SLO | 无 |
| **候选空间** | 每次请求的组合都不同，不可枚举 | 实体数有限 | 实体数有限 |
| **典型形态** | 排序、CTR 预估、实时风控、ASR | 召回列表刷新、用户向量更新 | 全量打分、离线画像 |
| **稳态利用率** | 50–70%（排队论上限，[00/02 §3](../00-foundations/02-capacity-estimation.md)） | 70–85% | 90%+ |

**成本差距被严重低估。** 在线服务既要按利用率 60% 配容量，又要按**峰值**配：一个峰谷比 4× 的业务，
在线路径的单次预测成本约为同模型离线打分的 **4–6 倍**（自算：`(1/0.6 × 4) ÷ (1/0.9) ≈ 6`）。
"能不能挪到离线"这个问题的价值高于任何引擎调优。

**撞墙条件**：离线预计算的失效点是**候选空间爆炸**。给 1 亿用户各存 top-500 商品可行（500 亿条 × 20 B ≈ 1 TB）；
按「用户 × query × 时段 × 设备」四维组合预计算就不可行。信号很明确：
**预计算表的行数开始随两个以上维度相乘增长时，这条路已经死了。**

**CPU 还是 GPU 也在这一步定。** AWS EKS 最佳实践口径（[一手](https://docs.aws.amazon.com/eks/latest/best-practices/aiml-cpu-inference.html)，2025）：
单 endpoint 持续 **> 100 req/s** 且 p95 要求 **< 50 ms** 才值得上 GPU；p95 允许 100–500 ms、QPS < 100 的
分类器 / embedding / 小模型，CPU 的每千次查询成本直接胜出。Netflix 的落地是同一判据：小模型直接在 JVM
服务进程内跑 CPU，大模型才走独立 GPU 栈（[Netflix TechBlog, 2026-07](https://netflixtechblog.com/in-house-llm-serving-at-netflix-a5a8e799ea2c)）。
⚠️ 公开的"盈亏平衡点"数字冲突极大（AWS 说 100 req/s，部分二手博客说 5000 req/s），**不要采信任何单一数字**，
统一自测**目标 p95 约束下的 cost per 1,000 queries**。

## 2. 同步、异步回调、异步轮询

判据一句话：**单请求的 p99 处理时间和调用方的超时预算，谁更大。**

| 形态 | 适用 | 实现要点 | 失败模式 |
|---|---|---|---|
| **同步返回** | p99 < 500 ms，调用方能一直占着连接 | 普通 HTTP/gRPC；服务端必须有请求级超时 | 服务端变慢 → 调用方连接池被占满 → 调用方自己也挂（[00-concepts §2](../00-foundations/00-concepts.md) 那条链） |
| **异步 + 回调** | 秒到分钟级，调用方是服务端且有可达地址 | 立刻返 `202` + `job_id`，算完 POST 回去 | 回调必须重试，且调用方必须幂等（同一条回调收两次和收一次结果相同，见 [00/01 §5](../00-foundations/01-fundamentals.md)）；地址失联要有死信 |
| **异步 + 轮询** | 同上，但调用方在浏览器/移动端，没有公网地址 | `202` + `Location: /jobs/{id}`，客户端指数退避轮询 | 轮询频率过高会压死网关；job 状态必须有 TTL |

**别把这个决定留给"以后再说"**：同步 API 一旦上线，改成异步就是一次不兼容变更
（[`02/04`](../02-architecture-patterns/04-api-design-and-versioning.md)）。经验规则：
**单请求 p99 超过 2 秒的推理一律不做同步** —— 视频理解、长文档抽取、多模型级联都属于这一类。
异步还有一个被忽略的好处：**它把队列从"服务内部的隐式队列"变成外部可观测、可持久化的显式队列**
（Kafka / SQS，见 [`01/03`](../01-building-blocks/03-messaging-and-streams.md)）——
本章后面讲的准入控制和及早丢弃在显式队列上做起来容易得多：积压看得见、年龄算得出、优先级重排得动。

## 3. Streaming 的两个意思，别混

**输入流式（input streaming）**：请求本身是持续的流 —— 语音、视频帧、实时事件。模型做**增量**推理，
服务端要维护跨 chunk 的状态（ASR 解码器状态、视频跟踪的目标 ID）。三条硬结论：

- 它把"批"的单位从 request 变成了 **chunk**：一次组批攒的是不同会话在同一时刻的 chunk。
- 参数量级：ASR 每 chunk 160–320 ms 音频，首字延迟 p95 < 300 ms → 凑批窗口只能是个位数毫秒。
- 状态在服务端 → **必须有会话亲和（session affinity：同一会话的后续 chunk 必须落到同一实例，见 [00-concepts §9](../00-foundations/00-concepts.md)）**，
  这一步把无状态服务变成有状态服务，扩缩容和滚动发布都要重做。

**输出流式（output streaming）**：结果分多次陆续返回（SSE / gRPC server streaming）。它对**非 LLM 模型基本
没有意义** —— 一次排序前向就出全部结果，没有"逐步"可言。只有两类例外：多阶段级联（先返粗排、再返精排修正），
以及本来就逐 token 产出的生成模型（属于 [04/01](../04-ai-agent-systems/01-llm-serving-infra.md) 的范畴）。

## 4. 动态批处理：原理与两个旋钮

**为什么要凑批。** GPU 一次前向的成本 = 固定开销 + 边际开销，而固定开销（kernel launch、权重从显存读进片上
缓存、框架调度）**与 batch 大小无关**：`batch=1` 时它可占到整次前向的 80% 以上，算力利用率个位数百分比。
Pinterest 的公开数据给了量级：用 CUDA Graphs 消掉 kernel launch 开销、把数百次 `cudaMemcpy()` 合并成一次后，
**P50 拷贝耗时从 10 ms 降到 sub-1 ms**；成本中性前提下能服务 **77× 更大的模型**、延迟还降 30%
（[Pinterest, 2022-08](https://medium.com/@Pinterest_Engineering/gpu-accelerated-ml-inference-at-pinterest-ad1b6a03a16d)，跨代际硬件需折算）。
动态批处理就是把它做在服务端：**客户端各发各的单条请求，服务端偷偷攒成一批。**

```
  req A ──►┌── 动态批处理器 ─────────────────────────────┐
  req B ──►│  等待队列 [A][B][C][D]…                     │
  req C ──►│    ├─ 触发条件 1：攒够 max_batch_size ───┐   │
  req D ──►│    └─ 触发条件 2：队头等满 max_queue_delay┤   │
           │                                        ▼   │
           │         拼成 [B, …] 张量 → 一次 GPU 前向     │
           └────────────────────┬───────────────────────┘
                                └──► 按行拆开 → resp A / B / C

  单请求延迟 = 排队时延 + 批等待 + 前向时间(batch)
                  ↑          ↑          ↑
              过载时主项  低载时主项   两者都低时主项
```

> 📖 **读图要点**：两个触发条件是 **OR** 不是 AND。低 QPS 时永远由条件 2 触发，意味着**每个请求都白等满整个
> `max_queue_delay`**；高 QPS 时永远由条件 1 触发，意味着 `max_queue_delay` **根本没有参与决策**。
> 这两句解释了它 90% 的调优困惑。

**Triton 的参数面**（[官方 `batcher.md`](https://github.com/triton-inference-server/server/blob/main/docs/user_guide/batcher.md)，一手）
是这类系统的事实标准语义，值得逐字抄：

```protobuf
max_batch_size: 64                     # 模型级硬上限，受显存约束
dynamic_batching {
  max_queue_delay_microseconds: 2000   # 凑批窗口 = 2 ms
  default_queue_policy {
    max_queue_size: 128                # 队列硬上限 —— 默认不设，这是事故的起点
    timeout_action: REJECT             # REJECT 立刻返错 / DELAY 继续排但不计入超时
    default_timeout_microseconds: 30000
  }
  priority_levels: 2                   # 数字越小优先级越高
  default_priority_level: 2
}
```

两条官方结论必须记住：**(a)** *"For most models, `preferred_batch_size` should not be specified."* ——
它只对有多个 optimization profile 的 TensorRT 模型有意义，大多数人调它是在调一个不生效的旋钮。
**(b)** 调优方法是**沿延迟预算爬坡**：*"try increasing delay values until the latency budget is exceeded."*

## 5. 延迟-吞吐权衡曲线

```
  吞吐 (req/s)                              单请求 p99 延迟 (ms)
  ▲                                         ▲
  │              ╭────────────── 饱和        │                     ╱
  │         ╭────╯   ← 拐点之后：             │                 ╱  线性增长
  │     ╭───╯          纯延迟惩罚             │             ╱     ≈ delay 本身
  │   ╭─╯  ← 陡峭段：1 ms delay              │         ╱
  │  ╭╯       换来显著吞吐                    │     ╱
  └─┴────┴────┴────┴────► delay(ms)         └──┴────┴────┴────► delay(ms)
    0    2    5   10   20                     0   2    5   10
         ▲ 拐点 ≈ 平均到达间隔 ×(B−1)              ▲ 上界 = p99 预算
                                                    − 单批前向 − 两端网络
  goodput = f(delay)： ╭──╮
                    ╭─╯  ╰──╮
                 ╭──╯       ╰───────► 0（吞吐还在涨，但全部超时）
```

> 📖 **读图要点**：三条曲线的拐点不在同一处。吞吐在拐点后**变平**（还涨一点），延迟在拐点后**继续线性涨**，
> 于是 goodput 在拐点后**开始下降并归零**。只盯左图调参的人，会一路把 delay 调到 goodput 已经是 0 的地方，
> 而监控面板上吞吐看起来"创了新高"。

**拐点怎么来的**：`max_batch_size = B`、平均到达间隔 `1/λ`，攒满一批的期望时间约 `(B−1)/λ`；delay 设到这个值时
绝大多数批都是"攒满才发车"，再加大只会让批**等得更久**，不会让批变大。⚠️ **来源标注**：`max_queue_delay`
与吞吐的**定量取舍曲线没有公开论文或厂商基准**（本书调研未找到），上面这条拐点关系是按排队模型推导的量级估计，
**必须在自己的流量分布上实测校准**；Triton 官方也只给方法（沿预算爬坡）而没给曲线。

| 负载区 | 判据 | `max_queue_delay` 该设成 | 理由 |
|---|---|---|---|
| **欠载** | 平均到达间隔 > 单批前向时间 | 几毫秒，取延迟预算能给的上限 | 唯一能靠等待换吞吐的区间 |
| **中载** | 队列平均深度 5–30 | 拐点值 `(B−1)/λ` | 刚好攒满就发车，等待和批大小都不浪费 |
| **饱和** | 队列常驻 ≥ B 个请求 | **0 或极小** | 队列里本来就够一批，等待带来的**只有纯延迟** |

**最反直觉的一条**：**过载时把 `max_queue_delay` 调大，吞吐一点都不会涨。** 这是 Triton 官方明确口径
（"只在未饱和区成立"），也是最常见的一条工程误解 —— 过载时你需要的不是更大的批，是准入控制（§9）。

## 6. 批大小的天花板：显存不是线性预算

**(1) 激活显存随 batch 线性增长，且常比权重大一个数量级。** 一个 640×640 输入的检测模型权重可能只有 100 MB，
但单样本激活峰值在 200–400 MB 量级，`batch=32` 就是 **6–12 GB**。
"权重才 100 MB，24 GB 卡怎么会 OOM"是每个人都问过一次的问题。

**(2) 注意力类模型有 O(seq²) 项。** 若实现会物化注意力分数矩阵（不是 FlashAttention 那种融合算子），
占用是 `batch × heads × seq × seq × 2 B`：`batch=32, heads=12, seq=512, FP16` →
`32×12×512×512×2 B ≈ 201 MB`**每层**，12 层就是 2.4 GB，且随 seq **平方**增长（seq 翻倍 = 4×）。

**(3) OOM 不是渐进的，是断崖。** 显存没有 CPU 那种 swap / overcommit 语义 —— 超一个字节就是进程崩溃、
整个实例的在途请求全部失败。所以生产的 `max_batch_size` 必须按**最坏输入**（最长序列、最大分辨率）
压测出来再打 15–20% 折，而不是按平均输入。

**收益侧还有一个更早的天花板**：batch 大到工作集超出 L2 cache 后吞吐边际收益迅速衰减，典型形状是
1→8 涨 4–6×、8→32 再涨 1.5–2×、32→128 只涨 10–20%。**收益递减点通常远在显存上限之前**，
所以先测吞吐曲线再看显存，顺序反了会白白牺牲延迟。

## 7. 变长输入：padding 浪费与分桶

```
  不分桶（按到达顺序组批，B=6）：           分 2 桶（[0,128) 与 [128,512]）：
  长度 512 ██████████████████████████████   桶1  48 61 73 44 90
       48  ██░░░░░░░░░░░░░░░░░░░░░░░░░░░░        → 补齐到 90
       61  ███░░░░░░░░░░░░░░░░░░░░░░░░░░░        → 316/450 = 利用率 70%
       73  ████░░░░░░░░░░░░░░░░░░░░░░░░░░   桶2  512
       44  ██░░░░░░░░░░░░░░░░░░░░░░░░░░░░        → 长请求单独成批，
       90  █████░░░░░░░░░░░░░░░░░░░░░░░░░           不再污染短请求
           ├有效┤├──────  padding  ──────┤
       有效 828 / 实算 6×512=3072 = 利用率 27%  ← 73% 算力白烧
```

> 📖 **读图要点**：盯左图那一条 512 —— 它一个人就决定了整批的成本。分桶解决的不是"平均长度"，
> 而是**长尾样本对全批征的税**。长度分布是单峰窄分布时，分桶不值得做。

**分桶的代价必须一起算**：分 `K` 桶后每桶到达率稀释成 `λ/K`，攒满 `B` 条的期望等待从 `(B−1)/λ`
变成 **`K(B−1)/λ`** —— 线性放大 K 倍。

| λ (QPS) | B | 桶数 K | 攒满一批的期望等待 | 结论 |
|---|---|---|---|---|
| 1000 | 32 | 1 | 31 ms | 已经吃掉大半预算 |
| 1000 | 32 | 4 | **124 ms** | 直接爆掉 120 ms 的 SLO |
| 1000 | 8 | 4 | 28 ms | 桶多了就必须把 B 调小 |

**实操结论**：桶数 **2–4 个**，边界取长度分布的 p50 / p90 分位而不是等距切；分桶必须**同时把 `max_batch_size`
调小**，否则排队延迟会把省下的 padding 全吐回去；**λ 低于约 `K × B × 10` QPS 时不要分桶**（攒不满，每桶都等满窗口）。
更省事的替代是**长请求走独立实例组** —— 两个实例（短/长）+ 路由层按长度分流，比在一个 batcher 里做多桶
简单得多，代价是多一份权重显存。

## 8. 和 LLM 的 continuous batching 有什么本质区别

面试里最容易露怯的一问。答"都是攒批提高利用率"等于没答。

| 维度 | 动态批处理（本章） | 连续批处理（[04/01 §3](../04-ai-agent-systems/01-llm-serving-infra.md)） |
|---|---|---|
| **调度粒度** | request-level：组批后**锁定到整批前向结束** | iteration-level：**每个 decode step 之后**重新组批 |
| **一次调用的计算次数** | 1 次前向出全部结果 | prefill 1 次 + decode N 次（N = 输出 token 数） |
| **队头阻塞** | 存在：批内最慢那条决定全批（§7 那条 512） | **在 decode 维度上消除**（某序列 EOS 后立刻把新请求塞进它的槽位），但**没有消失**：一次超长 prefill 仍会占住整个 step 把所有 decode 卡住 —— 这正是 chunked prefill（vLLM V1 默认开启）存在的理由；KV cache 被打满时也会重新出现队头阻塞（§9 的 Fill-and-Squeeze） |
| **该调的旋钮** | `max_batch_size` + `max_queue_delay` | `max_num_batched_tokens` + `max_num_seqs` |
| **凑批等待的价值** | 欠载区有价值 | **零价值，纯延迟浪费** |
| **过载表现** | 队列积压 → 排队时延爆炸 | 静默 preempt + 重算 → 错误率仍是 0，只有 p99 抬升 |

**本质就一句**：**连续批处理之所以可能，是因为生成模型的一次调用被切成了几百个 decode step，调度器每一步都有
机会换人；而一次 ResNet 前向是不可分割的原子操作，没有任何插空的缝隙。** 两条推论：

1. **不要在 vLLM / SGLang 前面再加一层凑批网关。** 引擎内部已做 iteration-level 调度，外面那层等待窗口是纯增延迟（[vLLM 调优文档](https://docs.vllm.ai/en/stable/configuration/optimization/)）。
2. **不要把 LLM 的过载排障经验搬到排序模型上。** LLM 引擎的过载信号是 preemption 计数器（`vllm:num_preemptions_total`
   —— KV cache 打满时**不返回 429**，而是静默重算）；排序服务的过载信号是队列深度和被拒率，两者监控完全不同。

## 9. 准入控制：过载时该拒绝谁

开篇那个事故的全部原因就是队列没有上限。**有界队列是在线推理服务的地基，不是优化项。**

**(1) 队列长度上限（`max_queue_size`）** —— 最粗但必须有。满了立刻返回 `429` / gRPC `RESOURCE_EXHAUSTED`。

**(2) 队列等待时间上限（`default_timeout_microseconds` + `timeout_action`）** —— 比长度更贴近 SLO。
`REJECT` 超时立刻返错并**释放容量**，是在线路径的默认选择；`DELAY` 只是不再计入延迟统计、请求继续排 ——
**在线路径上用 `DELAY` 等于没做准入控制**。

**(3) 基于 deadline 的及早丢弃** —— 最有效也最少人做。客户端把剩余预算随请求传下来（HTTP 头
`X-Request-Deadline` 或 gRPC deadline 传播），服务端在**出队那一刻**判断：

```python
# 关键：判断发生在出队时，不是入队时
def dequeue_and_admit(q, model_p99_ms):
    while (req := q.pop()) is not None:
        remaining = req.deadline_ms - now_ms()
        if remaining < model_p99_ms + POSTPROCESS_MS:
            metrics.inc("dropped_deadline_exceeded")   # 丢它只浪费一次入队
            req.fail(504)
            continue                                   # 继续看下一个
        return req
```

**为什么必须在出队时判断**：入队时你不知道它会等多久（排队时延取决于此刻的负载，不只是队列长度）；
出队时你同时知道"它已经等了多久"和"还剩多少预算"，这是全链路唯一信息完备的时刻。

> **面试金句**
> "过载时最重要的一条是：**队列必须有界，而且丢弃要发生在出队时而不是入队时**。入队时你还不知道这个请求要等多久；
> 出队时你知道它已经等了多久、也知道 deadline 还剩多少 —— 在这里扔掉它只浪费一次入队，不浪费一次 GPU 前向。"
> "The one thing that matters under overload is: bound the queue, and drop on dequeue, not on enqueue. When a request
> comes in you have no idea how long it's going to sit there. When you pull it off the queue you know exactly how long
> it waited and how much of its deadline is left — so that's where you throw it away. Dropping there costs you an
> enqueue; dropping after the forward pass costs you a full GPU batch."

**不做准入控制不只是稳定性问题，还是安全问题。** [arXiv:2602.07878](https://arxiv.org/abs/2602.07878)（2026-02）
在多租户推理服务上构造了 "Fill and Squeeze" 攻击：用少量请求打满共享资源触发队头阻塞，实测受害者首字延迟
劣化 **20–280×**、每 token 延迟劣化 **1.5–4×**，攻击者成本反而比正常用户低 30–40%。**共享推理服务默认不公平。**

**优先级与公平性**：`priority_levels` 能保证付费租户先走，但**优先级队列天然会饿死低优先级**。两个标准补丁：
**老化（aging）** —— 请求在低优先级队列每等 `T` 毫秒升一级，实现简单且能给出饥饿上界；**加权公平队列（WFQ）**
—— 每租户一条独立队列按权重轮询，能防"吵闹邻居"（一个租户的尖峰吃掉共享容量把别人挤死），代价是出队逻辑复杂
度上升。⚠️ **只有一条全局队列时任何优先级策略都保护不了你** —— 队头阻塞发生在队列层而不是调度层，
多租户服务必须**先按租户拆队列，再谈优先级**。

## 10. 队列管理：深度、纪律、丢弃

### 队列深度用 Little's Law 从 SLO 反推

```
  L = λ × W
  λ = 峰值 2000 QPS
  W = 分配给"排队"这一段的预算 = 30 ms   （见 §11 预算表）
  → L = 2000 × 0.030 = 60 → 队列深度设 60，超过就返回 429
```

**为什么不能设更大**：深度 600 意味着队尾要等 300 ms，它排到时调用方早已超时走人 ——
你只是把"快速失败"换成了"慢速失败 + 浪费一次前向"。

**一条必须说穿的性质**：**队列只能吸收突发（burst），不能吸收持续过载。** 到达率持续高于服务率时队列长度
**无界线性增长**，任何有限深度都只决定"多久之后开始拒绝"。开篇事故里扩容 3 倍没用，就是因为积压已经形成，系统
进入了**亚稳态失败（metastable failure：触发因素消失后系统靠自身反馈仍回不到正常态，必须外力干预）** —— 唯一出路是清空队列。

### FIFO vs LIFO：过载时结论会反转

| | 正常负载 | 持续过载 2× |
|---|---|---|
| **FIFO** | 公平，p99 可控 | **成功率趋近 0** —— 每个请求都要等完整个积压，全员超时 |
| **LIFO** | 与 FIFO 几乎无差别 | **成功率约等于容量比（~50%）** —— 新请求走快车道，队底老请求饿死 |

FIFO 保证的是"先来先服务"，但过载时它实际保证的是**"每个请求都等最久"**；LIFO 放弃公平，换来"至少一半人拿到了
结果"。Facebook 的 *Fail at Scale*（ACM Queue, 2015）把工程解法叫 **adaptive LIFO**：队列短时用 FIFO，一超阈值
就切 LIFO，并配合 **CoDel**（controlled delay：不看队列长度而看"队列最小驻留时间是否持续超过阈值"来决定丢弃，
能区分"短暂突发"和"真的堵了"）。**LIFO 的代价**：延迟分布变成双峰（新请求很快、老请求超时），
**p99 这个指标本身失去意义**；被饿死的老请求若带重试还会形成正反馈。所以 LIFO 只在确认过载时切换，不做常态策略。

### 三个必须上的监控指标

| 指标 | 为什么 | 用法 |
|---|---|---|
| **队列深度**（不是 GPU 利用率） | 利用率是**饱和指标**（延迟已坏了才涨），队列深度是**先行指标** | 扩缩容挂这个 |
| **实际批大小的直方图**（不是均值） | 均值 12 可能是"一半 1、一半 23"，两种情况调参方向相反 | 左偏 = 凑批失败；右偏撞上限 = 该加实例 |
| **被拒率 + 超时丢弃率** | 准入控制到底生效没有；两者之和是真实的 load shedding 量 | 长期 > 1% 说明容量不够，不是参数问题 |

"按队列深度扩容而不是按利用率扩容"是 2025–2026 的行业共识（[AWS EKS 最佳实践](https://docs.aws.amazon.com/eks/latest/best-practices/aiml-cpu-inference.html)、
Red Hat 的 KEDA 方案同口径）。用 Kubernetes HPA 挂 CPU 利用率扩推理服务，经典结果是**永远不扩容直到请求全部
超时** —— 因为一个被 GPU 打满的推理 pod，CPU 接近 idle。

## 11. 延迟预算分解：一个具体算例

目标：商品排序服务，端到端 **p99 ≤ 120 ms**（客户端视角）。

| 阶段 | p50 (ms) | p99 (ms) | 你能不能动 |
|---|---|---|---|
| 客户端 → 边缘网关（移动网络，跨城） | 15 | 35 | ❌ 硬成本 |
| 网关 → 排序服务（同 AZ） | 0.3 | 1 | ❌ |
| 鉴权 + 请求解析 | 1 | 3 | 🔸 微小 |
| 召回结果反序列化（500 候选） | 2 | 5 | ✅ 换序列化格式 |
| **在线特征取数** | 4 | 18 | ✅ **合并 feature view** |
| **排队时延** | 2 | 20 | ✅ **准入控制封顶** |
| **批等待** | 3 | 6 | ✅ **`max_queue_delay`** |
| 前处理（特征拼装 / tokenize） | 4 | 9 | ✅ 搬到写入侧 |
| **模型前向（batch=32）** | 18 | 26 | ✅ 量化 / 编译 / 裁剪 |
| 后处理（排序 + 业务规则 + 打散） | 3 | 7 | ✅ |
| 服务 → 网关 → 客户端 | 15 | 35 | ❌ 硬成本 |
| **朴素相加** | **67** | **165** | ← **这个数是错的** |
| **实测端到端** | **71** | **118** | |

**这张表最重要的是倒数第二行。** 各段 p99 相加得 165 ms 会让你以为已经违约，实测端到端 p99 只有 118 ms ——
因为各段的慢样本**不同时发生**，分位数不能相加（[00-concepts §3](../00-foundations/00-concepts.md)）。
**这张表不是用来求和的，是用来定位哪一段最肥的。** 读出来三个结论：

1. **两端网络在 p99 占了 70 ms，你一行代码都改不了**，真正留给整个服务的只有约 50 ms。任何"把推理从 26 ms 优化到 20 ms"的提案，对端到端 p99 的影响都在噪声里。
2. **排队 20 ms 是最大的可控项，且完全由准入控制决定** —— 投入产出比最高的一处。
3. **`max_queue_delay` 只能设到个位数毫秒**（表里 6 ms）。"调到 50 ms 提吞吐"的建议在这个预算下直接出局。

**特征取数那 18 ms 值得单说一句**：在线特征库的延迟主要由**一次请求要访问几个 feature view** 决定而不是特征个数
—— 10 个特征分散在 5 个 view 里就是 5 次串行往返（Redis 是例外，同 entity 共享一个 hash key，往返恒为 1 次）。
Redis 在线读的公开量级是 p50 600–700 µs / p99 2.5–3.0 ms，DynamoDB 是 p50 3–4 ms / p99 20–25 ms（Tecton 文档
口径）。**合并 view 比换存储引擎有效得多。**

## 12. 什么时候动态批处理反而有害

| 情况 | 为什么亏 | 撞墙信号 |
|---|---|---|
| **模型极小**（单条前向 < 5 ms） | 凑批窗口比推理还长，等待成本 > 固定开销节省 | 批大小集中在 1–2，但 p99 里排队占一半以上 |
| **LLM / 生成式模型** | 引擎已做 iteration-level 调度，外层等待纯增延迟 | 网关侧 delay > 0，TTFT 比直连引擎高一个固定偏移 |
| **QPS 低且不稳** | 到达间隔 ≫ delay，几乎每条都白等满窗口 | 平均批大小长期 < `max_batch_size / 4` |
| **延迟 SLO 极紧**（端到端 < 30 ms） | delay 吃掉全部余量 | 预算表里"批等待"这一行没有位置可放 |
| **变长输入 + 极重长尾** | padding 浪费 > 批处理收益（§7 那张 27% 利用率的图） | 有效 token / 实算 token < 40% 且分桶后排队爆掉 |
| **CPU 推理** | CPU 是**内存带宽瓶颈**不是 kernel launch 瓶颈，batch 边际收益远小于 GPU | batch 1→16 吞吐涨不到 2× |

**三条反模式，逐条点名：**

❌ **把 `max_queue_delay` 当吞吐旋钮往大调。** 它只在未饱和区能换吞吐（Triton 官方口径）；饱和时调大它，吞吐曲线纹丝不动、延迟线性上升、goodput 直接掉。正确做法是**从 0 沿延迟预算往上爬**。

❌ **用队列深度当"缓冲区"吸收持续过载。** 队列吸收得了突发，吸收不了持续过载 —— 无界队列把一次 1.5× 的流量超预期变成了需要重启才能恢复的亚稳态故障，就是开篇那个事故。

❌ **同一个 batcher 里塞进 SLO 差异巨大的流量。** 实时排序（p99 120 ms）和离线补数（分钟级）共用一个队列，结果是前者被后者的大 batch 队头阻塞。**按 SLO 拆实例组**比在一个队列里做优先级简单且可靠得多。

> **面试金句**
> "`max_queue_delay` 不是吞吐旋钮，它是**延迟旋钮**。它只在系统还没饱和时能换来吞吐 —— 一旦队列里本来就常驻着
> 够一批的请求，这个等待窗口带来的就只有纯延迟。所以我调它是从 0 沿延迟预算往上爬，而不是先设大值再往下砍。"
> "max_queue_delay isn't a throughput knob, it's a latency knob. It only buys you throughput while you're
> under-saturated. Once there's always a full batch sitting in the queue, that wait window buys you nothing but
> latency. So I tune it from zero upward against the latency budget — I never start big and walk it back."

## 13. 调优顺序（可执行）

1. **先写延迟预算表**（§11）。没有预算表的调参都是瞎调 —— 你不知道 delay 允许占几毫秒。
2. **定 `max_batch_size`**：用**最坏输入**压测显存上限再打 15–20% 折；同时测吞吐-batch 曲线，
   取「收益递减点」和「显存上限」的**较小者**。
3. **`max_queue_delay` 从 0 开始爬**：0 → 1 → 2 → 5 ms…，每档记录 (吞吐, p99, 平均批大小)，**p99 一碰到预算就停**。
4. **设 `max_queue_size` = λ_peak × W_queue**（§10），`timeout_action: REJECT`。
5. **上 deadline 及早丢弃**（§9 那段代码），把丢弃点从"前向之后"提到"出队之前"。
6. **扩缩容挂队列深度**，不挂 CPU / GPU 利用率。
7. **最后才考虑分桶**（§7），且只在实测 padding 利用率 < 40% 时做。

每一步之后都要看**批大小直方图**和**被拒率**，不要只看吞吐均值。

## 这一章的三句话

1. **在线推理服务的第一性问题不是"批开多大"，而是"过载时拒绝谁"。** 没有队列上限的推理服务，本质上是把 1.5 倍的流量超预期兑换成一次必须重启才能恢复的故障；准入控制是唯一能把"过载"从"不可自愈"变回"可自愈"的机制。

2. **`max_queue_delay` 在未饱和区是吞吐旋钮，在饱和区是纯粹的延迟税** —— 而生产系统出问题的时刻永远发生在饱和区。这就是它必须从 0 往上爬的理由，也是"调大它提吞吐"这条直觉恰好在最需要它的时候失效的理由。

3. **动态批处理和连续批处理的差别不是参数，是调度粒度：一次判别式模型前向是原子的，一次生成是几百步可插空的。** 想明白这句，你就同时知道了为什么 LLM 不该再凑批、为什么排序模型做不了 iteration-level 调度、以及为什么两者的过载信号完全不同。
