# 05 · 推理性能优化

> 大多数团队优化的是端到端时间里那 10%，而剩下 90% 在解码图片、拼特征、等 kernel 启动。
> 先测，再决定优化什么 —— 这个顺序反过来，你会用三周换来 4% 的收益。

---

## 读这一章之前

**你在工作中遇到过这个**

你负责的图像审核服务跑 ResNet-50，p99 是 180 ms，产品要压到 100 ms。你花三周把模型转成
TensorRT + INT8，离线压测里模型前向从 12 ms 降到 3.5 ms（3.4×），信心满满地上线 ——
p99 从 180 ms 变成 172 ms。用 Nsight Systems 抓一遍时间轴才看明白：JPEG 解码在 CPU 上花 96 ms、
resize 与归一化 21 ms、CPU 内存到显存的拷贝 14 ms，GPU 上真正跑模型的那段只占 12 ms。
你优化的是端到端链路的 7%。更难受的是，整整三周里 `nvidia-smi` 一直显示 GPU utilization 85–90%，
你据此认定"卡已经打满了，只能优化模型"—— 那个 90% 从头到尾就不是利用率。

**这一章要回答的问题**

1. 模型前向只要 8 ms，为什么端到端 p99 是 180 ms？我该用什么工具把这 172 ms 拆开？
2. 量化到 INT8 到底能省多少、掉多少点？哪些模型量化后会崩，为什么？
3. `nvidia-smi` 显示 90%，为什么我还能再塞两倍流量进去？该盯哪个指标？
4. 什么模型规模、什么 QPS 下，CPU 比 GPU 便宜？给我一个能在白板上算的公式。

**本章新引入的术语**

| 术语 | English | 一句话定义 |
|---|---|---|
| 算术强度 | arithmetic intensity | 每从显存搬进 1 字节数据，能做多少次浮点运算；单位 FLOP/Byte |
| Roofline 模型 | roofline model | 一张图，横轴算术强度、纵轴性能上限，用来判断"这个算子被算力卡住还是被显存带宽卡住" |
| 访存受限 / 算力受限 | memory-bound / compute-bound | 时间花在等数据从显存搬过来，还是花在真正做乘加 |
| 内核 | kernel | GPU 上被调度执行的一个函数，一次卷积、一次加法各是一个 |
| 内核启动开销 | kernel launch overhead | CPU 每让 GPU 跑一个 kernel 都要付的固定提交成本，约 3–10 µs，与这个 kernel 干多少活无关 |
| 算子融合 | operator fusion | 把连续几个算子编译成一个 kernel，中间结果留在片上寄存器，不往显存里写一遍再读回来 |
| CUDA Graph | CUDA graph | 把一整串 kernel 的启动顺序预先录下来，之后一次提交整段回放，把 N 次启动开销压成 1 次 |
| 训练后量化 | PTQ, post-training quantization | 模型已经训完，只用几百条样本统计数值范围就把它降到低精度 |
| 量化感知训练 | QAT, quantization-aware training | 训练过程中就模拟低精度的舍入误差，让模型自己适应 |
| 量化校准 | calibration (quantization) | 用一小批代表性样本跑一遍前向，记录每个张量的取值范围，据此定缩放系数。⚠️ **这个 `calibration` 和 [08/01 术语表](01-ml-system-overview.md)、[08/08](08-drift-and-monitoring.md) 里的"概率校准"是同名的两件事**：那个指"模型说 70% 会点击的那批样本实际点击率是不是 70%"，是质量指标；这个指低精度转换的定标步骤，是编译期动作。本章 §4 两个意思都出现（量化定标 vs 量化后要重做的概率校准），看上下文区分 |
| 蒸馏 | distillation | 用大模型输出的概率分布当作"软标签"，训练一个结构更小的模型去模仿它 |
| MFU | model FLOPs utilization | 模型有效 FLOPs ÷ 所选硬件/精度峰值；有助于解释算力利用，但跨硬件比较还要统一 FLOP 口径、精度、稀疏性与 SLO |

## 1. 先定位：这 180 ms 到底在哪

**一个在线推理请求的时间，至少分成七段。** 只有第 5 段是"模型"。

```
   t0        t1         t2          t3        t4         t5         t6        t7
   │  排队   │  反序列化 │  特征/前处理 │  H2D 拷贝 │ kernel 执行│ D2H 拷贝  │ 后处理+序列化 │
   ├────────┼──────────┼───────────┼─────────┼──────────┼─────────┼────────────┤
   │  12ms  │   3ms    │   117ms   │  14ms   │   12ms   │  1ms    │    21ms    │
   │        │          │  ← CPU →  │         │ ← GPU →  │         │  ← CPU →   │
   └──────────────────────── 端到端 p99 = 180ms ───────────────────────────────┘
                            模型前向只占 6.7%
```

（**H2D / D2H**：host-to-device / device-to-host，CPU 内存与显存之间的拷贝。）

**工具与它们各自能看见什么：**

| 工具 | 粒度 | 看得见 | 看不见 |
|---|---|---|---|
| `torch.profiler` | 算子级 + CPU/GPU 两条时间线 | 哪个算子最贵、CPU 是否在等 GPU、显存分配尖峰 | 单个 kernel 内部为什么慢 |
| Nsight Systems (`nsys`) | 系统级时间轴 | **kernel 之间的空隙**、H2D 与计算有没有重叠、CPU 线程在干什么 | 算子在框架里的名字 |
| Nsight Compute (`ncu`) | 单 kernel 硬件计数器 | 这个 kernel 的算术强度、达到峰值算力的百分之多少、访存效率 | 端到端归因 |
| `torch.cuda.Event` | 手工插桩 | 自己圈定的一段的真实 GPU 时间 | 需要你先猜对该圈哪一段 |

⚠️ **最常见的测量错误：用 `time.time()` 测 GPU 时间。** CUDA 调用是异步的（asynchronous：调用返回
时活还没干完，只是提交给了 GPU），`time.time()` 量到的是**提交耗时**，通常几十微秒，和真实执行时间
无关。必须 `torch.cuda.synchronize()` 后再读时钟，或用 `torch.cuda.Event` 打点。
**用错这一条会让你得出"模型只要 0.05 ms"的结论，然后去优化别的地方。**

**从症状到结论的判据表：**

| 你观察到 | 大概率结论 | 下一步 |
|---|---|---|
| GPU 时间线上 kernel 之间有大量微秒级空隙 | 被 kernel 启动开销卡住（第 3 堵墙，见 §2） | CUDA Graph / 算子融合 |
| kernel 密集但 `ncu` 报 DRAM 带宽接近饱和 | 访存受限 | 量化、融合、提高 batch |
| kernel 密集且 tensor core 活跃比高 | 算力受限（少见，且是好消息） | 只剩换更低精度或换卡 |
| GPU 时间线大段空白，CPU 线程满负荷 | 前后处理是瓶颈 | §7 |
| p99 / p50 > 5 但 GPU 不忙 | 排队问题，不是模型问题 | §11 |

## 2. Roofline：判断你撞的是哪堵墙

**算术强度 I = 这段计算的 FLOP 数 ÷ 它必须搬运的字节数。** 硬件有两个上限：峰值算力（FLOP/s）
和显存带宽（Byte/s）。两者相除得到**机器平衡点（ridge point）**，单位也是 FLOP/Byte：

```
ridge = 峰值算力 / 显存带宽
A100 80GB SXM ：312 TFLOP/s (FP16 dense) / 2,039 GB/s = 153 FLOP/Byte
H100 SXM      ：989 TFLOP/s (BF16 dense) / 3,350 GB/s = 295 FLOP/Byte
```
（数值取自各自官方 datasheet 峰值，本书自算；dense 指不启用 2:4 结构化稀疏。）

**注意 H100 的 ridge 比 A100 高一倍。** 算力涨得比带宽快，意味着**卡越新，越多算子落在访存受限一侧**。
"换新卡"对访存受限的模型收益远低于纸面算力比，这是容量规划里最常被高估的一项。

**算一遍 ResNet-50（FP16，224×224）：**
参数 25.6 M → 权重 51 MB；单张图约 4.1 GMAC = 8.2 GFLOP（一次乘加记两次浮点运算）；
各层中间张量的读写合计约 40 MB/图（量级估计，随实现变动）。

| | FLOP | 搬运字节 | I = FLOP/Byte | 位置 | Roofline 时间下界 |
|---|---|---|---|---|---|
| batch = 1 | 8.2 G | 51 + 40 = 91 MB | **90** | 153 左侧 → 访存受限 | 91 MB / 2,039 GB/s = **45 µs** |
| batch = 32 | 262 G | 51 + 1,280 = 1,331 MB | **197** | 153 右侧 → 算力受限 | 262 G / 312 T = **840 µs** |

```
性能 (FLOP/s)
   ▲
312T┤                        ┌──────────────────────── 算力屋顶（tensor core 峰值）
    │                       ╱│
    │        斜率 = 带宽 → ╱  │  ● batch=32, I=197
    │                    ╱    │
 20T┤        ● batch=1 ╱      │
    │       I=90     ╱        │
    │              ╱          │
    └────────────╴┴───────────┴──────────────────────────► 算术强度 (FLOP/Byte)
                 90         153 = ridge
              访存受限区   │   算力受限区
```

> 📖 **读图要点**：batch=1 落在 ridge **左侧**（图上那个点画的是实测性能，它离斜边还很远 ——
> 差的那一截就是下面要讲的第三堵墙；I=90 处斜边本身的高度是 `90 × 2,039 GB/s ≈ 183 TFLOP/s`）。
> 关键在于**它的上限由带宽决定**：把算力翻倍（换更强的卡、用 INT8 的更高 TOPS）对它
> **一分钱收益都没有**，能救它的只有"少搬字节"。batch=32 那个点越过了 ridge 落在平顶上，
> 此时且仅此时，"INT8 tensor core 吞吐是 FP16 的 2 倍"这句话才兑现成 2 倍加速。

**但真实的 batch=1 延迟是 1.5 ms 左右，是 roofline 下界 45 µs 的 33 倍。** 差在哪？
ResNet-50 在 eager 模式下大约要启动 200 个 kernel，每个 3–10 µs 的启动开销，合计 0.6–2 ms ——
**它既没撞算力墙也没撞访存墙，它撞的是第三堵墙：启动墙。**

**三堵墙，对应三类完全不同的优化：**

| 墙 | 判据 | 有效手段 | 无效手段 |
|---|---|---|---|
| 启动墙 | kernel 多且小，时间轴上全是空隙 | CUDA Graph、算子融合、提高 batch | 量化（字节少了，但启动次数一样） |
| 访存墙 | DRAM 带宽接近饱和 | 量化、融合、提高 batch、改数据布局 | 换算力更强但带宽没涨的卡 |
| 算力墙 | tensor core 活跃比高 | 更低精度、稀疏、更强的卡 | 继续融合 |

**推论（这是推荐/排序系统的日常）**：一个"embedding 查表 + 三层 MLP"的排序模型，
单请求 batch 通常是几十到几百个候选，FLOP 很小、访存很碎、kernel 极多 ——
它几乎必然同时撞启动墙和访存墙，**量化对它的收益远小于 CUDA Graph**
（Pinterest 用 CUDA Graph 消除启动开销后的公开数字见 [08/04 §4](04-online-inference.md#4-动态批处理原理与两个旋钮)）。

## 3. 优化手段 ROI 总表

**排序依据是"单位工程投入的端到端收益"，不是加速比。** 表里的加速比一律指**端到端**，不是"模型前向"—— 后者是让你在复盘会上被问住的那个数字。

| # | 手段 | 端到端加速（典型） | 工程成本 | 精度风险 | 撞墙条件 / 代价 |
|---|---|---|---|---|---|
| 1 | **修前后处理**（GPU 解码、并行前处理、归一化融进模型） | **1.5–3×**（当前处理占比 >50% 时） | 3–10 人日 | 无 | 前处理占比降到 20% 以下后收益归零 |
| 2 | **pinned memory + 异步拷贝流水线** | 1.1–1.4× | 2–5 人日 | 无 | pinned 内存不可换页，开太多会挤爆宿主机内存 |
| 3 | **动态批处理**（非 LLM） | 吞吐 **2–10×** | 配置项 | 无 | 吞吐的收益**全部由 p99 支付**；见下方指针 |
| 4 | **CUDA Graph / 算子融合** | 小模型 **1.5–3×**，大模型 1.05–1.2× | 5–15 人日 | 无 | 要求 shape 固定、无 host 侧控制流；捕获本身要 warmup |
| 5 | **FP16 / BF16** | 1.5–3× | 1–3 人日 | 通常小，但需任务回归 | FP16 动态范围窄；BF16 精度位更少且依赖硬件/kernel 支持 |
| 6 | **INT8 PTQ** | 访存受限 **≤2×**；算力受限 **≤2×**（相对 FP16/BF16） | 5–20 人日（含精度验证） | 掉点 0–2%，个别模型崩 | 见 §4；per-tensor 对 Transformer 与深度可分离卷积是雷 |
| 7 | **torch.compile** | 1.1–2× | 2–5 人日 | 数值/图断点/缓存兼容风险 | 编译与缓存计入冷启动；版本、GPU、shape 变化需失效与回退 |
| 8 | **TensorRT / OpenVINO** | 1.3–3×（vs eager） | 10–30 人日 + 长期维护 | 需重新验证 | engine 绑定 GPU 架构 + 库版本，换卡就要重编；构建 15–40 min |
| 9 | **蒸馏成更小的模型** | **3–10×** | 4–12 人周（等于训一个新模型） | 掉点 1–3%，需 A/B 验证 | 学生模型上限受教师限制；数据分布变了要重蒸 |
| 10 | **结构化剪枝** | 1.2–2× | 3–8 人周 | 需 fine-tune | 成本接近蒸馏而收益不如，见 §6 |
| 11 | **非结构化剪枝** | **≈1×** | — | — | 稠密 kernel 不认零，90% 稀疏度在通用 GPU 上不产生加速 |
| 12 | **换更快的卡** | 1.5–3× | 1 人日 | 无 | 成本同步上涨；对访存受限模型收益远低于算力比（§2） |

**批处理不在本章展开，只给指针和一条警告：** 非 LLM 用 request-level dynamic batching
（组批后锁定到整批算完），完整旋钮与延迟-吞吐曲线见 [08/04 §4–5](04-online-inference.md#4-动态批处理原理与两个旋钮)；
LLM 用 iteration-level continuous batching（每个 decode step 之后重新组批），见
[04/01 §3](../04-ai-agent-systems/01-llm-serving-infra.md#3-分页连续批处理chunked-prefill)。**两者调优旋钮完全不同**，
在 LLM 前面再加一层"凑批等待"是纯延迟浪费。警告：Triton 官方的调法是沿延迟预算逐步加
`max_queue_delay_microseconds` 而不是设大值；`preferred_batch_size` 官方原话是
*"For most models, preferred_batch_size should not be specified."*（Triton `batcher.md`）。

## 4. 量化：省的是字节，不总是时间

**先看格式，再看流程，最后看哪些模型会崩。**

| 格式 | 位宽 | 指数/尾数 | 动态范围 | 硬件 | 典型用途 |
|---|---|---|---|---|---|
| FP32 | 32 | 8 / 23 | 极宽 | 全部 | baseline，生产上几乎没有理由留着 |
| TF32 | 19（存 32） | 8 / 10 | 同 FP32 | Ampere+ | 训练的默认档，推理少用 |
| **BF16** | 16 | **8** / 7 | **同 FP32** | Ampere+ | 推理默认档；不需要 loss scaling |
| FP16 | 16 | 5 / 10 | 窄（±65504） | Volta+ | 精度略优于 BF16，但**激活值大时会溢出成 NaN** |
| **FP8**(E4M3/E5M2) | 8 | 4/3 或 5/2 | 窄 | **Hopper+** | 算力与 INT8 同档，但保留浮点的动态范围 |
| **INT8** | 8 | 定点 | 由校准的缩放系数决定 | Turing+ / 几乎所有 CPU | 生产主力，CPU 上尤其重要 |
| INT4 | 4 | 定点 | 极窄 | 需专门 kernel | 权重可以，激活基本不行 |

**BF16 与 FP16 的差别只有一句话：BF16 的指数位和 FP32 一样宽，所以数值范围一样，
代价是有效数字更少。** BF16 较少遇到溢出，但它是支持良好的现代 GPU 上的常见起点，不是通用默认答案；最终需用目标硬件、kernel 和任务指标比较 FP16/BF16/FP32。

**PTQ 的完整流程（能在白板上写出来的版本）：**

```
1. 准备 128–1,000 条 *线上真实分布* 的样本（不是训练集头 1000 条）
2. 跑前向，记录每个张量的取值分布 → 定 scale（对称量化只需 scale，非对称还要 zero-point）
3. 权重按 per-channel 量化，激活按 per-tensor（per-channel 激活的 kernel 支持很差）
4. 敏感层回退 FP16：逐层做"只量化这一层"的消融，掉点最多的 5% 层留 FP16 → 混合精度
5. 验证：不看 top-1，看业务指标的分数分布
```

**QAT 只在 PTQ 掉点 >1% 时才上。** 它要重训（约原训练算力的 10–20%）、要改训练代码、
要重新过一遍模型发布流程 —— 工业界的实际选择是"先 PTQ + 混合精度，实在不行才 QAT"。

**哪些模型量化后掉点严重（这是面试的必考点）：**

| 模型/结构 | 现象 | 根因 | 对策 |
|---|---|---|---|
| Transformer 编码器（BERT 类） | per-tensor INT8 直接崩 | LayerNorm 之后少数 channel 的激活是**极端离群值**，一个 outlier 把整个 tensor 的 scale 拉爆，其余值全被压进几个量化格子 | per-channel、或把离群维度整体缩放（SmoothQuant，arXiv 2211.10438） |
| MobileNet / EfficientNet | 掉点 5–10% | 深度可分离卷积每个 channel 的数值范围差几个数量级 | 必须 per-channel |
| 参数量 <10 M 的小模型 | 掉点显著 | 本来容量就紧，冗余不够吸收量化误差 | 只量化权重不量化激活，或直接放弃 |
| **CTR / 排序模型** | AUC 只掉 0.002，但线上跌 1% | 它的输出是**要拿去排序和定价**的分数，不是 argmax。量化降低的是分数分辨率，靠近的候选被打成同分 | 输出层保 FP32；量化后必须重做概率校准 |
| Embedding 表 | 通常安全 | 查表本身是访存操作，量化直接减半带宽 | INT8 甚至 INT4 都可以，是性价比最高的一处 |

**一条反直觉但必须记住的上限：在访存受限的场景，量化的收益上限就是字节数的比。** INT8 相对 FP16
最多 2×，不会因为 INT8 的 TOPS 是 FP16 的两倍就变成 4×。
**算力受限那一侧的上限同样是 2×**，因为 tensor core 的 INT8 : FP16/BF16 峰值比就是 2:1 ——
A100 是 624 TOPS : 312 TFLOPS，H100 是 1,979 TOPS : 989 TFLOPS
（[A100 datasheet](https://www.nvidia.com/content/dam/en-zz/Solutions/Data-Center/a100/pdf/nvidia-a100-datasheet-us-nvidia-1758950-r4-web.pdf)）。
**只有拿 FP32（非 TF32）当分母时才会出现 4×** —— 而生产的 baseline 是 BF16，所以报 4× 就是在虚报分母。
**先判断你在 roofline 的哪一侧，再决定要不要花三周做量化。**

**验证方法不是 accuracy。** 分类任务 top-1 掉 0.3% 你会觉得没事，但线上排序结果可能已经变了。
正确做法是同时比较任务指标（AUC/NDCG/召回/业务约束）、逐样本排序变化、分数分布，以及有标签时的校准曲线。分布变化是排查信号，不等于质量必然下降；分布相同也不能证明逐样本决策正确。按风险设门禁并用金丝雀验证。

## 5. 图优化与算子融合：三条路线的实际边界

| | torch.compile | ONNX Runtime | TensorRT / OpenVINO |
|---|---|---|---|
| 适用 | 迭代快、模型每两周就换 | 要跨硬件、跨后端移植 | 模型稳定、shape 固定、愿意养一条编译流水线 |
| 加速比 | 1.1–2× | 与 eager 相当到 1.5× | 1.3–3× |
| **编译产物可持久化** | **否** | 是（.onnx 是中间表示） | **是** |
| 真正的坑 | 无图序列化 → 编译时间全额计入冷启动；动态 shape 触发重编译 | **坑在导出侧不在运行侧** | engine 绑死 GPU 架构 + TRT 版本 + CUDA 版本 |

**torch.compile 的冷启动代价是可量化的**：vLLM 上跑 Qwen3.6-35B-A3B 的单机实测，冷编译 39 s、
命中缓存后 10 s（route179，2026-06-30）。缓存产物放在 `VLLM_CACHE_ROOT`（默认 `~/.cache/vllm`），
**可以跨机拷贝或直接烤进镜像** —— 这是投入产出比最高且零风险的一项。非 LLM 的小模型编译只要几秒，
但性质一样：**每个进程启动都要付一次**，pod 数越多、扩缩越频繁，这笔账越大。

**ONNX 的坑集中在导出侧而不是运行侧**：2025 年 PyTorch 有多个开放 issue 报告 `dynamic_shapes`
在导出时被忽略、`dynamic_axes` 与 `dynamo=True` 混用出错、opset 自动降级转换失败。
所有 ONNX Runtime 版本支持 opset ≥ 7，ONNX 1.23.0 对应 opset 28 / IR_VERSION 13。
**导出后必须逐层比对输出，不能只看模型能不能跑起来。**

⚠️ **TensorRT vs ONNX Runtime 的中立跨模型加速比，目前没有可信的公开数据**（本书调研结论）。
常见的"TensorRT EP 减少 10–30% 延迟"只出现在低质量聚合站。唯一稳妥的表述是：**固定模型 + 固定
shape + 愿意维护编译流水线时 TensorRT 最快；要跨硬件移植时用 ORT。** 面试里被追问加速比，
正确答案是"我会自测，因为公开基准都是厂商自测的"。

**CUDA Graph 的三个硬约束**（它是小模型的最大杠杆，所以约束必须记住）：
1. **shape 必须固定**。动态 batch 要预先为一组离散 batch size 各捕获一张图，请求进来向上取整到最近的桶。
2. **捕获前必须先跑几次 warmup 前向**，把 cuBLAS 初始化、autotune 这些一次性开销先做完，
   否则它们会被录进图里或在第一个真实请求上爆发。⚠️ **warmup 必须覆盖你将要捕获的全部 batch size 集合**，
   否则线上遇到未捕获的形状会静默回落到 eager 慢路径 —— 表现为"p99 偶尔翻三倍"且监控上看不出原因。
   完整的预热方法与就绪探针设计见 [08/03 §3](03-model-loading-and-warmup.md#3-预热跑什么跑多少次怎么算跑完了)。
3. 捕获本身要花时间，LLM 上是 30–60 s 量级（vLLM 文档），小模型是秒级。**它计入冷启动预算。**

## 6. 剪枝与蒸馏：为什么工业界几乎只用蒸馏

**非结构化剪枝（把单个权重置零）在通用 GPU 上不产生加速。** 稠密矩阵乘 kernel 不知道哪些是零，
90% 稀疏度也照样把它们乘一遍。唯一有硬件支持的是 Ampere 起的 **2:4 结构化稀疏**
（每 4 个权重里固定 2 个为零），理论 2×、实际端到端 1.1–1.5×，且需要重训。

**结构化剪枝（剪掉整个 channel / attention head）确实加速**，但请看清它的本质：
剪完你得到的是**一个更小的新架构**，还要 fine-tune 才能恢复精度。
那么它和"直接设计一个小架构 + 蒸馏"的差别只剩下起点不同，而工程成本几乎一样。

| | 结构化剪枝 | 蒸馏 | 直接换更小的现成模型 |
|---|---|---|---|
| 典型加速 | 1.2–2× | 3–10× | 3–20× |
| 工程链路 | 需要剪枝框架 + 敏感度分析 + fine-tune | 教师推理/软标签、学生训练、调参和完整上线验证 | 仍需兼容性、质量与性能评测 |
| 精度可控性 | 差（剪多少不好预判） | 好（教师提供软标签，收敛稳定） | 差（现成模型未必贴你的数据） |
| 什么时候选它 | 已有模型必须保留、且只需约 1.5× | 任务窄、量大、教师明显更强且有长期 owner | 有成熟小模型且你的任务不特殊 |

**蒸馏的优势是可以复用已有训练流水线，但成本不只是教师前向。** 还包括软标签存储/治理、学生架构与损失调参、多种子训练、任务评测和持续重蒸；教师前向可离线并用便宜算力完成，但不是全部工程量。
**它的代价**：学生模型上限受教师限制（教师错的它照学）、数据分布变了要重蒸，
**而且蒸出来的是一个全新模型，必须走完整的 shadow（复制一份线上流量喂给它但不用它的结果）→ canary
流程，不能当作"优化"直接替换**，判据见 [08/09 §2](09-model-deployment.md#2-模型金丝雀该看什么指标每个多久能出结论)。

## 7. 前后处理：经常比推理本身还慢

这一节是本章 ROI 最高的一节，也是最常被跳过的一节。

| 环节 | 典型耗时（单核 CPU） | 优化后 | 手段 |
|---|---|---|---|
| JPEG 解码 1080p | 5–15 ms/张 | 0.3–1 ms/张 | nvJPEG / DALI，把解码放到 GPU |
| resize + normalize | 2–5 ms/张 | 融进模型第一层 → 0 | 归一化变成一个 conv 前的 scale/shift |
| 分词（Python 实现） | 单条 0.5–3 ms | 快 3–10× | 换 Rust 实现的 tokenizer |
| 在线特征取数 | p50 0.6–0.7 ms、p99 2.5–3 ms（特定 Redis/Tecton 快照） | — | 延迟取决于物理读取、串并行/批量、载荷与后端；view 数只在映射成独立读取时直接增加 RTT |
| H2D 拷贝（pageable） | ~6 GB/s | ~24 GB/s（PCIe Gen4 ×16 量级；Gen3 ×16 上限约 12 GB/s） | pinned memory + `non_blocking=True` + 独立 stream |

**"用 pandas 做请求时的特征变换"是一个高频错误**：向量化框架的固定开销被压到单行请求上，
Feast 实测换成原生 Python 快 3–10×（Feast 博客，2025-01-14）。**单请求场景下，框架开销 > 计算本身。**
表里在线特征取数的完整延迟预算与 view/key 映射权衡见 [08/06 §5](06-feature-and-data.md#5-在线特征的延迟预算几百个特征怎么在-10-ms-内取完)。

```
优化前（串行，GPU 大段空闲）：
  CPU: [解码 96ms][归一化 21ms]                          [后处理 21ms]
  PCIe:                        [H2D 14ms]      [D2H 1ms]
  GPU :                                  [12ms]
        └──────────────── 180ms，GPU 占空比 6.7% ─────────────────┘

优化后（GPU 解码 + pinned 异步拷贝 + 三级流水，稳态每 18ms 出一批）：
  CPU: [读字节 2ms]        [响应 3ms]
  PCIe:  [H2D 原始字节 2ms]
  GPU :    [nvJPEG 解码 4ms][归一化+前向 12ms]
        └────── p99 ≈ 24ms，稳态吞吐 ×7 ──────┘
```

> 📖 **读图要点**：注意第二张图里 CPU 那一行几乎空了 —— 解码从 CPU 挪到 GPU 之后，
> **端到端时间的下界重新变成"模型前向 12 ms"**，此时（也只有此时）§4 的量化才值得做。
> 优化的正确顺序是把瓶颈推到模型上，再优化模型。

## 8. CPU vs GPU 的盈亏平衡：公式与算例

**一个实用的选型指标是“目标 p95 约束下，每 1,000 次查询多少钱”**；还要同时检查容量阶梯、可用性、冷启动和工程成本：

```
C_1k = 1000 × 实例小时价 / (3600 × 该实例在 p95 约束下的可达 QPS)
```

**算例**（BERT-base、seq 128、文本分类；价格为 us-east-1 按需，2026 年中量级，随时变动）：

| | c7i.4xlarge (16 vCPU, INT8/OpenVINO) | g5.xlarge (A10G, FP16 + 动态批处理) |
|---|---|---|
| 小时价 | $0.71 | $1.01 |
| p95 约束下可达 QPS | ~120 | ~700 |
| C_1k @ 该实例打满 | $0.00164 | $0.00040 |
| C_1k @ 全站 100 QPS | **$0.00197**（1 台） | $0.00281（1 台，只用了 14%） |
| C_1k @ 全站 1,000 QPS | $0.00178（9 台） | **$0.00056**（2 台） |

**容量按整台阶梯购买。** 当总流量 Q 低于单卡容量 q_gpu 时，GPU 路线至少一张卡；CPU 也不是连续可分割，而是 `ceil(Q/q_cpu)` 台：

```
CPU 成本 = ceil(Q / q_cpu) × P_cpu
GPU 成本 = ceil(Q / q_gpu) × P_gpu
本例 Q≤120 时 CPU 一台 $0.71/h 更便宜；Q 刚超过 120 时 CPU 跳到两台 $1.42/h，
而一张 GPU $1.01/h 可撑到约 700 QPS，所以第一个成本交点约在 120 QPS 之后，不是 171 QPS。
```

分数台近似 `Q* = P_gpu/P_cpu × q_cpu` 只适合容量可连续购买或规模足够大时；低流量必须画 `ceil()` 阶梯，且 q_gpu 决定 GPU 下一次扩容的位置。MIG / 多模型共卡通过分摊 `P_gpu` 改变阶梯。不同 endpoint 的模型、SLO 和价格差异很大，一律自测 `cost-per-1,000-queries @ 目标 p95`。

| 选 CPU | 选 GPU |
|---|---|
| 参数量 <2 B（量化后）、embedding 模型、分类器 | 8 B 以上要低延迟；70 B 以上没得选 |
| p95 预算 100–500 ms 可接受 | p95 <50 ms |
| 单 endpoint 持续 <100 req/s | 持续 >100 req/s |
| 多模型高密度共存（几十个小模型） | 单模型独占且能打满 |
| 编排 / 检索 / ETL / 批量打分 | 在线实时打分 |

**CPU 推理是内存带宽瓶颈，不是算力瓶颈**，直接后果是**模型小 3.5× 就快约 3.5×**（llama.cpp 口径：
Q4_K_M 约 4–5×、Q5_K_M 约 3.5×、Q8_0 约 2×；AWS EKS BP 2025）。在 CPU 上量化几乎总是划算的。

⚠️ **CPU 路线必须显式限制线程数**：`OMP_NUM_THREADS` / `MKL_NUM_THREADS` / `OPENBLAS_NUM_THREADS` /
`INTRA_OP_NUM_THREADS`。否则密集 bin-pack 时每个 pod 都按**节点的 vCPU 总数**起线程（20 个 pod ×
32 线程 = 640 个计算线程抢 32 个核），节点在上下文切换上抖动，p99 直接炸。
**"密集部署 CPU 推理 pod 就能省钱"是一个有明确失败模式的误解。**

## 9. GPU 利用率：`nvidia-smi` 为什么会骗你

**`nvidia-smi` 的 `utilization.gpu` 的官方定义是：过去一个采样周期里，有一个或多个 kernel
在 GPU 上执行的时间占比。** 注意它说的是**时间**，不是**算力**。
一个只用到 1 个计算单元（SM）的 kernel 连续跑一秒，它显示 100%。

| 指标 | 定义 | 从哪拿 | 它能证明什么 | 它不能证明什么 |
|---|---|---|---|---|
| `utilization.gpu` | 有 kernel 在跑的时间占比 | `nvidia-smi` / `DCGM_FI_DEV_GPU_UTIL` | 卡没闲着 | **算力用了多少** |
| SM active | 至少有一个线程组活跃的 SM 的时间加权比例 | `DCGM_FI_PROF_SM_ACTIVE` | 有多少 SM 真被用上 | 每个 SM 内部填满没有 |
| SM occupancy | 驻留线程组数 / 硬件上限 | `DCGM_FI_PROF_SM_OCCUPANCY` / `ncu` | 并行度够不够 | 高 occupancy ≠ 高吞吐 |
| Tensor core 活跃比 | tensor 流水线活跃周期占比 | `DCGM_FI_PROF_PIPE_TENSOR_ACTIVE` | **你到底有没有走 tensor core** | — |
| DRAM 活跃比 | 显存带宽占用 | `DCGM_FI_PROF_DRAM_ACTIVE` | 是不是访存受限 | — |
| **MFU** | 有效 FLOPs ÷ 所选精度峰值 FLOPs | 自算 | 在口径一致时衡量算力效率 | 访存、启动墙、SLO 余量；跨架构并非天然可比 |
| 显存占用 | 已分配显存 | `nvidia-smi` | 还能不能塞下一个模型 | **和算力利用率无关** |

**MFU 算例（自算，口径必须写清楚）**，A100 FP16 峰值 312 TFLOP/s、ResNet-50 8.2 GFLOP/图：

| 场景 | 实测吞吐 | 有效算力 | **MFU** | 同时 `nvidia-smi` 显示 |
|---|---|---|---|---|
| 在线，batch=1，p99 优先 | 700 img/s | 5.7 TFLOP/s | **1.8%** | 85% |
| 在线，batch=32，动态批处理 | 12,000 img/s | 98 TFLOP/s | **31%** | 99% |

**同一张卡，两个 `nvidia-smi` 读数几乎一样，真实效率差 17 倍。**

> **面试金句**：
> "`nvidia-smi` 上的 utilization 只告诉你卡没闲着。上面那台显示 85%、MFU 不到 2%，也不能直接推出还能塞十倍流量；它可能被显存带宽、kernel 启动或 p99 卡住。我会看 DCGM 指标并压测联合 SLO 下的 goodput；
> 扩缩容一律挂**队列深度**，绝不挂 utilization —— utilization 是饱和指标，
> 等它开始动的时候 p99 早就坏了。"
>
> *"GPU utilization in `nvidia-smi` isn't a utilization number — it just tells you the GPU
> wasn't idle. A box at 85% util and under 2% MFU may still be bottlenecked on memory or latency, so I load-test goodput before adding traffic. Then I inspect SM active and tensor-core active.
> And I autoscale on queue depth, never on util — util is a saturation signal, it only starts
> moving after your p99 has already gone bad."*

**运维上的直接推论**：满载的 GPU 推理实例，**CPU 利用率接近 idle**，
HPA 挂 CPU/内存指标永远不会扩容，直到请求开始超时。必须用 KEDA 或自定义指标挂队列深度
（AWS EKS BP 2025）。队列纪律与准入控制见 [08/04 §9–10](04-online-inference.md#9-准入控制过载时该拒绝谁)。

## 10. 多实例与 GPU 共享

单模型打不满卡（MFU < 20%）时，第一反应应该是**共卡**，而不是买更小的卡。三种方式的隔离强度差异很大：

| 方式 | 隔离能力 | 硬限制 | 什么时候用 |
|---|---|---|---|
| **Time-slicing** | **无显存隔离、无故障隔离** | 单纯轮转，互相拖尾延迟 | 老卡（不支持 MIG）的唯一选择，且只用于同一团队 |
| **MPS** | 共享一个 CUDA context，小 kernel 场景利用率显著更好 | NVIDIA device plugin 下**显存按 replica 数均分**，超了 OOM；与 time-slicing 互斥 | 同信任域内的多模型共存 |
| **MIG** | **硬件级隔离**（算力 + 显存 + 故障域） | **只有部分数据中心卡有**：A100 / A30 / H100 / H200 / GB200 一线；⚠️ **Ada 系（L4 / L40 / L40S）不支持 MIG**，"卡更新 = 一定有 MIG"是错的（[NVIDIA L40S 产品页](https://www.nvidia.com/en-us/data-center/l40s/)）。profile 静态，改配置要重配 | 跨租户时它是**唯一的分卡选项**；卡不支持 MIG 时跨租户只剩整卡独占 |

⚠️ **MPS 的致命失效模式**：一个进程在执行 kernel 时异常退出，会连带拖垮与它共享 IPC 与统一内存的
其他进程。**所以 MPS 不能用于跨信任域的多租户隔离** —— 一个租户的段错误会打死另一个租户。

**显存"超售"在 GPU 上基本不成立**（没有 CPU 那种 swap / overcommit 语义），
真正可用的是**时间维度**：按需 load / unload 模型，或用 sleep mode 不停服务就释放大部分显存 ——
多模型共存的显存管理见 [08/03 §7](03-model-loading-and-warmup.md#7-多模型共存显存管理与超售的风险)。

**共卡的代价**：多个模型会在同一批 SM 和同一条带宽上打架。两个各自 40% MFU 的模型共卡后，
总利用率不会是 80%，现实里 60–70% 是好结果，而两者的 p99 都会变差。

## 11. 什么时候不要优化模型，而该优化别的

**判据只有一条：模型前向占端到端 p99 的比例。** 低于 30% 就不要碰模型。

| 症状 | 真正的瓶颈 | 该做的事 |
|---|---|---|
| 模型前向 < 30% 端到端 | 前后处理 / 特征取数 / 序列化 | §7 |
| p99 / p50 > 5，GPU 不忙 | 排队与准入控制 | 限制在途请求数、按队列深度扩容 |
| 单实例 QPS 远低于压测峰值 | 并发度、线程池、序列化格式 | 先修服务框架 |
| 成本高但 QPS 低 | **卡没打满** | 共卡 / MIG / 换 CPU（§8、§10） |
| 每天扩缩几十次，冷启动很长 | 镜像与编译缓存 | 顺序是**镜像 > 权重 I/O 并行 > 编译缓存**，不是换更快的 GPU（[08/03 §4](03-model-loading-and-warmup.md#4-缩短冷启动的手段收益代价撞墙条件)） |
| 同一份输入反复被打分 | 没有做结果缓存 | 见下 |

**最有说服力的一个数字**：Meta 的 Mosaic 服务优化里，AOTI 编译 + 模型切分带来 −56% GPU 用量，
**再叠加一层 memcache 之后累计 −79%**（arXiv 2607.24015，2026-07-27）—— 缓存这一层贡献的边际收益
超过了整套编译优化的一半。**在动模型之前，先问一句"这个请求是不是刚才已经算过一遍了"**
（缓存的完整方法见 [01/02](../01-building-blocks/02-caching.md)）。

**反模式清单：**

1. **先量化，后 profile。** 本章第一段那个故事的标准结局。
2. **用 `time.time()` 测 GPU 时间不 synchronize。** 你测的是提交耗时，量级差 100 倍。
3. **拿 `nvidia-smi` 的 utilization 当容量指标。** HPA 因此永远不扩，直到请求超时。
4. **用 batch size 换吞吐但不改 SLO。** 吞吐的收益全部由 p99 支付，账要记在同一张纸上。
5. **把 `torch.compile` 当免费加速。** 无图序列化，编译时间全额计入冷启动，pod 越多越贵。
6. **只在 FP32 baseline 上报加速比。** 分母虚高。生产的 baseline 是 BF16。
7. **追求 100% GPU 利用率。** 排队论说利用率越过约 80% 后排队延迟非线性上涨
   （[00/02 §3](../00-foundations/02-capacity-estimation.md#3-排队论queueing-theory为什么-80-利用率utilization是危险的)）；把卡"用满"和把 SLO 守住是两件冲突的事。
8. **量化后只看 accuracy 不看分数分布。** 排序类模型的退化不改变 accuracy，也不改变 HTTP 状态码。
9. **给一个每两周就要换的模型上 TensorRT。** engine 绑死架构与版本，
   维护成本会在第三次换卡时吃掉全部收益。
10. **离线指标已经不行了还在优化推理。** 你只是让系统更快地给出更差的答案。

## 这一章的三句话

1. **优化的第一步永远是把端到端时间拆成七段并画出来，因为"模型很慢"这个直觉的正确率不到一半。**
   一个 p99 180 ms 的服务里模型只占 12 ms 是常态，不是特例；在拆图之前做的任何优化都是赌博。
2. **量化和换卡只对撞了访存墙或算力墙的模型有用；小 batch 的推荐与 CV 模型撞的是第三堵墙 ——
   kernel 启动墙，它只吃 CUDA Graph 和算子融合。** 先用 roofline 判断自己在哪一侧，
   再去挑手段；顺序反了，加速比会稳定地停在 1.05×。
3. **`nvidia-smi` utilization 只说明卡没闲着，MFU 补充说明有效算术占峰值多少；两者都不是容量。**
   容量规划用满足联合 SLO 的实测 goodput，扩缩容结合队列等待/拒绝率，成本决策用“目标 p95 下的每千次查询成本”——
   这三件事没有任何一件该看 utilization。
