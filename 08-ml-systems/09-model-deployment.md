# 09 · 模型部署：金丝雀、回滚与多模型

> 服务的金丝雀在问"坏没坏"，模型的金丝雀在问"变差了没有" —— 前者五分钟就有答案，后者需要样本量，
> 而你的金丝雀窗口通常根本攒不到那个样本量。承认这一点，才能设计出对的门禁。

---

## 读这一章之前

**你在工作中遇到过这个**

你按服务发布的老规矩给新排序模型开金丝雀：25% 起步、bake 30 分钟、门禁挂 5xx 率和 p99。
30 分钟后一切正常（5xx 0.02%，p99 从 41 ms 到 43 ms），你在 1 小时内推到 100%。
第二天早上大盘：CTR 跌 1.8%，人均下单跌 0.6%，折算约每天六位数收入。你把模型 alias 指回上一版 —— 指标只回来一半，
因为这次上线同时改了特征管道，把 `user_7d_ctr` 的口径从"自然日全量日志"换成了"滚动 168 小时"，旧模型现在读到的是它训练时从没见过的分布。
真正恢复花了 11 个小时，其中 9 个小时全在争论"到底该回滚哪一半"。

**需要先懂的概念**

| 概念 | 一句话 | 详见 |
|---|---|---|
| 金丝雀与自动回滚判据 | 先给新版本 1–5% 流量，用并发基线组比对指标，任一门禁失败就自动回退 | [03/05 §3](../03-saas-platform/05-release-engineering.md) |
| 样本量与统计功效 | 要检出多小的差异，就得攒多少样本；差异缩一半，样本要涨四倍 | [08/07 §4](07-model-quality-and-experimentation.md) |
| 影子部署 | 把线上请求复制一份给候选模型，两边都打分，**候选输出永不返回给用户** | [08/07 §9](07-model-quality-and-experimentation.md) |
| 训练/服务偏斜 | 同一个特征名在训练侧和服务侧算出不同的值 —— 模型在线上看到的不是它学过的东西 | [08/06 §2](06-feature-and-data.md) |
| Registry、版本化与保留成本 | 模型 artifact 该记哪些字段、旧版本存多久、存在哪一档 | [08/02 §2、§5](02-model-lifecycle.md) |
| p50 / p99 与分位数不可平均 | 尾延迟要单独看，且不能把两个窗口的 p99 加起来除以二 | [00-concepts §3](../00-foundations/00-concepts.md) |

**这一章要回答的问题**

1. 服务金丝雀 5 分钟能判定，模型金丝雀为什么不能？到底哪些指标能在金丝雀窗口内给出结论，哪些不能？
2. 门禁到底该怎么设：什么信号可以自动回滚，什么信号只能报给人？多挂几个护栏为什么反而更危险？
3. 把模型版本指针指回上一版之后，为什么线上没有恢复到上一版的表现？回滚窗口里产生的数据要怎么处理？
4. 召回 / 粗排 / 精排这样的多级链路，改一级怎么评估？为什么单独给一级开金丝雀是错的？
5. 端侧模型和服务端模型，部署风险的差别在哪一条？

**本章新引入的术语**

| 术语 | English | 一句话定义 |
|---|---|---|
| 质量指标 | quality metric | 衡量"模型判断得对不对"的指标（CTR、转化率、准确率），与"服务有没有报错"无关 |
| 护栏指标 | guardrail metric | 不追求它变好、只要求它别变坏的指标；一旦跌破阈值就阻断发布 |
| 最小可检测效应 | minimum detectable effect (MDE) | 在给定样本量和显著性水平下，你**最小**能分辨出多大的差异；比它小的变化会被噪声吞掉 |
| 代理指标 | proxy metric | 真实目标标签迟迟不到时，用一个"来得快、且与目标高相关"的指标临时替代 |
| 标签延迟 | label delay（也说 label lag） | 从做出预测到拿到真实结果（是否点击 / 是否欺诈 / 是否续保）之间的时间差 |
| 预测分布 | prediction / score distribution | 模型输出分数在一批请求上的分布形状；不需要标签就能算，是最早能动的质量信号 |
| 校准 | calibration | 模型说"70% 会点"的那批样本，实际点击率是不是真的 70% |
| 特征时间旅行 | feature time travel | 把模型回滚到 X 天前，它却要读现在的特征管道 —— 于是拿到了训练时并不存在的口径 |
| 模型版本四元组 | model version quadruple | 一次可回滚的最小单位 = 权重 + 特征/预处理管道版本 + 依赖锁（容器 digest） + 配置 |
| 分流比例失配 | sample ratio mismatch (SRM) | 实际进入实验组/对照组的样本比例与设计比例显著不符；一旦发生，该实验所有指标结论都不可信 |
| 级联模型 | model cascade（排序语境也说 multi-stage ranking） | 召回 → 粗排 → 精排 → 重排这类逐级缩小候选集的链路，上游输出即下游输入分布 |
| 版本碎片化 | version fragmentation | 端侧下发后，同一时刻线上并存十几个模型版本，且你无法把它们同时收回 |

## 1. 为什么服务的金丝雀判据搬到模型上会失效

服务金丝雀能在 5 分钟内判定，靠的是一个隐含前提：**失败会改变 HTTP 状态码**。
5xx 是伯努利事件，基线率 0.1% 时，几千个请求就足以把"翻了 1.5 倍"和"抖动"分开。

模型的失败不改状态码。Uber 在 2025-10-30 的部署安全文章里把这件事写得很直白：
training-serving skew、概念漂移、上游数据问题
"can cause degradations in customer experience **without throwing off any production alarms**"
（[Uber, 2025-10-30](https://www.uber.com/us/en/blog/raising-the-bar-on-ml-model-deployment-safety/)）。
同一家公司的 D3 系统抓到过一起真实事故：某个费用组件在美国主要城市 **10% 的 session 里缺失，持续 45 天**，
没有任何服务级告警，靠人工发现；模拟影响约 **0.23% gross booking**
（[Uber D3, 2023-02-23](https://www.uber.com/us/en/blog/d3-an-automated-system-to-detect-data-drifts/)）。

更要命的是样本量。按标准双比例公式（α=0.05 双侧、power=80%）自算，推导见 [08/07 §4](07-model-quality-and-experimentation.md)：

| 你想检出的劣化 | 基线转化率 | 每组所需样本 |
|---|---|---|
| 相对 **1%** | 5% | **≈ 298 万** |
| 相对 **1%** | 2% | ≈ 769 万 |
| 相对 **5%** | 5% | **≈ 11.9 万** |
| 相对 1%，连续指标（人均收入，CV=3） | — | ≈ 141 万 |

**MDE 缩小 5 倍，样本量涨 25 倍**（样本 ∝ 1/Δ²）。代进一个日活 200 万的产品：1% 金丝雀流量 = 每天 2 万人进桶，
检出相对 5% 的 CTR 劣化要 11.9 万人 → **6 天**；检出相对 1% 要 298 万人 → **149 天**。而你的金丝雀 bake time 是 30 分钟。

```
   t=0  放量 1%
    │
    ├─ 30 s ─── 5xx / 超时 / 特征 null 率 / OOM ──────────► 可判（几百请求足够）
    ├─  5 min ─ p99 延迟 / GPU 显存 / 队列深度 ───────────► 可判
    ├─ 30 min ─ 预测分布 PSI、校准偏移、预测熵 ───────────► 可判（不需要标签）
    ├─  6 h ─── Top-K 重合度、曝光多样性、长尾覆盖 ───────► 可判（不需要标签）
    ├─ 2–7 d ── CTR（只能检出相对 ≥5% 的劣化）───────────► 勉强可判
    ├─ 2–4 w ── 转化率 / 人均收入 ────────────────────────► 金丝雀窗口早关了
    └─ 1–3 m ── 留存、长期效用 ───────────────────────────► 只有长期 holdout 能测
    ▲                       ▲
    └── 服务金丝雀住在这里 ──┘        └────── 模型的"好坏"住在这里 ──────►
```

**这张图是全章的地基**：技术信号和质量信号差了 **3–5 个数量级的时间尺度**，金丝雀窗口能覆盖前四行、覆盖不了后三行。
所以模型金丝雀真正的作用是**限制爆炸半径（blast radius）+ 抓技术故障 + 抓分布异常**，不是"证明新模型更好"；
"更好"必须由离线评测、交错实验和 A/B 去回答 —— 那是另一套基础设施，不是发布流水线。

> **面试金句**
> "A service canary asks *is it broken* — that's a yes-or-no you can answer in five minutes.
> A model canary asks *is it worse* — and *worse* is a number with an error bar on it.
> Nine times out of ten your canary window can't tell five percent worse from noise,
> so stop pretending the gate is statistical. It's a blast-radius limiter with a distribution check bolted on."
> 服务金丝雀问"坏没坏"，五分钟就能回答；模型金丝雀问"变差了没有"，而"差"是一个带误差棒的数。
> 十次里有九次，金丝雀窗口分不出"差 5%"和噪声 —— 别再假装那是统计门禁，它是一个爆炸半径限制器，外加一层分布检查。

## 2. 模型金丝雀该看什么指标，每个多久能出结论

把指标按"需要什么才能判定"分层，而不是按"重不重要"分层 —— **能不能自动化取决于层级，不取决于业务价值**。（这套分层与稳态运行期的监控分层是同一个骨架，区别只在于金丝雀窗口把可用的层数砍掉了一半，稳态版本见 [08/08 §5](08-drift-and-monitoring.md)。）

| 层 | 指标 | 判定所需 | 典型出结论时间 | 抓得到 | 抓不到 |
|---|---|---|---|---|---|
| **L0 技术** | 5xx / 超时率 / OOM / 模型加载失败 | 几百请求 | **30 s–2 min** | 崩溃、依赖缺失、算子不兼容 | 任何质量问题 |
| **L0 技术** | p99 推理延迟、队列深度、GPU 显存占用 | 数千请求 | **2–5 min** | 新模型变大/变慢、batch 配置错 | 同上 |
| **L0 数据** | 特征 null 率、越界率、类型错误率（**按特征分**） | 数千请求 | **2–5 min** | 特征管道断链、上游 schema 变更 | 值对但语义变了 |
| **L1 预测** | 预测分布漂移（PSI / Wasserstein，对**并发基线组**比） | 1–5 万条预测 | **15–60 min** | 口径变了、特征错位、模型选错 | 分布对但排序错 |
| **L1 预测** | 校准偏移（预测均值 vs 基线均值）、预测熵 | 1–5 万条 | **15–60 min** | 阈值/后处理改动、模型"变懒"（全打同一分） | 排序质量 |
| **L1 预测** | Top-K 与旧模型的重合度 / Kendall τ | 1–5 万条 | **30–90 min** | 排序剧变 | 剧变到底是好是坏 |
| **L2 即时行为** | CTR、首屏点击位置、翻页率、跳出率 | **≥ 11.9 万/组**（检出相对 5%，基线 5%） | **1–7 天** | 排序真的变差 | 相对 <5% 的劣化 |
| **L3 转化** | CVR、人均收入、退款率 | 141 万–298 万/组 | **2–4 周** | 真实业务影响 | 长期效应 |
| **L4 长期** | 留存、内容生态多样性、供给侧健康度 | 长期 holdout | **1–3 个月** | 新奇效应、退化反馈回路 | — |

几个必须记住的边界条件：
- **L1 的比对对象必须是并发基线组。** 对训练集比叫 skew（训练/服务偏斜），对上一时间窗比叫 drift（漂移），
  只做 drift 会漏掉"部署第一天就存在的管道实现差异"（[Vertex AI 文档](https://cloud.google.com/blog/topics/developers-practitioners/monitor-models-training-serving-skew-vertex-ai)）；
  金丝雀要做的是第三件事：**candidate vs 同时段 control**。
- **PSI 阈值 <0.1 无需关注 / 0.1–0.2 需调查 / >0.2 显著** 是信用评分行业的经验值，**不是统计推导**，必须按特征重标定。
- **别用 KS 检验做门禁**：样本 **>50,000 行/batch** 时它基本每批都报显著，纯噪声源；用效应量（PSI、Wasserstein）配多重检验校正。
  作为对照，Vertex AI 的 skew 检测默认阈值 **0.3**（数值特征 JS divergence、类别特征 L-infinity），监控频率**默认 24 小时、最小 1 小时** —— 这个"最小 1 小时"就是托管方案给你的分辨率下限，比你的 bake time 还长。
- **L2 及以下都有标签延迟**：点击秒级、欺诈数天、保险理赔数月到数年。
  标签延迟长于金丝雀窗口时，L2 以下所有格子在发布期间都是空的 —— 这不是"再等等"，是**结构性不可用**。

## 3. 双层门禁：技术护栏立即判 + 质量指标延迟判

真实可用的模型发布门禁只有一种形状：**两层，两种执行者。**

```
                     ┌──────────────── 第 1 层：技术护栏（自动执行）────────────────┐
   candidate ───┬───►│ 5xx↑ / p99↑ / null 率↑ / OOM / 加载失败 / 队列积压           │
   1% 流量      │    │  判定窗口 30 s–5 min  →  违反即【自动回滚 + 冻结流水线】      │
                │    └──────────────────────────────────────────────────────────────┘
                │
                │    ┌──────────────── 第 2 层：质量闸门（人工/流程执行）───────────┐
                └───►│ 预测分布 PSI / 校准 / Top-K 重合度   判定窗口 15–90 min       │
                     │ CTR 等行为指标                        判定窗口 1–7 天         │
                     │  违反即【停留在当前档位 + 呼人】，不自动回滚                  │
                     └──────────────────────────────────────────────────────────────┘
   control ─────► 同时段并发基线组（必须存在，否则第 2 层无意义）
```

**为什么第 2 层不自动回滚？** 因为它的假阳性率不受控，公开资料一致支持这个判断：Uber 的自动回滚触发条件是
**error rate / latency / CPU-GPU 利用率**击穿阈值，而 score distribution、calibration、entropy 这些预测级指标目前是
"**监控**"而不是"**自动回滚**"（[Uber, 2025-10-30](https://www.uber.com/us/en/blog/raising-the-bar-on-ml-model-deployment-safety/)）。
到 2026 年，"质量指标自动回滚"仍然没有被任何大厂公开背书。

**护栏数量本身是风险。** 假设 k 个近似独立的护栏，每个的单次假阳性率 α=0.01：

```
   family-wise 误触发率 = 1 − (1 − α)^k
   k=5  → 4.9%       k=10 → 9.6%       k=20 → 18.2%
   每天 3 次发布、k=20  →  平均每天 0.55 次误回滚
```

误回滚的真实后果不是"多发一次版"，而是**团队会关掉自动回滚**。这是从"多加护栏更安全"直接走到"完全没有护栏"的标准路径。
**结论：自动执行的护栏控制在 5–7 个以内，全部来自 L0；其余全部降级为告警。**

**阶梯与推进条件。** 模型金丝雀的起步流量是 **1–5%**，不是服务侧常见的 25%；阶梯是 `1% → 5% → 10% → 25% → 50% → 100%`，
**推进条件必须是 validation-gated 而不是 time-gated** —— 按时钟推进不是统计方法，只是排班表
（[GrowthBook, 2026-05-29](https://www.growthbook.io/insights/canary-releases-ai-models-what-changes-vs-traditional-software)）。可直接抄的门禁配置：

```yaml
# model-canary-gate.yaml —— 每一档都要同时满足"样本量"和"信号"两类条件
stages: [0.01, 0.05, 0.10, 0.25, 0.50, 1.00]
prerequisites:                      # 不满足则整个发布不允许开始（见下方三条）
  shadow_passed: true
  srm_check: {p_threshold: 0.0005}  # 分流比例失配检查，失败即中止
  warmup_as_readiness: true         # warmup 未完成不进 LB
promote_when:                       # 全部满足才进下一档
  min_requests: 20000               # 样本量门槛，不是时间门槛
  min_wall_clock: 15m               # 只作为下界，防止秒级冲档
  psi_vs_concurrent_control: "< 0.10"
  calibration_shift: "< 2%"         # 预测均值相对并发基线组的偏移
auto_rollback_when:                 # 仅 L0，5 条，全部立即执行
  - error_rate:  "candidate > control * 1.5 AND absolute > 0.1%"   # 窗口 5m
  - p99_latency: "candidate > control * 1.2"                        # 窗口 5m
  - feature_null_rate: "any_feature > control * 2"                  # 窗口 5m
  - new_error_fingerprint: true                                     # 立即
  - model_load_failure: true                                        # 立即
hold_and_page_when:                 # 停档呼人，不自动回滚
  - psi_vs_concurrent_control: "> 0.20"
  - ctr_relative: "< -5%"           # 窗口 24h，且样本量达标才判
```

三个容易漏掉的前置条件：

1. **SRM（分流比例失配）必须是硬前置门。** LinkedIn 约 **10%** 的 triggered 实验、Microsoft 约 **6%** 出现过 SRM；
   阈值取 **p < 0.0005（Microsoft）或 p < 0.001（Kohavi）**，远严于 0.05，因为每次发布都要跑它。
   SRM 触发时**该次金丝雀的所有指标结论一律作废**，不是"打个折看看"。
2. **warmup 必须做进就绪探针。** CUDA graph capture 典型 **30–60 s**，不做 warmup 的实例第一批请求会吃到这段尾延迟，
   然后被门禁判成"新模型变慢"从而误回滚。Triton 的 `ModelWarmup` 是可抄的语义：声明一组 warmup 请求（含 `batch_size` 和迭代 `count`），
   **实例必须全部成功执行完才标记 READY**；warmup 要覆盖将要捕获的 batch size 集合，完整拆解见 [08/03 §3](03-model-loading-and-warmup.md)。
3. **金丝雀之前必须有影子阶段。** 影子能验证延迟、稳定性、预测一致性、输入分布错配和成本；
   **验证不了任何业务指标** —— 预测不返回给用户就没有反馈闭环，CTR / 转化 / 留存一律测不到（边界见 [08/07 §9](07-model-quality-and-experimentation.md)）。
   代价是确定的 **2× 推理算力**（外加双份特征拉取与日志写入）。Uber 把 shadow 做成默认前置，覆盖 **>75% 的关键在线用例**。

| | 服务金丝雀 | 模型金丝雀 |
|---|---|---|
| 核心问题 | 坏没坏 | 变差了没有 |
| 主信号 | 5xx / p99 / 新错误指纹 | 预测分布、校准、行为指标 |
| 判定所需 | 几百~几千请求 | 1 万~数百万样本，**分层** |
| 出结论时间 | **5 分钟** | L0 5 分钟 / L1 1 小时 / L2 数天 / L3 数周 |
| 起步流量 | 5–25% | **1–5%** |
| 推进条件 | bake time（时钟） | **样本量（validation-gated）** |
| 自动回滚 | 可以挂业务 KPI | **只挂 L0**；质量指标停档呼人 |
| 回滚单位 | 容器镜像 | **权重 + 特征管道 + 依赖锁 + 配置** |
| 回滚后是否恢复 | 是 | **不一定**（见 §4） |
| 失败的样子 | 报警红一片 | **仪表盘全绿，钱在流失** |

## 4. 模型回滚 ≠ 代码回滚

代码回滚的隐含假设是：把二进制换回去，系统就回到了之前的状态。**模型不满足这个假设**，因为模型的行为由四样东西共同决定：

```
                                         回滚代价与可逆性
  ┌──────────────────────────────────────────────────────────────────────┐
  │ ① 权重指针（alias @champion → v41）      秒级    改一个字符串        │  ← 只回这一层
  ├──────────────────────────────────────────────────────────────────────┤    = 特征时间旅行
  │ ② 容器 digest（预处理代码、算子、依赖）  分钟级  重拉镜像 + 冷启动    │
  ├──────────────────────────────────────────────────────────────────────┤
  │ ③ 特征定义（窗口口径、填充、编码、分桶）  小时~天 回滚在线管道 + 回填  │
  ├──────────────────────────────────────────────────────────────────────┤
  │ ④ 回滚窗口内产生的数据（曝光/点击日志）  不可逆  只能打标 + 重加权     │
  └──────────────────────────────────────────────────────────────────────┘
     ①②③ 必须作为一个原子单位一起回；④ 永远回不去，只能在下一次训练时处理
```

**"特征时间旅行"是最典型的失效方式。** 模型和它的特征管道通常同步重训、同步上线；把 artifact 回滚到 X 天前，
它就要去处理 feature store 里**训练时并不存在的"未来"特征** —— 新加的列、改过口径的窗口、换过的填充策略，
结果是 version mismatch 与**静默劣化**（[arXiv 2604.08181](https://arxiv.org/pdf/2604.08181)）。公开资料的判断很硬：
**"rolling back just one part of the system creates new failures instead of solving the problem"** —— 只回滚一半比不回滚更糟。
语义不对称让它更隐蔽：Databricks 的 `lookback_window` **只在训练与批量推理生效，在线推理永远取最新值**，
同一份特征定义在训练侧和服务侧本来就是两种语义（成因分类见 [08/06 §2](06-feature-and-data.md)），回滚权重等于把旧权重扔进一套新语义里。

> **面试金句**
> "Rolling back the weights doesn't undo the incident — it hands you a combination nobody has ever tested.
> The unit of rollback is the weights plus the feature pipeline plus the container digest plus the config, or it's nothing."
> 把权重回滚回去并不能撤销事故 —— 它只是给了你一个从没有人测试过的组合。
> 回滚的单位是"权重 + 特征管道 + 容器 digest + 配置"，要么整个回，要么就别回。

### 4.1 回滚检查清单

发布前就要能逐条打勾，事故当天没人有时间设计流程。

- [ ] **版本是四元组**：`(weights_uri, feature_pipeline_version, container_digest, config_hash)` 作为一条不可分割的记录写进 registry；服务端只读 alias，**代码里不允许出现版本号字符串**
- [ ] **部署走 pointer 层**：MLflow alias（如 `@champion`，注意 Model Stages 自 2.9.0 起已弃用）/ KServe revision / SageMaker variant —— 保证回滚是"重指"而不是"重发布"
- [ ] **上一个 known-good 版本的镜像已预拉**，且**旧模型 warmup 走完才接流量**（同 §3 第 2 条）：否则回滚要吃完整冷启动 —— 8B 级未优化约 **11 分钟**（image pull 5–6 min + layer extract 3–4 min），镜像预拉后 70B 级约 **60–90 s**
- [ ] **特征管道可独立回滚，且回滚顺序写下来了**：先切模型指针还是先切特征管道？错误的顺序会制造一个两边都不匹配的中间窗口
- [ ] **回滚动作演练过**，且回滚后**自动冻结流水线** —— 否则下一个人 40 分钟后把同样的变更再推一遍
- [ ] **回滚窗口内的样本已被打标**：`serving_model_version` 必须落进曝光日志，否则这段数据会以"看起来正常"的方式污染下一次训练
- [ ] **对账**：回滚完成后，用一批固定的 golden 请求比对新旧预测，确认真的回到了旧模型的输出，而不是"旧权重 + 新特征"的第三种行为

### 4.2 回滚窗口里的数据怎么办

这是最多人漏掉的一步。金丝雀期间坏模型服务过的那部分流量产生了带偏的曝光和点击日志，
它们会以训练样本的形式进入下一个模型 —— 坏模型的行为被固化进了继任者。三种处理，按成本递增：

| 做法 | 代价 | 什么时候用 |
|---|---|---|
| 按 `serving_model_version` **直接剔除**该段样本 | 丢掉一段真实数据；金丝雀只占 1–5% 流量时几乎无损 | **默认选这个** |
| 保留但按曝光概率倒数**重加权（IPW）** | 需要记录每条曝光的 propensity（模型给它的分数/被选中的概率），没记就补不回来 | 金丝雀比例大（≥25%）、数据不能丢 |
| 什么都不做 | 坏模型的偏好进入下一代训练集；在推荐场景表现为**长尾坍塌**（只推热门 → 用户只消费热门 → 训练数据更热门） | 从来不该选 |

**这也是为什么曝光日志必须带 `serving_model_version` 和 propensity 两个字段** —— 它们在事故当天补不回来。

### 4.3 旧模型要保留多久，保留的成本是什么

公开资料里**未找到"旧模型保留期"的公认标准**。通用的保留策略与存储成本算例见 [08/02 §5](02-model-lifecycle.md)；这里只回答"为了能回滚，最少要留多久"，可以推一个下界：

```
   保留期 ≥ 标签回流周期 + 问题检测延迟 + 一个完整重训周期，再乘 2× 安全系数
   欺诈风控： 7 天（标签）+ 4.5 天（AI 事故中位检测时间，二手口径）+ 3 天（重训）≈ 15 天 → 30 天
   推荐排序： 1 天 + 4.5 天 + 1 天 ≈ 7 天 → 14 天
   保险核保： 90 天+（标签）→ 按季度算，且必须能重建训练环境
```

成本要分三档看，**"保留"这个词在三档里的含义完全不同**：

| 档位 | 内容 | 回滚耗时 | 成本量级 |
|---|---|---|---|
| **冷备** | artifact + 特征定义 + 容器 digest 存在对象存储 | 分钟~小时（要拉镜像、冷启动） | 对象存储 GB·月，量级 $0.02/GB·月 —— 一个 5 GB 排序模型存 30 个版本约 150 GB，几乎免费 |
| **温备** | 镜像已预拉到节点、权重在本地 NVMe | **60–90 s**（70B 级） | 节点磁盘 + 镜像分发带宽 |
| **热备** | 旧版本实例常驻在线，随时可切流 | **秒级** | **一整套推理容量的全时成本**，GPU 场景等于把账单翻倍 |

**判断规则：只有"错了就是钱"的模型才配热备**（广告出价、风控拒绝、支付路由 —— 回滚每晚一分钟都在直接烧钱），内容推荐用温备就够。
合规上还有一条硬约束：EU AI Act 的委员会监督与执法权自 **2026-08-02** 生效
（[artificialintelligenceact.eu](https://artificialintelligenceact.eu/implementation-timeline/)），
监管可直接索要训练数据来源、训练算力、训练时长等文档，而这些**训练结束后基本无法追溯补录** ——
所以"保留"至少要保留到元数据层面，保留权重远远不够。

## 5. 多模型共存：流量切分、显存与路由

### 5.1 切分维度决定了你能测什么

| 切分维度 | 语义 | 优点 | 代价 / 撞墙条件 |
|---|---|---|---|
| **按用户（sticky）** | `hash(user_id) % 100 < k` | 同一用户始终看到同一模型；**唯一能测留存和序列效应的切法** | 用户级方差大 → 样本量需求最高；用户量小的 B2B 场景直接失效 |
| **按请求** | 每次请求独立抽签 | 方差最小、样本累积最快 | **污染个体体验**（同一个人一会儿新一会儿旧）；测不了任何跨请求的效应（会话、留存、序列推荐） |
| **按地域 / 单元（cell）** | 整个 region 或 cell 切到新模型 | 爆炸半径清晰、运维简单、和现有 cell 架构对齐 | **基线不可比**：不同地域的用户构成、时区、供给都不同，只能做前后对比，不能做并发对照 |
| **按租户 / ring** | 内部 → 小客户 → 大客户 | 契约风险可控，B2B 的默认选择 | 每个 ring 内样本量都不够做统计判定；本质是风险排序不是实验 |

**默认组合**：技术验证用按请求（快速攒 L0/L1 样本），质量判定用按用户（排序实验为什么必须按用户分，见 [08/07 §3](07-model-quality-and-experimentation.md)），
高价值租户用 ring 单独排期。**同一次发布可以在不同阶段用不同切法，但同一个指标的结论必须来自同一种切法。**

### 5.2 多版本同时在线的显存账

服务代码多跑一个版本几乎不要钱，模型不是。

- **纯 dense 模型（CV、NLP encoder、排序的 MLP 塔）**：N 个版本 = N× 权重显存。2 GB 的排序塔在 24 GB 卡上开 3 个版本仍装得下。
- **带大 embedding 的推荐模型**：直接撞墙。Meta 公开的 embedding 表规模是**数十到数百 TB**（96 TB Model-F、200 TB+ Persia），
  占模型参数 **>99%**（[arXiv 2410.12794](https://arxiv.org/html/2410.12794v2)）—— 双版本全量驻留物理上不成立。
  **解法是把 embedding 层和网络层拆成两个独立版本化的服务**：embedding 共享，只对 dense 塔做多版本。
  代价是你从此无法在金丝雀里验证 embedding 变更，它只能走全量 + 快速回滚或离线冻结验证。
- **GPU 多版本共存与 GPU 共享是同一问题的两面**，显存超售的风险见 [08/03 §7](03-model-loading-and-warmup.md)，
  隔离方式（time-slicing / MPS / MIG）的取舍见 [04/01 §11](../04-ai-agent-systems/01-llm-serving-infra.md)。
  经验：**金丝雀不要和主版本抢同一张卡**，否则你测到的 p99 变化里混着调度噪声，门禁会误判。

### 5.3 模型路由：必须有一层 pointer

现成的语义可以直接抄，各有边界：

| 机制 | 语义 | 边界 |
|---|---|---|
| **SageMaker Deployment Guardrails** | blue/green 支持 all-at-once / canary（两步）/ linear（n 个等距步），另有 rolling（按 batch 增量替换实例）；每步后有 baking period，由预设 CloudWatch alarm 监控，报警即自动回滚 | **仅适用于 real-time 与 async inference endpoint** |
| **KServe canary** | 在 component spec 上设 `canaryTrafficPercent`，自动追踪"上一个 100% 流量的 good revision"并按比例分流；晋升方式是删掉该字段重新 apply | **只在 serverless（Knative）模式下支持** |
| **MLflow alias** | `@champion` / `@challenger` 这类别名可多个并存、可原地重指，把"部署"与"生产代码里的字符串"解耦 | Model Stages 自 **2.9.0 弃用**，别再用 `Production` 这个 stage 当控制面 |
| **Netflix Red-Black** | 新旧版本并存，健康检查通过后分阶段切流（新版扩容与旧版缩容同速），任一步失败触发**原子回滚** | 需要 2× 容量峰值 |

**唯一的硬规则：服务代码里不允许出现版本号。** 路由决策发生在 pointer 层，
否则每次回滚都变成一次代码发布 —— 而代码发布本身也有金丝雀，你会在事故中间叠一层金丝雀。

## 6. 部署拓扑：模型嵌在服务里，还是独立模型服务

| 维度 | 嵌进业务服务（进程内） | 独立模型服务（RPC） |
|---|---|---|
| 延迟 | **0 网络跳**，只有推理本身 | **+0.5–2 ms**（同 AZ RTT）+ 序列化开销；特征张量大时序列化可能超过推理本身 |
| 部署耦合 | 改模型必须发业务服务 | 模型独立发版，业务不动 |
| 回滚粒度 | 模型和业务代码绑死，**只能一起回** | 可以只回模型 |
| 资源隔离 | 推理和业务逻辑抢同一份 CPU / 内存；一次 OOM 全挂 | 独立扩缩、独立限流，故障域分开 |
| 硬件 | 只能用业务服务的机型（通常 CPU） | 可以单独用 GPU 机型 |
| 团队边界 | ML 工程师改代码要走业务服务的发布流程 | ML 团队自主发布 |
| 多服务复用 | 每个调用方各嵌一份，版本必然漂 | 单一版本真相 |
| 撞墙条件 | 模型 >1–2 GB、需要 GPU、或有 ≥2 个调用方 | QPS 极高且模型极小时，网络开销占比失控 |

**判据（按优先级）**：① 需要 GPU → 必须独立；② 有 ≥2 个调用方 → 必须独立（否则版本漂移不可控）；
③ 模型更新频率 > 业务服务发布频率 → 独立；④ 以上都不满足且模型 < 100 MB、延迟预算 < 10 ms → 嵌进去。

Netflix 的实践正好是这条判据的两端：**小模型在 JVM 服务层进程内跑 CPU，大模型走独立的模型服务层**
（[Netflix TechBlog, 2026-07](https://netflixtechblog.com/in-house-llm-serving-at-netflix-a5a8e799ea2c)）。
反方向的锚点：AWS 的选型口径里 sub-2B 模型**在 CPU 上性价比直接胜出**，持续 >100 req/s 的单 endpoint 才该上 GPU ——
很多"应该独立部署"的直觉在小模型上并不成立，先算 `目标 p95 下的 cost-per-1,000-queries` 再决定。

## 7. 级联模型：改一级会改变下游的输入分布

推荐和搜索几乎都是多阶段的：

```
   候选池 ~10^6 ──[召回 recall]──► ~10^4 ──[粗排 pre-rank]──► ~5×10^2 ──[精排 rank]──► ~20 ──[重排]──► 曝光
                      │                        │                          │
                      └────────────────────────┴──────────────────────────┘
                       每一级的输出 = 下一级的输入分布 = 下一级训练集的采样分布
```

**问题的形状**：精排是在"老召回产生的候选"上训练的。你换掉召回，精排就要给一批它从没在训练集里见过的物品打分 ——
这不是"精排会稍微不准"，而是**精排的输入分布本身变了**，分数不再可比，于是你对精排设的所有 L1 门禁（PSI、校准）会一起报警，
而报警的原因是上游变了、不是精排坏了。这类改动的评估必须是**整链联合的**，三种做法：

| 做法 | 怎么做 | 代价 | 撞墙条件 |
|---|---|---|---|
| **整链金丝雀** | 把"新召回 + 现有下游"作为一个整体版本切流，指标只看链路终点 | 定位困难：出问题不知道是哪一级 | 默认做法 |
| **冻结下游** | 上线新召回时，把精排冻结在当前版本，禁止同期发版 | 阻塞其他团队，通常只能冻 1–2 周 | 组织成本高，只用于大改 |
| **联合重训** | 用新召回的输出重新生成精排训练样本，两级一起上 | 周期从天变成周；两个变更混在一起，出事无法二分定位 | 召回改动大到下游分布明显偏移时唯一正解 |

**离线指标在这里尤其不可信。** RecSys 2025 的一项实测（2650 万次曝光、5 个测试组、个体级回归标定）给出的系数是：
`Recall@20 → CTR` **0.8985（p<1e-4）**，方向和直觉一致；但 `Recall@20 → CVR` 是 **−0.204（p=0.0174）—— 负相关**
（[arXiv 2507.09566](https://arxiv.org/html/2507.09566)）。也就是说**把召回的 Recall 提上去会把转化率拉下来**；
只盯上游离线指标做发布决策，你会稳定地把链路推向"上游更准、终点更差"的状态。

还有一个几乎没人在发布评审里提的坑：**共生偏差（symbiosis bias，WWW 2025）** —— A/B 两组算法共享同一份训练数据池时，
A 组的探索数据喂养了 B 组，违反 SUTVA 的 "no hidden treatments" 假设，你测到的"新模型效果"里混着"新模型帮老模型变好了"。
缓解设计有 cluster-randomized、data-diverted、user-corpus co-diverted 三种，代价都是每组能用的训练数据变少。

**排序类改动的正确评估阶梯**：离线指标（廉价，只用于剪枝）→ 交错实验 / 反事实评测（数天，**50–100× 样本效率**，见 [08/07 §8](07-model-quality-and-experimentation.md)）→ A/B + 长期 holdout。
但交错**只能当筛选器不能当判决器**：Airbnb 公开的数据是与 A/B 的相关系数 **0.6**、**方向一致率仅 82%**（约五分之一会看反），
且在集合级优化场景下会**系统性低估** treatment、给出与 A/B 相反的结论（[arXiv 2508.00751](https://arxiv.org/abs/2508.00751)）。

## 8. 边缘 / 端侧部署：回滚不了才是最大的风险

服务端所有讨论的隐含前提是"我随时能把它收回来"。端侧没有这个前提。

```
   服务端：   发布 ──► 全量生效 ≤ 10 min ──► 回滚生效 ≤ 60 s        （你控制 100% 的执行环境）
   端侧：     下发 ──► 7 天覆盖 60–80% ──► 长尾数周~数月            （你控制 0%）
                 │                              │
                 └── 同一时刻线上并存 10+ 个模型版本 ───► 回滚 = 再下发一次 = 再等一个覆盖周期
```

**版本碎片化是端侧的默认状态，不是异常状态。** 由此推出三条硬性设计要求：

1. **必须有服务端可控的 kill switch。** 端侧模型的"回滚"不能依赖再下发一个新模型（那要等一个完整覆盖周期），
   必须是一个**服务端下发的开关**：关掉后端侧立即回退到"上一个已缓存的模型版本"或"服务端推理"或"规则兜底"。
   这个开关的生效路径必须独立于模型下发通道，且必须在正常发布流程里定期演练 —— 没演练过的 kill switch 等于没有。
2. **端侧必须上报 `model_version`**，否则你的线上指标是十几个版本的混合平均，任何金丝雀结论都是伪的。
   上报链路本身也要监控：它挂掉会表现为"某个版本的样本突然消失"，极容易被误读成"该版本用户流失"。
3. **分档下发，档位按"不可控维度"切**（设备型号 / OS 版本 / APP 版本 / 地域）—— 这几个维度恰好是端侧推理性能差异最大的地方，
   同一个模型在旗舰机上 15 ms，在三年前的中端机上可能 200 ms。

**容量约束也不是一个量级**：模型体积直接影响下发成功率和 APP 包大小，预算通常几 MB 到几十 MB，量化是必选项而非优化项 ——
**Q4_K_M 约 4–5× 加速、困惑度 +1–3%**，7B BF16 约 14 GB → Q4_K_M 约 4 GB；注意 **CPU 推理是内存带宽瓶颈不是算力瓶颈**，
模型小 3.5× 就快约 3.5×，这个近似线性关系是端侧容量规划的主要依据。

**最该写进 runbook 的一句**：端侧发布评审必须回答"如果这个模型在 30% 的设备上崩溃，我们多久能止血"。答案若是"等下一个版本"，它就不该上端侧。

## 9. 什么时候不该做模型金丝雀（反模式）

| 反模式 | 为什么错 | 该怎么办 |
|---|---|---|
| **低流量场景照做金丝雀** | 1% 流量跑 48 小时可能只有 **~200 次交互**（GrowthBook 明确点名的反例）。200 个样本连相对 30% 的劣化都检不出，你只是把 1% 的用户随机暴露给了一个未验证的模型 | 影子跑全量流量 + golden dataset 离线门禁 + **直接 100% 上线**，把全部投入放在"回滚要多快"上。样本少的时候，快速回滚的期望损失小于长时间小流量暴露 |
| **把金丝雀当 A/B 用** | 金丝雀的比例在变、没有随机化保证、没有 SRM 检查、没有预注册的指标和样本量 —— 它不满足实验的任何一个前提 | 金丝雀回答"安不安全"，A/B 回答"好不好"。两套流量、两套统计、两套决策人 |
| **给质量指标挂自动回滚** | 假阳性率不受控，误回滚几次之后团队会关掉整个自动回滚 | 质量指标只做"停档 + 呼人"；自动执行留给 L0 |
| **护栏越多越安全** | k=20、α=0.01 时 family-wise 误触发率 **18.2%** | 自动护栏 ≤ 5–7 个，其余降级为告警 |
| **用"昨天同一时刻"当基线** | 周期性、外部事件、别的团队发版全都会污染它；模型场景还多一层——用户构成本身在变 | 必须是**同时段并发基线组** |
| **只回滚权重** | 特征时间旅行，把一个问题变成两个 | 回滚四元组，见 §4.1 |
| **对标签延迟极长的模型做质量门禁** | 保险理赔标签数月到数年，金丝雀期间那一格永远是空的 | 用代理指标（要求"滞后短 + 与目标高相关"）做实时环，真实性能等标签到齐后在延迟环里跑；**别假装门禁存在** |
| **单独给级联链路的一级开金丝雀** | 上游改动会让下游所有分布门禁一起报警，报警原因不是下游坏了 | 整链金丝雀 + 终点指标，见 §7 |
| **用金丝雀替代离线评测** | 生产用户不是你的测试集；实验正向率的公开口径是 Microsoft ~33%、Bing/Google 10–20%、Airbnb ~8%，中位约 10% —— 十个改动里九个不该到线上 | 离线剪枝 → 影子 → 金丝雀 |
| **同一次发布改多件事** | 模型 + 特征 + 后处理阈值一起改，出事无法二分定位，回滚也只能整体回 | 一次发布一个变量；确实要一起改就明确接受"无法定位"这个代价 |

## 这一章的三句话

1. **模型金丝雀的主要产出不是"新模型更好"的证据，而是爆炸半径的上限。** 质量证据需要的样本量比金丝雀窗口能提供的高 1–3 个数量级
   （检出相对 1% 的 CTR 变化约需 298 万人/组），所以门禁必须诚实分成两层：L0 自动执行、质量指标停档呼人 —— 假装质量门禁是统计门禁的团队最后都会关掉自动回滚。
2. **回滚的单位是四元组，不是权重指针。** 只把 alias 指回上一版，你得到的是"旧权重 + 新特征管道"这个从没测试过的第三种系统；
   而回滚窗口里产生的曝光日志是唯一真正不可逆的部分 —— 它会以训练样本的形式把坏模型的偏好固化进下一代。
3. **端侧部署把"回滚"从工程问题变成了产品问题。** 服务端 60 秒能收回的东西，端侧要等一个数周的覆盖周期，
   因此端侧唯一有效的止血手段是一个独立于模型下发通道、并且定期演练过的服务端 kill switch。

## 面试官会追问

1. 服务金丝雀 5 分钟能判，模型金丝雀为什么不能？给我一个具体的样本量计算。
2. 你的模型金丝雀门禁里，哪些指标可以自动回滚、哪些不行？为什么这么分？
3. 为什么护栏指标多了反而更危险？给我算一下 family-wise 误触发率。
4. 回滚模型权重之后线上没恢复，可能是什么原因？你会怎么排查、怎么预防？
5. 金丝雀期间坏模型服务过的那部分流量，产生的日志怎么处理？不处理会发生什么？
6. 旧模型要保留多久？这个数字怎么推出来的？冷备、温备、热备的成本差在哪？
7. 一个日活 5 万的 B2B 产品要上新排序模型，你还做金丝雀吗？不做的话怎么控制风险？
8. 召回改了会影响精排，你怎么做联合评估？为什么不能只给召回开金丝雀？
